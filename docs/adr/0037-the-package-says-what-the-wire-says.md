# ADR-0037 — enum ใน package สะกดตามที่ออกสาย ไม่ใช่ตามธรรมเนียมของ package

- **สถานะ**: ตัดสินแล้ว 19 สิงหาคม 2569
- **ที่มา**: [issue #68](https://github.com/khthana/Deep-Portfolio/issues/68)
  รอบ announcement
- **เกี่ยวข้อง**: [ADR-0032](0032-activity-follows-the-row.md) ซึ่งเจอว่า `as`
  ที่ครอบทั้งวัตถุกลบรูปของทุก field ที่เหลือไปด้วย — รอบนี้เจอตัวเดียวกันอีกตัว
  และ [ADR-0036](0036-a-bare-scalar-gets-no-name.md) ซึ่งวางเส้นแบ่งว่า
  response แบบไหนควรมีชื่อ ใบนี้ไม่ได้ทบทวนข้อไหนของทั้งสองใบ

## บริบท

ประกาศของ section มีสามเส้น: `GET /announcement` (ฟีด), `POST /announcement`
(ประกาศใหม่ ซึ่งกระจายได้หลาย section) และ `GET /announcement/:id/attachments`

เส้นที่สามไม่ต้องตั้งชื่อให้เลย มันเอา `AttachmentDetailResp` ใส่ `data` ตรง ๆ ไม่
เติมอะไรของตัวเองเลย (envelope ยังห่ออยู่เหมือนทุกเส้น) ซึ่งตรงข้ามกับ
`GET /student-activity/attachments` ที่เรียก service ตัวเดียวกันแล้วแบนผลลัพธ์ลง
เป็นรูปของตัวเองก่อนตอบ (ADR-0034)

เส้นแรกเป็นตัวที่มีเรื่องให้เล่า

## สิ่งที่ `as` ปิดไว้

`getAnnouncements` spread แถว Prisma ทั้งแถวแล้วปิดท้ายด้วย
`as AnnouncementDetailResp` ซึ่ง**ทั้งสองฝั่ง**ประกาศไว้สิบฟิลด์ แถวมีสิบเอ็ด

| จุด                          | type เดิมบอก                     | ของจริง                                    |
| ---------------------------- | -------------------------------- | ------------------------------------------ |
| `section_id`                 | ไม่ได้ประกาศทั้งสองฝั่ง          | อยู่บนสาย เพราะ spread ทั้งแถว             |
| `status` (ฝั่ง web)          | `AttachmentType`                 | `draft \| published \| archived`            |
| `content` (ฝั่ง web)         | `JSON` — type สากลของ JS         | เอกสารของ editor ที่ API ไม่เคยเปิดอ่าน    |
| `attachments`                | `\| null` ทั้งสองฝั่ง            | ไม่เคยเป็น null                            |
| สามวันที่                     | `Date` ทั้งสองฝั่ง               | string ตอนถึงมือผู้เรียก                   |

`status: AttachmentType` เป็นตัวที่แปลกที่สุดในรอบไหน ๆ ของ #68: `AttachmentType`
คือ `FILE | IMAGE | LINK` ซึ่งบอกว่าไฟล์แนบเป็นชนิดไหน ไม่ได้เกี่ยวอะไรกับสถานะ
ของประกาศเลยสักตัวอักษร มันไม่ใช่ชื่อที่ลอยอยู่ในไฟล์นั้นด้วย — บรรทัดแรกของไฟล์
`import type { AttachmentType } from "./attachment-type.type";` ไว้จริง ๆ และ
`AttachmentType` ก็ถูก import ไปใช้อีกสิบสองไฟล์ฝั่ง web มันจึงเป็นชื่อที่ใช้งาน
อยู่จริง ถูกหยิบมาวางผิดที่ ที่ไม่มีใครอ่านคือ `status` ของประกาศต่างหาก ไม่มีหน้าจอไหนแตะมันเลย
ประกาศที่ผิดจึงอยู่มาได้โดยไม่มีอะไรพัง

`attachments` ที่เขียนว่า `| null` ก็ผิดทั้งสองฝั่ง service เรียกตัวอ่านไฟล์แนบให้
ทุกแถว และตัวอ่านนั้นตอบ `{ file: [], url: [] }` เมื่อไม่มีอะไร ไม่ใช่ตอบว่าไม่มี
คอมโพเนนต์ที่เรนเดอร์จึงเขียน `props.announcement.attachments && …` คร่อมไว้สองที่
โดยไม่มีวันเป็นเท็จ

## การตัดสินใจ

**1. `AnnouncementStatus` สะกดเป็นตัวเล็ก เพราะสิ่งที่ออกสายเป็นตัวเล็ก**

`ActivityType` ใน package เขียนว่า `"INDIVIDUAL" | "GROUP"` ตัวใหญ่ ส่วน
`AnnouncementStatus` เขียนว่า `"draft" | "published" | "archived"` ตัวเล็ก

ต้นทางของสองตัวนี้ไม่เหมือนกันเลย และต้องพูดให้ตรง `announcements.status` เป็น
enum ของ Postgres จริง ๆ ชื่อ `announcement_status` สะกดตัวเล็กสามค่า ส่วน
`activities.activity_type` **ไม่ใช่ enum** — เป็น `VarChar(20)` ที่ไม่มีอะไร
อยู่ข้างหลัง เก็บตัวเล็กแล้วแปลงเป็นตัวใหญ่ตอนออก ตามที่คอมเมนต์เหนือ
`ActivityType` ใน `activity.ts` อธิบายไว้อยู่แล้ว (`activity_type_enum` ใน schema
มีอยู่ก็จริง แต่ไม่มี model ไหนใช้มัน — เป็นหนึ่งใน enum ว่างสองตัวของ #58)

สิ่งที่ตัดสินตรงนี้จึงไม่ใช่ "ตาม enum" แต่คือ**ตามสิ่งที่ออกจาก service**:
`activity.service.ts` มี `toActivityType()` ที่ `toUpperCase()` ก่อนส่งออก ส่วน
`announcement.service.ts` ส่งค่าจากคอลัมน์ต่อไปดิบ ๆ ผู้เรียกจึงได้ตัวใหญ่จาก
เส้นหนึ่งและตัวเล็กจากอีกเส้นหนึ่ง — และ package บอกความจริงข้อนั้น ไม่ว่าปลายทาง
ในฐานข้อมูลจะเป็น enum หรือเป็นสตริงเปล่า

ทางเลือกที่ไม่เอาคือทำให้เหมือนกัน ซึ่งแปลว่าต้องแก้ฝั่ง API ให้ `toUpperCase()`
ตัวนี้ด้วย นั่นเป็นการเปลี่ยนสิ่งที่ผู้เรียกเห็นเพื่อความสวยของ type ซึ่ง #68 ไม่ได้
มาทำ และ ADR-0028 บอกไว้ตั้งแต่ต้นว่า package เขียนตามสิ่งที่ endpoint ตอบจริง
ไม่ใช่ตามสิ่งที่ควรจะตอบ ถ้าจะรวบให้เหมือนกัน มันเป็นตั๋วของตัวเอง ไม่ใช่ท้ายรอบนี้

**2. `status` ไม่เคยมีค่า และเขียนไว้ว่าอย่างนั้น**

คอลัมน์ไม่มี `@default` และ `POST /announcement` ไม่ได้ set มัน ผู้เขียนตารางนี้มี
รายเดียวคือ service ตัวนั้น ทุกแถวที่ระบบเคยสร้างจึงเป็น null และเคสที่ปักรูปของ
แถวก็ assert `status: null` ตรง ๆ

สามชื่อใน union ยังอยู่เพราะคอลัมน์รับมันได้ ไม่ใช่เพราะมีใครเคยเห็น คอมเมนต์
เหนือ type บอกไว้ตรงนั้น — คนอ่านคนต่อไปจะได้ไม่เขียนหน้าจอที่รอ `published`

**3. `AnnouncementIdResp` มีชื่อ ตามเส้นที่ ADR-0036 ลากไว้**

`POST /announcement` ตอบ `{ announcement_id }` เป็นวัตถุ ผู้อ่านต้องรู้ชื่อคีย์ถึง
จะอ่านค่าออก จึงได้ชื่อ เหมือน `GroupIdResp` — ต่างจาก `POST /score-weight` ที่
ตอบตัวเลขเปล่า และ ADR-0036 ตัดสินว่าไม่ต้องตั้งชื่อ

ไม่มีใครอ่านค่าที่มันตอบเหมือนกัน: ผู้เรียกรายเดียวเช็ค `success` ขึ้นข้อความ แล้ว
พาไปหน้าฟีด ซึ่งไปดึงข้อมูลของตัวเองใหม่

**4. `content` เป็น `unknown` และแปลงที่คนอ่านคนเดียว**

เหมือนที่ ADR-0032 กับ ADR-0033 ทำกับ `detail` ของงานสองแบบ — API ไม่รู้ว่าข้างใน
เป็นอะไร และไม่เคยเปิดอ่าน `announcement-card.tsx` เป็นที่เดียวที่รู้ว่ามันคือ
`JSONContent` ของ tiptap และเป็นที่เดียวที่เขียนว่ารู้

ของเดิมฝั่ง web เขียนว่า `JSON` ซึ่งเป็น type ของ `JSON.parse`/`JSON.stringify`
ไม่ใช่ "ข้อมูล JSON" มันผ่าน `generateHTML()` มาได้เพราะ `JSONContent` มี index
signature ที่ยอมรับเกือบทุกอย่าง ไม่ใช่เพราะมันถูก

## ผลที่ตามมา

- เหลือสำเนาฝั่ง web 35 ไฟล์ 1,837 บรรทัด (จาก 35 ไฟล์ 1,845 หลังรอบ
  score-weight) นับด้วย glob ชุดเดียวกับที่ ADR-0028 ประกาศไว้
- `apps/web/src/types/course-type.type.ts` เหลือ `LessonPlanResp` ตัวเดียว และ
  import ทั้งสองบรรทัดบนหัวไฟล์ก็ตายไปพร้อมกัน — ไฟล์นี้จะหายไปทั้งไฟล์ในรอบ
  lesson-plan ตามเหตุผลเดียวกับ ADR-0029 ข้อ 3
- `apps/api/src/models/announcement.model.ts` ไม่ถูกลบ เพราะยังถือ
  `CreateAnnouncementReqBody` ซึ่งเป็นรูปฝั่งเข้า ไม่ใช่ฝั่งออก ส่วน
  `UploadFileDetail` ที่เคยอยู่ข้าง ๆ มันถูกลบทิ้ง — ไม่มีไฟล์ไหนใน repo อ้างถึงมัน
  เลยแม้แต่ไฟล์เดียว รอบนี้เจอเพราะต้องอ่านไฟล์ทั้งไฟล์เพื่อจะรู้ว่าเหลืออะไร
- API เพิ่มหนึ่งเคส คือเคสที่ไล่ชื่อทุกคีย์ของฟีด รวมเป็น 1,072 เคส ส่วนเคสของ
  `POST` ปัก `toEqual({ announcement_id })` ไว้ครบอยู่แล้วตั้งแต่ก่อนรอบนี้
- ฝั่ง web ไม่เพิ่มไม่ลดเคส (448)
- `npm run lint` ยังเท่าเดิมที่ 216 warning
- **`props.announcement.attachments &&` สองที่ใน `announcement-card.tsx` ยังอยู่**
  ทั้งที่ตอนนี้ type บอกแล้วว่าเป็นเท็จไม่ได้ รอบนี้ไม่แตะ เพราะการลบมันคือการ
  แก้คอมโพเนนต์ที่รอบนี้ไม่ได้มาแก้ และมันไม่ได้ทำอะไรผิด — บันทึกไว้ให้คนที่มา
  เก็บกวาด
