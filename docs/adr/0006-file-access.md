# ADR-0006 — ไฟล์เสิร์ฟด้วย URL ที่ API เซ็นเอง และมีอายุ

- **สถานะ**: ตัดสินแล้ว 10 สิงหาคม 2569
- **ที่มา**: [issue #36](https://github.com/khthana/Deep-Portfolio/issues/36)
  (แยกออกมาจาก #31)
- **เกี่ยวข้อง**: [ADR-0001](0001-portfolio-access.md) ปิด **metadata** ของไฟล์ใน
  แฟ้มสะสมผลงาน แล้วเขียนค้างไว้ว่า "ตัวไฟล์ยังไม่อยู่หลังกติกานี้" — ไฟล์นี้คือ
  ส่วนที่ค้างอยู่ และคุมไฟล์ของทั้งระบบ ไม่ใช่ของ `portfolio_*` อย่างเดียว

## บริบท

ไฟล์ทุกไฟล์ในระบบอยู่ใน MinIO และออกสู่เบราว์เซอร์ผ่าน API ทางเดียว —
`GET /files?path=<object key>` ใน `apps/api/src/routes/files.route.ts` route นี้
**ไม่มี middleware ตรวจสิทธิ์เลยแม้แต่ `requireUser`** ใครก็ตามที่รู้ object key
ก็โหลดไฟล์นั้นได้ ไม่ต้องล็อกอิน ไม่ต้องเป็นเจ้าของ ครอบคลุมทั้งใบประกาศนียบัตร
รูปโปรไฟล์ งานที่นักศึกษาส่ง และเอกสารประกอบการเรียนของทุกกลุ่มเรียน

ผลคือกติกาที่ ADR-0001 กับ ADR-0002 วางไว้ปิดได้แค่ครึ่งเดียว — ต้องเป็นเจ้าของแถว
ถึงจะเห็น `file_path` แต่พอเห็นแล้วส่งต่อให้ใครก็ได้ และ key เองก็เดาได้ไม่ยาก
เพราะประกอบจาก prefix ของ endpoint กับชื่อไฟล์เดิม

สามอย่างที่กำหนดรูปของทางออก

**คุกกี้ตามไปกับ `<img>` ไม่ได้** session เป็นคุกกี้ `httpOnly` + `sameSite: "lax"`
ส่วนไฟล์ถูกโหลดผ่าน `<img src>` และ `<a href>` ซึ่งบน dev เว็บกับ API คนละ origin
กัน การเอา `requireUser` มาแปะหน้า `/files` เฉย ๆ จึงทำให้รูปทุกใบในระบบพัง ไม่ใช่
แค่ของคนอื่น

**share link ต้องเปิดได้โดยไม่ต้องล็อกอิน** `GET /portfolio/public/:token` ตั้งใจให้
คนนอกที่ไม่มีบัญชีในระบบเปิดดูได้ (ADR-0001) ถ้าไฟล์ในแฟ้มต้องมี session ฟีเจอร์แชร์
จะเหลือแต่ข้อความ

**`getAttachments` เป็นคอขวดจุดเดียว** ทุก endpoint ที่ส่ง `file_path` ออกไป — 20
จุดใน 12 service รวมทั้ง endpoint ของ share link — ผ่าน
`AttachmentsService.getAttachments` ทั้งหมด ที่นั่นคือจุดเดียวที่ address ของไฟล์
ออกจาก API

อีกสองทางที่เคยเสิร์ฟไฟล์ — `GET /uploads/:filename` กับ
`express.static("uploads")` — เป็นโค้ดตาย `middlewares/upload.ts` (multer แบบเขียน
ลงดิสก์) ไม่มี route ไหนเรียกเลยตั้งแต่รับมอบ ทุก route ใช้ `upload-minio` โฟลเดอร์
`uploads/` จึงว่างตลอด

## สิ่งที่ต้องตัดสิน

ใครโหลดไฟล์ไหนได้ และบังคับกฎนั้นตรงไหน มีสามทาง

1. **ตรวจสิทธิ์ที่ `/files` ทีละคำขอ** — `requireUser` แล้วไล่จาก object key กลับไป
   หาแถวที่ไฟล์แขวนอยู่ เพื่อถามว่าผู้เรียกมีสิทธิ์เห็นแถวนั้นไหม
2. **ให้เบราว์เซอร์ยิง MinIO ตรง ๆ ด้วย presigned URL** — `getFile` ใน
   `upload.service.ts` ที่เขียนค้างไว้ก็คือทางนี้
3. **API เซ็น URL อายุสั้นเอง** — ออก URL ที่มีลายเซ็นตอนที่ address ของไฟล์ออกจาก
   API แล้วให้ `/files` ตรวจลายเซ็นนั้น

## การตัดสิน

> **สิทธิ์ตัดสินตอนที่ address ของไฟล์ออกจาก API ไม่ใช่ตอนที่ไฟล์ถูกขอ**
> `getAttachments` ส่งออกเป็น `/files?path=…&exp=…&sig=…` ที่เซ็นด้วย HMAC และมี
> อายุ 1 ชั่วโมง `GET /files` เสิร์ฟเฉพาะ URL ที่ตัวเองเซ็นและยังไม่หมดอายุ
> เท่านั้น ไม่มีลายเซ็น = ไม่ได้ไฟล์ ไม่ว่าจะล็อกอินอยู่หรือไม่

เลือกทางที่ 3 ด้วยเหตุผลสามข้อ

**กฎเดียวคุมได้ทั้งสามแบบ** ไฟล์ของแฟ้มสะสมผลงาน ไฟล์ของรายวิชา และไฟล์ที่นักศึกษา
ส่ง เดินออกทางเดียวกันหมด กติกาจึงเป็นข้อเดียว: **ใครก็ตามที่เข้าถึงแถวที่ไฟล์แขวน
อยู่ได้ ก็โหลดไฟล์นั้นได้** และคำถามว่าใครเข้าถึงแถวไหนได้ ถูกตอบไปแล้วที่ endpoint
ของแถวนั้นเอง ตาม ADR-0001 / 0002 / 0003 ไม่ต้องเขียนกฎชุดที่สองที่จะเพี้ยนจากชุดแรก

**ทางที่ 1 ต้องเขียนกฎชุดที่สองจาก object key** key ไม่ได้บอกว่าตัวเองแขวนอยู่กับ
แถวไหน ต้อง join `attachments` กลับไปหา 12 ตารางเชื่อมเพื่อหาเจ้าของ แล้วยังแก้
`<img>` ข้าม origin ไม่ได้อยู่ดี

**ทางที่ 2 เปิด MinIO ให้เบราว์เซอร์** ต้องมี host ของ MinIO ที่เบราว์เซอร์เข้าถึงได้
จริงบน production ซึ่งผูกกับการ deploy ที่ยังไม่ได้ตัดสิน และย้ายการควบคุมไปไว้
นอกระบบ ทางที่ 3 ได้ผลเดียวกันโดยไฟล์ยังไหลผ่าน API เหมือนเดิม

### คำตอบของ `GET /files`

| สถานการณ์ | คำตอบ |
| --- | --- |
| ลายเซ็นถูก ยังไม่หมดอายุ มีไฟล์ | `200` stream จาก MinIO |
| ไม่มี `sig` หรือ `exp` | `403` `ลิงก์ไฟล์นี้ไม่ถูกต้อง` |
| ลายเซ็นผิด หรือแก้ `path` / `exp` เอง | `403` เหมือนกัน |
| ลายเซ็นถูกแต่เลยเวลา | `410` `ลิงก์ไฟล์นี้หมดอายุแล้ว กรุณาโหลดหน้านี้ใหม่` |
| ลายเซ็นถูกแต่ไม่มี object นั้น | `404` `ไม่พบไฟล์ที่ต้องการ` |
| ไม่ส่ง `path` มาเลย | `400` ตามกติกาของ schema |

**ไม่มีลายเซ็นตอบ `403` ไม่ใช่ `400`** ต่างจากกติกาปกติของ repo นี้ที่คำขอผิดรูป
ได้ `400` (ADR-0002) เพราะลายเซ็นไม่ใช่รูปร่างของคำขอ มันคือตัวสิทธิ์ทั้งอัน คำขอ
ที่ไม่มีลายเซ็นจึงไม่ใช่คำขอที่พิมพ์ผิด แต่คือคำขอที่ไม่มีสิทธิ์ — ซึ่งเป็นรูเดิม
ของ endpoint นี้พอดี

**หมดอายุตอบ `410` ไม่ใช่ `403` อีกใบ** เพราะสองอย่างนี้ต้องการคนละอย่างจากคนอ่าน
ลายเซ็นผิดแปลว่าลิงก์นี้ไม่เคยเป็นของเรา ส่วนหมดอายุแปลว่าเปิดหน้านี้ทิ้งไว้นาน
เกินไป โหลดหน้าใหม่แล้วจะได้

### กุญแจแยกจาก `JWT_SECRET` แต่ derive มาจากมัน

`createHmac("sha256", JWT_SECRET).update("deep-portfolio/file-url/v1")` เป็นกุญแจ
ของ route นี้เอง สองการใช้งานจึงแยกขาดจากกัน — สิ่งที่เซ็นที่นี่เอาไปใช้เป็น session
ไม่ได้ และสิ่งที่ session เซ็นก็ชี้ไฟล์ไม่ได้

ไม่ทำเป็น `FILE_URL_SECRET` ตัวใหม่ เพราะ `env.ts` ห้าม secret มีค่า fallback (D5)
ตัวแปรใหม่จึงต้องเป็น required และโปรเจกต์ที่ขายตัวเองว่า `docker compose up`
คำสั่งเดียวก็จะมีค่าที่ต้องตั้งเพิ่มอีกหนึ่งก่อนอะไรจะสตาร์ตได้ ราคาที่จ่ายคือหมุน
`JWT_SECRET` เมื่อไหร่ ลิงก์ไฟล์ที่ออกไปแล้วตายพร้อมกัน — อย่างมาก 1 ชั่วโมง

### ลบสองทางที่เหลือทิ้ง ไม่ใช่เอา middleware ไปแปะ

`GET /uploads/:filename` และ `express.static("uploads")` ถูกลบทั้งคู่ พร้อม
`middlewares/upload.ts`, volume `api-uploads` ใน `docker-compose.yml` และ
`mkdir uploads` ใน `Dockerfile` การเฝ้าทางที่ไม่มีอะไรเดินผ่านคือการเพิ่มโค้ดที่
ทดสอบไม่ได้จริง ทางเข้าไฟล์ควรมีทางเดียวและมีลายเซ็น

## ผลที่ตามมา

- **`file_path` ในทุก response ไม่ใช่ object key อีกต่อไป** เป็น URL พร้อมใช้
  ดู [`BEHAVIOR-CHANGES.md`](../../BEHAVIOR-CHANGES.md) — `apps/web` ตามไปแก้ที่
  `utils/get-file.ts` จุดเดียว จุดเรียกทั้ง 40 กว่าจุดไม่ต้องแก้
- **ลายเซ็นผูกกับไฟล์ ไม่ได้ผูกกับคน** ใครถือ URL ที่ยังไม่หมดอายุก็เปิดได้ นี่คือ
  สิ่งที่ทำให้ `<img>` ข้าม origin และ share link ทำงานได้ และเป็นราคาที่จ่ายเพื่อ
  สองอย่างนั้น — คนที่เปิดแฟ้มของตัวเองแล้ว copy URL ไปให้เพื่อน เพื่อนเปิดได้ภายใน
  1 ชั่วโมง สิ่งที่กติกานี้ปิดคือ **การเดา key แล้วโหลดไฟล์ของคนที่ไม่เคยแชร์ให้**
  ซึ่งเป็นรูที่ #36 พูดถึง
- **ยกเลิกการแชร์ไม่ได้ผลทันที** URL ที่ออกไปก่อนเจ้าของกดยกเลิก share link ยังใช้
  ได้จนหมดอายุ ถ้าวันหนึ่งต้องการให้ตัดทันที ต้องเปลี่ยนไปเก็บสถานะฝั่ง server
  ไม่ใช่เซ็นแล้วปล่อย
- **ไม่ได้แตะการลบไฟล์** ตอนที่ตัดสินไฟล์นี้ ลบแถวแล้ว object ยังค้างอยู่ในถัง
  เหมือนเดิม เป็นคนละเรื่องและอยู่ที่
  [#34](https://github.com/khthana/Deep-Portfolio/issues/34) ซึ่งปิดไปแล้ว —
  กติกาการลบอยู่ใน [ADR-0008](0008-attachment-lifecycle.md)
- **`GET /files` ไม่ต้องมี `requireUser`** และต้องไม่มี — ถ้าใส่ share link จะพัง
  ทันที ผู้ที่มาแก้ไฟล์นี้ต่อควรอ่านบรรทัดนี้ก่อน

## จะกลับมาทบทวนเมื่อไหร่

- เมื่อ deploy จริงแล้วเว็บกับ API อยู่ origin เดียวกันหลัง reverse proxy ตอนนั้น
  คุกกี้ตามไปกับ `<img>` ได้ และการเพิ่ม `requireUser` **ทับ** ลายเซ็น (ไม่ใช่แทน)
  ก็เป็นไปได้สำหรับไฟล์ที่ไม่ได้อยู่ในแฟ้มที่แชร์
- เมื่อมีคนต้องการยกเลิกการเข้าถึงไฟล์ให้มีผลทันที ตอนนั้นอายุ 1 ชั่วโมงไม่พอ และ
  ต้องมีรายการ token ที่ถูกเพิกถอนฝั่ง server
