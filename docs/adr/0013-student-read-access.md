# ADR-0013 — สามเส้นสุดท้ายใน `/student` แต่ละเส้นได้กฎของเพื่อนบ้าน ไม่ใช่กฎเดียวกัน

- **สถานะ**: ตัดสินแล้ว 11 สิงหาคม 2569
- **ที่มา**: [issue #41](https://github.com/khthana/Deep-Portfolio/issues/41)
- **เกี่ยวข้อง**: [ADR-0011](0011-self-read-parameter.md) (กฎ "ตามเพื่อนบ้านของแต่ละ
  เส้น" เกิดที่นั่น และเขียนไว้เองว่าเหลือสามเส้นนี้),
  [ADR-0002](0002-section-access.md) (section ที่อาจารย์สอน),
  [ADR-0003](0003-enrolment-access.md) (section ที่นักศึกษาลงทะเบียน),
  [ADR-0001](0001-portfolio-access.md) (`requireOwnEntry` และเหตุผลที่ "ไม่ใช่ของคุณ"
  กับ "ไม่มีแถวนี้" พูดประโยคเดียวกัน)

## บริบท

หลัง #40 เหลือสามเส้นใน `student.route.ts` ที่ไม่มี middleware อะไรเลย — ไม่ต้อง
ล็อกอินด้วยซ้ำ:

| เส้น | สิ่งที่ผู้เรียกที่ไม่ได้ล็อกอินได้ไป |
| --- | --- |
| `GET /student/list?section_id=` | ชื่อและรหัสของนักศึกษาทุกคนในกลุ่มเรียนนั้น |
| `GET /student/activities/details/:student_activity_id` | คะแนน ความเห็นอาจารย์ และไฟล์แนบของงานชิ้นนั้น |
| `GET /student/activities/list?section_id=&student_id=` | สถานะการส่งงานทุกชิ้นในกลุ่มเรียนนั้น ของนักศึกษาคนไหนก็ได้ |

`section_id` เป็น autoincrement เลขน้อย ๆ ส่วน `student_id` เป็นรหัสนักศึกษาที่พิมพ์
อยู่บนบัตร ทั้งสองอย่างไม่ใช่ความลับ ตัวคำขอเองจึงเป็นสิ่งเดียวที่กั้นอยู่

สามเส้นนี้ไม่ได้ปิดพร้อม #40 เพราะแต่ละเส้นต้องการคำตอบเชิงนโยบายคนละข้อ

## สิ่งที่ต้องตัดสิน

1. `GET /student/list` เป็นของใคร — อาจารย์คนไหนก็ได้ หรืออาจารย์ที่สอน section นั้น
2. `GET /student/activities/details/:id` ต้องเปิดให้ portfolio สาธารณะอ่านไหม
3. `GET /student/activities/list` ตัด `student_id` ทิ้ง หรือเก็บไว้แล้วตรวจ

## การตัดสิน

### 1. `GET /student/list` — `requireRole("TEACHER")` + `requireOwnSection`

รายชื่อนักศึกษาในกลุ่มเรียนเป็นหน้าจอของอาจารย์: ผู้เรียกทั้งหมดฝั่ง web อยู่ใต้
`features/teacher/` (`student-table.tsx` และ gradebook) ไม่มีหน้าจอของนักศึกษาไหน
เรียกมันเลย

และเมื่อเป็นของอาจารย์ ADR-0002 ก็ตอบข้อที่สองไว้แล้ว: อาจารย์เอื้อมถึง section ที่
ตัวเองสอน `requireOwnSection("query")` เป็น middleware ตัวเดียวกับที่ 20 กว่าเส้นใน
`/activity`, `/announcement`, `/gradebook` ใช้อยู่ ไม่ได้เขียนกฎใหม่

เส้นนี้จึงตอบ `403` ทั้งกรณี "ไม่ได้สอน section นี้" และ "ไม่มี section นี้" ตามที่
`sectionRule` ตั้งใจไว้ตั้งแต่ต้น — การแยกสองอย่างออกจากกันคือการบอกว่าเลขไหนมีอยู่จริง

### 2. `GET /student/activities/details/:id` — เจ้าของงานเท่านั้น

ข้อสมมติที่ #41 ตั้งไว้ว่า portfolio สาธารณะเรียกเส้นนี้ **ไม่จริง** อ่านโค้ดฝั่ง web
แล้วได้ว่า:

- `portfolio.service.ts` ฝั่ง API เรียก `getActivityDetailsByStudentActivityId()` ที่
  ชั้น service ตรง ๆ ไม่ได้วิ่งผ่าน HTTP เส้นนี้ — `GET /portfolio/public/:token` จึง
  ไม่ได้พึ่งมันเลย และ `student-experience-detail-page.tsx` ก็ส่ง `skip=true` ให้
  `usePortfolio` เมื่ออยู่ในโหมดสาธารณะ
- ฝั่งอาจารย์ก็ไม่ได้เรียก — `teacher-activity-action.ts` ใช้
  `getStudentActivityDetail` ซึ่งชี้ไป `/student-activity/…` คนละเส้นกัน

ผู้เรียกที่เหลือทั้งสี่ที่ (`create-work-form.tsx`, `work-card.tsx`,
`use-portfolio.ts`, `student-work-detail-page.tsx`) เป็นหน้าจอ e-Portfolio ของ
เจ้าของเองทั้งหมด สองที่หลังอยู่บนเส้นทางที่เปิดสาธารณะได้ด้วย แต่ทั้งคู่ออกจาก
ฟังก์ชันก่อนถึงบรรทัดนี้เมื่อมี `shareToken` กฎที่ถูกจึงเป็นกฎของ `requireOwnEntry`
ตาม ADR-0001 — งานชิ้นหนึ่งเป็นของคนที่ส่งมันเข้ามา

`student_activity` เป็นแถวเดียวใน `entryOwner` ที่ไม่ใช่แถวของ portfolio และเป็นแถว
เดียวที่คอลัมน์เจ้าของไม่ได้ชื่อ `user_id` — ชื่อ `student_id` ซึ่งเป็น foreign key ไป
`users.user_id` อยู่แล้ว lookup จึงแค่เปลี่ยนชื่อคอลัมน์ตอน select

`requireOwnEntry` รับชื่อ path parameter เป็นอาร์กิวเมนต์ตัวที่สอง (default `"id"`)
เพราะเส้นนี้สะกดว่า `:student_activity_id` และ schema ของมันใช้ชื่อนั้นในข้อความ `400`
ที่ผู้เรียกได้เมื่อส่งค่าที่ไม่ใช่ตัวเลข การอ่านชื่อผิดในที่นี้**เงียบ**: segment ที่
ไม่มีอยู่หน้าตาเหมือนแถวที่ไม่มีอยู่ และ middleware ก็ปล่อยผ่าน ชื่อจึงถูกส่งเข้าไป
ไม่ใช่เดา

### 3. `GET /student/activities/list` — ตัด `student_id` ทิ้ง + `requireEnrolledSection`

คำถามของเส้นนี้คือ "งานในกลุ่มเรียนนี้ พร้อมคำตอบของฉันเอง" ซึ่งมีสองครึ่ง และแต่ละ
ครึ่งได้ middleware ของตัวเอง:

- **ฉันคือใคร** — จาก session รูปเดียวกับอีกห้าเส้น "เรื่องของฉัน" ใน router นี้ และ
  เป็นทางที่ #40 เลือกไปแล้วสำหรับ `/enrolled/subjects` ที่ผู้เรียกฝั่ง web เป็น
  ไฟล์เดียวกันด้วยซ้ำ
- **section ไหน** — จาก query แล้วให้ `requireEnrolledSection("query")` ตรวจตาม
  ADR-0003 การลงทะเบียนเรียนคือสิ่งที่ทำให้ครึ่งนี้เป็นเรื่องของผู้เรียกเอง

การตัด `student_id` ทิ้งยังปิดข้อบกพร่องที่ซ้อนอยู่ด้วย: `where: { student_id:
undefined }` ของ Prisma ไม่ใช่ตัวกรองที่ไม่ตรงกับอะไรเลย แต่**ไม่มีตัวกรอง** ผู้เรียก
ที่ไม่ส่งพารามิเตอร์นี้จึงเคยได้สถานะการส่งงานของนักศึกษาทุกคนใน section — ไม่มีค่าให้
ละเว้นอีกแล้ว และไม่มีชื่อคนอื่นให้ใส่

## ขอบเขต

- **ไม่ได้เพิ่มกฎ "อาจารย์ดูงานของนักศึกษาที่ตัวเองสอน" ที่ข้อ 2** — อาจารย์มีเส้นของ
  ตัวเองอยู่แล้วที่ `/student-activity` ซึ่ง #38 ปิดไปแล้ว การเพิ่มสาขาที่สองให้
  `requireOwnEntry` ที่นี่จะเป็นการเขียนกฎให้ผู้เรียกที่ไม่มีอยู่จริง
- **ไม่ได้เปลี่ยนรูปของ `404` ที่ `getActivityDetails` โยนเอง** — นักศึกษาที่ถาม
  ถึงงานที่ไม่มีอยู่ยังได้ `404` `ไม่พบงานที่ต้องการ` ที่ controller เหมือนเดิม
  เพราะ `requireOwnEntry` เขียนว่า `if (row && …)` แถวที่ไม่มีจึงผ่าน middleware
  ไปถึงปลายทาง ตาม ADR-0001 · ผู้เรียกที่ไม่ใช่นักศึกษาไม่เคยเห็น `404` นั้น เพราะ
  `requireRole("STUDENT")` ตอบ `403` ก่อน ซึ่งเป็นรูปเดียวกับอีกเจ็ดเส้นใน router
  นี้ และการเป็นเจ้าของงานที่ส่งเข้ามาเป็นเรื่องของนักศึกษาโดยนิยามอยู่แล้ว

## ผลที่ตามมา

- `/student` ทั้งแปดเส้นที่เป็น GET ต้องมี session แล้ว ไม่มีเส้นไหนใน router นี้ที่
  ผู้เรียกที่ไม่ได้ล็อกอินเข้าถึงได้อีก และ `student.schema.ts` ไม่มีฟิลด์ไหนที่ระบุ
  ตัวบุคคลเหลืออยู่เลย
- `requireOwnEntry` รับชื่อ parameter ได้ — router อีก 56 เส้นของกลุ่ม `portfolio`
  ไม่ต้องแก้ เพราะ default ยังเป็น `"id"` ตามที่ทุกเส้นสะกด
- `entryOwner` มีแถวที่ไม่ใช่ portfolio อยู่หนึ่งแถวแล้ว ชื่อของ object ยังเหมาะอยู่
  (มันคือ "เจ้าของของแถว" ไม่ใช่ "เจ้าของของ portfolio") แต่ comment ต้องบอกว่าแถวนี้
  ต่างออกไปตรงไหน
- `getActivitiesBySectionId()` ฝั่ง web เลิกรับ `studentId` และผู้เรียกเดียวของมัน
  (`create-work-form.tsx`) เลิกส่ง

## จะกลับมาทบทวนเมื่อไหร่

เมื่อมีหน้าจอที่อาจารย์ต้องอ่านรายละเอียดงานผ่านเส้นของนักศึกษา หรือเมื่อ portfolio
สาธารณะย้ายจากการเรียกชั้น service มาเรียกผ่าน HTTP จริง ๆ ตอนนั้นข้อ 2 ต้องเลือกว่า
จะเพิ่มสาขาให้ `requireOwnEntry` หรือแยกเป็น endpoint ใหม่ที่มีกฎของตัวเอง
