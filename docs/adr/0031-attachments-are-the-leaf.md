# ADR-0031 — #68 เดินจากใบล่างขึ้น ไม่ใช่จาก feature ที่ใหญ่ที่สุด

- **สถานะ**: ตัดสินแล้ว 19 สิงหาคม 2569
- **ที่มา**: [issue #68](https://github.com/khthana/Deep-Portfolio/issues/68)
  รอบ attachment
- **เกี่ยวข้อง**: [ADR-0029](0029-api-types-per-feature.md) คือกติกาของแต่ละรอบ
  และ [ADR-0030](0030-evaluation-row-union.md) คือรอบก่อนหน้า ใบนี้ไม่ได้ทบทวน
  ข้อไหนของทั้งสองใบ — มันตอบคำถามที่ยังไม่มีใครถาม คือ **ย้าย feature ไหนก่อน**

## บริบท

รอบนี้ตั้งใจจะย้าย feature `student-activity` เพราะรอบ gradebook ทิ้ง
`packages/api-types/src/student-activity.ts` ไว้ให้แล้วหนึ่งไฟล์ ถือ type เดียว
พร้อมคอมเมนต์ว่าที่เหลือรอรอบของมัน — ฟังดูเป็นตัวเลือกที่ต่อเนื่องที่สุด

พออ่านข้างในจริงกลับพบว่าย้ายไม่ได้ในรอบเดียว

```
GetStudentActivityDetailResp = GetActivityDetailResp   ← feature activity
                             & GetStudentActivityDetail
                             & { submitted_files: AttachmentDetailResp }
```

`GetActivityDetailResp` เป็นของ feature `activity` ซึ่งยังไม่ย้าย และตัวมันเอง
ก็อิง `RubricDetail`, `ScoreWeightDetail` และ `AttachmentDetailResp` ต่อไปอีก
ย้าย `student-activity` จึงแปลว่าลาก activity, rubric, score-weight และ
attachment มาด้วยทั้งหมดในรอบเดียว ซึ่งขัดกับข้อที่ #68 เขียนไว้เองว่า
"ทำทีละ feature หนึ่ง PR ต่อหนึ่ง feature" และขัดกับเหตุผลที่ ADR-0028 ข้อ 3 ให้
ไว้ว่าทำไมถึงต้องทีละ feature — "diff ที่ใหญ่กว่านี้ตรวจไม่ไหว"

## การตัดสินใจ

**ลำดับของ #68 กำหนดโดยกราฟการพึ่งพา ไม่ใช่โดยขนาดของ feature**

รอบต่อไปต้องเป็น type ที่ไม่มีขาออกไปหา feature ที่ยังไม่ย้าย ถ้าไม่มี feature
ไหนเข้าเกณฑ์ ให้มองหา**ใบล่างที่หลาย feature ใช้ร่วมกัน**แล้วย้ายอันนั้นก่อน
ถึงแม้มันจะไม่ใช่ feature ในความหมายที่ #68 ใช้คำ

รอบนี้ใบล่างคือ attachment `AttachmentDetailResp`, `FileDetail` และ `URLDetail`
ไม่ import อะไรเลย และมีหก feature ฝังมันไว้ข้างใน — ประกาศข่าว, เอกสารประกอบ
การสอน, กิจกรรมการประเมิน, กิจกรรมการเรียนรู้ และการส่งงานทั้งสองแบบ ย้ายรอบ
เดียวปลดล็อกทั้งหกใบพร้อมกัน

ทางเลือกที่ไม่เอาคือย้าย `student-activity` เฉพาะส่วนที่ไม่ติด activity
(`GetAllSubmittedActivityByActivityIdResp`, `Submission`, `SubmissionGroup`)
แล้วทิ้ง `GetStudentActivityDetailResp` ไว้ ราคาที่จ่ายคือ feature เดียวถูกหั่น
เป็นสองรอบ แล้วรอบหลังไม่มีอะไรบอกว่ายังเหลืออะไรนอกจากต้องไปอ่านเอง

ข้อนี้ **ใบนี้ตัดสินเอง** ไม่ได้อ้าง ADR ใบไหน ADR-0029 ข้อ 3 พูดเรื่อง shim
(ไฟล์ที่ว่างแล้วเหลือไว้ re-export) ไม่ได้พูดเรื่องการหั่น feature และ ADR-0029
ข้อ 2 ก็**ทำ**การย้ายครึ่งเดียวไปแล้วด้วยซ้ำ — `student-activity.ts` ถือ type
เดียวพร้อมคอมเมนต์ว่าที่เหลือรอรอบของมัน ซึ่งใบนั้นถือว่าถูกต้อง

ความต่างอยู่ที่ว่าครึ่งเดียวแบบไหน ข้อ 2 ย้าย type ตัวเดียวที่**จบในตัวเอง** ไป
ไว้ที่บ้านของมัน ส่วนที่จะทำที่นี่คือย้าย response บางเส้นของ feature เดียวกัน
แล้วทิ้งเส้นที่เหลือไว้เพราะมันติดอยู่กับ feature อื่นที่ยังไม่ย้าย รอบหลังจึงต้อง
เปิดสองที่เพื่อจะรู้ว่า `student-activity` ย้ายไปแค่ไหนแล้ว ย้ายใบล่างก่อนไม่มี
ปัญหานั้น เพราะแต่ละรอบจบเป็นก้อน

## `AttachmentType` ไม่ได้ย้าย และย้ายไม่ได้

`apps/web/src/types/attachment-type.type.ts` ถือของสองอย่างที่ต่างกันคนละชนิด

```ts
export const AttachmentType = { FILE: "FILE", IMAGE: "IMAGE", LINK: "LINK" } as const;
export type AttachmentType = keyof typeof AttachmentType;
```

ตัว `const` เป็น**ค่าตอน runtime** มีห้าไฟล์ที่ import มัน สี่ในนั้นอ่านค่าจริง
ตอน runtime (ปุ่มอัปโหลดสองตัวกับฟอร์มส่งงานสองไฟล์) อีกหนึ่งใช้เป็น type ส่วน package
นี้ไม่มี build step ได้เพราะข้างในเป็น type ล้วน ซึ่งถูกลบทิ้งตอนคอมไพล์
(ADR-0028 ข้อ 4) ใส่ `const` เข้าไปเมื่อไรข้อนั้นก็พังทันที ไฟล์นี้จึงไม่ถูกลบ
เหลือค่าตัวนี้ไว้พร้อมคอมเมนต์ว่าที่เหลือย้ายไปไหนแล้ว

นี่คือความต่างระหว่างใบนี้กับ ADR-0029 ข้อ 3 ที่บอกให้ลบไฟล์ที่ว่างลง — ไฟล์นี้
**ไม่ว่าง** และสิ่งที่เหลืออยู่ก็อยู่ที่นี่ไม่ได้ที่อื่น

อนึ่ง `const` ก้อนนี้มีสำเนาเหมือนกันทุกตัวอักษรอยู่อีกที่หนึ่ง ที่
`apps/web/src/features/teacher/announcement/types/announement-type.tsx` รอบนี้
ไม่แตะ เพราะเป็นค่าตอน runtime ทั้งคู่ จึงอยู่นอก #68 ทั้งใบ แต่บันทึกไว้ตรงนี้
เพื่อให้คนที่มาเก็บกวาดค่าฝั่ง web รู้ว่ามีสองที่ ไม่ใช่ที่เดียว

## สิ่งที่รอบนี้เจอ

`uploaded_at` เขียนว่า `Date | null` ทั้งสองฝั่ง ของจริงคือ string เสมอ —
แบบที่ 1 ในสามแบบที่ #68 เตือน `attachments.service.ts` เขียนออกมาเป็น
`toISOString()` เองแล้ว ด้วยเหตุผลเดียวกับรอบก่อน ๆ คือ `JSON.stringify` เรียก
`toJSON()` ของ `Date` อยู่แล้ว response จึงเหมือนเดิมทุกไบต์

น่าสนใจตรงที่ **ฝั่ง web ไม่มีจุดไหนพังเลย**จากการเปลี่ยนนี้ ทั้งสี่จุดที่อ่าน
`uploaded_at` ส่งมันเข้า `convertDateToThaiFormat` ซึ่ง ADR-0029 ข้อ 5 ขยายเป็น
`Date | string | null` ไว้ตั้งแต่รอบ gradebook — ข้อนั้นถูกเขียนเพื่อกันไม่ให้
รอบหลัง ๆ พังพร้อมกัน และรอบนี้คือรอบแรกที่ได้ประโยชน์จากมันจริง

`file_size` เป็น `BigInt` ในคอลัมน์ ซึ่ง `JSON.stringify` **โยน error** ไม่ใช่
แปลงให้ service อ่านผ่าน `Number()` อยู่แล้วมาตั้งแต่ต้น จึงไม่ต้องแก้อะไร แต่
`Number()` ทำให้แถวที่ไม่มีขนาดกลายเป็น `0` ไม่ใช่ `null` — เขียนกำกับไว้ใน type
เหมือนที่ `GradebookStudentActivity.full_score` ทำ

## ผลที่ตามมา

- เหลือสำเนาฝั่ง web 38 ไฟล์ 2,096 บรรทัด (จาก 2,111 หลังรอบ evaluation)
- หก feature ที่ฝัง attachment ไว้ พร้อมย้ายแล้วในแง่ของ dependency ข้อนี้
- รอบต่อไปให้ดูกราฟก่อนเลือก ตัวถัดไปที่เป็นใบล่างคือ `RubricDetail` กับ
  `ScoreWeightDetail` ซึ่ง `GetActivityDetailResp` อิงอยู่ — จบสองตัวนั้นแล้ว
  activity ถึงจะย้ายได้ และ student-activity ตามหลัง activity อีกที
- ถ้ารอบไหนเจอ type ที่มีทั้งค่า runtime และ type ปนกันในไฟล์เดียวอีก ให้แยก
  เหมือนรอบนี้ อย่าย้ายทั้งไฟล์
- **ไฟล์แนบของ portfolio ไม่ได้จบไปกับรอบนี้** `portfolio-*.model.ts` เจ็ดไฟล์
  เขียนรูปไฟล์แนบของตัวเองไว้ inline ซึ่งเป็นคนละรูปกับที่ย้าย — ไม่มี `title`,
  `file_type` หรือ `uploaded_at` มี `url` กับ `file_path` อยู่บนวัตถุเดียวกัน
  และเป็นรายการเดียวไม่ได้แยกไฟล์กับลิงก์ service ของมัน**เรียก**
  `getAttachments` จริง แต่แล้วแบนผลลัพธ์ลงเป็นรูปของตัวเองก่อนตอบ สิ่งที่ออก
  สายจึงไม่ใช่ `AttachmentDetailResp` รอบนี้จึงไม่แตะ และทั้งเจ็ดไฟล์รอรอบของ
  feature portfolio เอง (สังเกตว่ามันไม่ได้อ่าน `uploaded_at` ด้วย การเปลี่ยน
  field นั้นจึงไม่ถึงมัน)
