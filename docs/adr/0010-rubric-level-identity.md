# ADR-0010 — ระดับคะแนนมีตัวตนของตัวเอง ไม่ใช่ตำแหน่งในแถว

- **สถานะ**: ตัดสินแล้ว 11 สิงหาคม 2569
- **ที่มา**: [issue #39](https://github.com/khthana/Deep-Portfolio/issues/39)
- **เกี่ยวข้อง**: [#25](https://github.com/khthana/Deep-Portfolio/issues/25)
  ทำเรื่องเดียวกันหนึ่งชั้นบน — เกณฑ์ (`rubric_activity_mapping`) ส่ง `id` กลับมาเพื่อ
  ไม่ให้ `PUT /activity` เขียนรูบริกใหม่ทั้งชุด ไฟล์นี้ทำต่อในระดับช่วงคะแนน

## บริบท

`saveRubricLevels` จับคู่ช่วงคะแนนด้วย `level_no` ซึ่งฐานข้อมูลรับรองว่าไม่ซ้ำกันใน
เกณฑ์เดียว (`@@unique([rubric_id, level_no])`) แต่ "ไม่ซ้ำ" กับ "ไม่ขยับ" เป็นคนละเรื่อง

ปุ่มลบช่วงคะแนนใน `rubric-form.tsx` (`deleteScoreColumn`) เรียงเลขที่เหลือใหม่ทั้งแถว
ลบช่วงกลางของสามช่วงแล้ว ช่วงบนสุดกลับมาในชื่อ "ระดับ 2" — เลขเดียวกับที่ช่วงกลาง
เคยถือ ผลคือ

- ไม่มีอะไรส่งเลข 3 มาอีก แถวที่เป็นระดับ 3 จึงถูกอ่านว่า "ถูกลบ" ทั้งที่อาจารย์เก็บมัน
  ไว้ — หายไปพร้อมคะแนนที่ให้ไว้ที่ระดับนั้น
- แถวที่เป็นระดับ 2 คือแถวที่อาจารย์ลบ แต่มันตรงเลขกับสิ่งที่ส่งมา จึงอยู่ต่อและถูก
  `upsert` ทับด้วยคำบรรยายของระดับ 3 คะแนนที่ให้ไว้ที่ระดับ 2 ยังชี้ที่แถวเดิมและกลาย
  เป็นคะแนนของช่วงบนสุดเงียบ ๆ

อาจารย์แก้คำในตารางหนึ่งช่อง แล้วคะแนนที่ตรวจไปแล้วเปลี่ยนความหมายโดยไม่มีอะไรบอก
เป็นชนิดของความเสียหายที่ #25 ตั้งใจปิด เพียงแต่ปิดไม่สุด — ตอนนั้นบันทึกไว้ใน
`BEHAVIOR-CHANGES.md` ว่าเกินขอบเขต และปักหมุดไว้ด้วย test

## สิ่งที่ต้องตัดสิน

1. อะไรคือตัวตนของช่วงคะแนน
2. คำขอเก่าที่ไม่มี `id` ต้องยังใช้ได้ไหม
3. คำขอที่ `id` หรือ `level_no` ขัดกันเองต้องตอบว่าอะไร

## การตัดสิน

> **`rubric_levels.id` คือตัวตน `level_no` เป็นแค่ลำดับที่แสดงผล — form ส่ง `id`
> กลับมา และการจับคู่ด้วย `level_no` เหลือไว้เป็นทางถอย**

### 1. `id` ก่อน แล้วค่อยถอยไปใช้ `level_no`

`saveRubricLevels` จับคู่ตามลำดับนี้

1. ช่วงที่ส่ง `id` มา → แถวนั้น
2. ช่วงที่ไม่มี `id` → แถวที่ `level_no` ตรงกันและยังไม่มีใครจอง
3. ไม่เจอทั้งสองอย่าง → สร้างใหม่

แถวเดิมที่ไม่มีใครจับคู่ด้วยคือแถวที่ถูกลบ คะแนนที่ให้ไว้ที่แถวนั้นถูกลบก่อน
(foreign key ของ `student_activity_rubric_score.rubric_level_id` ไม่ cascade) แล้วจึง
ลบแถว — เหมือนที่ #25 ตัดสินไว้สำหรับเกณฑ์

**ไม่ได้เพิ่มคอลัมน์ใหม่** และ **ไม่ได้แก้สัญญาของ `GET /activity`** — ตอนเขียน #25
คิดว่าต้องแก้ แต่ `getActivityDetail` `include: { rubric_levels: true }` อยู่แล้ว `id`
จึงออกไปถึง form ตั้งแต่แรก สิ่งที่ขาดคือ form ทิ้งมันตอน `handleInitEditForm` และ
schema ฝั่งรับไม่ยอมรับมันกลับเข้ามา

### 2. ทางถอยด้วย `level_no` ยังอยู่

`id` เป็น optional เหมือน `id` ของเกณฑ์ รูบริกที่ส่งกลับมาครบทุกช่วงโดยไม่มี `id` เลย
จึงยังจับคู่ได้เหมือนเดิมทุกประการ กรณีเดียวที่ต้องพึ่ง `id` คือกรณีที่เพิ่ม `id` เข้ามา
เพื่อแก้ — ลำดับของช่วงคะแนนเปลี่ยน

เหตุผลคือ `POST /activity` ใช้ code เดียวกันแต่ไม่มีอะไรให้เก็บ และ "รูบริกกลาง" ที่
ติ๊กมาจาก modal ก็สร้างช่วงคะแนนใหม่ทุกช่วง การบังคับ `id` จะทำให้ทั้งสองทางต้องแยกโค้ด
โดยไม่ได้อะไรเพิ่ม

### 3. `400` เมื่อ `id` หรือ `level_no` ขัดกันเอง

สามข้อความใหม่ (ภาษาไทย เพราะ frontend พิมพ์ออกหน้าจอตรง ๆ) ตรวจใน `assertOwnRubric`
ก่อนการเขียนทุกอย่าง ด้วยเหตุผลเดิมของ #25: `createAttachments` อัปโหลดขึ้น MinIO นอก
transaction การปฏิเสธหลังจากนั้นจะทิ้งไฟล์ค้างไว้

| | |
| --- | --- |
| `id` ซ้ำในเกณฑ์เดียว | `400` — `มีระดับคะแนนเดียวกันถูกส่งมาซ้ำ` |
| `id` ที่ไม่ใช่ของเกณฑ์นั้น | `400` — `มีระดับคะแนนบางรายการที่ไม่ใช่ของเกณฑ์นี้` |
| `level_no` ซ้ำในเกณฑ์เดียว | `400` — `มีระดับคะแนนซ้ำลำดับกันในเกณฑ์เดียวกัน` |

สองข้อแรกคือกฎของ `assertOwnRubric` ลงมาอีกชั้น โดยเทียบกับช่วงคะแนน**ของเกณฑ์ที่ส่งมา
ด้วยกัน** ไม่ใช่ของทั้งกิจกรรม — ช่วงคะแนนเป็นของเกณฑ์ ไม่ใช่ของกิจกรรม เกณฑ์ที่ไม่มี
`id` (เกณฑ์ใหม่) จึงไม่มีช่วงคะแนนของตัวเองเลย `id` อะไรก็ตามที่ส่งมาใต้มันเป็นของคนอื่น
ทั้งสองข้อใช้กับ `PUT /activity` เท่านั้น เพราะ `POST` ไม่มี `id` ให้ส่งมาตั้งแต่แรก

ข้อสามไม่ใช่การลงมาอีกชั้น แต่เป็นของใหม่: ก่อนหน้านี้ `upsert` ทำให้ตัวหลังเขียนทับตัวหน้า
เงียบ ๆ ตอนนี้จับคู่ด้วย `id` แล้วสองแถวจะชนกันที่ unique constraint และได้ `500` แทน
และเพราะเป็นเรื่องของ body ล้วน ๆ ไม่ต้องอ่านฐานข้อมูลเลย `POST /activity` จึงตรวจข้อนี้
ด้วย — ที่นั่น `createMany` ชนกับ constraint เดียวกันและตอบ `500` มาตลอด (D9: เจอตอนเขียน
test ก็แก้ตรงนั้น)

### 4. เขียนสองรอบเมื่อลำดับเปลี่ยน

`level_no` unique ต่อเกณฑ์ และการเรียงเลขใหม่เดินผ่านตำแหน่งที่ยังมีคนอยู่ — ระดับ 3 ที่
กำลังจะเป็นระดับ 2 ชนกับระดับ 2 ที่ยังไม่ได้ย้ายออก ทางแก้คือย้ายทุกแถวที่เก็บไว้ไป
พักเหนือเลขสูงสุดของทั้งของเดิมและของใหม่ก่อน แล้วค่อยเขียนเลขจริง

ทำเฉพาะเมื่อมีแถวไหนเปลี่ยนตำแหน่งจริง ๆ การบันทึกที่ไม่ได้ยุ่งกับลำดับ (ซึ่งเป็นส่วน
ใหญ่) จึงยิง query เท่าเดิม

## ขอบเขต

- **ไม่ได้แตะการจับคู่ของ `POST /activity`** — ตอนสร้างยังไม่มีช่วงคะแนนให้จับคู่ ทุกช่วง
  เป็นของใหม่หมด สิ่งเดียวที่ endpoint นั้นได้จากไฟล์นี้คือ `400` ของ `level_no` ซ้ำ
- **ไม่ได้คำนวณ `student_activity.score` ใหม่** — ตามที่ #25 ตัดสินไว้ คะแนนรวมยังเป็น
  ของอาจารย์ที่ต้องตรวจใหม่เอง ไฟล์นี้แค่ทำให้คะแนนรายช่วงยัง**ชี้ถูกช่วง**
- **ไม่ได้ห้ามอาจารย์แก้คำบรรยายของช่วงที่มีคนได้คะแนนไปแล้ว** — แก้คำผิดต้องทำได้ สิ่งที่
  ห้ามคือความหมายเปลี่ยนโดยที่ไม่มีใครสั่ง

## ผลที่ตามมา

- `rubricIdsOf` กลายเป็น `rubricOf` และอ่านช่วงคะแนนมาด้วยในคำขอเดียว ทั้งการตรวจและการ
  ปรับปรุงจึงทำงานบนภาพเดียวกัน และ `saveRubricLevels` ไม่ต้องอ่านซ้ำรายเกณฑ์อีก
- `apps/web` ต้องส่ง `id` กลับมาถึงจะได้ประโยชน์ — `handleInitEditForm` เก็บ `lvl.id`
  ไว้ `deleteScoreColumn` กระจาย `...level` อยู่แล้ว `id` จึงติดไปกับแถวตอนเรียงเลขใหม่
  และ `toRubricPayload` ส่งมันออกไปแบบเดียวกับ `id` ของเกณฑ์
- client อื่นที่ยังไม่ส่ง `id` ไม่พังและไม่แย่ลงกว่าเดิม แต่ก็ไม่ได้ดีขึ้น — พฤติกรรม
  ของมันคือทางถอยในข้อ 2

## จะกลับมาทบทวนเมื่อไหร่

ถ้าวันหนึ่งต้องเก็บประวัติว่าคะแนนหนึ่งถูกให้ตอนที่ช่วงคะแนนเขียนว่าอะไร (เช่น เพื่อ
ออกใบรับรองย้อนหลัง) นั่นคือการทำ `rubric_levels` ให้เป็นข้อมูลแบบมีเวอร์ชัน ซึ่งเป็น
คนละการตัดสินและใหญ่กว่านี้มาก ไฟล์นี้แค่ทำให้ "ช่วงคะแนนนี้" หมายถึงช่วงเดิมเสมอ
