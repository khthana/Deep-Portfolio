# ADR-0009 — งานที่ส่งต้องเป็นงานของคนที่กดส่ง

- **สถานะ**: ตัดสินแล้ว 11 สิงหาคม 2569
- **ที่มา**: [issue #38](https://github.com/khthana/Deep-Portfolio/issues/38)
- **เกี่ยวข้อง**: [ADR-0007](0007-group-membership.md) วางกฎว่าสิทธิ์ในกลุ่มอ่านจาก
  `student_activity_group_member` และตรวจใน service ภายใน transaction — ไฟล์นี้ใช้กฎ
  เดียวกันกับทางส่งงาน [ADR-0002](0002-section-access.md) เป็นที่มาของข้อสงวนเรื่อง
  "การปฏิเสธต้องไม่บอกว่าอะไรมีอยู่จริง" ซึ่งข้อ 3 ข้างล่างตอบไว้

## บริบท

`POST /student/submit/activity` และฝาแฝดฝั่ง learning activity รับ
`student_activity_id` (หรือ `student_learning_activity_id`) กับ `group_id` มาจาก body
ส่วนตัวตนของผู้ส่งมาจาก session — controller ทับด้วย `sessionUserId(req)` เสมอ
ตั้งแต่ #30 แล้ว แต่ไม่มีจุดไหนเทียบสองอย่างนี้เข้าหากัน

ผลคือช่องสามชั้น ซึ่งกว้างขึ้นหลัง #34 เพราะไฟล์ที่หลุดการเชื่อมถูกลบทิ้งถาวรแล้ว

1. **ส่งเดี่ยว** — รู้ `student_activity_id` ของเพื่อนก็ส่งงานแทนเพื่อนได้ และเพราะ
   ทางนี้ตัดไฟล์แนบเดิมทิ้งทุกครั้งก่อนผูกของใหม่ ไฟล์ที่เพื่อนส่งไว้หายถาวร
2. **ส่งกลุ่ม** — เขียนถึงสมาชิกที่ตอบรับแล้ว **ทุกคน** ในคำขอเดียว คนนอกที่รู้
   `group_id` จึงกดส่งแทนทั้งกลุ่มพร้อมทับไฟล์ของทุกคนได้
3. **คำตอบ** — ทางกลุ่มคืน `getStudentActivityDetail(student_activity_id)` ตามเลขที่
   body ส่งมาโดยไม่ตรวจ จึงอ่านรายละเอียดงานของคนอื่นได้แม้ไม่เขียนอะไร

test ปักหมุดพฤติกรรมนี้ไว้ตั้งแต่ #18 (`student-submit.test.ts`) และ
`BEHAVIOR-CHANGES.md` บันทึกไว้ในหัวข้อ "สิ่งที่ **ไม่ได้** เปลี่ยน" มาตลอด

## สิ่งที่ต้องตัดสิน

1. ปฏิเสธด้วยสถานะและข้อความอะไร
2. แก้กี่เส้น
3. คำขอที่ระบุ id ซึ่งไม่มีอยู่จริง กับ id ของคนอื่น ต้องแยกออกจากกันหรือไม่

## การตัดสิน

> **`403` พร้อมประโยคของตัวเอง ตรวจทั้งสี่เส้น และยังแยก "ไม่มีของชิ้นนี้" ออกจาก
> "ของชิ้นนี้ไม่ใช่ของคุณ"**

### 1. `403` ไม่ใช่ `400` หรือ `404`

ตาม ADR-0007: `403` เมื่อ**สิทธิ์ของผู้เรียก**ถูกปฏิเสธ `400` เมื่อ**ค่าใน body**
ผิด สิ่งที่เกิดขึ้นตรงนี้เป็นอย่างแรก — เลขที่ส่งมาถูกต้องทุกประการ มีแถวจริง อยู่ใน
กิจกรรมจริง เพียงแต่เป็นของคนอื่น สองประโยคใหม่ (ภาษาไทย เพราะ frontend พิมพ์ออก
หน้าจอตรง ๆ)

| | |
| --- | --- |
| `NOT_YOUR_SUBMISSION` | `403` — `ส่งงานได้เฉพาะงานของตัวเองเท่านั้น` |
| `NOT_YOUR_GROUP` | `403` — `ส่งงานกลุ่มได้เฉพาะกลุ่มที่ตัวเองเป็นสมาชิกเท่านั้น` |

แยกสองประโยคเพราะเป็นคนละสถานการณ์ในสายตาของนักศึกษา อย่างแรกคือ "กดผิดงาน"
อย่างหลังคือ "ยังไม่ได้อยู่ในกลุ่มนี้ ไปตอบรับคำเชิญก่อน" — ข้อความเดียวคลุมทั้งคู่
จะบอกทางออกผิดให้ครึ่งหนึ่งของคนที่เจอ

### 2. ตรวจทั้งสี่เส้น ทั้งสองชั้น

`submitActivity`, `submitGroupActivity`, `submitLearningActivity` และ
`submitGroupLearningActivity` เป็นโค้ดคนละชุดที่มีรูปเดียวกันสี่ครั้ง แก้เฉพาะเส้นที่
pin ไว้จะเหลืออีกสามเส้นที่เปิดอยู่เหมือนเดิม โดยที่ผู้อ่านโค้ดข้างหลังจะเข้าใจว่าปิดไป
แล้ว

ทางเดี่ยวเทียบ `student_id` ของแถวกับ session ทางกลุ่มตรวจสองชั้น

1. session ต้องอยู่ใน `members` ที่ `status: "ACCEPT"` ของกลุ่มที่ระบุ ไม่งั้น
   `NOT_YOUR_GROUP` — วางไว้ก่อนการเขียนทุกอย่าง ถัดจากการตรวจว่ากลุ่มมีสมาชิกไหม
2. `student_activity_id` ที่ระบุต้องเป็นแถวของ session เอง ไม่งั้น
   `NOT_YOUR_SUBMISSION` — ชั้นนี้ปิดช่องที่ 3 ในบริบทข้างบน การเป็นสมาชิกกลุ่มไม่ได้
   แปลว่าจะขอรายละเอียดงานของเพื่อนร่วมกลุ่มได้

ชั้นที่ 1 ซ้ำกับชั้นที่ 2 ในทางตรรกะ (ถ้าแถวเป็นของ session และอยู่ในชุดของกลุ่ม
session ก็ต้องเป็นสมาชิก) แต่แยกไว้เพื่อให้ได้ข้อความที่ถูกต้องตามข้อ 1

การตรวจอยู่**ใน service ภายใน transaction** ไม่ใช่ middleware ด้วยเหตุผลเดียวกับ
ADR-0007: สิ่งที่ตรวจคือค่าใน body ที่ต้องอ่านฐานข้อมูลถึงจะรู้ และคำตอบต้องยังจริงอยู่
ตอนที่เขียน

### 3. `404` ของ id ที่ไม่มีอยู่จริง ยังเป็น `404`

id ที่ไม่ตรงกับแถวไหนเลยยังได้ `ไม่พบงานที่ต้องการส่ง` เหมือนเดิม การแยกสองกรณีนี้ออก
จากกันเปิดเผยแค่ว่า "มีแถวที่ถือเลขนี้อยู่" ซึ่งเป็นสิ่งที่ระบบบอกอยู่แล้วโดยโครงสร้าง
— นักศึกษาทุกคนในชั้นมีแถว `student_activity` หนึ่งแถวต่อกิจกรรมหนึ่งชิ้นเสมอ รู้ว่า
เลขหนึ่งมีอยู่จึงไม่ได้รู้อะไรที่รายชื่อชั้นเรียนไม่ได้บอก

สิ่งที่ได้กลับมาคือข้อความที่ใช้ได้จริง: นักศึกษาที่เปิดหน้าเก่าค้างไว้แล้วกิจกรรมถูกลบ
ไปแล้ว ต้องอ่านว่า "ไม่พบงาน" ไม่ใช่ "งานนี้ไม่ใช่ของคุณ" ซึ่งชวนให้เข้าใจผิดว่ามีคน
ไปยุ่งกับบัญชี

ต่างจาก ADR-0002 ที่การมีอยู่ของ section เป็นข้อมูลของหลักสูตรที่ผู้เรียนไม่ควรสำรวจ
ได้ ที่นี่การมีอยู่ของแถวเป็นผลพลอยได้จากการลงทะเบียนที่ทุกคนในห้องรู้อยู่แล้ว

## ขอบเขต

- **ไม่ได้แตะการให้คะแนน** — `POST /student-activity/grade` ยังรวมสมาชิกที่ยังไม่ตอบรับ
  ตามที่บันทึกไว้ตั้งแต่ #14 เป็นการตัดสินเชิงนโยบายคนละเรื่อง
- **ไม่ได้ตรวจว่านักศึกษาลงทะเบียนใน section นั้นจริง** — ถ้ามีแถว `student_activity`
  ของตัวเองอยู่ ก็แปลว่าลงทะเบียนไว้แล้วโดยปริยาย การตรวจซ้ำไม่ได้ปิดอะไรเพิ่ม
- **ไม่ได้แตะกำหนดส่ง** — ส่งหลังเดดไลน์ยังส่งได้และถูกนับว่าสาย ตามที่ #15 ตัดสินไว้

## ผลที่ตามมา

- คำขอที่ถูกปฏิเสธไม่เขียนอะไรเลย เพราะการตรวจอยู่ก่อนคำสั่งเขียนทุกคำสั่งใน
  transaction เดียวกัน ไฟล์ที่ multer รับไว้แล้วไม่ถูกอัปโหลด (`createAttachments`
  อยู่หลังการตรวจ)
- frontend ไม่ต้องแก้ — `submit-classwork-section.tsx` ส่ง `classworkDetail.id`
  ซึ่งเป็นแถวของนักศึกษาที่ล็อกอินอยู่เสมอ ทั้งโหมดเดี่ยวและโหมดกลุ่ม
- เครื่องมือหรือสคริปต์ที่เคยส่งงานแทนคนอื่น (ถ้ามี) ใช้ไม่ได้อีก — ตั้งใจให้เป็นแบบนั้น

## จะกลับมาทบทวนเมื่อไหร่

ถ้าวันหนึ่งอาจารย์ต้องส่งงานแทนนักศึกษาได้ (เช่น นักศึกษาส่งงานเป็นกระดาษ) นั่นเป็น
เส้นทางใหม่ที่ต้องตรวจสิทธิ์ของ**อาจารย์**ต่อ section ไม่ใช่การผ่อนกฎนี้ กฎนี้พูดถึง
`requireRole("STUDENT")` เท่านั้น
