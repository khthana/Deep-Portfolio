# ADR-0039 — เส้นที่ตอบ "แถวเดิมบวกอะไรบางอย่าง" เขียนเป็นการต่อกัน ไม่ใช่เขียนใหม่ทั้งแถว

- **สถานะ**: ตัดสินแล้ว 19 สิงหาคม 2569
- **ที่มา**: [issue #68](https://github.com/khthana/Deep-Portfolio/issues/68)
  รอบ lesson-plan
- **เกี่ยวข้อง**: [ADR-0030](0030-evaluation-row-union.md) ซึ่งตัดสินว่า response
  ที่ถือแถว**คนละแบบ**เขียนเป็น union แยกตาม discriminant ใบนี้เป็นอีกครึ่งของ
  คำถามเดียวกัน คือแถว**แบบเดียวกัน**ที่บางเส้นเติมของเข้าไป และ
  [ADR-0036](0036-a-bare-scalar-gets-no-name.md) ข้อ 2 เรื่อง `/options` กับข้อ 4
  เรื่อง null ที่ไปจบที่จุด map ใบนี้ไม่ได้ทบทวนข้อไหนของทั้งสองใบ

## บริบท

แผนการสอนรายสัปดาห์มีหกเส้น มากกว่าทุก feature ที่ #68 เคยเจอมา และตอบห้ารูป
สี่รูปย้ายเข้า package รอบนี้ อีกรูปเป็นของ `/options` ซึ่งอยู่ที่เดิม

| เส้น                        | ตอบ                                          |
| --------------------------- | -------------------------------------------- |
| `GET /lesson-plan`          | แถว + `allActivities`                        |
| `GET /lesson-plan/student`  | แถว + `allActivities` + `course_materials`   |
| `PUT /lesson-plan`          | แถวเปล่า ๆ                                    |
| `POST`, `DELETE`            | `{ lesson_plan_id }`                          |
| `GET /lesson-plan/options`  | `{ label, value }` — ไม่ย้าย                  |

สามรูปแรกคือแถวเดียวกันของตาราง `course_syllabus` ต่างกันแค่ว่ามีอะไรแขวนอยู่ข้าง ๆ

## สิ่งที่ประกาศเดิมปิดไว้

| จุด                                   | type เดิมบอก                    | ของจริง                                  |
| ------------------------------------- | ------------------------------- | ---------------------------------------- |
| `year`, `semester`, `subject_id`      | ฝั่ง web ประกาศไว้บนแถว          | ไม่ใช่คอลัมน์ของตารางนี้ ไม่เคยส่ง       |
| `section_id`                          | ฝั่ง web ไม่ได้ประกาศ            | ส่งมาด้วยเสมอ เพราะ spread ทั้งแถว       |
| `title`, `description`, `remark`      | `string` ฝั่ง web                | ทั้งสามคอลัมน์เป็น nullable              |
| `created_at`, `updated_at`            | `Date` ทั้งสองฝั่ง               | string ตอนถึงมือผู้เรียก และ null ได้    |
| response ของ `PUT`                    | ฝั่ง web ใช้ type เดียวกับ `GET` | ไม่มี `allActivities` เพราะเป็นของที่อ่านสร้าง |

สามชื่อแรกน่าสนใจกว่าตัวอื่น เพราะเป็นฟิลด์ที่ **ไม่มีอยู่** ไม่ใช่ฟิลด์ที่ผิดชนิด
`course_syllabus` มีเก้าคอลัมน์และไม่มี `year`, `semester`, `subject_id` อยู่ใน
นั้นเลย — ปีการศึกษากับภาคเรียนเป็นของ section ไม่ใช่ของสัปดาห์ ผู้เรียกฝั่ง web
ที่อ่านมันไปจะได้ `undefined` มาตลอด และไม่มีใครอ่าน

`LessonPlanResp` ตัวเดียวถูกใช้ทั้งกับ `GET` (เป็น array) และกับ `PUT` ผู้เรียกของ
`PUT` จึงเชื่อว่ามี `allActivities` อยู่ในมือ ทั้งที่ไม่มี — ไม่มีใครอ่านเหมือนกัน

## การตัดสินใจ

**1. แถวเป็น type ของตัวเอง แล้วเส้นที่เติมของเขียนเป็น `&`**

```ts
LessonPlanRow            // PUT
LessonPlanWeek           = LessonPlanRow & { allActivities }
StudentLessonPlanWeek    = LessonPlanWeek & { course_materials }
```

ทางเลือกที่ไม่เอาคือเขียนเก้าคอลัมน์ซ้ำสามครั้ง ซึ่งเป็นสิ่งที่ทั้งสองฝั่งทำอยู่
ก่อนหน้านี้ — และเป็นเหตุผลที่ `PUT` ถูกประกาศผิด: พอสองรูปต้องเขียนแยก คนเขียน
ก็หยิบตัวที่ใกล้ที่สุดมาใช้แทนที่จะเขียนตัวที่สาม

ADR-0030 ตัดสินไว้ว่าแถว**คนละแบบ**ในเส้นเดียวกันเป็น union บน discriminant ใบนี้
คือกรณีตรงข้าม: แถวแบบเดียวกันในหลายเส้น ที่บางเส้นเติมของ กติกาจึงอ่านคู่กันได้ว่า
**อะไรที่ต่างกันจริงให้แยก อะไรที่เหมือนกันจริงให้ต่อ** และทั้งสองอย่างตัดสินจาก
สิ่งที่ endpoint ส่งจริง ไม่ใช่จากว่ามันดูเป็นพี่น้องกันไหม

ผลข้างเคียงที่จับต้องได้: ถ้าวันหนึ่ง `course_syllabus` เพิ่มคอลัมน์ มีที่เดียวที่
ต้องแก้ และทั้งสามเส้นได้ตามกันหมด — ต่างจากตอนนี้ที่จะต้องไปแก้สามที่แล้วลืมที่หนึ่ง

**2. `course_materials` เป็น null ได้ด้วยเหตุผลแคบ ๆ และเขียนไว้ว่าเหตุผลอะไร**

`?? null` ในเส้นของนักศึกษา (ซึ่งเป็น `|| null` ก่อนรอบนี้) ไม่ได้แปลว่า "สัปดาห์นี้ไม่มีเอกสาร" สัปดาห์ที่ไม่มี
เอกสารได้รายการว่างสองรายการ ไม่ใช่ null — เพราะสิ่งที่มันไปค้นคือผลของ
`/course-material` ซึ่งตอบแถวละสัปดาห์ของ section เดียวกัน สัปดาห์ที่มีอยู่จึงหา
ตัวเองเจอเสมอ

fallback นั้นจะทำงานก็ต่อเมื่อสัปดาห์หนึ่งถูกลบระหว่างการอ่านสองครั้ง ซึ่งเกิดได้
จริง รอบนี้จึงเก็บ `| null` ไว้ แต่เขียนกำกับว่าทำไม — เคสที่ปักรูปยืนยันว่าปกติ
ได้รายการว่าง ไม่ใช่ null (ผมเขียนเคสแรกไว้ผิดข้อนี้ และเคสเป็นตัวบอกว่าผิด)

**3. `title`, `description`, `remark` ที่เป็น null ไปจบที่ `?? ""` ตาม ADR-0036 ข้อ 4**

ต่างจากสองรอบก่อนตรงที่คราวนี้ **null ไปถึงได้จริงสองในสามตัว**:
`addLessonPlanBody.description` กับ `.remark` เป็น `optionalText` สัปดาห์ที่เพิ่ม
มาโดยไม่กรอกสองช่องนั้นได้ null ทันที ส่วน `title` เป็น `text` บังคับทั้งบนเส้นเพิ่ม
และเส้นแก้ จึงไปไม่ถึงเหมือน `title` ของ course-material ในรอบที่แล้ว

และต่างจากสองรอบก่อนอีกอย่างหนึ่ง: **คราวนี้ runtime ขยับจริง และเป็นการซ่อมของเสีย**
ตอนแรกผมเขียนไว้ในคอมเมนต์และในใบนี้ว่า "ไม่มีอะไรขยับ" ซึ่งผิด รีวิวเป็นคนจับได้

ฝั่งอ่านไม่ขยับจริง — `lesson-plan-column.tsx` เรนเดอร์ `text ? text : "-"` ทั้งสาม
ช่อง null กับ `""` เป็น falsy เหมือนกัน ได้ขีดเท่ากัน แต่**ฝั่งเขียนขยับ**: `edit()`
ยัดทั้งแถวเข้าฟอร์มด้วย `form.setFieldsValue({ ...record })` ช่องที่ผู้ใช้ไม่ได้พิมพ์
จึงเดินทางกลับออกไปเป็น null ตัวเดิม และ `optionalText` ปฏิเสธ null (ดูข้อ 4)
สัปดาห์ที่เพิ่มมาโดยไม่กรอกเนื้อหาจึง**แก้ไขไม่ได้เลย** — ได้ `400` แล้วขึ้น
"ไม่สามารถแก้ไขข้อมูล กรุณาลองใหม่อีกครั้ง" ทุกครั้ง

การ coalesce ที่จุด map จึงเป็นการซ่อมตาม D9 ไม่ใช่การรักษาพฤติกรรมเดิม และถูก
บันทึกไว้ใน `BEHAVIOR-CHANGES.md`

**4. `optionalText` แปลว่า "ไม่ส่งก็ได้" ไม่ได้แปลว่า "ส่ง null ได้" และมีเคสปักไว้แล้ว**

`blankToUndefined` เปลี่ยน `""` เป็น undefined และ**ส่งของที่ไม่ใช่ string ผ่านไป
ตรง ๆ** null จึงไปถึง `z.string().optional()` แล้วโดนปฏิเสธ นี่คือเหตุผลที่ข้อ 3
ต้อง coalesce ไม่ใช่ปล่อยผ่าน และรอบนี้เพิ่มเคส `PUT` ที่ส่ง `description: null`
แล้วได้ `400` พร้อม `ต้องเป็นข้อความ` เพื่อให้เหตุผลนั้นอยู่ในเทสต์ ไม่ใช่อยู่ใน
ความจำของคนเขียน

ข้อนี้เป็นเรื่องทั้งระบบ ไม่ใช่ของ lesson-plan: ทุกที่ที่ฝั่ง web map ค่าจาก
response ลงฟอร์มโดยตรง คอลัมน์ nullable ตัวใดที่คู่กับ `optionalText` จะมีอาการ
เดียวกัน รอบที่เหลือของ #68 ควรดูจุดนี้ทุกครั้งที่เติม `?? ""` ว่าค่าที่ coalesce
เดินทางกลับออกไปทางไหนบ้าง ไม่ใช่ดูแค่ว่าหน้าจอวาดเหมือนเดิมไหม

**5. `PUT` ตอบแถวเปล่า และเคสของมันไล่ชื่อทุกคีย์แล้ว**

เคสเดิมใช้ `toMatchObject` กับสองฟิลด์ รอบนี้เปลี่ยนเป็น `toEqual` ทั้งวัตถุ ซึ่ง
เป็นสิ่งที่พิสูจน์ว่าไม่มี `allActivities` อยู่จริง — ไม่ใช่แค่ว่า type ใหม่บอกว่าไม่มี

`updated_at` ในเคสนั้นเขียนเป็นค่าที่แถวถูกสร้างมา ด้วยเหตุผลเดียวกับที่ ADR-0036
ข้อ 3 เจอกับสัดส่วนคะแนน: คอลัมน์มี default แต่ไม่มี `@updatedAt` ข้างหลัง

**6. ไฟล์ type ฝั่ง web ที่ว่างลงให้ลบด้วย — ใบนี้เป็นคนตัดสิน ไม่ใช่ ADR-0029 ข้อ 3**

ADR-0029 ข้อ 3 พูดถึง **ไฟล์ model ฝั่ง API** ที่ว่างลง และตัวอย่างในนั้นคือ
`apps/api/src/models/gradebook.model.ts` ล้วน ๆ ไม่ได้พูดถึงไฟล์ฝั่ง web เลย
ADR-0038 อ้างข้อนั้นตอนลบ `course-material-type.ts` ฝั่ง web ซึ่งอ้างเกินสิ่งที่
ข้อนั้นเขียนไว้ ใบนี้จึงรับข้อนี้มาเป็นของตัวเอง

เหตุผลเดียวกันข้ามฝั่งได้ตรง ๆ คือ shim ที่เหลือไว้ให้ re-export ทำให้มีสองทางที่
import สิ่งเดียวกันได้ และรอบต่อไปจะเดาไม่ถูกว่าทางไหนคือทางที่ตั้งใจ
`apps/web/src/types/course-type.type.ts` จึงหายไปทั้งไฟล์ และผู้เรียกทั้งสามที่
เคยอ่านมันชี้ไป package ตรง ๆ ในรอบเดียวกัน

ต่างจากฝั่ง API อยู่จุดหนึ่งที่ควรพูด: ไฟล์ฝั่ง web ปนของสองอย่าง คือ response
ที่ต้องย้าย กับ request body และ params ที่ ADR-0028 กันออกไปตั้งแต่ต้น ไฟล์จะ
"ว่าง" ก็ต่อเมื่อไม่เหลือทั้งสองอย่าง — `course-type.ts` ฝั่งนักศึกษาในรอบนี้จึง
ยังอยู่ ทั้งที่ `GetStudentLessonPlanWithMaterialResp` ในนั้นย้ายออกไปแล้ว

## ผลที่ตามมา

- เหลือสำเนาฝั่ง web **33 ไฟล์ 1,765 บรรทัด** (จาก 34 ไฟล์ 1,814 หลังรอบ
  course-material) นับด้วย glob ชุดเดียวกับที่ ADR-0028 ประกาศไว้
- **`apps/web/src/types/course-type.type.ts` หายไปทั้งไฟล์** ไฟล์นี้เคยถือ
  `CourseDetail`, `CLOResp`, `PLOResp` (ย้ายไปตั้งแต่รอบ course),
  `ScoreWeightResp`, `AnnouncementDetailResp` และ `LessonPlanResp` — ตอนนี้ย้าย
  ครบทั้งหกตัวแล้ว
- `apps/api/src/models/lesson-plan.model.ts` ไม่ถูกลบ เพราะยัง re-export request
  body จาก schema อยู่ และ import ที่รอบ course-material เพิ่งเพิ่มให้มันก็หายไป
  พร้อมกัน เพราะรูปที่มันยืมย้ายมาอยู่ในไฟล์เดียวกับที่มันต้องการแล้ว
- API เพิ่มสามเคส (ไล่ชื่อทุกคีย์ของ `GET` และของ `GET /student` และ `PUT` ที่ส่ง
  `description: null` แล้วได้ `400`) และรัดเคสของ `PUT` ให้เป็น `toEqual` ทั้งวัตถุ
  รวมเป็น **1,076 เคส**
- ฝั่ง web ไม่เพิ่มไม่ลดเคส (448) เพราะจุดที่แก้เป็นการ map ในคอมโพเนนต์
- **มีบันทึกใน `BEHAVIOR-CHANGES.md`** ต่างจากทุกรอบของ #68 ที่ผ่านมา ยกเว้นรอบ
  student-activity — ดูข้อ 3
- `npm run lint` ยังเท่าเดิมที่ 216 warning
- ใน 33 ไฟล์ที่เหลือ **14 ไฟล์เป็นของ portfolio** ซึ่งมากกว่าทุก feature อื่นรวมกัน
  และมี 10 route รออยู่ ที่เหลือกระจายอยู่ที่ calendar, home ทั้งสองฝั่ง, student,
  user, mapping และไฟล์ที่ผ่านรอบมาแล้วแต่ยังไม่ว่าง — ซึ่งอันหลังนี้ต้องเปิดอ่าน
  ทีละไฟล์ ไม่ใช่เดาจากชื่อ ว่าที่เหลือในนั้นเป็น response หรือเป็น request กับค่า
  runtime ที่ ADR-0028 กันออกไปตั้งแต่ต้น
