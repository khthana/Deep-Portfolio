# ADR-0023 — คนที่ยังไม่ตอบรับ อยู่ในช่องของตัวเอง

- **สถานะ**: ตัดสินแล้ว 12 สิงหาคม 2569
- **ที่มา**: [issue #53](https://github.com/khthana/Deep-Portfolio/issues/53)
- **เกี่ยวข้อง**: [ADR-0017](0017-group-membership-means-accepted.md) ตัดสินว่า
  **`ACCEPT` คือคำตอบของ "อยู่ในกลุ่มนี้" ทุกที่ที่ตัดสินว่าใครได้อะไร** แล้วยก
  คำถามที่ตามมา — "แล้วอาจารย์จะรู้ได้อย่างไรว่ามีคนค้างอยู่" — ไปเป็น #53 ทั้ง
  ก้อน พร้อมทางเลือกสองทาง (ปนใน `members` หรือแยกเป็นช่องใหม่) ไฟล์นี้เลือกทาง
  หนึ่งในสองทางนั้น กติกาของ ADR-0017 เลือกให้ไม่ได้ เพราะมันพูดถึงการ **ให้**
  ไม่ใช่การ **แสดง** — การบอกอาจารย์ว่ามีใครค้างอยู่ ไม่ได้ทำให้คนนั้นได้อะไร

## บริบท

เส้นทางที่แสดงกลุ่มพร้อม `status` ของสมาชิกเป็นของนักศึกษาทั้งหมด — ทั้งหกเส้นใน
`student-activity-group.route.ts` และทั้งหกของคู่ฝั่ง learning-activity ขึ้นต้น
ด้วย `requireRole("STUDENT")` เส้นทางเดียวที่อาจารย์เห็นกลุ่มคือ
`getGroupSubmissions` (`student-activity.service.ts` และคู่ของมัน) ซึ่งเดิมกรอง
`status: "ACCEPT"` ไว้ใน query เลย คนที่ยัง `PENDING` จึงไม่ได้ปรากฏเป็น
"รอตอบรับ" แต่หายไปจากคำตอบทั้งคน

หลัง ADR-0017 คนคนนั้นไม่ได้คะแนนของกลุ่มแล้ว และคำเชิญมีอายุเจ็ดวันโดยไม่มี
endpoint ส่งซ้ำ อาจารย์จึงเป็นคนเดียวที่อยู่ในฐานะจะสังเกตเห็นว่ารายชื่อที่ตัวเอง
กำลังตรวจอยู่ขาดคนไป — แต่ข้อมูลที่จะสังเกตนั้นไม่เคยถูกส่งไปถึงเลย

ผู้เรียกฝั่งหน้าจอมีสองที่ และทั้งสองอ่าน `group.members` ตรง ๆ เป็นรายชื่อที่
แสดงบนตาราง: `teacher-activity-detail-page.tsx` map `members` สองรอบ (รายการทั้งหมด
รอบหนึ่ง รายการที่ติดดาวอีกรอบหนึ่ง) และ
`teacher-learning-activity-detail-page.tsx` ทำแบบเดียวกัน

## สิ่งที่ต้องตัดสิน

1. ให้อาจารย์เห็นคนที่ยังไม่ตอบรับผ่านทางไหน — ปนใน `members` พร้อม `status`
   หรือแยกเป็นช่องใหม่
2. `REJECTED` นับเป็นแบบเดียวกับ `PENDING` หรือไม่แสดงเลย
3. งานนี้จบที่ API หรือรวมหน้าจอของอาจารย์ด้วย

## การตัดสิน

> **`members` ยังแปลว่า "คนที่จะได้คะแนนก้อนนี้" เหมือนเดิมทุกตัวอักษร คนที่ยังไม่
> ตอบรับไปอยู่ในช่องใหม่ `unaccepted_members` พร้อม `status` กำกับว่าเป็นความเงียบ
> แบบไหน**

```jsonc
"group": {
  "group_id": 12,
  "members": [                       // ACCEPT เท่านั้น (เหมือนเดิม)
    { "student_id": "...", "first_name_th": "...", "last_name_th": "..." }
  ],
  "unaccepted_members": [            // ใหม่
    { "student_id": "...", "first_name_th": "...", "last_name_th": "...",
      "status": "PENDING" }
  ]
}
```

### 1. ช่องใหม่ ไม่ใช่การปนเข้าไปใน `members`

ทางที่ปนเข้าไปพังทันทีถ้าหน้าจอไม่ตามแก้ ผู้เรียกทั้งสองที่ข้างบน map `members`
เป็นรายชื่อบนตารางโดยไม่อ่าน `status` เพราะวันนี้ไม่มี `status` ให้อ่าน ถ้า API
ใส่คนที่ยัง `PENDING` ลงไปในลิสต์เดิม หน้าจอจะขึ้นชื่อคนที่ไม่ได้คะแนนปนกับคนที่ได้
ทันทีในวันที่ deploy — และการเติม `status` เข้าไปในแต่ละแถวก็ไม่ช่วยจนกว่าจะมีคน
เขียนโค้ดอ่านมัน นั่นคือการเปลี่ยนที่ **ผิดโดยปริยาย** จนกว่าจะมีใครตามแก้

ช่องใหม่ผิดไปทางที่ปลอดภัยกว่า หน้าจอที่ยังไม่รู้จักมันก็ยังถูกเหมือนเดิมทุกอย่าง
เพียงแต่ยังไม่ได้บอกอะไรเพิ่ม ความเสี่ยงจึงเป็น "ยังไม่ได้ประโยชน์" ไม่ใช่
"แสดงผิด" และคำว่า `members` ก็ไม่ต้องเปลี่ยนความหมายกลางทาง ซึ่งสำคัญเพราะ
ADR-0017 เพิ่งผูกความหมายนั้นไว้กับการให้คะแนน

### 2. `REJECTED` อยู่ในช่องเดียวกัน และบอกว่าเป็นคนละแบบ

คำถามที่อาจารย์ถามคือ "รายชื่อที่ตรวจอยู่ขาดใครไปหรือเปล่า" คนที่กดปฏิเสธก็หายไป
จากรายชื่อด้วยเหตุผลเดียวกับคนที่ไม่กดอะไรเลย การซ่อน `REJECTED` ไว้ ก็คือการสร้าง
ปัญหาเดิมของ #53 ขึ้นมาใหม่ในขนาดที่เล็กลง — หายไปเงียบ ๆ โดยไม่มีร่องรอย

แต่สองสถานะนี้ไม่ได้เรียกร้องสิ่งเดียวกันจากอาจารย์ คนที่กดปฏิเสธคือเรื่องที่จบ
แล้ว ส่วนคนที่ยังไม่ตอบอาจแค่ยังไม่ได้เปิดอีเมล และยังกดรับได้ถ้าโทเคนยังไม่หมด
อายุ แต่ละแถวจึงพก `status` ของตัวเองไปด้วย ให้หน้าจอเลือกได้เองว่าจะแยกแสดงหรือ
รวมเป็น "ยังไม่ตอบรับ" ก้อนเดียว — ถูกกว่าการให้ API ตัดสินแทนด้วย boolean ที่
บอกได้อย่างเดียวว่าใช่หรือไม่ใช่

`ACCEPT` โผล่ในช่องนี้ไม่ได้เลย และชนิดของมันก็เขียนไว้แบบนั้นตรง ๆ —
`Exclude<MemberStatus, "ACCEPT">` ไม่ใช่ `MemberStatus`

### 3. งานนี้จบที่ API

หน้าจอทั้งสองของอาจารย์ไม่ถูกแตะในงานนี้ การเลือกว่าจะแสดงคนที่ค้างตรงไหนของตาราง
ให้เห็นชัดแค่ไหน และเรียกมันว่าอะไร เป็นการตัดสินใจเรื่องหน้าตาที่ควรตัดสินโดย
เจ้าของงาน ไม่ใช่ผลพลอยได้ของการแก้ API ที่นี่จึงทำครึ่งที่เป็นข้อเท็จจริง —
ข้อมูลถูกส่งไปถึงแล้ว — และบันทึกไว้ใน
[`BEHAVIOR-CHANGES.md`](../../BEHAVIOR-CHANGES.md) ว่าไฟล์ไหนของ `apps/web` ต้อง
ตามแก้ ตามเกณฑ์ยอมรับข้อสุดท้ายของ #53 เอง

### 4. เส้นทางติดดาวยังไม่ต้องแก้

ADR-0017 หัวข้อ 3 ปล่อย `addStudentActivityGroupToBookmark` กับคู่ของมันไว้โดยไม่
กรอง `status` — ดาวยังถูกเขียนลงแถว `student_activity` ของทุกคนในกลุ่มรวมทั้งคนที่
ไม่เคยตอบรับ — และเขียนไว้ว่า "ถ้า #53 ทำให้อาจารย์เห็นคนที่ยังไม่ตอบรับจริง ๆ
ที่นั่นคือจุดถัดไปที่ต้องกลับมาดู" กลับมาดูแล้ว และคำตอบยังเหมือนเดิม

`unaccepted_members` ไม่ได้พา `is_bookmark` ของใครออกไป — แต่ละแถวมีแค่ชื่อ รหัส
นักศึกษา และ `status` ส่วนดาวของกลุ่มยังอ่านจากแถวของสมาชิกที่ตอบรับแล้วเหมือน
เดิม ดาวที่ค้างอยู่บนแถวที่ไม่เคยถูกส่งจึงยังไม่ปรากฏที่ไหน และเหตุผลเดิมของ
ADR-0017 (ดาวไม่ได้ตัดสินว่าใครได้อะไร) ก็ยังใช้ได้ทั้งข้อ

## ผลที่ตามมา

- **response ของสองเส้นทางเปลี่ยนรูป แบบเพิ่มอย่างเดียว**
  `GET /activity/submitted/list` และ `GET /learning-activity/submitted/list`
  มีช่อง `unaccepted_members` เพิ่มเข้ามาในทุก submission ที่เป็นงานกลุ่ม ไม่มี
  ช่องไหนถูกลบหรือเปลี่ยนความหมาย ผู้เรียกเดิมจึงไม่พัง ดู
  [`BEHAVIOR-CHANGES.md`](../../BEHAVIOR-CHANGES.md)
- **`apps/web` ยังไม่ได้ตาม** สี่ไฟล์ที่ต้องแก้เมื่อถึงคิว — type สองไฟล์และหน้าจอ
  สองไฟล์ — ระบุชื่อไว้ใน `BEHAVIOR-CHANGES.md` แล้ว
- **query ดึงสมาชิกทั้งกลุ่มแทนที่จะกรองในฐานข้อมูล** การแยกย้ายไปทำใน
  `splitByAcceptance` (`src/utils/group-members.ts`) ซึ่งใช้ร่วมกันทั้งสองฝั่ง
  กลุ่มหนึ่งมีสมาชิกไม่กี่คน ส่วนต่างจึงไม่มีนัย และการมีที่เดียวที่ตอบว่า
  "ACCEPT อยู่ทางนี้ ที่เหลืออยู่ทางนั้น" คุ้มกว่าการกรองซ้ำสองไฟล์
- **กลุ่มที่ยังไม่ส่งงาน ยังไม่ปรากฏ** `getGroupSubmissions` ดึงเฉพาะกลุ่มที่
  `status` ไม่ใช่ `NOT_SUBMITTED` อยู่แล้วตั้งแต่เดิม อาจารย์จึงเห็นคนที่ค้างเฉพาะ
  ในกลุ่มที่ส่งงานแล้วเท่านั้น กลุ่มที่ยังไม่ส่ง ไม่มีใครในนั้นปรากฏบนหน้าจอนี้อยู่
  แล้วไม่ว่าจะตอบรับหรือไม่ นี่คือขอบเขตเดิมของเส้นทางนี้ ไม่ใช่สิ่งที่ #53 เปลี่ยน
- **ไม่มี migration และไม่มีข้อมูลเดิมถูกแตะ** เป็นการเปลี่ยนรูปคำตอบล้วน ๆ

## จะกลับมาทบทวนเมื่อไหร่

- **เมื่อมี endpoint ส่งคำเชิญซ้ำ** ตอนนี้อาจารย์เห็นแล้วว่าใครค้าง แต่สิ่งที่ทำ
  ได้ยังมีแค่บอกให้หัวหน้ากลุ่มถอดชื่อออกแล้วใส่กลับเพื่อออกโทเคนใบใหม่ ซึ่ง
  ADR-0017 บันทึกไว้ว่าไม่มีที่ไหนบอกและไม่มีใครเดาได้ การเห็นโดยทำอะไรไม่ได้ ดีกว่า
  ไม่เห็น แต่ยังไม่ใช่คำตอบทั้งหมด
- **เมื่อ `apps/web` หยิบช่องนี้ไปแสดงจริง** ตอนนั้นจะรู้ว่าข้อมูลเท่านี้พอไหม —
  วันหมดอายุของคำเชิญ หรือบทบาทในกลุ่ม อาจเป็นสิ่งที่หน้าจอต้องการเพิ่ม
- **เมื่ออาจารย์ต้องเห็นกลุ่มที่ยังไม่ส่งงานด้วย** ซึ่งเป็นคำถามของเส้นทางนี้ทั้ง
  เส้น ไม่ใช่ของช่องใหม่ช่องเดียว
