# ADR-0045 — service เดียวคือรอบเดียว ต่อให้ฝั่ง web จะเป็นห้า feature

- **สถานะ**: ตัดสินใจแล้ว
- **วันที่**: 2026-08-22
- **บริบท**: [#68](https://github.com/khthana/Deep-Portfolio/issues/68) รอบที่สิบเจ็ด
  — `/student` ทั้ง router
- **ต่อจาก**: [ADR-0040](0040-the-portfolio-is-ten-features.md) ที่นิยามคำว่า
  "feature" ของ #68 ไว้ แล้วใช้นิยามนั้นแตก e-Portfolio ออกเป็นสิบรอบ,
  [ADR-0044](0044-a-response-is-what-was-selected.md) ข้อ 1 เรื่อง query ที่ไม่มี
  `select`, [ADR-0033](0033-learning-activity-and-the-absent-key.md) เรื่องคีย์ที่
  หายไปกับคีย์ที่เป็น null, [ADR-0035](0035-one-group-shape-for-both-halves.md)
  เรื่องรูปเดียวกันได้ประกาศเดียว และ
  [ADR-0037](0037-the-package-says-what-the-wire-says.md) เรื่อง package มีหน้าที่
  บอกว่าเส้นไหนแปลงค่าก่อนตอบ

## บริบท

`/student` มีสิบเส้น และฝั่ง web กระจายอยู่ห้าที่: `student/course`,
`student/home`, `student/calendar`, `student/portfolio` และ `teacher/student`
เส้นที่มากที่สุดในรอบไหนก็ตามของ #68 ที่ผ่านมา และ service เดียวที่ยาว 1,094
บรรทัดตอนเปิดอ่าน

คำถามแรกจึงเป็นคำถามเดียวกับที่ ADR-0040 เจอ กลับด้าน: ตอนนั้นคือ URL prefix
เดียวกันแต่เป็นสิบ feature รอบนี้คือหน้าจอห้าหน้าแต่เป็นอะไร

## การตัดสินใจ

### 1. หน่วยของรอบคือ service ไม่ใช่หน้าจอ

ADR-0040 เขียนนิยามไว้ว่า feature ของ #68 คือ "กลุ่มเส้นที่ใช้รูปร่วมกันและมี
service เป็นของตัวเอง" `/student` เข้านิยามนั้นทั้งดุ้น: `student.route.ts`,
`student.controller.ts`, `student.service.ts`, `student.model.ts` และ
`student.mapper.ts` อย่างละหนึ่ง และรูปก็ใช้ร่วมกันจริง —

- `ClassworkDetail` หนึ่งตัวเติมทั้ง `/classwork/list` (หน้า course) และ
  `/all/classwork/list` (หน้า home) ผ่าน mapper ตัวเดียวกัน แยกรอบเมื่อไหร่ก็ต้อง
  ประกาศซ้ำหรือย้ายครึ่งเดียว ซึ่งเป็นสถานการณ์ที่ ADR-0034 บอกให้ย้ายรอบเดียวกัน
  แทนที่จะแตกตามชื่อ
- `/calendar` เริ่มจากการเรียก `getStudentCourseList` ของตัวเอง แล้วอ่าน
  `CourseDetail` ที่ได้มาแปลงเป็น `CalendarCourseEvent` — ปฏิทินไม่มี query
  เป็นของตัวเองสักตัว
- `/enrolled/subjects`, `/activities/list` และ `/activities/details/:id` ตอบให้
  ตัวเลือกงานของ e-Portfolio ทั้งสามเส้น และทั้งสามเส้นอยู่ใน service เดียวกันนี้

**กติกาที่ตามมา**: ชื่อโฟลเดอร์ฝั่ง web ไม่ใช่เกณฑ์แบ่งรอบ เกณฑ์คือ service —
เส้นที่ mapper หรือ query ตัวเดียวกันเติมให้ ต้องอยู่รอบเดียวกัน ADR-0040 กับใบนี้
เป็นกฎข้อเดียวกันอ่านคนละทิศ: หนึ่ง router ที่มีสิบ service คือสิบรอบ และห้า
หน้าจอที่ใช้ service เดียวคือรอบเดียว

เส้นเดียวที่ไม่เข้าพวกคือ `/student/list` ซึ่งเป็น roster ของอาจารย์ ไม่ใช่เรื่อง
ของนักศึกษาเลย แต่มันอยู่ใน service เดียวกันและอ่านตาราง `student` ตัวเดียวกัน
จึงมาด้วย

### 2. สหภาพที่มีอยู่แล้วสองตัว ประกอบเป็นตัวที่สามได้ ไม่ต้องเขียนใหม่

`ClassworkDetail.type` มาจากคอลัมน์สองคอลัมน์คนละตาราง — `activities.activity_type`
กับ `learning_activities.learning_activity_type` — เพราะ list นี้เอาสองตารางมารวม
เป็น array เดียว package มีสหภาพของทั้งคู่อยู่แล้ว และ ADR ของ
`LearningActivityType` เขียนไว้ชัดว่าจงใจไม่ยืมของอีกตัว เพราะ "คนละคอลัมน์ คนละ
schema ที่คุม และการที่ตัวหนึ่งมีค่าที่สามไม่ควรทำให้อีกตัวกว้างขึ้นเงียบ ๆ"

รอบนี้จึงเขียน

```ts
export type ClassworkType = ActivityType | LearningActivityType;
```

ไม่ใช่ `"INDIVIDUAL" | "GROUP"` เป็นครั้งที่สาม เหตุผลที่การประกอบไม่ขัดกับกติกา
ของสองใบนั้น: แถวของ list นี้**เป็นได้ทั้งสองอย่างจริง ๆ** วันที่ตัวใดตัวหนึ่ง
กว้างขึ้น แถวของ list นี้ก็กว้างขึ้นตามด้วยจริง ๆ การกว้างตามจึงเป็นสิ่งที่ถูก
ไม่ใช่ผลข้างเคียงที่หลุด

### 3. สองเส้นที่ตอบคำศัพท์ไม่เท่ากันบนรูปเดียวกัน ไม่ใช่ drift เสมอไป

ADR-0034 ข้อ 3 ตอบไว้ว่า `LATE` ไม่ย้ายไปกับ feature submission เพราะ "มันไปถึง
หน้าจอทางเดียวคือรายการงานของนักศึกษา ซึ่งเป็นของ feature `student` ที่ยังไม่ถึง
คิว" — รอบนี้คือคิวนั้น

`ClassworkStatus` คือ `StudentActivityStatusDB | "LATE"` ห้าค่า แต่ไม่มีเส้นไหน
ส่งครบห้า

- `/classwork/list` เรียก `getDisplayStatus` ซึ่งเทียบ deadline กับนาฬิกาแล้วตอบ
  `LATE` แทน `NOT_SUBMITTED` — ค่าที่ไม่มีในคอลัมน์และไม่ถูกเขียนลงที่ไหนเลย
- `/all/classwork/list` ไม่เรียก และส่งคอลัมน์ดิบ เพราะมันคิดเรื่องเลยกำหนดเอง
  ด้วยการหย่อนแถวลง bucket `late` — มันไม่ต้องใช้คำนั้น

ตอนแรกอ่านว่านี่คือ drift ที่รอบนี้ควรลบ แต่การทำให้เท่ากันคือการเรียก
`getDisplayStatus` ในเส้นที่สองด้วย ซึ่งจะพัง `classifyClasswork` ทันที: มันเช็ค
`status !== "NOT_SUBMITTED"` เพื่อแยกงานที่ส่งแล้ว แถว `LATE` จะกลายเป็น
"submitted" ทั้งหมด และ bucket `late` จะว่างตลอดกาล

**กติกาที่ตามมา**: ก่อนจะเรียกความไม่เท่ากันระหว่างสองเส้นว่า drift ให้ถามว่า
"ถ้าทำให้เท่ากันแล้วอะไรพัง" ถ้าคำตอบคือ logic ที่อ่านความต่างนั้นอยู่ แสดงว่ามัน
เป็นการออกแบบ ไม่ใช่ความบังเอิญ — หน้าจอหนึ่งอ่านสถานะ อีกหน้าจออ่านว่าแถวมาถึงใน
ถังไหน ประกาศเป็น type เดียวที่กว้างพอสำหรับทั้งคู่ แล้วเขียน doc บอกว่าเส้นไหน
ส่งอะไร ตามหน้าที่ที่ ADR-0037 ให้ package ไว้

### 4. `Record` ที่ครอบไม่ครบ กลายเป็น `Partial` ไม่ใช่คำที่เดาขึ้นมา

`ClassworkStatus` กว้างขึ้นเป็นห้าค่า ทำให้ map ห้าตัวใน `course-type.ts` —
label, icon สองชุด และสีสองชุด — ครอบไม่ครบ เพราะไม่มีตัวไหนมีคีย์ `GRADING`

ทางเลือกคือเติมคำไทยกับ icon กับสีให้ `GRADING` เอง แต่ [#69](https://github.com/khthana/Deep-Portfolio/issues/69)
เปิดไว้แล้วสำหรับคำถามนี้บนตารางประเมิน และคำว่าอะไรกับ icon ไหนเป็นการตัดสินใจ
ของคนออกแบบ ไม่ใช่ของรอบย้าย type ทั้งห้าตัวจึงเป็น
`Partial<Record<ClassworkStatus, string>>` ซึ่งพูดสิ่งที่เป็นจริง: การ lookup พลาด
ได้ ค่าที่ได้อาจเป็น `undefined` และไม่มีอะไรใน `apps/api` เขียน `GRADING` วันนี้

นี่คือช่องเดียวกับที่ #69 บันทึกไว้ คนละหน้าจอ รอบนี้จึงเพิ่มหน้าจอที่สองเข้าไปใน
issue เดิม แทนที่จะเปิดใบใหม่หรือเดาคำตอบ

ADR-0034 ข้อ 3 เขียนไว้ว่า `ClassworkDetailFull.status` "ไม่ใช่กรณีเดียวกับ #69
ตรงที่ไม่มีใครเอาค่านี้ไป lookup ในตารางคำแปล" ซึ่งถูกสำหรับรูปนั้น รูปของ list
เป็นอีกเรื่อง: `ClassworkCard` เอา `status` ไป lookup สามตาราง — คำ ไอคอน และสี

### 5. `select` ที่ขาด ก็เป็นหนี้ของรอบเหมือน `select` ที่ไม่มี

ADR-0044 ข้อ 1 พูดถึง query ที่ไม่มี `select` เลย ซึ่งตอบเกิน รอบนี้เจอสิ่งที่ตรง
กันข้าม: `select` มีอยู่ แต่ขาดคอลัมน์ที่รูปสัญญาไว้ — สามคอลัมน์ ใน query สองตัว
— และ `as` ที่ท้าย `map` คือสิ่งที่ทำให้มันผ่าน typecheck

| ที่ | ขาดอะไร | ผลที่ caller เห็น |
| --- | --- | --- |
| `getAllStudentLearningActivity` | `section_id`, `detail` | ทุกกิจกรรมการเรียนรู้บน `/classwork/list` ได้ `section_id: 0` ซึ่งเป็น fallback ของ mapper และไม่มีคีย์ `detail` เลย |
| `getAllStudentActivityBySectionIdList` | `score` | ทุกงานบน `/all/classwork/list` ไม่มีคีย์ `received_point` ทั้งที่ list อีกตัวที่ mapper เดียวกันเติมมีครบ |

ทั้งสามคอลัมน์มองไม่เห็นบนหน้าจอวันนี้ และเหตุผลที่มองไม่เห็นเป็นเรื่องเดียวกัน
— **แต่ละเส้นขาดสิ่งที่หน้าจอของอีกเส้นอ่าน** ไล่ทุก route ที่แถวไปถึงแล้ว: แถวจาก
`/classwork/list` ลงที่ `courseSlice.allClasswork` แล้วไปที่ `ClassworkCard`
ทางเดียว ซึ่งอ่านแปดฟิลด์และไม่มี `section_id` กับ `detail` อยู่ในนั้น (link ของมัน
ใช้ `secId` จาก route) ส่วนแถวจาก `/all/classwork/list` ลงที่
`homeSlice.allClasswork` แล้วไปที่ `AssignmentCard` ทางเดียว ซึ่งอ่านเก้าฟิลด์
รวม `section_id` กับ `detail` แต่ไม่อ่าน `received_point` เลย — arm `CLASSWORK`
ของ `EventDetailItem` ไม่มีใครสร้างขึ้นมาสักที่ ปฏิทินจึงไม่ได้รับแถวพวกนี้

แต่ "มองไม่เห็นวันนี้" ไม่ใช่เหตุผลให้ type โกหก และค่า `0` ที่ปลอมเป็น section id
คือสิ่งที่อันตรายที่สุดในสามอย่างนี้ ถ้าวันหนึ่งมีคนเอาไปสร้าง link

**กติกาที่ตามมา**: รอบที่เขียนรูปลง package เป็นเจ้าของทั้งสองทิศ — คอลัมน์ที่
query ตอบเกินกว่ารูป และคอลัมน์ที่รูปสัญญาแต่ query ไม่ได้ขอ อย่างหลังหาเจอได้จาก
การไล่ `as` ทุกตัวใน service ที่รอบนั้นแตะ

### 6. `as` ทุกตัวใน service ที่รอบนี้แตะ ถูกลบหรือถูกบีบให้แคบลง

ห้าตัว สองแบบ

**สี่ตัวที่ปิดของไว้** คือ `as GetAllStudentActivity` กับ
`as GetAllStudentLearningActivity` ที่ท้าย `map` ทั้งสี่ก้อน — ตัวที่ทำให้ข้อ 5
เกิดขึ้นได้ ทั้งสี่หายไป โดยดึงตัว `map` ออกมาเป็น `toClassworkRow` ตัวเดียวต่อ
ไฟล์ ที่มี return type ประกาศไว้และรับ `status` เป็นพารามิเตอร์ (ซึ่งเป็นสิ่งเดียว
ที่ผู้เรียกสองรายต่างกัน ตามข้อ 3) `getDisplayStatus` ก็แคบลงจาก
`(string, Date | null) => string` เป็น
`(student_activity_status, Date | null) => ClassworkStatus`

เหลือ cast เดียวในแต่ละไฟล์ และมันคร่อม `activity_type` ตัวเดียว ไม่ใช่ทั้ง object
เพราะคอลัมน์เป็น `VarChar(20)` — การ `toUpperCase()` ข้อความอิสระไม่มีทางแคบลงเป็น
สหภาพสองค่าได้ด้วยตัวเอง cast ที่คร่อมนิพจน์เดียวปิดสิ่งที่มันปิดไว้เท่านั้น

พอ return type บังคับจริง คอลัมน์ที่ประกาศผิดอีกสองตัวก็โผล่ทันที:
`learning_activities.section_id` เป็น `Int` ไม่ใช่ `Int?` (ต่างจาก
`activities.section_id`) ส่วน `course_syllabus_id` เป็น `Int?` ไม่ใช่ `Int` — model
เขียนกลับกันทั้งคู่ และ `?? 0` ของ mapper ตายไปแล้วบนครึ่ง learning

**ตัวที่ห้าไม่ได้ปิดอะไรเลย** `as CalendarCourseEvent` ใน
`getStudentCalendarEvent` คร่อม object ที่ตรงกับ `CourseDetail` ทุกฟิลด์อยู่แล้ว
ลบทิ้งแล้วใส่ annotation บนตัวแปรแทน — ADR-0032 เจอ `as` ที่ปิดของไว้ ใบนี้บันทึก
ว่าตัวที่ยังไม่ปิดอะไรก็ไม่ควรอยู่ต่อ เพราะวันหนึ่งมันจะปิด

### 7. รูปที่เหมือนกันข้าม feature ใช้ชื่อของ feature ที่มาถึงก่อน

`GET /student-activity/attachments` ตอบ `{ attachment_id, url, file_path,
original_filename, file_size }` ซึ่งตรงกับ `PortfolioSectionAttachment` ที่
ADR-0041 ตั้งชื่อไว้ทุกฟิลด์ ADR-0035 บอกว่ารูปเดียวกันได้ประกาศเดียว รอบนี้จึง
import ชื่อเดิมข้าม feature ไปเลย

ชื่อยังไม่โกหก เพราะผู้เรียกเดียวของเส้นนี้คือ `use-portfolio.ts` ที่เอาไปประกอบ
ส่วน "ผลงาน" ของ e-Portfolio — คนอ่านที่เจอชื่อนี้ในไฟล์ของนักศึกษาจะเดาถูกว่า
มันไปโผล่ที่ไหน

### 8. `?` ต้องพิสูจน์ ไม่ใช่เดาจากสิ่งที่ TypeScript อนุมานได้

รอบนี้เขียน `course?: string` ลงบน `CalendarClassworkEvent` ก่อน ด้วยเหตุผลที่
อ่านดูดี: service ใช้ `studentCourses.find(...)?.course_name_en` และ `find` ที่ไม่
เจอคืน `undefined` ซึ่ง `JSON.stringify` จะทิ้งคีย์ทิ้ง ตาม ADR-0033 เป๊ะ

แต่มันไม่เคยเกิด ไล่ย้อนสามบรรทัดจะเห็นว่า `sectionIds` ถูกอ่านมาจาก
`studentCourses` ตัวนั้นเอง หลัง `filter` แล้ว และ query ทั้งสองตัวกรองด้วย
`section_id: { in: sectionIds }` — ทุกแถวที่กลับมาจึงมีคู่ใน list เสมอ
`getCourseDetail` ก็คืน `section_id` ตัวที่ถูกถามมา ไม่ใช่ตัวอื่น `find` ตัวนั้น
พลาดไม่ได้เลยสักครั้ง

ADR-0043 ข้อ 2 นับไว้ว่ามี **สี่รอบติดกัน** ที่เจอคำถามนี้ และในสี่รอบนั้นมีสาม
ที่คีย์ไม่เคยหายจริง (อีกหนึ่งคือ `attachments` ของ personal ซึ่งหายจริงบน write)
ใบนี้เป็นใบที่เกือบเพิ่มลงกองแรก และสิ่งที่ต่างคือมันไม่ได้ลอก type เก่ามา —
มันอนุมานจาก `?.` ในโค้ดตรงหน้า

**กติกาที่ตามมา**: `?.` ในโค้ดไม่ใช่หลักฐานว่าคีย์หายได้ มันเป็นแค่หลักฐานว่า
