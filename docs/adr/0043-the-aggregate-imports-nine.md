# ADR-0043 — รอบรวมของ e-Portfolio: type ที่ import ไฟล์ของทั้งเก้า section

- **สถานะ**: ตัดสินใจแล้ว
- **วันที่**: 2026-08-22
- **บริบท**: [#68](https://github.com/khthana/Deep-Portfolio/issues/68) รอบที่สิบห้า
  และรอบสุดท้ายของ e-Portfolio
- **ต่อจาก**: [ADR-0040](0040-the-portfolio-is-ten-features.md) ที่กัน
  `/portfolio` ไว้ท้ายสุด, [ADR-0042](0042-an-any-is-an-unnamed-shape.md)
  ที่วางกติกาเรื่อง `any` คร่อม response

## บริบท

ADR-0040 บอกไว้ว่า e-Portfolio ไม่ใช่หนึ่ง feature แต่เป็นสิบ และ router ที่ชื่อ
`/portfolio` เองต้องเดินท้ายสุด เพราะ endpoint หนึ่งของมัน —
`GET /portfolio/public/:token` — เรียก service ของอีกเก้า section ทั้งหมดแล้วตอบ
รวมมาในก้อนเดียว รอบนี้คือรอบนั้น

`/portfolio` มีเก้าเส้น แปดเส้นตอบเรื่องของตัวเอง (แถวของตาราง `portfolio`
ที่บอกว่าจะโชว์ section ไหน ใช้เทมเพลตอะไร สีอะไร และเลือกทักษะใดขึ้นหน้าปก)
ส่วนเส้นที่เก้าคือลิงก์แชร์ ซึ่งเป็น route เดียวในกลุ่มที่ไม่มี session อยู่ข้างหลัง
เลย — token ในลิงก์คือตัวยืนยันสิทธิ์เอง (ADR-0001)

## สิ่งที่พบเมื่อเปิดอ่าน

ฝั่ง web ไม่ได้เขียนสำเนาของ response ไว้ใน `types/` เหมือน feature อื่น แต่เขียน
ไว้ในไฟล์ service ของตัวเอง และเขียนด้วยวิธีที่แย่กว่าการคัดลอก:

```ts
export interface PortfolioBackendResp
  extends Omit<PortfolioConfig, "id" | "selectedSkillIds"> {
  id: string;
  selectedSkillIds: number[];
}
```

`PortfolioConfig` คือ **view model** ของเทมเพลต ไม่ใช่ response การประกาศแบบนี้
ทำให้ view model กลายเป็นนิยามของสิ่งที่ API ตอบ แล้วทุกอย่างที่มันผิดก็มองไม่เห็น
เพราะไม่มีที่ไหนให้เทียบ — มันผิดสี่ฟิลด์ด้วยวิธีนี้ (`templateId`,
`portfolioName`, `templateName`, `templateColor` ล้วนเป็น null ได้และถูกประกาศเป็น
`string` เปล่า) และผิดอีกฟิลด์ด้วยตัวมันเอง คือ `shareExpiresAt` ที่เป็น `Date`
ซึ่งไม่มีที่ไหนเป็นนอกจากใน process ของ API

ส่วน `GET /portfolio/public/:token` ไม่มีชื่อเลยทั้งสองฝั่ง: hook เรียก
`axiosInstance.get` ตรง ๆ ไม่ใส่ argument แล้ว destructure สิบสองคีย์ออกมาจาก
`any`

## การตัดสินใจ

### 1. ไฟล์ของรอบรวม import ไฟล์ของอีกเก้า section

`packages/api-types/src/portfolio.ts` import ไฟล์ของทั้งเก้า section ที่ย้ายมา
ก่อนหน้า บวก `student.ts` อีกใบสำหรับ leaf ที่มันฝัง รวมสิบใบ แล้วประกอบเป็น
`PublicPortfolioDetail` ซึ่งสิบในสิบสองคีย์ของมันคือ response ของ feature อื่น
ทั้งดุ้น

นี่คือเหตุผลที่ ADR-0040 กันรอบนี้ไว้ท้ายสุด ไฟล์อื่นใน package ก็ import กันเอง
อยู่แล้ว — `student-learning-activity.ts` import ห้าใบ `student-activity.ts` สี่ใบ
— แต่สิบใบคือมากที่สุดเท่าที่มี และต่างจากที่อื่นตรงที่ไม่ใช่การยืม leaf มาใช้
แต่เป็นการเอา response ทั้งก้อนของ feature อื่นมาวางเป็นคีย์

**กติกาที่ตามมา**: ลำดับของรอบที่เหลือใน #68 ยังเป็นกราฟ dependency ตาม ADR-0031
ไม่ใช่ขนาดของ feature และตอนนี้มีตัวอย่างที่ชัดที่สุดแล้วว่าทำไม — ถ้ารอบรวมเดิน
ก่อน มันจะต้องเขียนสำเนาของทั้งเก้า section ทิ้งไว้ในไฟล์เดียว

### 2. optional ที่ไม่เคยหายไป — ครั้งที่สี่ติดกัน

`PortfolioResp` ฝั่ง API ประกาศ `templateName`, `publicShareToken` และ
`shareExpiresAt` เป็น optional ทั้งสามตัว ทั้งที่ไฟล์นั้นมี mapping function เดียว
ที่สร้าง response ทุกก้อน และมันเซ็ตครบทั้งสามทุกครั้ง

นับรวมกับสามรอบก่อนหน้าเป็นสี่รอบติด: `attachments` ของ personal หายจริงบน write
(ADR-0040), `attachments` ของหกsection ไม่เคยหาย (ADR-0041), `mappings` ของ skill
ไม่เคยหาย (ADR-0042) และสามตัวนี้ก็ไม่เคยหาย

**กติกาที่ตามมา**: `?` บน response type ไม่ใช่ข้อมูล จนกว่าจะเปิดอ่านโค้ดที่สร้าง
response นั้นแล้วเห็นเส้นทางที่ไม่เซ็ตคีย์ ถ้าอ่านแล้วไม่เจอ ให้ตัด `?` ทิ้งแล้ว
เขียน test ปักคีย์นั้นไว้ — รอบนี้ปักด้วย `Object.keys(...).sort()` สิบเก้าคีย์

### 3. leaf ที่เป็นของ feature อื่น ย้ายตอนที่คนใช้ต้องใช้

`userData` ใน `PublicPortfolioDetail` คือ `StudentDetail` ซึ่งเป็นของ feature
`user` (`GET /user/student`) ที่ยังไม่ย้าย package import จาก `apps/` ไม่ได้ ดังนั้น
ทางเลือกมีสองทาง: เขียนสำเนาที่สองไว้ในไฟล์ของ portfolio หรือย้าย `StudentDetail`
มาก่อน

เลือกอย่างหลัง และวางไว้ใน `student.ts` ซึ่งมีอยู่แล้วและถือ leaf ของนักศึกษาอยู่
สองใบ นี่คือกติกาเดียวกับ ADR-0031 ที่ย้าย `AttachmentDetailResp` ไปก่อนหกsection
ที่ฝังมัน ต่างกันแค่ว่าคราวนี้ leaf เป็นคำตอบทั้งก้อนของ endpoint หนึ่ง ไม่ใช่
ชิ้นส่วนที่หลาย feature ใช้ร่วมกัน

`UserDetail` ซึ่งเป็นของ `GET /user` อีกเส้นหนึ่ง ยังอยู่ที่เดิม — รอบนี้ย้าย
เฉพาะสิ่งที่ตัวเองฝัง ไม่ใช่ทั้ง feature

สิ่งที่ `StudentDetail` โกหก: สี่ในสิบฟิลด์ประกาศว่า null ได้ ทั้งที่ service
`?? ""` ทุกตัวก่อนตอบ ผู้อ่านจึงไม่เคยเห็น null เห็นแต่ string ว่าง ซึ่งเป็นคนละ
เรื่องกันเวลาเขียนเงื่อนไข

### 4. ชื่อคีย์ของ response รวม เป็นสัญญา ไม่ใช่ของชั่วคราว

สิบสองคีย์ของ `PublicPortfolioDetail` ชื่อ `educationData`, `trainingData`,
`certificateData` ไล่ไปจนครบ ซึ่งอ่านแล้วเหมือนชื่อตัวแปรที่หลุดออกมาเป็น API
มากกว่าชื่อฟิลด์ แต่ hook ทั้งสองตัวที่อ่าน endpoint นี้ destructure ด้วยชื่อพวกนี้
การเปลี่ยนชื่อจึงเป็นการเปลี่ยนสิ่งที่ caller เห็น ไม่ใช่การจัดบ้าน

**กติกาที่ตามมา**: รอบของ #68 บันทึกชื่อที่ wire ใช้จริง แม้จะเป็นชื่อที่ไม่มีใคร
จะตั้งถ้าเริ่มใหม่ เหมือนที่ ADR-0037 ตัดสินเรื่องตัวพิมพ์ของ enum และ ADR-0042
เรื่อง `isShowX` แบบ camelCase การจัดชื่อใหม่เป็นงานของ ticket ที่ตั้งใจเปลี่ยน
พฤติกรรม

### 5. view model กับ response แยกกัน และ mapper ไม่ใส่ค่า default ให้ใคร

`PortfolioBackendResp` หายไป `PortfolioDetail` เป็น response และ
`PortfolioConfig` ยังเป็น view model ของเทมเพลตเหมือนเดิม ทั้งสองต่อกันด้วย
`mapBackendToFrontend` ที่แปลงแค่ `selectedSkillIds` จากตัวเลขเป็นสตริง

คำถามที่ต้องตอบคือสี่ฟิลด์ที่ null ได้ — จะ coalesce ที่ mapper แล้วให้ view model
เป็น `string` ต่อไปไหม คำตอบคือไม่ เพราะแต่ละหน้าจอมี default ของตัวเองที่ไม่
เหมือนกัน: ฟอร์มแก้ไขใช้ `"Standard"` เป็นชื่อเทมเพลต หน้า preview ใช้
`ModernBlueTemplate` และสีก็มีสามค่าต่างกันในสามที่ ถ้า mapper coalesce เป็น `""`
ทุก `??` ปลายทางจะไม่ทำงานอีกเลย และฟอร์มแก้ไขจะได้ค่าว่างแทน `"Standard"` ซึ่ง
เป็น regression ที่ type pass สร้างขึ้นเอง

จึงขยาย `PortfolioConfig` ให้รับ null ตามความจริง แล้วให้ความจริงไหลไปหาคนอ่าน —
ซึ่งส่วนใหญ่มี `??` ของตัวเองรออยู่แล้ว การที่โค้ดกันไว้ทุกที่ทั้งที่ type บอกว่า
ไม่ต้องกัน คือรูปร่างของโค้ดที่รู้ว่า type โกหก

**กติกาที่ตามมา**: เมื่อ response ที่ null ได้ไหลเข้า view model ที่ไม่ยอมรับ null
ให้ขยาย view model ไม่ใช่ coalesce ที่ mapper — เว้นแต่จะพิสูจน์ได้ว่ามีคนอ่าน
คนเดียวและ default ของมันคือ default เดียวในระบบ

### 6. `cleanNullStr` เป็น generic และนั่นคือที่มาของ `any[]` แปดบรรทัด

`use-portfolio.ts` ประกาศผลของทั้งแปด section เป็น `any[]` เรียงกันแปดบรรทัด
เหตุผลไม่ใช่ว่าไม่รู้ชนิด แต่เพราะทุกตัวผ่าน `cleanNullStr` ซึ่งเป็น
`(val: any): any`

ฟังก์ชันนั้นเดินทับค่าโดยเปลี่ยน string เป็น string, array เป็น array ความยาวเดิม
และ object เป็น object ที่มีคีย์เดิม รูปร่างจึงไม่เปลี่ยนเลย `<T>(val: T): T` จึง
เป็นคำอธิบายที่ตรง และพอเปลี่ยนแล้ว `any[]` ทั้งแปดบรรทัดก็หายไปเอง

**กติกาที่ตามมา**: `any` ที่คร่อม response บางครั้งไม่ได้อยู่ที่จุดเรียก endpoint
แต่อยู่ที่ utility ที่ค่าไหลผ่านระหว่างทาง ให้ตามหาต้นตอก่อนจะไปเติมชนิดที่
ปลายทางทีละบรรทัด

`|| []` ที่ตามหลัง `cleanNullStr` ทั้งแปดบรรทัดยังอยู่ และเป็นคนละเรื่องกับ
`(skill.mappings ?? [])` ที่ ADR-0042 ตัดทิ้ง: ตัวนั้นกัน optional ที่ type
คิดขึ้นเอง ส่วนตัวนี้กัน envelope — `ResponseWrapper` บอกว่า `data` มีเสมอ ส่วน
`ApiResponse` ที่ API ตอบจริงบอกว่า optional ([#67](https://github.com/khthana/Deep-Portfolio/issues/67))
จนกว่าเรื่องนั้นจะจบ การ์ดนี้ยังมีงานทำ

## สิ่งที่พังอยู่และถูกแก้ในรอบนี้

การใส่ชนิดให้ถูกทำให้เจอสองอย่างที่โค้ดอ่านค่าผิดมาตลอด ทั้งคู่ผู้ใช้เห็น และ
บันทึกไว้ใน `BEHAVIOR-CHANGES.md` แล้ว

1. **ไฟล์แนบของชิ้นงานในลิงก์แชร์อ่านคีย์ที่ไม่มี** `use-public-portfolio.ts` อ่าน
   `a.original_filename` เพื่อหานามสกุลไฟล์ แต่ `realWorks` เปลี่ยนชื่อทุกฟิลด์ตอน
   ประกอบและส่งคีย์ชื่อ `fileName` ค่าที่อ่านได้จึงเป็น `undefined` ตลอด และ `isImg`
   เป็นเท็จเสมอ ที่ `/p/:shareToken/work/:workId` ซึ่งแยกไฟล์แนบด้วย
   `fileType === "image"` รูปทุกรูปจึงตกไปอยู่ในรายการไฟล์ท้ายหน้า
2. **หน้ารายละเอียดโครงงานซ่อนหัวข้อที่ flag เป็น null**
   `student-project-detail-page.tsx` ส่ง `t.is_show_role` ต่อดิบ ๆ ทั้งที่คอลัมน์
   default เป็น true และทั้ง modal แก้ไขกับเทมเพลตสาธารณะต่างก็ `?? true` แถวที่
   เขียนไว้ก่อนคอลัมน์มี default จึงถูกซ่อนบนหน้านี้หน้าเดียว

**กติกาที่ตามมา และรอบนี้ทำผิดเองก่อน**: ข้อ 1 เกือบถูกเขียนลง ADR ฉบับนี้ว่า
"ผู้ใช้ไม่เห็น" เพราะไล่หาคนอ่าน `works[].attachments` แล้วเจอแต่ `awards-section.tsx`
ที่อ่าน `attachments` ของ `awardData` — การไล่หยุดอยู่แค่ในโฟลเดอร์
`e-portfolio-template/` และไม่ได้ตามไปที่ `pages/` ซึ่งมีหน้าที่รับ `works` จาก hook
ตัวนี้ทั้งก้อนแล้วเรนเดอร์ไฟล์แนบเอง รีวิวเป็นคนจับได้ กติกาจึงเป็นว่า "type error
ที่โผล่ขึ้นมา" ไม่เท่ากับ "ของเสียที่ผู้ใช้เห็น" **และ** การพิสูจน์ว่าไม่เห็นต้องไล่ให้
ครบทุก route ที่อ่านค่านั้น ไม่ใช่ครบทุกไฟล์ในโฟลเดอร์ที่นึกออก — ถ้าไล่ไม่ครบ
ให้ถือว่าเห็น

ทั้งสองอย่างอยู่นอกรอยต่อที่ T2 กำหนดไว้ — ฝั่ง web ทดสอบเฉพาะ pure function และ
ทั้งสองจุดอยู่ใน hook กับ page ที่ต้อง render ถึงจะเห็น สิ่งที่ปักได้คือฝั่ง API:
เคสใหม่ปักชื่อคีย์ที่ `realWorks` ส่งจริง (`fileName`, `fileType`, `url`) ซึ่งเป็น
สัญญาที่ฝั่ง web อ่านผิด ส่วนอีกครึ่งเป็นงานของ
[#62](https://github.com/khthana/Deep-Portfolio/issues/62)

## สิ่งที่รอบนี้ไม่ทำ

- **ไม่แตะ `services/student.service.ts`** ซึ่งมี `ResponseWrapper<any>` สองเส้นที่
  `use-portfolio.ts` เรียก (`/student/activities/details/:id` และ
  `/student-activity/attachments`) เส้นแบ่งของ ADR-0042 §1 คือ **จุดที่เรียก**
  ในไฟล์ service ของ feature นั้นเอง และไฟล์นั้นเป็นของ feature `student`
  `use-portfolio.ts` จึงยังมี cast สองก้อนกับคอมเมนต์บอกว่ารออะไรอยู่
- **ไม่ยุบการประกอบ `realWorks` ที่ทำซ้ำสองที่** API ประกอบให้ลิงก์สาธารณะ ส่วน
  `use-portfolio.ts` ประกอบเองอีกรอบสำหรับหน้าจอของเจ้าของแฟ้ม การรวมสองอันเป็น
  งาน refactor ไม่ใช่งานของ type pass
- **ไม่ยุบบล็อกหา `ext`/`isImg` ที่เขียนซ้ำสิบสี่ครั้ง** ทั้งสอง hook มีบล็อกเดียวกัน
  ฝั่งละเจ็ดครั้ง และรอบนี้แตะเกือบทุกอันตอนถอด `: any` ออก ที่ไม่ยุบเพราะหางของมัน
  ไม่เหมือนกัน — บางที่จบที่ `"file"` บางที่แยก `"pdf"` ออกมา บางที่คืน `ext` ดิบ
  การยุบจึงต้องตัดสินว่าอันไหนถูก ซึ่งเป็นการเปลี่ยนพฤติกรรม ไม่ใช่การย้าย type
- **ไม่แตะ `PortfolioConfig` เกินกว่าที่ความจริงบังคับ** view model 243 บรรทัดใน
  `e-portfolio-template/types.ts` ไม่ใช่ของ #68 ตามที่ ADR-0040 เขียนไว้ รอบนี้
  แก้เฉพาะฟิลด์ที่รับค่ามาจาก response โดยตรง
