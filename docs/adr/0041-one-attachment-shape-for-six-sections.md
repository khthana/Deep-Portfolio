# ADR-0041 — รูปที่หก section ใช้ร่วมกันมีชื่อเดียว และความ nullable ของมันมาจากจุดที่แบนสองรายการเข้าด้วยกัน

- **สถานะ**: ตัดสินแล้ว 22 สิงหาคม 2569
- **ที่มา**: [issue #68](https://github.com/khthana/Deep-Portfolio/issues/68)
  รอบหก section ที่เหลือของ e-Portfolio (training, certificate, award, thesis,
  activity, internship)
- **เกี่ยวข้อง**: [ADR-0031](0031-attachments-are-the-leaf.md) ซึ่งย้าย
  `AttachmentDetailResp` เป็นใบล่างของหก feature ใบนี้เจอใบล่างอีกใบที่ ADR-0031
  ยังไม่เห็น, [ADR-0040](0040-the-portfolio-is-ten-features.md) ข้อ 3 ซึ่งตัดสิน
  ว่ารูปโปรไฟล์ของ personal ไม่ใช่ `AttachmentDetailResp` ใบนี้ตอบคำถามเดียวกัน
  ให้อีกหก section และ [ADR-0036](0036-a-bare-scalar-gets-no-name.md) ข้อ 4 กับ
  [ADR-0038](0038-a-factory-must-be-able-to-say-null.md) ข้อ 2 เรื่อง null ที่
  ไปจบที่จุด map ใบนี้ไม่ได้ทบทวนข้อไหนของทั้งสี่ใบ

## บริบท

หก section ที่เหลือ (นอกจาก skill กับรอบรวม) เหมือนกันจนน่าตกใจ: อย่างละ 5 เส้น,
อย่างละ 1 รูป, สี่เส้นตอบแถวพร้อมไฟล์แนบ และ `DELETE` ตอบ `data: null` เหมือนกัน
ทั้งหก

และทั้งหกเขียน**รูปของไฟล์แนบ**ไว้เองซ้ำกันคนละที่ ฝั่ง API หกครั้ง (เขียนคาไว้
ในแต่ละ type เลย) ฝั่ง web อีกเจ็ดครั้ง — ห้าครั้งใน `src/types/` (สี่ชื่อ
`AttachmentResp` อีกชื่อ `PortfolioActivityAttachment`) กับอีกสองครั้งใน
`features/student/portfolio/types/` รวม **สิบสามสำเนา**ของห้าฟิลด์เดียวกัน

สิบสองในสิบสามสำเนาเขียนเหมือนกันทุกตัวอักษร คือยอม null ทั้งสี่ฟิลด์ เหลือหนึ่ง
สำเนาที่ต่าง คือของ thesis ฝั่ง web ซึ่งรู้ว่า `url` กับ `original_filename` ไม่ยอม
null แต่เขียน `file_size` เป็น string จึงมีอยู่**สองแบบ ไม่ใช่สามแบบ** — และแบบ
ที่มีสิบสองสำเนานั้นคือแบบที่ผิด

## สิ่งที่ประกาศเดิมปิดไว้

| จุด | ของเดิมบอก | ของจริง |
| --- | --- | --- |
| `attachments` | ฝั่ง API ห้าในหกไฟล์เขียน `attachments?` | ทุกเส้นที่ตอบแถวตอบคีย์นี้เสมอ ไม่มีก็เป็นรายการว่าง — internship เขียนถูกอยู่ไฟล์เดียว |
| `date`, `start_date`, `end_date` | ฝั่ง API เขียน `Date` | เป็น string ตอนถึงมือผู้เรียก |
| `url`, `original_filename` ของไฟล์แนบ | ฝั่ง API เขียน `\| null` ทั้งคู่ | เป็น null ไม่ได้เลย |
| `file_size` ของไฟล์แนบ | ฝั่ง web ของ thesis เขียน `string \| null` | เป็น `number \| null` |
| `name` กับสี่ `is_show_*` ของ thesis | ฝั่ง web เขียนไม่ยอม null | คอลัมน์ยอมทั้งห้าตัว |

## การตัดสินใจ

**1. รูปของไฟล์แนบที่หก section ใช้ร่วมกันมีชื่อเดียวคือ `PortfolioSectionAttachment`**

มันไม่ใช่ `AttachmentDetailResp` — ตัวนั้นแยกไฟล์กับลิงก์เป็นสองรายการ คนละรูป
ส่วนตัวนี้คือ**สองรายการนั้นแบนรวมกันเป็นรายการเดียว** พร้อมเปลี่ยนชื่อฟิลด์ระหว่าง
ทาง เหตุผลเดียวกับที่ ADR-0040 ข้อ 3 ไม่ยอมยัดรูปโปรไฟล์ให้เป็น
`AttachmentDetailResp`: บังคับให้เหมือนกันจะทำให้ type โกหกว่ามีสองรายการรออยู่

ทางเลือกที่ไม่เอาคือให้แต่ละ section มีรูปของตัวเอง ซึ่งเป็นสิ่งที่ทั้งสองฝั่งทำอยู่
แล้วสิบสามครั้ง และเป็นเหตุผลที่ห้าฟิลด์นี้ประกาศไม่ตรงกันสองแบบ

และชื่อนี้ต้องมีคนใช้จริง ไม่ใช่ประกาศไว้เฉย ๆ: service ทั้งหกเคยตั้ง alias ของ
ตัวเองว่า `NonNullable<Portfolio<X>Detail["attachments"]>[number]` ซึ่งเป็นทาง
เลือกที่ข้อนี้ปฏิเสธไปพอดี รอบนี้จึงลบทั้งหก alias แล้วให้ทั้งหก import ชื่อกลาง
มาตรง ๆ (`NonNullable` ก็ตายไปพร้อมกัน เพราะข้อ 3 ทำให้คีย์นั้นไม่ optional แล้ว)

**2. ความ nullable ของมันอ่านจากจุดที่แบน ไม่ใช่จากคอลัมน์**

```
ไฟล์  → { url: file_path, file_path, original_filename, file_size }
ลิงก์  → { url, file_path: null, original_filename: title, file_size: null }
```

`url` กับ `original_filename` จึงเป็น null ไม่ได้ เพราะทั้งสองสาขามีของใส่เสมอ
ส่วน `file_path` กับ `file_size` เป็น null เฉพาะฝั่งลิงก์

ที่มาของ "ไม่เป็น null" ของสองตัวนั้นไม่เหมือนกัน และควรเขียนแยกให้ชัด
ฝั่งลิงก์มาจาก `URLDetail.url` กับ `URLDetail.title` ซึ่งคอลัมน์ไม่ยอม null จริง
ส่วนฝั่งไฟล์มาจาก `FileDetail.file_path` กับ `FileDetail.original_filename` —
ตัวแรกคอลัมน์ nullable แต่ผ่าน `signFileUrl()` ซึ่งคืน string เสมอ ส่วน**ตัวหลัง
คอลัมน์ nullable และ `attachments.service.ts` ใช้ `!` ยืนยันทิ้งไว้** พร้อมกับ
`file_path`, `file_size` และ `file_type` รูปในใบนี้จึง**รับข้อสมมติเดิมมา** ไม่ได้
ตั้งข้อสมมติใหม่ ถ้าวันหนึ่ง `!` สี่ตัวนั้นถูกทบทวน `FileDetail` กับใบนี้ต้อง
เปลี่ยนพร้อมกัน

น่าสนใจตรงที่**สองสำเนาที่ต่างกัน ต่างคนต่างถูกคนละครึ่ง**: สิบสองสำเนาแรกเขียน
ทั้งสี่เป็น nullable ซึ่งกว้างเกินไปสองตัว ส่วนสำเนาของ thesis ฝั่ง web รู้ว่า
`url` กับ `original_filename` ไม่เป็น null แต่เขียน `file_size` เป็น string ซึ่ง
ผิดชนิด การเปิดอ่านทั้งสองที่แล้วเทียบกับ**จุดที่สร้างค่า** จึงเป็นวิธีเดียวที่ได้
คำตอบถูก ไม่ใช่หยิบข้างใดข้างหนึ่งมาเชื่อ

**3. `attachments` ไม่ optional — ห้าในหกไฟล์ฝั่ง API เขียนผิดตรงกัน**

ทุกเส้นที่ตอบแถวตอบคีย์นี้: เส้นอ่านสร้างมัน ส่วน create กับ update อ่านซ้ำผ่าน
`getById` ที่สร้างมันอยู่แล้ว ไม่มีก็ได้รายการว่าง ไม่ใช่คีย์ที่หายไป — ต่างจาก
`attachments` ของ personal ในรอบที่แล้วที่หายไปจริงบนเส้นเขียน (ADR-0040 ข้อ 4
เป็นคนบันทึกเรื่องนั้น ส่วน ADR-0033 เป็นคนวางเส้นแบ่งระหว่าง "ไม่มีคีย์" กับ
"คีย์เป็น null" ไว้ตั้งแต่ต้น)

`?` ที่เขียนกันมาห้าไฟล์จึงไม่ได้แปลว่า "บางทีก็ไม่มี" แต่แปลว่าไม่มีใครไล่ดู
internship เป็นไฟล์เดียวที่เขียนถูก และเขียนถูกโดยไม่มีอะไรบอกว่าทำไมมันต่าง

**4. เจอสำเนาที่สามของ activity ซึ่งซ่อนอยู่หลัง alias**

`src/types/portfolio-activity-type.type.ts` ถือ `PortfolioActivityResp` และ
service ฝั่ง web อ่านจากที่นั่น แต่ **component สามตัวไม่ได้อ่านจากที่นั่น** มันเขียน

```ts
import type { PortfolioActivityType as PortfolioActivityResp } from "../../types/activity-type.type";
```

คือ import อีกไฟล์หนึ่งที่ถือรูปเดียวกันคนละสำเนา **แล้วตั้งชื่อเล่นให้เป็นชื่อของ
สำเนาแรก** อ่านผ่าน ๆ จะนึกว่าทั้งไฟล์ใช้ตัวเดียวกัน

สองสำเนานั้นไม่ตรงกันด้วย: ตัวที่ซ่อนอยู่เขียน `date` เป็น string ซึ่งถูก ส่วน
`url` กับ `original_filename` ของไฟล์แนบเป็น nullable ซึ่งผิด รอบนี้ย้ายทั้งคู่และ
ให้ทั้งสามตัวชี้ไป package ตรง ๆ

**กติกาที่ตามมา**: การนับสำเนาด้วย `grep` ชื่อ type ไม่พอ เพราะ alias ทำให้ชื่อ
เดียวกันชี้ไปคนละไฟล์ได้ รอบที่เหลือของ #68 ต้องดู `from "…"` ด้วย ไม่ใช่ดูแค่ชื่อ

**5. สี่ `is_show_*` ของ thesis ที่เป็น null ไปจบที่ `?? true` ที่จุด map**

`true` เป็นค่า default ของคอลัมน์เอง จึงยืมมาใช้ได้ตาม ADR-0036 ข้อ 4 และ null
ก็ไปถึงไม่ได้จริงตามแบบ ADR-0038 ข้อ 2 ด้วย: `optionalBool` ให้ผลได้แค่ boolean
หรือ undefined และ undefined แปลว่าไม่แตะคอลัมน์ ไม่มีสายไหนเขียน null ลงไปได้

ที่ต้อง coalesce ไม่ใช่แค่ให้สวิตช์วาดถูก แต่เพราะค่านั้น**เดินทางกลับออกไปกับฟอร์ม**
และ `optionalBool` ปฏิเสธ null เหมือนที่ ADR-0039 ข้อ 4 เจอกับ `optionalText` —
กติกาข้อนั้นใช้ได้กับทุกคู่ helper ไม่ใช่เฉพาะ text

**6. `formatDate` ของบัตรใบประกาศประกาศพารามิเตอร์เป็น `Date` มาตลอด**

`new Date(date)` ข้างในรับได้ทั้งสองอย่าง หน้าจอจึงไม่เคยรู้ว่ารับ string มา
ตลอด รอบนี้แก้ให้ตรง ไม่มีอะไรขยับตอน runtime

## ผลที่ตามมา

- เหลือสำเนาฝั่ง web **33 ไฟล์ 1,650 บรรทัด** (จาก 33 ไฟล์ 1,746 หลังรอบแรกของ
  e-Portfolio) นับด้วย glob ชุดเดียวกับที่ ADR-0028 ประกาศไว้ — รอบนี้ลด 96
  บรรทัด มากกว่ารอบที่แล้วห้าเท่า เพราะย้ายรูปเจ็ดรูปพร้อมกันและลบสำเนาของไฟล์แนบ
  ไปเจ็ดชุด
- ในนั้น **14 ไฟล์ 600 บรรทัดยังเป็นของ e-Portfolio** ซึ่ง 212 เป็น view model ของ
  เทมเพลตที่ไม่ใช่งานของ #68 (ADR-0040 ข้อ 7) เหลือของจริง 388 บรรทัด คือ
  skill กับรอบรวม
- package ได้ไฟล์ใหม่เจ็ดไฟล์ — หก section กับ `portfolio-attachment.ts` — และทั้ง
  หก service ฝั่ง API import ชื่อกลางนั้นมาใช้จริง ไม่ได้ปล่อยให้ประกาศไว้เฉย ๆ
- **เพิ่มหนึ่งเคส** (1,077 เคส API / 448 เคส web) ตอนแรกรอบนี้ไม่เพิ่มเลย เพราะ
  เคสของทั้งหก section ไล่ชื่อทุกคีย์อยู่ก่อนแล้ว รวมถึง `attachments: []` และ
  วันที่ที่เขียนเป็น ISO string แต่รีวิวจับได้ว่า **certificate ปักไว้แค่สาขาไฟล์
  ไม่มีเคสลิงก์เลย** ทั้งที่อีกห้า section มีครบทั้งสองสาขา ข้อความในใบนี้ที่ว่า
  "type ลอกมาจากเคสที่มีอยู่" จึงเป็นจริงห้าในหก section เท่านั้น รอบนี้เติมเคส
  ลิงก์ของ certificate ให้ครบ
- `npm run lint` ยังเท่าเดิมที่ 216 warning
- ไม่มีอะไรที่ผู้เรียกเห็นเปลี่ยน `BEHAVIOR-CHANGES.md` จึงไม่มีหัวข้อใหม่
