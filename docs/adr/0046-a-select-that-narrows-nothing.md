# ADR-0046 — `select` ที่ไม่ได้ตัดอะไรเลย ก็ยังต้องใส่

- **สถานะ**: ตัดสินใจแล้ว
- **วันที่**: 2026-08-22
- **บริบท**: [#68](https://github.com/khthana/Deep-Portfolio/issues/68) รอบที่สิบแปด
  — `/rubric` ซึ่งเป็นสอง endpoint อ่านอย่างเดียวของ shared rubric
- **ต่อจาก**: [ADR-0044](0044-a-response-is-what-was-selected.md) ข้อ 1 ที่วางกติกา
  เรื่อง query ที่ไม่มี `select`, [ADR-0029](0029-api-types-per-feature.md) ข้อ 1
  เรื่องชื่อใน package ที่ต้องไม่ชนกัน และ
  [ADR-0045](0045-one-service-many-screens.md) ข้อ 5 ที่ขยายกติกาของ ADR-0044 ไป
  อีกทิศหนึ่ง ใบนี้ปิดทิศที่สาม

## บริบท

`/rubric` เล็กที่สุดในบรรดารอบที่เหลือ: สอง endpoint อ่านอย่างเดียว ไม่มีเส้นไหน
เขียน `rubrics` หรือ `rubric_details` เลยทั้งระบบ (ADR-0014) ฝั่ง web เขียนไว้สอง
type รวม 24 บรรทัด

แล้วปรากฏว่า**ทั้งสองสำเนาเขียนถูกทุกฟิลด์** ซึ่งรอบก่อน ๆ ของ #68 แทบไม่เคย
เจอ — 8 คอลัมน์ของ `rubrics` และ 12 คอลัมน์ของ `rubric_details` ตรงกับสิ่งที่
สายส่งจริงทุกตัว ชนิดตรง ความ nullable ตรง `weight` ที่เป็น `Decimal(5,2)` ก็
ประกาศเป็น `number | null` ถูกแล้ว เพราะ service แปลงให้ก่อนตอบ

รอบนี้จึงไม่มีอะไรจะแก้ในความหมายที่รอบก่อน ๆ มี และคำถามกลายเป็นว่า
"แล้วรอบแบบนี้ยังต้องทำอะไรอีกไหม นอกจากย้ายไฟล์"

## การตัดสินใจ

### 1. ยังต้องใส่ `select` ถึงจะไม่ตัดอะไรออกเลย

ทั้งสอง query เป็น `findMany` ที่ไม่มี `select` ซึ่ง ADR-0044 ข้อ 1 เรียกว่า
"การไม่ได้ตัดสินใจ" — แต่ต่างจากกรณีของ ADR-0044 ตรงที่**ไม่มีคอลัมน์ไหนเกิน**
ตารางมีเท่าที่ type บอกพอดี ตัด `select` เข้าไปแล้ว body ไม่ขยับสักไบต์

ทำอยู่ดี เพราะประโยคที่ ADR-0044 เขียนไว้ไม่ได้พูดถึงการตัด มันพูดว่า "รูปที่เขียน
คือคำสัญญา และ query ที่ไม่จำกัดตัวเองจะผิดคำสัญญาทุกครั้งที่มีคนเพิ่มคอลัมน์"
วันนี้ตารางกับ type ตรงกัน พรุ่งนี้ที่มีคนเพิ่มคอลัมน์ลง `rubrics` คอลัมน์นั้นจะ
ออกสายไปโดยไม่มีใครแตะไฟล์ type เลยสักบรรทัด

**กติกาที่ตามมา**: `select` เป็นหนี้ของรอบเสมอเมื่อรอบนั้นเขียนรูปลง package
ไม่ว่ารูปจะแคบกว่าตารางหรือเท่ากับตาราง กรณีที่เท่ากันคือกรณีที่กติกามีค่าที่สุด
เพราะมันไม่มี `BEHAVIOR-CHANGES.md` ให้เขียน ไม่มีอะไรให้เห็น และไม่มีอะไรเตือนว่า
รอบนี้ข้ามมันไป

ปักด้วยเคสที่เทียบ `Object.keys(...).sort()` กับแปดคีย์และสิบสองคีย์ เคสแบบนี้
ไม่ได้พิสูจน์ว่าอะไรเปลี่ยน มันพิสูจน์ว่าอะไรจะไม่เปลี่ยนโดยไม่มีใครรู้

### 2. `Resp` ไม่ได้บอกอะไร และ `Detail` ที่แปลว่า "แถวลูก" ทำให้เข้าใจผิด

สองสำเนาชื่อ `SharedRubricResp` กับ `SharedRubricDetailResp` เข้า package เป็น
`SharedRubric` กับ `SharedRubricCriterion`

- `SharedRubricDetailResp` อ่านว่า "รายละเอียดของ shared rubric" แต่หนึ่งแถวคือ
  **หนึ่งเกณฑ์** ที่มีคำอธิบายสี่ระดับอยู่ในแถวเดียวกัน ชื่อ `Criterion` บอกว่า
  ตอบมาเป็น list ของอะไร ซึ่งเป็นสิ่งที่คนอ่าน `SharedRubricCriterion[]` ต้องรู้
  นี่คือเหตุผลหลัก และเป็นเหตุผลเดียวที่ต้องใช้
- `Resp` ทิ้งไปตามกัน เพราะมันไม่ได้บอกอะไรเพิ่มในสองชื่อนี้ — **ไม่ใช่**เพราะ
  package มีกติกาห้ามคำนี้ ตรวจแล้วไม่มีกติกาแบบนั้นอยู่จริง: `index.ts` export
  ชื่อที่ลงท้าย `Resp` อยู่ 23 ตัว ทั้งกับก้อนที่ endpoint ตอบทั้งก้อน
  (`ActivityDetailResp`) กับแถวเดี่ยว (`PLOResp` ซึ่ง doc ของมันเขียนเองว่าเป็น
  "แถวของ `learning_outcomes` ทั้งแถว") และกับรูปที่ถูกฝังในก้อนอื่น
  (`AttachmentDetailResp`) การทิ้ง `Resp` รอบนี้จึงไม่ได้ตั้งกติกาให้ใคร มันเป็น
  การตัดสินของสองชื่อนี้เท่านั้น

ADR-0029 ข้อ 1 อนุญาตให้เปลี่ยนชื่อตอนย้ายไว้แล้ว และเหตุผลเดิมยังใช้ได้: ราคาถูก
ที่สุดคือตอนนี้ และมันแพงขึ้นทุกรอบที่ปล่อยไว้ รอบนี้แตะสามไฟล์ฝั่ง web —
ไฟล์ที่ประกาศ, service ที่ยิง และ thunk ที่รับ

### 3. ชื่อที่ชนกันเองใน feature เดียว ก็แก้ตอนย้ายเหมือนกัน

`rubric-type.type.ts` ประกาศ `RubricLevel` ไว้ ส่วน package ก็มี `RubricLevel`
ที่ย้ายไปตั้งแต่รอบ activity (ADR-0032) — คนละอย่างกันคนละเรื่อง ตัวใน package คือ
แถว `rubric_levels` ที่กลับมาจากสาย ตัวฝั่ง web คือระดับหนึ่งบน**ฟอร์ม** ที่ยัง
ไม่มี `id` จนกว่าจะเซฟ

วันนี้ยังไม่มีไฟล์ไหน import ทั้งคู่ การชนจึงยังไม่เกิด แต่ทั้งสองอยู่ใน feature
เดียวกันและถูกอ่านคู่กันในหน้าจอเดียวกัน เปลี่ยนเป็น `RubricLevelForm` ตามพี่น้อง
ของมันเอง (`RubricDetailForm` อยู่ในไฟล์นั้นอยู่แล้ว) แตะสองไฟล์

ADR-0029 ข้อ 1 พูดถึงชื่อที่จะชนกัน**ใน package** ใบนี้บันทึกด้านที่สาม: ชื่อที่
รอบของ #68 ทำให้ชนกันข้ามฝั่ง เพราะครึ่งหนึ่งย้ายเข้า package ไปแล้ว

### 4. เมธอดที่ไม่มีใครเรียก ให้ลบ ไม่ใช่หา type ให้

`rubric.service.ts` มี `getRubric(activity_id)` ตัวที่สาม ที่อ่าน
`rubric_activity_mapping` พร้อม `rubric_levels` — ไม่มี controller เรียก ไม่มี
service เรียก ไม่มี test เรียก ทั้ง repo มีคำนี้อยู่ที่เดียวคือบรรทัดที่ประกาศมัน

หน้าที่ของรอบ #68 คือตั้งชื่อรูปที่ endpoint ตอบ เมธอดที่ไม่มีใครเรียกไม่ได้ตอบ
อะไรใคร มันจึงไม่มีรูปให้ตั้งชื่อ และการใส่ `Promise<RubricDetail[]>` ให้มันจะ
เป็นการเขียนคำสัญญาให้โค้ดที่ไม่มีใครฟัง ลบทิ้ง — `activity.service.ts` เป็นคน
อ่าน rubric ของกิจกรรมจริง ๆ และรูปนั้นย้ายไปตั้งแต่ ADR-0032 แล้ว

## สิ่งที่ไม่ได้ทำ

- **ไม่มีรายการใน `BEHAVIOR-CHANGES.md`** ไม่มีอะไรที่ caller เห็นเปลี่ยนเลย
  ในรอบนี้ ซึ่งเป็นเรื่องปกติของ #68 — สิบแปดรอบที่ผ่านมามีแค่ห้ารอบที่มีหัวข้อ
  ในไฟล์นั้น เขียนไว้ตรงนี้เพราะการ "ไม่มีรายการ" แยกไม่ออกจากการ "ลืมเขียน"
  ถ้าไม่มีใครพูด
- **ไม่ได้แตะ `created_by` / `updated_by`** ที่ทั้งสองเส้นส่งออกไปโดยไม่มีใครอ่าน
  มันเป็นคอลัมน์ของตาราง reference ที่ไม่มี endpoint ไหนเขียน และคำถามว่าควรส่ง
  หรือไม่เป็นคำถามเดียวกับที่ doc comment ของ `RubricDetail` ใน
  `packages/api-types/src/rubric.ts` เปิดค้างไว้ตั้งแต่รอบ activity ไม่ใช่คำถาม
  ของรอบย้าย type
