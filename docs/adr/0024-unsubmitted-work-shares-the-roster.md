# ADR-0024 — งานที่ยังไม่ถูกส่ง อยู่ในตารางเดียวกับงานที่ส่งแล้ว

- **สถานะ**: ตัดสินแล้ว 13 สิงหาคม 2569
- **ที่มา**: [issue #56](https://github.com/khthana/Deep-Portfolio/issues/56)
- **เกี่ยวข้อง**: [ADR-0023](0023-unaccepted-members-have-their-own-field.md)
  เพิ่มช่อง `unaccepted_members` ให้อาจารย์เห็นว่าใครยังไม่ตอบรับคำเชิญ ไฟล์นี้คือ
  เหตุผลที่ช่องนั้นเพิ่งจะมองเห็นได้จริง — กลุ่มที่มีคนค้างมากที่สุดคือกลุ่มที่ยัง
  ไม่ได้ส่งงาน และกลุ่มแบบนั้นไม่เคยหลุดออกจาก query มาถึงหน้าจอเลย · ADR-0023
  ตัดสินว่า**อะไร**อยู่ในคำตอบ ไฟล์นี้ตัดสินว่า**ใคร**อยู่ในคำตอบ เป็นคนละคำถามกัน
  และ ADR-0023 เลือกให้ไม่ได้

## บริบท

`GET /activity/submitted/list` กับ `GET /learning-activity/submitted/list` เป็น
เส้นทางเดียวที่อาจารย์เห็นว่าใครทำงานชิ้นหนึ่งไปถึงไหนแล้ว ทั้งสองเส้นเดินผ่าน
เมท็อดส่วนตัวสองตัวต่อฝั่ง — `getIndividualSubmissions` กับ `getGroupSubmissions`
— และทั้งสี่ตัวกรอง `status: { not: "NOT_SUBMITTED" }` ไว้ตั้งแต่ระดับ query

แถว `student_activity` / `student_learning_activity` ถูกเปิดไว้ให้นักศึกษาทุกคนที่
ลงทะเบียนตั้งแต่ตอนสร้างกิจกรรม (`assign-tasks.job.ts`) โดยตั้งต้นเป็น
`NOT_SUBMITTED` ข้อมูลว่าใครยังไม่ส่งจึงมีอยู่ครบมาตลอด แต่ถูกกรองทิ้งก่อนตอบทุกครั้ง
ผลคือตารางตรวจงานของอาจารย์ตอบได้แค่ "ใครส่งแล้วบ้าง" ไม่เคยตอบ "ใครยังไม่ส่ง"

**ตัวปัญหาที่เขียนไว้ใน #56 เองผิด** มันบอกว่าเรื่องนี้เป็นของงานกลุ่ม แต่ตัวกรอง
อยู่ครบทั้งสี่จุดรวมงานเดี่ยวด้วย นักศึกษาที่ไม่เคยส่งงานเดี่ยวก็หายไปจากสายตา
อาจารย์เท่ากันทุกประการ — แก้ตัว issue แล้ว ไม่ได้ทำตามที่มันเขียนไว้

บนงานกลุ่มยังมีคนอีกกลุ่มหนึ่งที่ลึกกว่านั้น คือคนที่**ไม่ได้อยู่ในกลุ่มไหนเลย**
แถวของเขาถูกเปิดไว้พร้อมคนอื่น แต่ไม่มีแถว `student_activity_group_member` ชี้มาหา
query ที่เดินจากตารางกลุ่มจึงไปไม่ถึงเขาไม่ว่าจะกรองอย่างไร

## สิ่งที่ต้องตัดสิน

1. แถวของงานที่ยังไม่ส่ง อยู่ที่ไหนบนหน้าจอของอาจารย์
2. ครอบคลุมงานกลุ่มอย่างเดียว หรือทั้งงานกลุ่มและงานเดี่ยว
3. นักศึกษาที่ไม่มีกลุ่มบนงานกลุ่ม ปรากฏอย่างไร
4. ลำดับของแถวเป็นอย่างไร

## การตัดสิน

> **ตารางตรวจงานคือรายชื่อของทุกคนที่งานชิ้นนี้ถูกสั่งให้ ไม่ใช่รายชื่อของคนที่ส่ง**
> แถวที่ยังไม่ส่งอยู่ในตารางเดิม แยกด้วยสถานะที่สาม ไม่ใช่ด้วยตารางที่สอง

### 1. ตารางเดิม บวกสถานะที่สาม

`SubmissionStatus` ฝั่งหน้าจอเดิมมีสองค่า — `GRADED` (ตรวจแล้ว) กับ `PENDING`
(ยังไม่ตรวจ) — และทั้งสองหน้าคำนวณมันด้วยนิพจน์เดียวกันเขียนซ้ำ:
`status === "GRADED" ? "GRADED" : "PENDING"` นิพจน์นั้นถูกต้องตราบใดที่ทุกแถวที่มา
ถึงหน้าจอมีของอยู่ข้างใน เพราะ "ไม่ใช่ตรวจแล้ว" ก็แปลว่า "รออาจารย์" ได้จริง

พอแถวที่ไม่มีของเข้ามาอยู่ในตารางเดียวกัน นิพจน์นั้นจะโกหก มันจะบอกอาจารย์ว่ามีงาน
รอตรวจอยู่ ทั้งที่ไม่มีอะไรให้ตรวจ ค่าที่สาม `NOT_SUBMITTED` ("ยังไม่ส่ง") จึงเกิด
พร้อมกับแถว และตรรกะย้ายไปอยู่ที่ `apps/web/src/utils/format-submission-status.ts`
ตัวเดียวที่ทั้งสองหน้าใช้ร่วมกัน ด้วยเหตุผลเดียวกับ `format-marked-students.ts` ของ
#54 คือแถวเดียวกันต้องอ่านได้เหมือนกันทั้งสองหน้า

ทางที่ไม่เลือกคือแยกเป็นตารางที่สอง ("ยังไม่ส่ง") ต่างหาก — มันตอบคำถาม "ใครยังไม่
ส่ง" ได้ดีกว่า แต่ทำให้คำถามที่อาจารย์ถามบ่อยกว่า ("ห้องนี้ไปถึงไหนแล้ว") ต้องอ่าน
สองที่แล้วบวกเอง และทำให้ช่องค้นหา การเรียง และคอลัมน์ทุกคอลัมน์ต้องมีสองชุด

สีของชิปเป็น**เทา** ไม่ใช่เหลืองอย่าง `PENDING` เพราะงานที่ไม่มีอยู่ไม่ใช่งานที่ค้าง
อยู่ที่อาจารย์ สีจึงไม่ควรเรียกร้องความสนใจแบบเดียวกัน

### 2. ทั้งงานกลุ่มและงานเดี่ยว

ตัวกรองอยู่ทั้งสี่จุด แก้เฉพาะฝั่งกลุ่มตามที่ #56 เขียนไว้จะได้ระบบที่ตอบคำถาม
เดียวกันคนละแบบบนหน้าจอหน้าตาเดียวกัน ซึ่งเป็นความไม่สม่ำเสมอชนิดที่ #45 กับ #53
ต้องตามเก็บมาแล้วสองรอบ

### 3. คนที่ไม่มีกลุ่ม เป็นแถวของตัวเอง

บนงานกลุ่ม คนที่ยังไม่ได้อยู่กลุ่มไหนคือปัญหาที่เร่งด่วนที่สุดของอาจารย์ — ไม่มีใคร
ชวนเขา และเขาไม่ได้ชวนใคร กลุ่มที่รอคำตอบอยู่อย่างน้อยก็มีคนกำลังรออยู่ แต่คนที่ไม่มี
กลุ่มไม่มีอะไรจะรอเลย

เขาปรากฏเป็นแถวเดี่ยว (`submission_type: "INDIVIDUAL"` ไม่มีช่อง `group`) ซึ่งทำให้
สองคอลัมน์ที่บอกว่าแถวนี้กำลังให้คะแนนใคร อ่านได้เหมือนงานเดี่ยวโดยไม่ต้องแก้อะไร
เพิ่ม — `format-marked-students.ts` รองรับทั้งสองรูปอยู่แล้วตั้งแต่ #54

ทางที่ไม่เลือกคือยัดเขาไว้ใน `unaccepted_members` ของกลุ่มใดกลุ่มหนึ่ง ซึ่งไม่มี
กลุ่มไหนเป็นเจ้าของเขาจริง ๆ และจะทำให้ช่องนั้นแปลว่าสองอย่างพร้อมกัน

### 4. แถวที่ยังไม่ส่ง เรียงท้ายสุด

`byUnsubmittedLast` (`apps/api/src/utils/submission-order.ts`) เอาแถวที่ส่งแล้ว
ขึ้นก่อน เรียงตาม `submitted_at` จากใหม่ไปเก่าเหมือนเดิม แล้วต่อด้วยแถวที่ยังไม่ส่ง

การเรียงตัดสินจาก **`status` ของแถว** ไม่ใช่จากการที่ `submitted_at` เป็น `null`
เพราะ `status` คือสิ่งที่ตารางแสดง การเรียงจึงตรงกับที่ตาเห็นเสมอ แถวที่เท่ากันอยู่
ที่เดิมที่ query วางไว้ และทุก query ที่ป้อนเข้ามาเรียงด้วย `id`

งานของอาจารย์คือการตรวจ สิ่งที่ตรวจได้จึงควรอยู่บนสุด รายชื่อคนที่ยังไม่ส่งเป็น
ข้อมูลประกอบ ไม่ใช่คิวงาน

## ผลที่ตามมา

- **คำตอบของทั้งสองเส้นยาวขึ้นมาก** จากเดิมที่ยาวเท่าจำนวนคนที่ส่งแล้ว กลายเป็นยาว
  เท่าจำนวนคนในชั้นเรียน ตั้งแต่วันแรกที่ประกาศงาน ทั้งสองเส้นเป็นของอาจารย์และตอบ
  ทีละกิจกรรม จำนวนแถวจึงมีเพดานเท่าขนาดห้อง ไม่มีการแบ่งหน้า และไม่ได้เพิ่มเข้ามา
  ใน ticket นี้
- **`unaccepted_members` ของ ADR-0023 มองเห็นได้จริงแล้ว** กลุ่มที่ยัง
  `NOT_SUBMITTED` คือกลุ่มที่มีคำเชิญค้างมากที่สุด และเป็นกลุ่มที่ถูกกรองทิ้ง
- **แถวที่ไม่มีอะไรอยู่ข้างใน กดเข้าหน้าตรวจงานได้** ปุ่ม "ดูงาน" ของตารางไม่ได้ดู
  `status` และหน้าตรวจงานอ่าน `activity_type` จาก**ตัวกิจกรรม** ไม่ใช่จากแถว งานกลุ่ม
  จึงส่ง `GROUP` มาเสมอ แถวของคนที่ไม่มีกลุ่มเคยได้ `500` จาก
  `throw new Error("Group not found")` ที่ #42 pin ไว้ ตอนนี้เป็น `400` พร้อมประโยค
  ไทย ส่วนคำถามว่าคนที่ไม่มีกลุ่ม**ควร**ให้คะแนนได้หรือไม่ เป็นการตัดสินใจเชิง
  หลักสูตร ไม่ใช่เชิงโค้ด — แยกไปเป็น
  [#64](https://github.com/khthana/Deep-Portfolio/issues/64)
- **factory ของ test พูดความจริงขึ้นหนึ่งข้อ** `createSubmission` เคยเขียน
  `submitted_at: new Date()` ให้แถวที่ `status: "NOT_SUBMITTED"` ด้วย ซึ่งเป็นแถวที่
  ระบบจริงสร้างไม่ได้ — ทางส่งงานเขียนสองคอลัมน์นี้พร้อมกันใน transaction เดียวเสมอ
  ตอนนี้ `NOT_SUBMITTED` ได้ `submitted_at: null` การเรียงในข้อ 4 ไม่ได้พึ่งข้อนี้
  (มันดู `status`) แต่ test ที่อ่านค่าที่โกหกอยู่ก็พิสูจน์อะไรไม่ได้เหมือนกัน
- **สถิติบนหน้ารายการกิจกรรมไม่ถูกแตะ** `submitted_count` / `pending_grading_count`
  / `student_count` มาจากเส้นทางคนละตัวและนับด้วยกติกาของตัวเอง ไฟล์นี้ไม่ได้
  เปลี่ยนความหมายของเลขทั้งสาม

## จะกลับมาทบทวนเมื่อไหร่

- **เมื่อ #64 ได้คำตอบ** ถ้าคนที่ไม่มีกลุ่มควรให้คะแนนได้ หน้าตรวจงานต้องเลือกทาง
  ตาม `submission_type` ของแถว ไม่ใช่ตามประเภทของกิจกรรม และข้อ 3 ของไฟล์นี้จะกลาย
  เป็นเหตุผลว่าทำไมแถวนั้นถึงพก `submission_type` ของตัวเองมาตั้งแต่แรก
- **เมื่อห้องเรียนใหญ่จนต้องแบ่งหน้า** การเรียงในข้อ 4 เกิดขึ้นในหน่วยความจำหลัง
  query ถ้าวันหนึ่งต้องแบ่งหน้าจริง กติกาการเรียงต้องย้ายลงไปอยู่ใน query ก่อน
  ไม่งั้นแต่ละหน้าจะเรียงถูกเฉพาะภายในหน้าตัวเอง
