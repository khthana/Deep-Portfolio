# ADR-0004 — ใครแก้รายชื่อกลุ่มได้ และกลุ่มถูกยุบอย่างไร

- **สถานะ**: ตัดสินแล้ว 10 สิงหาคม 2569
- **ที่มา**: [issue #27](https://github.com/khthana/Deep-Portfolio/issues/27)
- **เกี่ยวข้อง**: [ADR-0003](0003-enrolment-access.md) (การอ่านกลุ่ม ซึ่งค้างเรื่อง
  การเขียนไว้ให้ไฟล์นี้), [ADR-0002](0002-section-access.md) (แถวที่ไม่มีอยู่จริง
  ตอบ `403`), [ADR-0001](0001-portfolio-access.md) (ผู้กระทำคือเจ้าของ session)

## บริบท

`PATCH /student-activity-group` และ `PATCH /student-learning-activity-group` รับ
`{ group_id, members }` แล้ว **ลบสมาชิกทั้งกลุ่มทิ้งก่อน** จากนั้นเขียนรายชื่อใน
คำขอกลับลงไป โดยเก็บ `invite_token` กับสถานะการตอบรับของคนที่อยู่เดิมไว้ให้ รูปแบบ
นี้แปลว่า `members` ไม่ใช่ส่วนต่าง แต่คือ "กลุ่มนี้จะหน้าตาแบบนี้"

ก่อน #27 ไม่มีการตรวจอะไรเลยนอกจาก `requireRole("STUDENT")` ผลที่ตามมามีสามอย่าง

1. **สมาชิกคนไหนก็แก้ได้** คนที่ถูกชวนเข้ามาและยังไม่ตอบรับด้วยซ้ำ เขียนรายชื่อ
   ใหม่ทับได้ จะเตะหัวหน้าออกหรือตั้งตัวเองเป็นหัวหน้าก็ได้
2. **ส่ง `members: []` ได้** สมาชิกถูกลบหมดแล้วไม่มีอะไรเขียนกลับ เหลือแถวกลุ่ม
   ลอยอยู่ที่ไม่มี endpoint ไหนเข้าถึงได้อีก เพราะทุกตัวหาจากสมาชิก นี่คือทาง
   "ยุบกลุ่ม" ที่มีอยู่จริงโดยไม่ได้ตั้งใจ
3. **`group_id` ที่ไม่มีอยู่จริงได้ `500`** เพราะ `update` ของ Prisma โยน

ข้อ 1 กับ 2 ไม่ต้องใช้แม้แต่การเดา — `group_id` เป็นจำนวนเต็มเรียงกัน

## สิ่งที่ต้องตัดสิน

1. ใครมีสิทธิ์แก้รายชื่อ — เฉพาะ `LEADER` หรือสมาชิกที่ `ACCEPT` แล้วทุกคน
2. การยุบกลุ่มควรเป็น endpoint ของตัวเองหรือไม่

## การตัดสิน

### 1. เฉพาะ `LEADER`

> การเขียนรายชื่อกลุ่มเป็นสิทธิ์ของ `LEADER` ของกลุ่มนั้นเท่านั้น "เป็นหัวหน้า" คือ
> มีแถวใน `student_activity_group_member` (หรือคู่แฝดฝั่ง learning activity) ที่
> `group_id` ตรงกับที่คำขอระบุ `role = LEADER` และ `student_id` ตรงกับเจ้าของ session

ไม่ผ่านแล้วได้ `403` พร้อม
`{ "success": false, "message": "เฉพาะหัวหน้ากลุ่มเท่านั้นที่แก้ไขกลุ่มได้" }`

เลือกแบบนี้เพราะ **รูปของ endpoint บังคับอยู่แล้ว** รายชื่อมาทั้งก้อน ใครเขียนได้ก็
เขียนทับทั้งกลุ่มได้ ถ้าให้สมาชิกที่ `ACCEPT` แล้วทุกคนเขียนได้ ก็เท่ากับทุกคนไล่
กันออกได้ ตั้งตัวเองเป็นหัวหน้าได้ และเขียนทับกันเองได้โดยไม่มีอะไรบอกว่าใครมาทีหลัง
กลุ่มในระบบนี้มีหัวหน้าอยู่แล้วตั้งแต่ตอนสร้าง (`created_by` และ `role = LEADER`
หนึ่งแถว) การให้สิทธิ์ตามนั้นจึงไม่ได้เพิ่มแนวคิดใหม่ แค่ทำให้ข้อมูลที่มีอยู่มีผล

`apps/web` ก็คิดแบบนี้อยู่แล้ว — `create-groupwork-modal.tsx` ใส่คนที่ล็อกอินเป็น
`LEADER` ให้เสมอ และ `show-groupwork-modal.tsx` ไม่ยอมให้ถอดคนที่ตอบรับแล้วออก
ที่เปลี่ยนคือปุ่ม "แก้ไข" ซึ่งเคยขึ้นให้สมาชิกทุกคนเห็น ตอนนี้ขึ้นเฉพาะหัวหน้า

### กลุ่มที่ไม่มีอยู่จริงตอบ `403` เหมือนกัน

ไม่ใช่ `404` และไม่ใช่ `500` แบบเดิม เหตุผลชุดเดียวกับ ADR-0002: `group_id` เป็น
จำนวนเต็มเรียงกัน ถ้าคำตอบแยกได้ว่า "ไม่มีกลุ่มนี้" กับ "มีแต่ไม่ใช่ของคุณ" ผู้เรียก
ก็ไล่หมายเลขนับกลุ่มของชั้นเรียนที่ตัวเองไม่ได้เกี่ยวข้องได้ กลุ่มที่ไม่มี `LEADER`
เลย (ซึ่งเขียนใหม่ไม่ได้แล้ว ดูข้อถัดไป) ก็ตกในคำตอบเดียวกัน

### `members` ต้องมีอย่างน้อยหนึ่งคน และมีหัวหน้าหนึ่งคนพอดี

อยู่ใน schema ไม่ใช่ middleware เพราะเป็นเรื่องรูปของคำขอ ไม่ใช่เรื่องว่าใครถาม
ใช้กับทั้ง `POST` และ `PATCH` ของทั้งสอง router ผ่านตัวเดียวกันคือ `memberList`

- **ว่างไม่ได้** → `400` `"ต้องมีอย่างน้อย 1 รายการ"` การยุบกลุ่มมี endpoint ของ
  ตัวเองแล้ว ดูข้อ 2
- **ต้องมีหัวหน้าหนึ่งคนพอดี** → `400` `"ต้องมีหัวหน้ากลุ่มหนึ่งคน"` รายชื่อที่ไม่มี
  หัวหน้าเลยจะสร้างกลุ่มที่ไม่มีใครแก้ได้อีกภายใต้กติกาข้อ 1 ส่วนสองหัวหน้าเป็น
  ปัญหาเดียวกันจากอีกด้าน คือมีสองคนเขียนทับกันได้ ตอน `POST` ยังมีผลอีกอย่างคือ
  `created_by` ซึ่งอ่านจากคนที่ `role = LEADER` เคยเป็นสตริงว่างถ้าไม่มีใครเป็น

### 2. การยุบกลุ่มเป็น `DELETE /:group_id`

> `DELETE /student-activity-group/:group_id` และคู่แฝด ตรวจสิทธิ์ด้วยกติกาข้อ 1
> ตัวเดียวกัน ลบแถวกลุ่ม สมาชิกหายไปตาม `onDelete: Cascade` ที่ schema ประกาศไว้
> อยู่แล้ว **แถวการส่งงาน (`student_activity`) ไม่ถูกลบ**

งานที่แต่ละคนทำเป็นของคนนั้น ไม่ใช่ของกลุ่ม กติกาเดียวกับที่ `PATCH` ใช้อยู่แล้ว
ตอนหัวหน้าถอดสมาชิกออกจากรายชื่อ — คนนั้นกลับไปส่งงานเดี่ยวโดยไม่เสียสิ่งที่ส่งไป
แล้ว

ทำเป็น endpoint แยกแทนที่จะปล่อยให้ `members: []` แปลว่ายุบ เพราะสองอย่างนี้เป็นคน
ละเจตนา และคำขอที่ส่งรายชื่อว่างมาโดยไม่ตั้งใจ (bug ของ frontend, ฟอร์มที่ยังโหลด
ไม่เสร็จ) ไม่ควรลบกลุ่มทิ้ง `DELETE` บอกเจตนาชัดเจนในตัวมันเอง และตรวจสิทธิ์ที่
เดียวกับ `PATCH`

`apps/web` ยังไม่เรียก `DELETE` ตัวนี้ — ไม่มีปุ่มยุบกลุ่มในหน้าไหนอยู่แล้ว และ
ไม่ได้เพิ่มใน #27 เพราะเกณฑ์ยอมรับขอ endpoint ที่ตรวจสิทธิ์ ไม่ได้ขอหน้าจอ ที่
สำคัญกว่าคือ **ของเดิมก็ยุบกลุ่มจากหน้าจอไม่ได้อยู่แล้ว** — modal ไม่ยอมให้ถอด
หัวหน้าออกจากรายชื่อ ทางที่หายไปจึงเป็นทางที่ต้องยิง API ตรงเท่านั้น

### middleware อยู่หลัง `validate`

เหมือน ADR-0001 ถึง ADR-0003 ลำดับคือ `requireRole("STUDENT")` → `validate` →
`requireGroupLeader` คำขอที่ไม่ระบุ `group_id` หรือระบุมาผิดรูปจึงเป็น `400`

## ผลที่ตามมา

- `requireGroupLeader` กับตารางค้นหัวหน้า `groupLeader` อยู่ใน
  `apps/api/src/middlewares/owner.middleware.ts` ข้างกติกาของสาม ADR ก่อนหน้า
  รับตำแหน่งที่จะไปอ่าน `group_id` (`"body"` สำหรับ `PATCH`, `"params"` สำหรับ
  `DELETE`) เหมือนที่ `sectionRule` รับ `"query" | "body"`
- ผู้เรียกที่เคยได้ `200` แล้วตอนนี้ได้ `403` หรือ `400` ดู
  [`BEHAVIOR-CHANGES.md`](../../BEHAVIOR-CHANGES.md)
- ปุ่ม "แก้ไข" ใน `show-groupwork-modal.tsx` ขึ้นเฉพาะหัวหน้ากลุ่ม
- **`POST` ยังไม่ตรวจว่าผู้เรียกคือหัวหน้าที่ตัวเองระบุ** นักศึกษายังสร้างกลุ่มโดย
  ตั้งคนอื่นเป็น `LEADER` แล้วไม่ใส่ตัวเองลงไปได้ ซึ่งเป็นการสร้างกลุ่มในนามคนอื่น —
  ตรงข้ามกับกติกา "ผู้กระทำคือเจ้าของ session" ของ ADR-0001 ไม่ได้แก้ใน #27 เพราะ
  เกณฑ์ยอมรับพูดถึงการ **แก้** รายชื่อกับการลบกลุ่ม และการแก้ `POST` ต้องตัดสิน
  เพิ่มว่าผู้สร้างต้องเป็นหัวหน้าเสมอหรือแค่ต้องอยู่ในรายชื่อ อยู่ที่
  [#37](https://github.com/khthana/Deep-Portfolio/issues/37)
- **ยังไม่ตรวจว่าสมาชิกที่ระบุลงทะเบียนกลุ่มเรียนเดียวกับชิ้นงาน** หัวหน้ายังดึงคน
  นอกชั้นเรียนเข้ากลุ่มได้ ADR-0003 ชี้ไว้แล้วว่า `student_course` ตอบคำถามนี้ได้
  ไม่ได้ทำใน #27 ด้วยเหตุผลเดียวกัน คืออยู่นอกเกณฑ์ยอมรับ และอยู่ที่ #37 เช่นกัน
- **ไม่มีการดูสถานะการส่งงาน** ทั้ง `PATCH` และ `DELETE` ยอมให้หัวหน้าทำกับกลุ่มที่
  `SUBMITTED` หรือ `GRADED` แล้วได้ `PATCH` เป็นแบบนี้มาก่อน #27 และ `DELETE` รับ
  กติกาเดียวกันมาโดยตั้งใจ เพื่อไม่ให้ ticket นี้ตัดสินคำถามที่ไม่ได้ถาม
  หน้าจอซ่อนปุ่ม "แก้ไข" เมื่อ `GRADED` อยู่แล้ว แต่ API ไม่ได้บังคับ ถ้าจะบังคับก็
  ควรบังคับพร้อมกันทั้งสองตัวและตัดสินว่าอาจารย์ยังต้องแก้ได้หรือไม่

## จะกลับมาทบทวนเมื่อไหร่

เมื่อกลุ่มต้องเปลี่ยนหัวหน้าได้จริง ตอนนี้ `PATCH` ทำได้อยู่แล้วโดยหัวหน้าคนเดิม
ส่งรายชื่อที่ยก `LEADER` ให้คนอื่น ซึ่งเป็นการสละสิทธิ์แบบทางเดียว ถ้าวันหนึ่งต้องมี
กรณี "หัวหน้าหายไป" — ลาออก พ้นสภาพ ไม่ตอบ — ทางออกคือให้อาจารย์ของกลุ่มเรียนนั้น
แก้ได้ผ่าน endpoint ของตัวเองที่ใช้ `requireOwnSection` ไม่ใช่ผ่อนกติกาข้อ 1 ให้
สมาชิกทุกคน
