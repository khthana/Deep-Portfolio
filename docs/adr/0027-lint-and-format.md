# ADR-0027 — lint ผ่านทั้ง repo, จัดรูปแบบด้วย Prettier ค่า default, และ CI ล้มเฉพาะ error

- **สถานะ**: ตัดสินแล้ว 13 สิงหาคม 2569
- **ที่มา**: [issue #60](https://github.com/khthana/Deep-Portfolio/issues/60)
- **เกี่ยวข้อง**: [ADR-0026](0026-ci-runs-what-a-developer-runs.md) ตัดสินไว้ว่า
  workflow เรียก npm script ของ repo เอง และเว้น step `npm run lint` ไว้ให้ใบนี้
  พร้อมกับส่งคำถามเรื่อง git hook มาด้วย ไฟล์นี้ตอบทั้งสองอย่าง

## บริบท

`npm run lint` ที่ root คือ `npm run lint --workspaces --if-present` ก่อนใบนี้มัน
ทำสองอย่างที่ไม่ควรทำพร้อมกัน:

- **มันล้ม** — `apps/web` มี 8 errors ทั้งหมดเป็น `@typescript-eslint/no-unused-vars`
  รูปแบบเดียวกันหมด คือหน้าจอที่อ่าน `studentId` ออกจาก home slice แล้วไม่ได้ใช้
- **มันตรวจแค่ครึ่งเดียว** — `apps/api` ไม่มี script `lint` เลย `--if-present` จึง
  ข้ามมันไปเงียบ ๆ ทั้งที่โค้ดฝั่ง API มีมากกว่าฝั่ง web

และไม่มี formatter ผูกกับ repo เลย ไม่มี `.prettierrc` ไม่มี `.editorconfig` ทั้งที่
โค้ดที่ส่งมอบมาเขียนด้วยเครื่องมือที่เปิด Prettier ค่า default ไว้แทบทั้งหมด — วัดก่อน
ตัดสินใจแล้วพบว่ามีไฟล์ราวหนึ่งในห้าที่หลุดจากค่านั้น ส่วนใหญ่คือบรรทัดที่ยาวเกิน 80
คอลัมน์แล้วไม่ได้ตัด

## การตัดสินใจ

**1. แก้ error ที่ต้นเหตุ ไม่ใช่ปิดกฎ**

8 ข้อฝั่ง web ลบทิ้งได้จริง — ไม่มี request type ของการสร้างตัวไหนมีฟิลด์ id ของผู้ใช้
เลย เพราะ API อ่านผู้เรียกจาก token ค่านั้นจึงไม่มีทางถูกใช้ในอนาคตอันใกล้ selector
กับ import ที่พามันเข้ามาถูกลบตามไปด้วย

`apps/api` ได้ config ของตัวเอง (`apps/api/eslint.config.mjs`) ที่ใช้กฎชุดเดียวกับ web
ลบส่วนของ React ออก: `no-explicit-any` เป็น warning, `no-unused-vars` เป็น error โดย
ยกเว้นพารามิเตอร์ (`args: "none"`) เพราะพารามิเตอร์ที่อยู่ก่อนตัวที่ถูกใช้ลบไม่ได้ และ
ยกเว้นชื่อที่ขึ้นต้นด้วย `_` นามสกุลไฟล์เป็น `.mjs` ไม่ใช่ `.js` เพราะ `apps/api` เป็น
CommonJS — ต่างจาก `apps/web` ที่ `"type": "module"` ทำให้ `eslint.config.js` เป็น ESM
ได้อยู่แล้ว

config ตัวนั้นเจอเพิ่มอีก 26 errors ไม่มีข้อไหนเป็นพฤติกรรม: import กับ type ที่ไม่มี
ใครอ้าง 14 ข้อ, ผลของ `prisma.<model>.update` ที่ผูกกับตัวแปรแล้วไม่เคยอ่าน 5 ข้อ (การ
update ยังเกิดเหมือนเดิม หายไปแค่ตัวแปร), `catch (error)` ที่ไม่ได้ใช้ `error` 1 ข้อ และ
อีก 6 ข้อเป็นรูปแบบเดียวกันคือฟังก์ชันที่มีอยู่เพื่อให้อ่าน type จาก return value ของมัน
เท่านั้น — Prisma มี `Prisma.<model>GetPayload<{ include: … }>` ให้ทำเรื่องนี้ตรง ๆ อยู่
แล้ว type จึงมาจาก schema และฟังก์ชันตายทั้งหกตัวหายไป

**2. Prettier ค่า default จัดรูปแบบทั้ง repo ครั้งเดียว แล้วบันทึก revision นั้นไว้**

`prettier.config.mjs` เป็น `export default {}` โดยตั้งใจ เหตุผลอยู่ในหัวไฟล์: สี่ในห้า
ของ repo ตรงกับค่า default อยู่แล้ว การเลือกค่าอื่นแปลว่าต้องไปแก้ไฟล์ที่ไม่ได้มีปัญหา
เพื่อตอบคำถามที่ไม่มีใครในโปรเจกต์นี้มีความเห็น และเพราะทั้ง `js.configs.recommended`
กับ `recommended` ของ typescript-eslint ไม่ได้เปิดกฎเชิงรูปแบบสักข้อ ESLint กับ
Prettier จึงไม่มีทางขัดกัน — ไม่ต้องมี `eslint-config-prettier`

การจัดรูปแบบรอบเดียวนั้นแยกเป็น commit ของตัวเอง (`14e7fc9`, 121 ไฟล์) ที่ไม่มีอะไร
อื่นปนเลย แล้วใส่ SHA ของมันไว้ใน `.git-blame-ignore-revs` เพื่อให้ `git blame` มองทะลุ
ไปหาคนที่เขียนบรรทัดจริง ๆ (GitHub อ่านไฟล์นี้เอง ส่วนบนเครื่องต้องสั่ง
`git config blame.ignoreRevsFile .git-blame-ignore-revs` หนึ่งครั้ง)

`.prettierignore` กัน `*.md` ออกทั้งหมด — `README.md`, `BEHAVIOR-CHANGES.md` และ
`docs/` เป็นย่อหน้าภาษาไทยที่ตัดบรรทัดด้วยมือตามความกว้างที่อ่านสบาย และมีตารางที่จัด
คอลัมน์ไว้ Prettier จะจัดใหม่ทั้งหมดโดยไม่ได้ทำให้อะไรดีขึ้น ที่เหลือคือ `dist`,
`package-lock.json`, `data/` และ `apps/web/public/pdf.worker.min.mjs` ที่เป็นไฟล์ minified
ซึ่ง react-pdf โหลดไปใช้ตามที่มันเป็น

**3. CI ล้มเมื่อมี error ไม่ล้มเมื่อมี warning**

`ci.yml` ได้ step `npm run lint` กับ `npm run format:check` ต่อจาก `npm run typecheck`
ทั้งคู่เป็น npm script ที่คนรันเองได้ ตามข้อ 1 ของ ADR-0026

ไม่ตั้ง `--max-warnings` วันนี้ repo มี 217 warnings — ฝั่ง web 215 ข้อ (`no-explicit-any`
141, `react-hooks/exhaustive-deps` 74) และฝั่ง API อีก 2 ข้อ (`no-explicit-any` ทั้งคู่
อยู่ใน `apps/api/test/course.test.ts`) ซึ่งเป็นเนื้อของ
[#63](https://github.com/khthana/Deep-Portfolio/issues/63) กับ
[#66](https://github.com/khthana/Deep-Portfolio/issues/66) เพดานที่ไม่มีวันเลื่อนเองคือ
การยกกฎขึ้นเป็น `error` ตอนที่ใบนั้น ๆ เคลียร์จุดของตัวเองหมด — #66 มีข้อนี้อยู่ใน
รายการที่ต้องตัดสินก่อนหยิบใบ ส่วนการเขียนตัวเลขลงใน `ci.yml` ได้เพดานที่ค้างทันทีที่มี
คนแก้โค้ดอย่างสุจริตแล้วจำนวนขยับ คนถัดไปก็ต้องมาแก้ตัวเลขในไฟล์ที่ไม่เกี่ยวกับงาน
ตัวเอง

**4. ยังไม่มี git hook**

ADR-0026 ส่งคำถามนี้มาให้ใบนี้เพราะเหตุผลที่ hook ยังไม่เกิดตอนนั้นคือ lint ที่ยังล้ม
ตอนนี้ lint ผ่านแล้ว แต่คำตอบยังเหมือนเดิม: `main` มีประตูอยู่แล้วคือ CI และ hook เป็น
ของบนเครื่องคนเขียนโค้ด — คนที่รู้สึกว่ามันช้าจะ `--no-verify` ทับ ซึ่งได้ hook ที่ไม่ได้
กันอะไรเลยแต่ทำให้ทุกคนพิมพ์ธงนั้นจนชิน ใครอยากให้เครื่องตัวเองรัน `npm run lint` หรือ
`npm run format` ก่อน commit ตั้งเองได้ และ repo ไม่ต้องรู้เรื่องนั้น

ถ้าวันหนึ่งมีคนหลายคนเขียนพร้อมกันจนรอบ CI ที่แดงเพราะ format กลายเป็นเรื่องกวนใจ
จริง ๆ ค่อยกลับมาเปิดข้อนี้ใหม่ พร้อมตัวเลขว่ามันเกิดบ่อยแค่ไหน

## ผลที่ตามมา

- `npm run lint` ที่ root ตรวจทั้งสอง workspace แล้ว และออก 0
- คนที่แก้โค้ดต้องรัน `npm run format` ก่อน commit ไม่งั้น `format:check` ใน CI แดง
  ข้อความที่ได้จะบอกเฉพาะว่าไฟล์ไหนไม่ตรง ไม่ได้บอกว่าโค้ดผิด
- warning เพิ่มได้โดยไม่มีอะไรเตือน จนกว่าจะมีใบที่ยกกฎของตัวเองขึ้นเป็น `error`
- `git blame` บนบรรทัดที่ `14e7fc9` แตะ จะชี้ผิดจนกว่าจะตั้ง `blame.ignoreRevsFile`
  บนเครื่อง ส่วนบน GitHub ถูกอยู่แล้ว
