# ADR-0036 — response ที่เป็นค่าเดี่ยว ไม่ตั้งชื่อให้

- **สถานะ**: ตัดสินแล้ว 19 สิงหาคม 2569
- **ที่มา**: [issue #68](https://github.com/khthana/Deep-Portfolio/issues/68)
  รอบ score-weight
- **เกี่ยวข้อง**: [ADR-0035](0035-one-group-shape-for-both-halves.md) รอบก่อน
  หน้า ซึ่งตั้ง `GroupIdResp` ให้ `{ group_id }` ใบนี้อ่านคู่กับใบนั้น เพราะ
  สองรอบดูเหมือนตัดสินคนละอย่างกับของหน้าตาคล้ายกัน และ
  [ADR-0032](0032-activity-follows-the-row.md) ซึ่งเป็นเจ้าของคำตอบเรื่อง
  `/options` ใบนี้ไม่ได้ทบทวนข้อไหนของทั้งสองใบ

## บริบท

`/score-weight` มีห้าเส้น และรอบนี้เป็นรอบแรกของ #68 ที่เดินมาเจอ**รูประดับ
response ของ endpoint ตัวเอง**เขียนรอไว้แล้ว ก่อนหน้านี้มีรอบที่เจอของเขียนรอไว้
เหมือนกัน แต่เป็นคนละอย่าง: ADR-0031 ย้าย `AttachmentDetailResp` ล่วงหน้าเพราะหก
feature ฝังมันไว้ข้างใน — เป็นชิ้นส่วนที่หลายคนใช้ ส่วนรอบนี้เจอรูป**ทั้งแถว**ที่
เส้นของตัวเองตอบ เขียนไว้ให้โดยรอบของ feature อื่น

รอบ activity เจอว่าสองเส้นอ่านตาราง `subject_score_ratio` คนละแบบ
จึงเขียน `ScoreWeightBrief` กับ `ScoreWeightDetail` แยกกัน แล้วทิ้งคอมเมนต์ไว้ว่า

> `GET /score-weight` มีรอบของตัวเองรออยู่ และตอบทั้งแถว — จะเจอ
> `ScoreWeightDetail` เขียนไว้ให้แล้ว

รอบนี้ไปพิสูจน์ และคำทำนายนั้นถูก: เคสที่ไล่ชื่อทุกคีย์ของ `GET /score-weight`
ผ่านกับ `ScoreWeightDetail` ตัวเดิมโดยไม่ต้องเพิ่มฟิลด์ไหน และ `PUT` กับ `DELETE`
ก็ตอบแถวเดียวกันนั้นอีก — แถวที่เพิ่งแก้ และแถวที่เพิ่งลบ package จึงไม่ได้ type
ใหม่สักตัวจากรอบนี้ ซึ่งเป็นผลลัพธ์ที่ดีที่สุดที่รอบหนึ่งจะให้ได้

เหลือสองเส้นที่ไม่ลงล็อกนั้น

## สิ่งที่ประกาศเดิมปิดไว้

| จุด                              | type เดิมบอก                       | ของจริง                                       |
| -------------------------------- | ---------------------------------- | --------------------------------------------- |
| `section_id` (ทุกเส้นที่ตอบแถว)  | ฝั่ง web ไม่ได้ประกาศ              | ส่งมาด้วยเสมอ เพราะแถวถูกส่งทั้งแถว           |
| `weight`                         | `number`                           | `Int?` — คอลัมน์รับ null ได้                  |
| `created_at`, `updated_at`       | `string` ไม่ยอม null               | `DateTime?` ทั้งคู่                           |
| `POST /score-weight`             | `{ score_weight_id: number }`      | ตัวเลขเปล่า ๆ ไม่ใช่วัตถุ                     |

`{ score_weight_id: number }` ผิดสองชั้นในบรรทัดเดียว: ผิดรูป (วัตถุ ทั้งที่มา
เป็นตัวเลข) และผิดชื่อคีย์ (คอลัมน์ชื่อ `score_ratio_id`) — ข้อหลังต้องพูดให้แคบ
กว่าที่อยากพูด เพราะ `score_weight_id` **มีอยู่จริง**ที่อื่น: `student.mapper.ts`
เปลี่ยนชื่อ `score_ratio_id` เป็นมันตอนสร้างรายการงานของนักศึกษา ที่ไม่มีคือไม่มี
เส้นไหนใต้ `/score-weight` ส่งคีย์นั้น และเส้นนี้ไม่ได้ส่งวัตถุมาตั้งแต่แรก
ไม่มีใครจับได้เพราะไม่มีใครอ่านค่าที่มันตอบเลย — ผู้เรียกรายเดียวเขียน
`await dispatch(postScoreWeight(body)).unwrap()` แล้วโหลดตารางใหม่ ไม่ได้แตะผลลัพธ์
เลยแม้แต่ฟิลด์เดียว

## การตัดสินใจ

**1. response ที่เป็นค่าเดี่ยว ไม่ตั้งชื่อให้ใน package**

`POST /score-weight` ตอบ `score_ratio_id` เป็นตัวเลขเปล่า service จึงเขียนว่า
`Promise<number>` และฝั่ง web เขียนว่า `ResponseWrapper<number>` ไม่มี
`ScoreWeightIdResp` ใน package

รอบที่แล้วตั้ง `GroupIdResp` ให้ `{ group_id }` ซึ่งดูเผิน ๆ เหมือนกัน แต่ไม่ใช่:
สิ่งที่ `GroupIdResp` ตั้งชื่อให้คือ**การเลือกของ API** ว่าจะห่อ id ไว้ในวัตถุที่มี
คีย์ชื่อนี้ — คนอ่านต้องรู้ชื่อคีย์ถึงจะอ่านค่าออก และชื่อนั้นไม่มีอะไรบอกนอกจาก
ตัว type ส่วน `number` ไม่มีอะไรให้รู้เพิ่ม `ResponseWrapper<number>` บอกครบแล้ว
ว่าอะไรจะมา การตั้งชื่อทับมันมีแต่จะเพิ่มชั้นที่ต้องตามไปเปิดอ่าน

เส้นแบ่งจึงอยู่ที่ว่า type นั้น**บอกอะไรที่ค่ามันเองไม่ได้บอก**หรือเปล่า ไม่ได้อยู่
ที่ว่าเป็นเส้นเขียนหรือเส้นอ่าน

**2. `GET /score-weight/options` ไม่ย้าย — ใบนี้ขยายเหตุผลของ ADR-0032 มาถึงมัน**

มันตอบ `{ label, value }` เหมือน `/activity/options` และ
`/learning-activity/options` ทุกตัวอักษร

ต้องพูดให้ตรง: **ADR-0032 พูดถึงสองเส้นนั้น ไม่ได้พูดถึงเส้นนี้** สิ่งที่ใบนั้น
ตัดสินคือรูป `{ label, value }` เป็นรูปที่ web กำหนดให้ API ตอบตาม ไม่ใช่รูปที่ API
กำหนดขึ้น จึงเป็นคำถามประเภทเดียวกับ envelope ใน #67 เหตุผลนั้นไม่ได้ผูกกับ
feature ไหนเลย — มันผูกกับรูป ใบนี้จึงรับเหตุผลนั้นมาใช้กับเส้นที่สาม และเป็น
เจ้าของการขยายนั้นเอง ไม่ใช่อ้างว่า ADR-0032 ตัดสินไว้ให้แล้ว

ผลคือ `getScoreWeightOptions` ยังไม่มี return annotation เหมือน
`getActivityOptions` และเมื่อ #67 ตอบคำถาม envelope ทั้งสามเส้นจะย้ายพร้อมกัน

**3. `updated_at` ไม่ใช่สิ่งที่ชื่อมันบอก และปักหมุดไว้**

คอลัมน์มี `@default(now())` แต่ไม่มี `@updatedAt` อยู่ข้างหลัง `PUT` จึงคืนค่าที่
แถวถูกสร้างมาพร้อมกัน ไม่ใช่เวลาที่เพิ่งแก้ เคสของ `PUT` เขียนค่าที่คาดไว้เป็น
`created_at` ของ fixture ตรง ๆ และคอมเมนต์บอกเหตุผล — เพราะคนอ่านคนต่อไปจะอ่าน
ชื่อคอลัมน์แล้วเชื่อมัน

นี่ไม่ใช่บั๊กที่รอบนี้แก้ การทำให้มันขยับคือการเปลี่ยนสิ่งที่ผู้เรียกเห็น และไม่มี
ใครฝั่ง web อ่านค่านี้เลยสักจุด รอบนี้จึงเขียนความจริงลงไปเฉย ๆ ทั้งในเคสและใน
คอมเมนต์ของ type

**4. `weight` ที่เป็น null ไปจบที่ `?? 0` ที่จุด map ไม่ใช่ที่ type ของตาราง**

พอ `ScoreWeightDetail.weight` บอกว่า `number | null` คอมไพเลอร์ทักสองที่ทันที คือ
ตารางสัดส่วนคะแนนทั้งฝั่งอาจารย์และฝั่งนักศึกษา ซึ่ง `DataType.weight` ของทั้งคู่
เป็น `number`

`DataType` เป็นรูปของแถวในตาราง ant design ไม่ใช่รูปที่ API ตอบ การขยายมันเป็น
`number | null` จะลาก null ไปทั่วทั้งฟอร์มแก้ไข ตัวรวมยอด และ `InputNumber` ที่
ผูกกับมัน รอบนี้จึงแปลงที่จุด map แทน ด้วย `?? 0` ซึ่งเป็น default ของคอลัมน์เอง

เหตุผลที่ทำแบบนี้ได้โดยไม่เปลี่ยนสิ่งที่ใครเห็นคือ **null เขียนลงคอลัมน์นี้ไม่ได้
เลยผ่านทางไหน**: `addScoreWeightBody.weight` กับ `updateScoreWeightBody.weight`
เป็น field บังคับทั้งคู่ สอง service method นั้นคือผู้เขียนตารางนี้ทั้งหมด และ
importer ไม่แตะ `subject_score_ratio` เลย คอลัมน์รับ null ได้ก็จริง แต่ไม่มีสายไหน
ใส่ให้ `?? 0` จึงเป็นการทำให้ type ฝั่ง UI พูดตรงกับ type ฝั่ง API เฉย ๆ

ที่พูดแบบนี้เพราะเหตุผลที่อ่อนกว่านั้นไม่พอ: ตัวรวมยอดอ่าน `item.weight || 0`
อยู่แล้วก็จริง แต่มันเป็นผู้อ่านคนเดียวในสามคน อีกสองคนคือเซลล์ที่เรนเดอร์ กับ
`InputNumber` ในฟอร์มแก้ไขซึ่งตั้ง `require: true` ไว้ ถ้า null ไปถึงได้จริง
`?? 0` จะเปลี่ยนทั้งสองอย่าง — ช่องว่างกลายเป็น `0` และปุ่มบันทึกที่เคยถูกกั้นจะ
ผ่าน ซึ่งเป็นกับดักที่ #68 เตือนไว้เอง ว่าค่าแทนต้องเหมือนของเดิมทุกทางที่มีคนอ่าน
ไม่ใช่เฉพาะทางที่เรนเดอร์

## ผลที่ตามมา

- เหลือสำเนาฝั่ง web 35 ไฟล์ 1,845 บรรทัด (จาก 35 ไฟล์ 1,851 หลังรอบ group)
  นับด้วย glob ชุดเดียวกับที่ ADR-0028 ประกาศไว้ — `apps/web/src/types/*.ts`,
  `apps/web/src/features/**/types/*.ts` และ `apps/web/src/features/**/types.ts`
  ตัดไฟล์ `*.test.ts` ออก แล้ว `wc -l` รวม เขียนวิธีนับไว้ตรงนี้เพราะตัวเลขนี้
  ต่อกันมาหลายใบแล้ว และ glob ที่ต่างไปนิดเดียวก็ให้คนละตัวเลข
  `src/types/course-type.type.ts` ยังเหลือ `LessonPlanResp` กับ
  `AnnouncementDetailResp` ซึ่งเป็นของอีกสอง feature ส่วน
  `features/teacher/course/types/score-weight-type.type.ts` ไม่มีอะไรให้ย้ายเลย
  ตั้งแต่ต้น — ในนั้นเป็น request body กับรูปของฟอร์มล้วน ๆ
- package ไม่ได้ type ใหม่สักตัว ได้แต่คอมเมนต์ที่แก้จาก "รอรอบของมัน" เป็น
  "รอบนั้นมาแล้ว และคำทำนายถูก"
- API เพิ่มหนึ่งเคส คือเคสที่ไล่ชื่อทุกคีย์ของ `GET` และรัดอีกสามเคสเดิม: `PUT`
  กับ `DELETE` เปลี่ยนจาก `toMatchObject` เป็น `toEqual` ทั้งวัตถุ ส่วนเคสของ
  `POST` เพิ่มบรรทัดยืนยันว่าที่ตอบมาเป็นตัวเลข ไม่ใช่วัตถุ รวมเป็น 1,071 เคส
- ฝั่ง web ไม่เพิ่มไม่ลดเคส (448)
- **`activity.service.ts` ยังสร้าง `ScoreWeightDetail` ของมันเองอยู่ในบรรทัด**
  ด้วยนิพจน์เดียวกับ `toScoreWeightDetail` เป๊ะ ๆ รอบนี้ไม่ดึงออกมาใช้ร่วมกัน
  เพราะบล็อกนั้นเป็นหนึ่งในห้าที่แปลงวันที่แบบเดียวกันเรียงกันอยู่ในฟังก์ชันเดียว
  (ตัวกิจกรรมเอง, สัดส่วนคะแนน, rubric, ระดับของ rubric) ดึงออกอันเดียวจะทำให้
  ฟังก์ชันนั้นอ่านไม่เท่ากันทั้งก้อน ซึ่งแย่กว่าการซ้ำ บันทึกไว้ให้รอบที่จะจัดการ
  ทั้งห้าพร้อมกัน
- `npm run lint` ยังเท่าเดิมที่ 216 warning — `{ score_weight_id: number }` ที่
  หายไปไม่ใช่ `any` มันเป็นวัตถุที่ประกาศผิดเฉย ๆ ซึ่งไม่มีกฎไหนจับได้
