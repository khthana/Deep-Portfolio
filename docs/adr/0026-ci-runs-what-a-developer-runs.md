# ADR-0026 — CI รันคำสั่งชุดเดียวกับที่คนรันบนเครื่องตัวเอง

- **สถานะ**: ตัดสินแล้ว 13 สิงหาคม 2569 — ข้อ 3 (ยังไม่ใส่ `npm run lint`) และคำถาม
  เรื่อง git hook ในหัวข้อผลที่ตามมา ถูก
  [ADR-0027](0027-lint-and-format.md) รับไปตอบในวันเดียวกัน ที่เหลือยังใช้อยู่
- **ที่มา**: [issue #59](https://github.com/khthana/Deep-Portfolio/issues/59)
  ครึ่งแรก — ตัว issue เองเสนอไว้ว่า "แยกเป็นสองใบได้ถ้าจะทำจริง: **CI** ทำได้
  ทันทีโดยไม่ต้องรู้ข้อ 1 ส่วน **CD** รอข้อ 1"
- **เกี่ยวข้อง**: T2 ของ spec กำหนดรอยต่อที่ test ยิงเข้าไป และ D13 กำหนดว่า repo
  เป็น public จึงไม่มีค่าลับอยู่ในนั้น สองข้อนี้รวมกันคือเหตุผลที่ workflow ไม่ต้อง
  ใช้ secret เลยแม้แต่ตัวเดียว

## บริบท

จนถึงวันนี้ไม่มีอะไรรันอัตโนมัติเลย ไม่มี `.github/workflows` ไม่มี git hook
`npm test`, `npm run typecheck`, `npm run lint` รันด้วยมืออย่างเดียว เอกสาร
ปริญญานิพนธ์อ้างถึง Jenkins แต่ไม่มี `Jenkinsfile` ติดมากับโค้ด

สิ่งที่ทำให้ CI เกิดขึ้นได้ตอนนี้โดยไม่ต้องรู้ว่า server ปลายทางคืออะไร คือ suite
ฝั่ง API พึ่งพาเครื่องที่รันมันน้อยมาก:

- `apps/api/test/global-setup.ts` สั่ง `docker compose -f docker-compose.test.yml
  up -d --wait` ให้เอง แล้วรอจน PostgreSQL กับ MinIO รับ connection จริง
- `apps/api/test/setup.ts` เขียนตัวแปรทุกตัวที่ `src/config/env.ts` ต้องการลง
  `process.env` ก่อน import อะไรทั้งสิ้น — ไม่ต้องมีไฟล์ `.env` และไม่มีค่าลับจริง
  เข้ามาเกี่ยวข้อง
- ฝั่ง web เป็นฟังก์ชันบริสุทธิ์ล้วน ๆ และบล็อก `test.env` ใน
  `apps/web/vite.config.ts` (ไฟล์เดียว ไม่ได้แยก `vitest.config.ts` เหมือนฝั่ง API)
  ตั้ง `VITE_BACKEND_URL` กับ `VITE_GOOGLE_CLIENT_ID` เป็นค่าสมมติไว้ในตัวเอง

แปลว่าเครื่องเปล่าที่มี Node กับ Docker รัน `npm ci && npm run typecheck && npm test`
ได้เลย ซึ่งคือทั้งหมดที่ runner ของ GitHub Actions มีให้อยู่แล้ว

## การตัดสินใจ

**1. หนึ่ง job ที่เรียก npm script ของ repo ไม่ใช่ workflow ที่เขียนขั้นตอนขึ้นใหม่**

`.github/workflows/ci.yml` มี job เดียวชื่อ `check` ทำสี่อย่างเรียงกัน: `npm ci`,
`npm run typecheck`, `npm test` (บวก checkout กับ setup-node) ไม่มีอะไรใน workflow
ที่ repo ไม่ได้เก็บไว้ในที่อื่นอยู่แล้ว คนที่แก้ test แล้วอยากรู้ว่า CI จะทำอะไร
อ่านได้จาก `package.json` ตัวเดียวกับที่ตัวเองรัน

แยกเป็นหลาย job ก็ได้ แต่แต่ละ job ต้อง `npm ci` ใหม่ทั้งหมด ซึ่งแพงกว่าที่ประหยัด
ได้จากการรันขนานกัน — `npm test` ทั้งสอง workspace ใช้เวลาราวครึ่งนาทีเมื่อ
container อุ่นแล้ว

**2. บริการฐานข้อมูลมาจาก `docker-compose.test.yml` ไม่ใช่ `services:` ของ Actions**

GitHub Actions มี `services:` ให้ยก container ขึ้นเองได้ แต่ compose file ตัวนี้ไม่ได้
มีแค่ image กับ port — มันตั้ง `fsync=off`, `full_page_writes=off`,
`synchronous_commit=off`, `max_connections=300`, `TZ=UTC`, `PGTZ=UTC` และ tmpfs
ทั้งของ Postgres และ MinIO ค่าพวกนี้คือเหตุผลที่ suite สร้างฐานข้อมูลหนึ่งตัวต่อ
ไฟล์ได้โดยไม่ช้า ถ้าย้ายไป `services:` ก็ต้องคัดลอกมันไปทั้งชุด แล้วจากนั้นสองที่จะ
ค่อย ๆ ต่างกันโดยไม่มีใครรู้ตัว

`TEST_SKIP_DOCKER=1` ที่ `global-setup.ts:31` เตรียมไว้ให้ยังอยู่ครบสำหรับคนที่อยาก
ทำแบบนั้นในอนาคต workflow นี้แค่ไม่ได้ตั้งมัน

**3. ยังไม่ใส่ `npm run lint`**

`npm run lint` วันนี้ออก non-zero — 8 errors กับ 215 warnings ทั้งหมดฝั่ง web และ
`apps/api` ไม่มี script `lint` เลย ซึ่งคือเนื้อของ
[#60](https://github.com/khthana/Deep-Portfolio/issues/60) ทั้งใบ

ใส่ไปเลยแล้วปล่อยแดงก็ตรงตามที่ #59 เขียนไว้มากกว่า แต่ราคาคือ CI ที่แดงตั้งแต่
commit แรกและแดงต่อไปเรื่อย ๆ ซึ่งสอนทุกคนให้ชินกับสีแดง แล้ว CI ก็หมดประโยชน์ไป
ทั้งอัน ส่วนการใส่แบบ `continue-on-error` ได้ไฟเขียวที่ไม่ได้แปลว่าผ่าน ซึ่งแย่กว่า
ไม่มีเลย — จึงเลือกให้ step lint เข้ามาพร้อมกับ #60 ที่เป็นคนแก้มัน และเขียนกำกับไว้
ทั้งในหัวไฟล์ workflow และในใบ #60

`npm run build` ก็ไม่ได้ใส่ ด้วยเหตุผลคนละแบบ: #59 ระบุไว้สามอย่างคือ test,
typecheck, lint และ `typecheck` ฝั่ง web คือ `tsc -b` ตัวเดียวกับครึ่งแรกของ `build`
อยู่แล้ว ที่เพิ่มมาจริง ๆ มีแค่ `vite build` ซึ่งคุ้มจะใส่ตอนที่มีคนต้องใช้ผลของมัน
คือตอนทำ CD

**4. ทริกเกอร์: ทุก push เข้า `main` และทุก PR**

repo นี้ทำงานบน `main` เป็นหลัก การกันเฉพาะ PR จึงแทบไม่ได้รันเลย ส่วนทาง
กลับกัน `push:` ที่ไม่ระบุ branch เลยก็เกินความจำเป็น — branch ระหว่างทางถูก PR
คลุมอยู่แล้ว และ branch ที่ push ขึ้นมาพักไว้เฉย ๆ ไม่มีใครรอคำตอบของมัน จึงจำกัด
`push:` ไว้ที่ `main` แล้วให้ `pull_request` รับที่เหลือ ผลรวมคือทุก commit ที่จะเข้า
`main` ถูกตรวจอย่างน้อยหนึ่งครั้ง ซึ่งเป็นสิ่งที่ #59 ต้องการจากคำว่า "ทุก push"

ส่วน
`cancel-in-progress` เปิดเฉพาะ ref ที่ไม่ใช่ `main` — push ทับกันบน branch ระหว่างทาง
ทำให้คำตอบของรอบก่อนหมดค่า แต่ประวัติของ `main` เป็นสิ่งที่อาจมีคนย้อนมาอ่านทีหลัง

## ผลที่ตามมา

- `main` ที่พังจะรู้ตัวภายในไม่กี่นาที ไม่ใช่ตอนที่คนถัดไป pull มา
- คนแก้ #60 ต้องเพิ่ม step `npm run lint` เข้า `ci.yml` ด้วย ไม่ใช่แค่ทำให้คำสั่งผ่าน
- **git hook ยังไม่มี และไม่ได้อยู่ในไฟล์นี้** — #59 นับ "ไม่มี git hook ใด ๆ" เป็นอาการ
  ของปัญหาเดียวกัน แต่ hook เป็นของบนเครื่องคนเขียนโค้ด ไม่ใช่ประตูของ `main` และสิ่งที่
  จะให้ hook รันได้เร็วพอที่คนจะไม่ปิดมันทิ้งคือ lint ซึ่งวันนี้ยังล้ม คำถามนี้จึงไปอยู่กับ #60
  ที่เป็นเจ้าของเครื่องมือฝั่งนั้นทั้งชุด ไม่ใช่ค้างอยู่กับใบที่ปิดไปแล้ว
- CD ยังไม่มีและไม่ได้อยู่ในไฟล์นี้ — ข้อ 1–5 ของ #59 (server ปลายทาง,
  `VITE_BACKEND_URL` ของ build จริง, Google OAuth client ID, ที่เก็บค่าลับ,
  วิธีย้ายข้อมูลจริง) ยังตัดสินไม่ได้เพราะไม่มีข้อมูล จึงย้ายไปอยู่ใบใหม่ที่ติดป้าย
  `needs-info` ต่อ
- push ครั้งแรกที่มีไฟล์นี้ต้องใช้ token ที่มีสิทธิ์ `workflow` ถ้า push แล้วถูก
  ปฏิเสธด้วยข้อความเรื่อง workflow scope นั่นคือสาเหตุ ไม่ใช่ตัวไฟล์ผิด
