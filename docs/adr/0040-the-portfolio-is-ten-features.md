# ADR-0040 — e-Portfolio ไม่ใช่ feature เดียว แต่เป็นสิบ และรอบที่รวมทุกส่วนเดินท้ายสุด

- **สถานะ**: ตัดสินแล้ว 22 สิงหาคม 2569
- **ที่มา**: [issue #68](https://github.com/khthana/Deep-Portfolio/issues/68)
  รอบ portfolio-personal กับ portfolio-education
- **เกี่ยวข้อง**: [ADR-0031](0031-attachments-are-the-leaf.md) ซึ่งตัดสินว่าลำดับ
  ของรอบมาจากกราฟการพึ่งพา ใบนี้ใช้กฎเดิมกับสิ่งที่ ADR-0031 ยังไม่เคยเจอ คือ
  feature ที่**ใหญ่เกินกว่าจะเป็นรอบเดียว**, [ADR-0033](0033-learning-activity-and-the-absent-key.md)
  เรื่องคีย์ที่ไม่มีอยู่ต่างจากคีย์ที่เป็น null และ
  [ADR-0039](0039-the-row-and-what-is-added-to-it.md) ข้อ 1 เรื่องแถวที่เติมของ
  เขียนเป็นการต่อกัน ใบนี้ไม่ได้ทบทวนข้อไหนของสามใบนั้น

## บริบท

ตอนเลือก feature ถัดไป ตัวเลขที่มีอยู่บอกว่า e-Portfolio คือ "14 ไฟล์ 715 บรรทัด
ฝั่ง web" ซึ่งเป็นก้อนที่ใหญ่ที่สุดที่เหลือ และไฟล์ type ของมันทั้ง 14 ไฟล์
**ไม่ import อะไรเลยสักบรรทัด** จึงเป็นใบล่างตามเกณฑ์ ADR-0031 เต็มตัว

พอเปิดฝั่ง API ดูจริงกลับพบว่ามันไม่ใช่ feature เดียว

| | จำนวน |
| --- | --- |
| router | 10 |
| endpoint รวม | 58 |
| service / model / ไฟล์ test | อย่างละ 10 |

58 เส้นมากกว่ารอบไหนของ #68 หลายเท่า — ไม่มีรอบไหนที่ผ่านมากิน router เกินสองตัว
ทำ e-Portfolio รอบเดียวจึงขัดกับ ADR-0028 ข้อ 3 ที่ว่า diff ใหญ่กว่านั้นตรวจ
ไม่ไหว ตรง ๆ

เลข 58 นับจาก `router.get|post|put|patch|delete` ในไฟล์ route ทั้งสิบ (แปดตัวละ 5
บวก skill 9 บวกตัวรวม 9) `BEHAVIOR-CHANGES.md` หัวข้อ #31 เขียนไว้ว่า "56
endpoint" ซึ่งเป็นการนับคนละครั้งคนละเรื่อง — ตอนนั้นนับเส้นที่ใส่การตรวจสิทธิ์
ครบแล้ว ไม่ได้นับเส้นทั้งหมด ตัวเลขสองตัวนี้จึงไม่ได้ขัดกัน แต่เขียนกำกับไว้เพราะ
คนอ่านที่เจอทั้งสองที่จะสงสัย

## การตัดสินใจ

**1. e-Portfolio เดินเป็นหลายรอบ โดยนับ router หนึ่งตัวเป็นหนึ่ง feature**

สิ่งที่ #68 เรียกว่า "feature" ตลอดมาคือกลุ่มเส้นที่ใช้รูปร่วมกันและมี service
เป็นของตัวเอง ตามนิยามนั้น e-Portfolio มีสิบ feature ไม่ใช่หนึ่ง — แต่ละ router
มี service, model และไฟล์ test ของตัวเองครบ ชื่อ "portfolio" ที่ขึ้นต้นเหมือนกัน
เป็นเรื่องของ URL ไม่ใช่เรื่องของรูป

รอบหนึ่งจึงกิน section หนึ่งถึงสาม section แล้วแต่ว่าอ่านไหวแค่ไหน ไม่ใช่กินทั้ง
e-Portfolio รอบนี้กินสอง section คือรายละเอียดส่วนตัวกับประวัติการศึกษา

**2. `portfolio.routes.ts` ซึ่งเป็นรอบรวม เดินท้ายสุด**

`portfolio.service.ts` import service ของทั้งเก้า section เข้ามาแล้วประกอบเป็น
คำตอบเดียว มันจึงมีขาออกไปหาทุก feature ที่ยังไม่ย้าย ซึ่งเป็นเงื่อนไขที่
ADR-0031 บอกไว้ตรง ๆ ว่าห้ามย้ายก่อน ไม่ต้องคิดใหม่ ใบนี้แค่บันทึกว่ากฎนั้นชี้
ไปที่ใคร

**3. รูปโปรไฟล์ไม่ใช่ `AttachmentDetailResp` และไม่ควรทำให้เป็น**

`portfolio_personal` ถือรูปเดียว ไม่ใช่รายการ และสองฟิลด์ที่ตอบกลับมาก็พูดคนละ
เรื่องกันตามที่ไฟล์ถูกเก็บไว้ที่ไหน — ไฟล์ที่อัปโหลดใส่ path ลงทั้ง `url` และ
`file_path` ส่วนลิงก์ใส่ลิงก์ลง `url` แล้วปล่อย `file_path` เป็น null

ทางเลือกที่ไม่เอาคือยัดให้เป็น `AttachmentDetailResp` เพื่อให้ "เหมือนที่อื่น"
ซึ่งจะทำให้ type บอกว่ามีรายการสองรายการรออยู่ ทั้งที่ของจริงคือวัตถุเดียวหรือ
null รอบนี้จึงให้ `PortfolioPersonalPicture` เป็นชื่อของตัวเอง

**4. เส้นอ่านกับเส้นเขียนของ personal เป็นคนละรูป เพราะคีย์หนึ่งไม่มีอยู่**

`GET` ตอบแถวพร้อมรูป ส่วน `POST`, `PUT` และ upsert ตอบแถวที่ Prisma คืนมาตรง ๆ
**ซึ่งไม่มีคีย์ `attachments` เลย** ไม่ใช่มีแล้วเป็น null — เพราะรูปเป็นสิ่งที่
เส้นอ่านไปหยิบมาเอง

`DELETE` ไม่ได้ตอบแถว ทั้งของ personal และของ education — service อ่านแถวที่ลบ
กลับมาจริง แต่ controller เรียก `successResponse(res, null, …)` ผู้เรียกจึงได้
`data: null` ซึ่งเป็นคีย์ที่มีอยู่และเป็น null ไม่ใช่คีย์ที่หายไปแบบ ADR-0033
สองเส้นนี้จึงไม่มี type ใน package และไม่ใช่การลืม (ผมเขียนไว้ผิดสามที่ว่ามันตอบ
แถว รีวิวเป็นคนจับได้ และเคสเดิมของทั้งคู่ปัก `data` เป็น null ไว้อยู่ก่อนแล้ว)

ประกาศเดิมทั้งสองฝั่งใช้ type เดียวกับทั้งห้าเส้น แล้วทำ `attachments` เป็น
optional ซึ่งอ่านได้ว่า "บางทีก็ไม่มี" ทั้งที่สิ่งที่มันหมายถึงคือ "เส้นเขียนไม่มี
คีย์นี้" รอบนี้จึงแยกเป็น `PortfolioPersonalRow` กับ
`PortfolioPersonalDetail = Row & { attachments }` ตามรูปแบบของ ADR-0039 ข้อ 1
และปักด้วย `not.toHaveProperty("attachments")` ตาม ADR-0033

**5. `email` ของเส้นอ่านแคบกว่าของแถว และเขียนให้แคบตามนั้น**

`users.email` เป็น `@unique` และไม่ยอม null ส่วนเส้นอ่านทั้งสองสาขาก็ fallback
ไปหามันเมื่อคอลัมน์ของ portfolio ว่าง `PortfolioPersonalDetail.email` จึงเป็น
null ไม่ได้เลย ต่างจาก `PortfolioPersonalRow.email` ที่เส้นเขียนตอบตรงจากคอลัมน์
ซึ่ง nullable จริง

เขียนเป็น `Row & { email: string }` ตามรูปแบบข้อ 1 ของ ADR-0039 — intersection
ของ `string | null` กับ `string` คือ `string` การต่อ type จึงทำได้ทั้งการ**เติม**
ฟิลด์และการ**บีบ**ฟิลด์ที่มีอยู่ให้แคบลง ซึ่ง ADR-0039 ใช้แต่แบบแรก

`phone_number` ไม่บีบ เพราะ `users.phone` เป็น `String?` fallback จึงคืน null ได้
ของมันเอง — สองฟิลด์ที่อยู่คู่กันตลอดในโค้ด แต่ nullable ไม่เหมือนกัน

**6. ประวัติการศึกษาย้ายมาโดยไม่ต้องแก้อะไรเลย และนั่นเป็นเรื่องที่ควรเขียนไว้**

`PortfolioEducationResp` ทั้งสองฝั่งตรงกันทุกฟิลด์ รวมถึง `gpa` ที่เป็น `number`
ทั้งคู่ — ซึ่งไม่ได้บังเอิญ #16 เคยแก้ให้ service แปลง `Decimal` เป็นตัวเลขก่อน
ตอบไปแล้ว และเคสของมันก็ไล่ชื่อทุกคีย์อยู่ก่อนหน้ารอบนี้

เขียนไว้เพราะเป็น feature แรกของ #68 ที่ย้ายแล้วไม่เจอความต่างสักจุด กติกา
ไม่เปลี่ยน แต่คนอ่านที่เห็นแต่รอบที่เจอของจะได้รู้ว่ามีแบบนี้ด้วย

**7. `e-portfolio-template/types.ts` ไม่ใช่งานของ #68**

212 บรรทัดในนั้น — เกือบหนึ่งในสามของที่ e-Portfolio เหลือ — ไม่ใช่รูปที่ API
ตอบ แต่เป็น view model ของเทมเพลตที่ใช้เรนเดอร์ มี `portfolio-mapper.ts` เป็นคน
แปลงคำตอบจาก API มาเป็นรูปนี้อีกที ชื่อฟิลด์ก็คนละแบบ (`firstName`,
`profileImageUrl`, `contact`) ไม่ใช่ชื่อคอลัมน์

ADR-0028 กันของแบบนี้ออกไปตั้งแต่ต้นอยู่แล้ว ใบนี้เขียนไว้เพราะไฟล์อยู่ใน glob
ที่ใช้นับ คนที่เห็นตัวเลข "e-Portfolio เหลือ 696 บรรทัด" จะได้รู้ว่า 212 ในนั้น
ไม่มีวันลด และไม่ใช่งานค้าง

## ผลที่ตามมา

- เหลือสำเนาฝั่ง web **33 ไฟล์ 1,746 บรรทัด** (จาก 33 ไฟล์ 1,765 หลังรอบ
  lesson-plan) นับด้วย glob ชุดเดียวกับที่ ADR-0028 ประกาศไว้ — **ลดแค่ 19
  บรรทัดทั้งที่ย้ายสอง feature** เพราะทั้งสองไฟล์ยังถือ request body ไว้ จึงลบ
  ไม่ได้ตาม ADR-0039 ข้อ 6 และคอมเมนต์ที่บอกว่าของย้ายไปไหนก็กินบรรทัดคืน
  ตัวเลขบรรทัดจึงไม่ใช่มาตรวัดความคืบหน้าที่ดีในรอบท้าย ๆ ของ #68
- ในนั้น **14 ไฟล์ 696 บรรทัดยังเป็นของ e-Portfolio** ซึ่งเหลืออีกเจ็ด section
  กับรอบรวม
- API ไม่เพิ่มเคส (1,076) แต่รัดเคสเดิมสี่เคส: `POST /portfolio-personal` จาก
  `toMatchObject` สามฟิลด์ เป็น `toEqual` ทั้งวัตถุ และ `PUT` กับ upsert ทั้งสอง
  เคสได้ `not.toHaveProperty("attachments")` เพิ่ม เส้นเขียนทั้งสามจึงถูกปักครบ
  ไม่ใช่ปักเส้นเดียวแล้วให้อีกสองเส้นอาศัยคำพูดในใบนี้ (`DELETE` มีเคสปัก
  `data` เป็น null อยู่ก่อนแล้ว)
- ฝั่ง web ไม่เพิ่มไม่ลดเคส (448) แต่ fixture ของ `home-slice.test.ts` ต้องเขียน
  ครบทุกฟิลด์เป็นครั้งแรก — ของเดิมเขียนสามฟิลด์แล้วคอมไพล์ผ่าน เพราะ type ฝั่ง
  web ทำทุกอย่างนอกจาก `user_id` เป็น optional
- `npm run lint` ยังเท่าเดิมที่ 216 warning
- ไม่มีอะไรที่ผู้เรียกเห็นเปลี่ยน `BEHAVIOR-CHANGES.md` จึงไม่มีหัวข้อใหม่
