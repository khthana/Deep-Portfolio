# ADR-0007 — ใครสร้างกลุ่มได้ และใครอยู่ในกลุ่มได้

- **สถานะ**: ตัดสินแล้ว 10 สิงหาคม 2569
- **ที่มา**: [issue #37](https://github.com/khthana/Deep-Portfolio/issues/37)
- **เกี่ยวข้อง**: [ADR-0004](0004-group-leader.md) (การแก้รายชื่อกับการยุบกลุ่ม ซึ่ง
  ค้างสองข้อนี้ไว้ให้ไฟล์นี้), [ADR-0001](0001-portfolio-access.md) (ผู้กระทำคือ
  เจ้าของ session), [ADR-0003](0003-enrolment-access.md) (`student_course` คือคำตอบ
  ของ "อยู่ในกลุ่มเรียนนี้ไหม"), [ADR-0002](0002-section-access.md) (คำปฏิเสธไม่บอก
  ว่าอะไรมีอยู่จริง)

## บริบท

#27 ปิดฝั่ง `PATCH` กับ `DELETE` ไปแล้ว — เขียนรายชื่อได้เฉพาะ `LEADER` ของกลุ่ม
นั้น — แต่ ADR-0004 บันทึกไว้เองว่าเหลือสองช่องที่ยังเปิดอยู่ ทั้งสองช่องอยู่ที่
`POST` และ `PATCH` ของทั้ง `/student-activity-group` และ
`/student-learning-activity-group`

1. **`POST` ไม่ตรวจว่าผู้เรียกคือหัวหน้าที่ตัวเองระบุ** นักศึกษาสร้างกลุ่มโดยตั้ง
   คนอื่นเป็น `LEADER` แล้วไม่ใส่ตัวเองลงไปเลยก็ได้ กลุ่มนั้นจะเป็นของคนที่ไม่ได้
   ขอให้สร้าง และ (ตามกติกาข้อ 1 ของ ADR-0004) มีแต่คนนั้นที่แก้หรือยุบได้ ส่วน
   `created_by` ก็อ่านจากรายชื่อในคำขอ ไม่ใช่จาก session จึงไม่มีร่องรอยว่าใครสร้าง
2. **ทั้ง `POST` และ `PATCH` ไม่ตรวจว่าสมาชิกลงทะเบียนกลุ่มเรียนของชิ้นงานนั้น**
   ใส่รหัสนักศึกษาคนไหนก็ได้ในระบบ แล้วคนนั้นจะได้แถว `student_activity` (หรือ
   `student_learning_activity`) ของงานที่ไม่เคยถูกสั่งให้เขาทำ ค้างอยู่ในระบบ
   ต่อไปแม้จะถูกถอดออกจากกลุ่มแล้ว เพราะ ADR-0004 ตัดสินไว้ว่าแถวส่งงานไม่ถูกลบ
   ตามกลุ่ม ส่วนรหัสที่ไม่ใช่นักศึกษาเลยได้ `500` จาก foreign key ที่ล้มกลาง
   transaction

ทั้งสองข้อไม่ต้องใช้การเดา รหัสนักศึกษาเป็นเลข 8 หลักที่รู้กันอยู่แล้วในชั้นเรียน

## สิ่งที่ต้องตัดสิน

1. ผู้สร้างต้องเป็นหัวหน้าของรายชื่อที่ส่งมา หรือแค่ต้องอยู่ในรายชื่อก็พอ
2. คนนอกชั้นเรียนที่ถูกใส่มาในรายชื่อ ควรได้คำตอบเป็นอะไร และใช้กับ endpoint ไหนบ้าง

## การตัดสิน

### 1. ผู้สร้างต้องเป็น `LEADER` ของรายชื่อที่ตัวเองส่ง

> `POST` ของทั้งสอง router ปฏิเสธคำขอที่แถว `role = LEADER` ในรายชื่อไม่ใช่เจ้าของ
> session ตอบ `403` พร้อม
> `{ "success": false, "message": "สร้างกลุ่มได้เฉพาะกลุ่มที่ตัวเองเป็นหัวหน้าเท่านั้น" }`

"อยู่ในรายชื่อก็พอ" ถูกตัดทิ้งเพราะมันขัดกับ ADR-0004 โดยตรง สมาชิกที่ไม่ใช่หัวหน้า
แก้รายชื่อไม่ได้และยุบกลุ่มไม่ได้ ถ้าให้เขาสร้างได้ สิ่งเดียวที่เขาทำกับกลุ่มได้ก็คือ
สิ่งเดียวที่เขาถอนคืนเองไม่ได้ — ต้องไปขอให้คนที่เขาตั้งเป็นหัวหน้าจัดการให้

ผลข้างเคียงที่ยอมรับไว้อย่างตั้งใจคือ **"สร้างกลุ่มให้เพื่อนแล้วให้เพื่อนเป็นหัวหน้า"
ทำไม่ได้อีกต่อไป** ซึ่งเป็นกรณีใช้งานที่มีอยู่จริงในทางทฤษฎี แต่ `apps/web` ไม่เคย
ทำแบบนั้น — `create-groupwork-modal.tsx` ใส่คนที่ล็อกอินเป็น `LEADER` ให้เสมอ —
และทางที่หายไปจึงเป็นทางที่ต้องยิง API ตรงเท่านั้น ถ้าวันหนึ่งต้องมีจริง คำตอบคือ
endpoint "โอนหัวหน้า" ไม่ใช่การผ่อนกติกาตอนสร้าง

เป็น middleware `requireSelfLeader` อยู่ข้างกติกาของสี่ ADR ก่อนหน้าใน
`apps/api/src/middlewares/owner.middleware.ts` วางหลัง `validate` เหมือนกันหมด
คำขอที่ไม่มีหัวหน้าหรือมีสองหัวหน้าจึงเป็น `400` จาก `memberList` ก่อน (ADR-0004)
พอถึง middleware ตัวนี้จึงมีหัวหน้าหนึ่งคนพอดีเสมอ

### 2. คนนอกชั้นเรียนตอบ `400` ทั้ง `POST` และ `PATCH`

> ทุกคนในรายชื่อต้องมีแถวใน `student_course` ของ section ที่ชิ้นงานนั้นสังกัด ไม่ผ่าน
> ตอบ `400` พร้อม
> `{ "success": false, "message": "รายชื่อมีนักศึกษาที่ไม่ได้ลงทะเบียนกลุ่มเรียนนี้" }`
> ใช้กับ `POST` และ `PATCH` ของทั้งสอง router

**`400` ไม่ใช่ `403`** ด้วยเหตุผลชุดเดียวกับ `assertOwnRubric` ใน
`activity.service.ts` สิ่งที่ถูกปฏิเสธไม่ใช่สิทธิ์ของผู้เรียก — ผู้เรียกผ่านกติกา
ข้อ 1 มาแล้วและเป็นหัวหน้ากลุ่มจริง — แต่เป็น **ค่าในรายชื่อที่เขาส่งมา** ซึ่งเขา
แก้แล้วส่งใหม่ได้ `403` จะบอกว่าเขาไม่มีสิทธิ์ทำสิ่งนี้ ทั้งที่เขามี

**ตรวจทุกคนรวมทั้งหัวหน้า** ไม่ใช่แค่คนที่ถูกเพิ่มเข้ามา นี่คือสิ่งที่กันไม่ให้
นักศึกษานอกชั้นเรียนตั้งกลุ่มในชั้นเรียนที่ตัวเองไม่ได้ลงทะเบียน และเมื่อรวมกับ
กติกาข้อ 1 แปลว่า `POST` บังคับให้ผู้เรียกลงทะเบียน section นั้นด้วยโดยปริยาย
โดยไม่ต้องมีการตรวจแยกอีกชั้น

**รหัสที่ไม่ใช่นักศึกษาในระบบเลยตกในคำตอบเดียวกัน** ไม่มีใครลงทะเบียนด้วยรหัสที่ไม่มี
เจ้าของ เดิมกรณีนี้เป็น `500` จาก foreign key ตอนนี้เป็นประโยคภาษาไทยที่ frontend
แสดงได้ และ**ไม่บอกผู้เรียกว่ารหัสนั้นมีอยู่จริงหรือไม่** ตามเหตุผลของ ADR-0002

**ชิ้นงานที่ไม่สังกัด section ก็ตกในคำตอบเดียวกัน** `activities.section_id` เป็น
nullable ตาม baseline migration ที่รับมา (ฝั่ง `learning_activities` เป็น NOT NULL)
ไม่มี endpoint ไหนเขียน null ลงไป — `POST /activity` บังคับ `section_id` — และข้อมูล
จริงในฐานข้อมูลก็ไม่มีแถวแบบนั้น แต่ถ้ามีขึ้นมา ก็ไม่มีรายชื่อผู้ลงทะเบียนให้เทียบ
จึงปฏิเสธด้วยประโยคเดียวกัน ไม่ใช่ประโยคใหม่ที่บอกผู้เรียกว่าปัญหาอยู่ที่ตัวชิ้นงาน
มี test pin ไว้ทั้งที่ยังไปไม่ถึงผ่าน API

### ตรวจใน service ภายใน transaction ไม่ใช่ใน middleware

`assertMembersEnrolled` อยู่ใน `group.service.ts` ทั้งสอง service เรียกใช้ตัวเดียวกัน
รับ transaction client เข้าไปแล้วเรียกก่อนการเขียนแถวแรก เหตุผลเดียวกับที่ ADR-0001
ให้ไว้กับ `selectedSkillIds`: สิ่งที่ต้องตรวจคือ **รายการใน body** ไม่ใช่ตัวคำขอ และ
การตรวจกับการเขียนต้องอยู่ใน transaction เดียวกันเพื่อไม่ให้มีช่องว่างระหว่างกัน

ที่สำคัญกว่านั้นสำหรับ `PATCH`: service ลบสมาชิกทั้งกลุ่มทิ้งก่อนเขียนรายชื่อใหม่
การตรวจจึงต้องเกิดก่อนการลบ ไม่ใช่แค่ก่อน commit — ลำดับนี้คือสิ่งที่ทำให้คำขอที่ถูก
ปฏิเสธทิ้งกลุ่มไว้เหมือนเดิมทุกอย่าง และไม่มีแถวส่งงานของคนนอกค้างอยู่

## ผลที่ตามมา

- ผู้เรียกที่เคยได้ `200` หรือ `500` ตอนนี้ได้ `403` หรือ `400` ดู
  [`BEHAVIOR-CHANGES.md`](../../BEHAVIOR-CHANGES.md)
- สองข้อที่ ADR-0004 ค้างไว้ ("`POST` ยังไม่ตรวจว่าผู้เรียกคือหัวหน้าที่ตัวเองระบุ"
  และ "ยังไม่ตรวจว่าสมาชิกที่ระบุลงทะเบียนกลุ่มเรียนเดียวกับชิ้นงาน") ปิดแล้วทั้งคู่
- `apps/web` ไม่ต้องแก้ — modal ใส่ผู้ใช้ที่ล็อกอินเป็น `LEADER` ให้อยู่แล้ว และ
  รายชื่อที่เลือกได้มาจาก `/without-group` ซึ่งเป็นรายชื่อผู้ลงทะเบียน section นั้น
  อยู่แล้ว ทั้งสองประโยคที่เพิ่มมาเป็นภาษาไทยที่แสดงตรง ๆ ได้
- ข้อมูลจริงไม่ได้รับผลกระทบ ตอนตัดสิน (10 สิงหาคม 2569) `student_course`,
  `student_activity_group` และ `student_learning_activity_group` ยังว่างทั้งหมด
  จึงไม่มีกลุ่มเดิมที่กติกาใหม่จะทำให้แก้ไม่ได้
- **ยังไม่ดูสถานะการส่งงานเหมือนเดิม** ADR-0004 บันทึกไว้แล้วว่า `PATCH` และ
  `DELETE` ยอมให้ทำกับกลุ่มที่ `SUBMITTED` หรือ `GRADED` ได้ #37 ไม่ได้เปลี่ยนข้อนี้
  เพราะไม่ได้อยู่ในเกณฑ์ยอมรับ และการตัดสินยังต้องรวมถึงว่าอาจารย์แก้ได้ไหม
- **การถอนรายวิชาหลังตั้งกลุ่มแล้วยังไม่มีคำตอบ** กติกานี้ตรวจตอนเขียนรายชื่อเท่านั้น
  ถ้านักศึกษาถอน `student_course` ทีหลัง กลุ่มที่มีเขาอยู่ยังอยู่ต่อ และ `PATCH`
  ครั้งถัดไปจะปฏิเสธทั้งรายชื่อจนกว่าหัวหน้าจะถอดเขาออก นั่นคือพฤติกรรมที่ตั้งใจ —
  ระบบไม่ลบใครออกจากกลุ่มเงียบ ๆ แต่ก็ไม่ได้บอกหัวหน้าว่าทำไมถูกปฏิเสธเป็นรายคน

## จะกลับมาทบทวนเมื่อไหร่

เมื่อมีชิ้นงานข้าม section จริง — งานที่หลายกลุ่มเรียนทำร่วมกัน — กติกาข้อ 2 จะเลิก
เป็น "section เดียว" และต้องกลายเป็น "section ใดก็ได้ที่ชิ้นงานนี้ประกาศให้"
`assertMembersEnrolled` เป็นที่เดียวที่ต้องแก้ หรือเมื่อมี endpoint โอนหัวหน้า ซึ่ง
จะทำให้ผลข้างเคียงที่ตัดทิ้งไปในข้อ 1 กลับมาได้โดยไม่ต้องผ่อนกติกาตอนสร้าง
