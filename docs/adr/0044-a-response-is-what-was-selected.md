# ADR-0044 — response คือสิ่งที่ `select` ไว้ ไม่ใช่สิ่งที่ตารางมี

- **สถานะ**: ตัดสินใจแล้ว
- **วันที่**: 2026-08-22
- **บริบท**: [#68](https://github.com/khthana/Deep-Portfolio/issues/68) รอบที่สิบหก
  — `/user` กับเส้น `/auth` ที่ตอบเป็นรูป
- **ต่อจาก**: [ADR-0043](0043-the-aggregate-imports-nine.md) ที่ย้าย
  `StudentDetail` ไปก่อนครึ่งหนึ่งแล้ว, [ADR-0038](0038-a-factory-must-be-able-to-say-null.md)
  ที่วางกติกาเรื่อง `??` ใน factory

## บริบท

รอบก่อนย้าย `StudentDetail` เข้า package ล่วงหน้า เพราะ
`GET /portfolio/public/:token` ฝังมันไว้เป็น `userData` (ADR-0043 ข้อ 3) รอบนี้คือ
การกลับมาเก็บส่วนที่เหลือของ feature ที่เป็นเจ้าของมัน

คำถามว่า "ผู้เรียกคือใคร" มีสองเส้นตอบ และไม่มีเส้นไหนเป็นตัวย่อของอีกเส้น

- `GET /user?id=` ตอบแถวของตาราง `users` ให้หน้าโปรไฟล์ `requireSelf`
  ปฏิเสธ id ของคนอื่น (#40)
- `GET /auth` ตอบสี่อย่างที่แอปต้องรู้ก่อนจะวาดอะไรได้ — คุณคือใคร เรียกคุณว่า
  อะไร และคุณทำอะไรได้ ไม่รับ id เลย เพราะ session คือคำถาม

เส้นที่สามคือ `GET /user/student` ซึ่ง `StudentDetail` ของมันย้ายไปแล้ว

## สิ่งที่พบเมื่อเปิดอ่าน

`getUserDetail` เขียนไว้ว่า

```ts
const result = await prisma.users.findUnique({ where: { user_id: userId } });
return result;
```

`findUnique` ที่ไม่มี `select` คืนทุกคอลัมน์ที่เป็น scalar ของตาราง ซึ่งแปลว่า
`GET /user` ตอบ **สิบเจ็ดคีย์** ไม่ใช่สิบสาม สี่คีย์ที่เกินมาคือ `password`,
`verification_token`, `is_verified` และ `status` — ผู้ใช้ที่เปิดหน้าโปรไฟล์ตัวเอง
ได้รับ hash รหัสผ่านของตัวเองและ token ยืนยันตัวตนของตัวเองกลับไปด้วย

ไม่มีใครเห็นเรื่องนี้เพราะไม่มีที่ไหนเขียนไว้ว่าเส้นนี้ตอบอะไร: ฝั่ง API ไม่มี
return type ส่วนฝั่ง web เขียน `UserResp` ที่บอกสิบสามคีย์พอดี — คือคนที่เขียน
ฝั่ง web เขียนถูก แล้วก็ไม่มีทางรู้ว่าที่ได้รับจริงมีมากกว่านั้น

ส่วน `GET /auth` ไม่มีชื่อทั้งสองฝั่ง `use-auth.ts` เรียก `axiosInstance.get`
โดยไม่ใส่ argument แล้วเก็บผลไว้ใน `userData: any`

## การตัดสินใจ

### 1. `select` ทุกคอลัมน์ที่ตั้งใจจะตอบ และตอบเท่านั้น

`getUserDetail` ได้ `select` ของสิบสามคอลัมน์ที่ `UserResp` เคยประกาศไว้ ไม่มี
หน้าจอไหนเคยอ่านสี่คีย์ที่เกินมา การตัดจึงไม่ทำให้ caller ไหนพัง แต่ยังเป็นการ
เปลี่ยนสิ่งที่ caller เห็น จึงบันทึกลง `BEHAVIOR-CHANGES.md` ตาม D9

**กติกาที่ตามมา**: `findUnique`/`findMany` ที่ไม่มี `select` ไม่ใช่การตัดสินใจว่า
จะตอบทุกคอลัมน์ มันคือการไม่ได้ตัดสินใจ รอบของ #68 ที่เดินไปเจอ query แบบนี้บน
เส้นที่ตัวเองกำลังตั้งชื่อ ให้ `select` ให้ครบตามรูปที่เขียน — เพราะรูปที่เขียนคือ
คำสัญญา และ query ที่ไม่จำกัดตัวเองจะผิดคำสัญญาทุกครั้งที่มีคนเพิ่มคอลัมน์

รอบนี้ปักด้วยเคสที่เทียบ `Object.keys(...).sort()` กับสิบสามคีย์ ไม่ใช่
`toMatchObject` — เคสเดิมใช้ `toMatchObject` ซึ่งผ่านทั้งที่มีสิบเจ็ดคีย์

### 2. สองเส้นที่ตอบว่า "ผู้เรียกคือใคร" คือสองรูป

`SessionUser` ไม่ใช่ `UserDetail` ที่ตัดคอลัมน์ออก สองในสี่ฟิลด์ของมันไม่ใช่
คอลัมน์เลย — `name` คือสามคอลัมน์ต่อกัน และ `roles` คือการ lookup ผ่าน
`user_roles` การเขียนเป็น `Pick<UserDetail, …>` จึงเป็นไปไม่ได้ และการเขียนเป็น
`UserDetail & { name; roles }` จะโกหกว่าเส้นนี้ตอบคอลัมน์อื่นด้วย

นี่คือด้านกลับของ ADR-0035 ที่ยุบสองเส้นเป็นหนึ่งรูปเพราะมันตอบเหมือนกันทุกฟิลด์
กติกาเดียวกัน อ่านจากสิ่งที่ตอบจริง ไม่ใช่จากชื่อ feature

### 3. controller ที่เขียน envelope เองไม่ได้ผูกกับ envelope

ทั้งสอง handler ใน `user.controller.ts` เขียน `res.status(200).json({success,
message, data})` ด้วยมือ แทนที่จะเรียก `successResponse` ผลลัพธ์เป็น JSON ก้อน
เดียวกันเป๊ะ แต่ `successResponse` มี `satisfies ApiResponse<T>` อยู่ข้างใน ซึ่ง
เป็นเส้นที่ ADR-0028 ข้อ 2 บอกว่าเป็นตัวยึด envelope ไว้กับ package ส่วนก้อนที่
เขียนมือไม่มีอะไรยึด

เปลี่ยนมาใช้ `successResponse` ทั้งสองที่ ไม่มี byte ไหนของ response ขยับ

**กติกาที่ตามมา**: รอบของ #68 ที่เปิด controller ของ feature ตัวเองแล้วเจอ
envelope เขียนมือ ให้เปลี่ยนเป็น `successResponse`/`errorResponse` — มันคือ
`any` ในเวอร์ชันของ envelope

### 4. null ที่อยู่ในลิสต์ ยังอยู่ในลิสต์

`user_roles.role_id` เป็น nullable ดังนั้น `roles` ที่ `GET /auth` ตอบคือ
`(string | null)[]` ไม่ใช่ `string[]` แถวที่ `role_id` เป็น null คือแถวที่ไม่ได้
มอบ role ให้ใคร

ไม่กรองทิ้ง เพราะการลบสมาชิกออกจาก array ที่ตอบไปคือการเปลี่ยนสิ่งที่ caller เห็น
และรอบนี้ไม่มีเหตุผลจะเปลี่ยน — guard ทุกตัวเทียบกับ `"TEACHER"` และ `"STUDENT"`
null จึงไม่มีวันตรงอยู่แล้ว สิ่งที่ทำคือขยาย state ฝั่ง web ให้พูดความจริง
(`useState<SessionUser["roles"]>`) แทนที่จะบังคับให้เป็น `string[]`

**กติกาที่ตามมา**: รอบของ #68 ขยาย type ให้ตรงกับสิ่งที่ตอบ ไม่ใช่แก้สิ่งที่ตอบ
ให้ตรงกับ type ที่สวยกว่า เว้นแต่สิ่งที่ตอบนั้นผิดจนผู้ใช้เห็น (ซึ่งข้อ 5 คือ
ตัวอย่าง)

### 5. template literal คร่อมคอลัมน์ nullable คือ bug ที่ type ไม่ทัก

`name` เคยเขียนว่า

```ts
name: `${user.title_th} ${user.first_name_th} ${user.last_name_th}`;
```

ทั้งสามคอลัมน์ nullable และ template literal เขียนตัวอักษรสี่ตัว `null` ลงไปใน
สตริงสำหรับทุกตัวที่ว่าง ผู้ใช้ที่ไม่มีคำนำหน้าจะได้ชื่อว่า `"null สมชาย ใจดี"`
ซึ่ง navbar ฝั่งอาจารย์เอาไปวาด และ `cleanNullStr` ฝั่ง web ก็ช่วยไม่ได้ เพราะมัน
แทนที่เฉพาะค่าที่**เป็น** `"null"` ทั้งตัว ไม่ใช่ค่าที่**มี** `"null"` อยู่ข้างใน

`.filter(Boolean).join(" ")` แทน ผลลัพธ์สำหรับแถวที่กรอกครบเหมือนเดิมทุกตัวอักษร

**กติกาที่ตามมา**: คอมไพเลอร์ไม่เคยทัก template literal ที่คร่อมค่า nullable
เพราะมันแปลงเป็น string ได้เสมอ รอบของ #68 ที่ตั้งชื่อ field ที่ประกอบขึ้นมาแบบนี้
ต้องอ่านว่ามันประกอบจากอะไร ไม่ใช่แค่ประกาศว่ามันเป็น `string`

### 6. `??` ใน factory ที่เก่าที่สุด

เคสของข้อ 5 ต้องการ user ที่ `title_th` เป็น null แต่ `createUser` เขียนว่า
`title_th: options.title_th ?? "อ."` ซึ่งเปลี่ยน null กลับเป็นค่า default ทันที
นี่คือกับดักเดียวกับที่ ADR-0038 ตั้งชื่อไว้ในรอบ course-material เพียงแต่คราวนี้
อยู่ใน factory ที่เก่ากว่า ADR ใบนั้น

ขยายตามกติกาเดิม: เจ็ดฟิลด์ที่คอลัมน์รับ null ได้ — คำนำหน้ากับชื่อ-นามสกุลทั้ง
ไทยและอังกฤษหกตัว บวก `phone` — รับ `string | null` และเปลี่ยน `??` เป็น
`=== undefined` ส่วน `email` ยังเป็น `??` เพราะคอลัมน์มัน `@unique` และไม่รับ null

`createStudent` ต่างออกไปตรงที่มันเขียนชื่อไทยลง `student` ด้วย และคอลัมน์ทั้งสอง
ตรงนั้น **ไม่** รับ null `StudentOptions` จึงประกาศสองตัวนี้ทับกลับเป็น `string`
— เคสที่อยากได้นักศึกษาไม่มีชื่อ คือเคสที่พูดถึงแถวที่ฐานข้อมูลไม่ยอมเก็บ

### 7. bug เดียวกันที่อยู่ถัดไปสองย่อหน้า ก็เป็นของรอบนี้

`course.service.ts` ประกอบ `teacher_name_th` กับ `teacher_name_en` ด้วย template
literal คร่อมคอลัมน์ nullable หกตัว แบบเดียวกับข้อ 5 เป๊ะ — อาจารย์ที่ไม่มีคำนำหน้า
ออกมาเป็น `"null สมชาย ใจดี"` บนหน้ารายวิชา ซึ่งเป็นหน้าที่เปิดได้โดยไม่ต้อง log in

response ของ course ย้ายเข้า package ไปตั้งแต่รอบนำร่องแล้ว รอบนี้จึงไม่ได้ย้าย
type อะไรของมัน แต่รอบนี้ **เปิดไฟล์นั้นอ่าน** — `getUserDetail` ที่รอบนี้ใส่
`select` ให้ ถูกเรียกจากตรงนั้น และ ADR ฉบับนี้เองก็อ้างว่า "อ่านเก้าในสิบสามฟิลด์"
ซึ่งแปลว่าอ่านบรรทัดที่มี bug ไปแล้ว

**กติกาที่ตามมา**: ขอบเขตของรอบคือ feature ที่กำลังย้าย แต่ D9 ไม่ได้ผูกกับขอบเขต
— มันผูกกับ "เจอ" ถ้ารอบหนึ่งเปิดโค้ดของ feature อื่นอ่านจนอ้างอิงได้ ก็เจอแล้ว
และของเสียที่เจอต้องแก้หรือ pin ไม่ใช่ปล่อยไว้เพราะคนละ feature

แก้ด้วย `joinName` ตัวเดียวที่ใช้ทั้งสองชื่อ และเคสใหม่ใน `course.test.ts` ปักไว้
`null` ยังแปลว่า "ไม่มีอาจารย์" เหมือนเดิม ซึ่งเป็นสิ่งที่ caller เช็ค

### 8. `/auth` เข้ามาในรอบนี้เพราะถูกสั่ง ไม่ใช่เพราะเป็น feature เดียวกัน

#68 บอกว่าทำทีละ feature หนึ่ง PR ต่อหนึ่ง feature และ `/auth` เป็น router คนละตัว
ที่มี google login, logout และ refresh อยู่ด้วย ข้อ 2 ข้างบนยังบอกเองว่าสองเส้นนี้
ตอบคนละรูป ซึ่งเป็นเหตุผลที่จะ**แยก** ไม่ใช่ที่จะรวม

สิ่งที่ทำให้รวมได้คือการตัดสินใจของเจ้าของงานตอนเริ่มรอบ ไม่ใช่ข้อสรุปทางเทคนิค
และเหตุผลที่รับได้คือ `GET /auth` เป็นเส้นเดียวของ router นั้นที่ตอบเป็นรูป และรูป
นั้นก็อ่านมาจากตาราง `users` ตัวเดียวกัน สามเส้นที่เหลือของ `/auth` ยังไม่ได้แตะ

**กติกาที่ตามมา**: รอบที่กินเกินหนึ่ง router ให้เขียนใน ADR ว่าใครตัดสินและตัดสิน
ด้วยเหตุผลอะไร อย่าเขียนย้อนหลังให้เหมือนว่ามันเป็น feature เดียวกันมาแต่แรก

## สิ่งที่ pin ไว้ ไม่ได้แก้

`created_at` และ `updated_at` ที่ออกจากเส้นนี้ **ล้ำหน้าเวลาจริงไปเจ็ดชั่วโมง**
คอลัมน์เป็น `timestamp` ที่ไม่มี zone และ default ของมันคือ
`CURRENT_TIMESTAMP AT TIME ZONE 'Asia/Bangkok'` — Postgres จึงเก็บเวลาท้องถิ่น
กรุงเทพลงไปในคอลัมน์ที่ไม่มีป้ายบอกโซน แล้ว Prisma อ่านกลับมาเป็นเวลาเดียวกันนั้น
โดยถือว่าเป็น UTC

วัดจริงแล้วได้ `7.000004` ชั่วโมง ซึ่งเป็นเคสที่รอบนี้เพิ่มเข้าไปเพื่อปักไว้

ไม่แก้เพราะ default ตัวนี้อยู่บน **27 คอลัมน์** ทั่ว schema การแก้คือ migration
บวกกับการตัดสินใจว่าค่าที่เก็บไว้แล้วทั้งหมดหมายถึงอะไร ซึ่งใหญ่กว่า ticket นี้
และเป็นการตัดสินใจของคนอื่น ตามกติกาใน CLAUDE.md หัวข้อ "Behaviour changes"

## สิ่งที่รอบนี้ไม่ทำ

- **ไม่แตะสามเส้นที่เหลือของ `/auth`** `POST /auth/google`, `/logout` และ
  `/refresh` ตอบ `data: null` หรือไม่มี body เลย สิ่งที่มันส่งกลับจริง ๆ คือ cookie
  สองใบ ซึ่งไม่มี response type ไหนอธิบายได้
- **ไม่ย้าย type ของ `course.service.ts`** มันเรียก `getUserDetail` มาหาชื่อ
  อาจารย์ อ่านเก้าในสิบสามฟิลด์ และไม่เคยส่งแถวต่อไปทั้งแถว การ `select` จึงไม่
  กระทบมัน — response ของ course ย้ายไป package ตั้งแต่รอบนำร่องแล้ว สิ่งที่
  รอบนี้แตะในไฟล์นั้นคือ bug ของข้อ 5 ที่อยู่ตรงนั้นด้วย ดูข้อ 7
- **ไม่ยุบ `/user` กับ `/user/student` เข้าด้วยกัน** สองเส้นนี้ตอบคนละรูปให้คนละ
  หน้าจอ และเส้นหลังยังรวมสี่ตารางเข้าด้วยกัน การรวมเป็นการออกแบบ API ใหม่
