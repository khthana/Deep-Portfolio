# ADR-0047 — แคบลงเท่าที่การ์ดอ่าน และเส้นเขียนไม่ใช่เส้นอ่าน

- **สถานะ**: ตัดสินใจแล้ว
- **วันที่**: 2026-08-22
- **บริบท**: [#68](https://github.com/khthana/Deep-Portfolio/issues/68) รอบที่สิบเก้า
  และรอบสุดท้าย — `/mapping/activity` กับ `/mapping/learning-activity` ซึ่งเป็น
  สองครึ่งของหน้าจอผูกกิจกรรมเข้ากับ CLO
- **ต่อจาก**: [ADR-0044](0044-a-response-is-what-was-selected.md) ข้อ 1 เรื่อง
  query ที่ไม่มี `select`, [ADR-0046](0046-a-select-that-narrows-nothing.md) ข้อ 1
  ที่บอกว่ากติกานั้นใช้แม้ตอนที่ไม่มีอะไรให้ตัด,
  [ADR-0045](0045-one-service-many-screens.md) ข้อ 1 เรื่องหน่วยของหนึ่งรอบ และ
  [ADR-0036](0036-a-bare-scalar-gets-no-name.md) ที่ลากเส้นว่าอะไรได้ชื่อและอะไร
  ไม่ได้

## บริบท

รอบสุดท้ายของ #68 มีสอง service คนละไฟล์ ที่ป้อนหน้าจอเดียวกัน — คอลัมน์กลางของ
หน้าผูก CLO เป็นกิจกรรมการประเมิน คอลัมน์ขวาเป็นกิจกรรมการเรียนรู้ และทั้งสอง
คอลัมน์วาดการ์ดใบเล็ก ๆ ที่มีชื่อกับคำอธิบาย

ADR-0045 ข้อ 1 บอกว่าหน่วยของหนึ่งรอบคือ service ไม่ใช่หน้าจอ ซึ่งอ่านตรง ๆ แล้ว
รอบนี้ควรเป็นสองรอบ แต่ ADR-0034 บอกอีกทางว่าสอง feature ที่ใช้รูปร่วมกันควรเดิน
พร้อมกัน รอบนี้ไม่เข้าทั้งสองข้อ: สอง service นี้ไม่ได้ใช้รูปร่วมกันเลยสักตัว
(สิ่งที่ตอบต่างกันทั้งจำนวนคอลัมน์และความหมาย) แต่ก็ไม่ได้แยกจากกันจริง เพราะ
`mapping-type.type.ts` ไฟล์เดียวถือ type ของทั้งคู่ และ `mapping-section.tsx`
ตัวเดียวยิงทั้งสองเส้น การแยกเป็นสองรอบจะได้ผลลัพธ์คือไฟล์ฝั่ง web ไฟล์เดียวถูก
เขียนสองครั้ง โดยครั้งแรกทิ้ง type ครึ่งเดียวไว้

**กติกาที่ตามมา**: เกณฑ์ของ ADR-0045 ข้อ 1 คือ "อะไรจะถูกเขียนสองครั้งถ้าแยก" ไม่ใช่
"มีกี่ service" — service เป็นคำตอบที่ถูกในกรณีของมัน เพราะ `/student` มี service
เดียว การนับ service จึงตอบคำถามนั้นได้พอดี ที่นี่คำตอบคือไฟล์ type ฝั่ง web และ
มันมีไฟล์เดียว

## การตัดสินใจ

### 1. เส้นที่ไม่มี `select` แล้วมีผู้อ่านคนเดียว ให้แคบลงเท่าที่ผู้อ่านอ่าน

ทั้งสอง `getActivity` และ `getLearningActivity` อ่านตารางกิจกรรมด้วย `findUnique`
ที่ไม่มี `select` แล้วส่งทั้งแถวออกไป — สิบหกคอลัมน์ของ `activities` (บวก
`level_no` กับ `weight`) และสิบคอลัมน์ของ `learning_activities`

การ์ดที่รับไปอ่านห้าฟิลด์กับสองฟิลด์ตามลำดับ ที่เหลือไม่มีใครแตะ ไล่แล้วทุกเส้นทาง:
`mapping-section.tsx` เก็บลง `useState` ของตัวเอง ไม่ผ่าน slice (slice ของ feature
นี้ถือแต่ธง loading) แล้วส่งต่อไปที่ section → card ทางเดียว ไม่มีสาขาอื่น

`select` จึงเหลือสี่คอลัมน์กับสามคอลัมน์ ตามที่ ADR-0044 ข้อ 1 บอกว่าเป็นหนี้ของรอบ
และ ADR-0046 ข้อ 1 ย้ำว่าเป็นหนี้แม้ตอนที่ตัดอะไรไม่ได้เลย — รอบนี้เป็นด้านตรงข้าม
ของ ADR-0046 พอดี ที่นั่นตารางกับ type ตรงกันอยู่แล้วและ `select` ไม่ขยับ body
สักไบต์ ที่นี่มันตัดสิบสองคอลัมน์กับเจ็ดคอลัมน์ทิ้ง

เส้นที่สามของ router นี้ก็ติดหนี้ก้อนเดียวกัน แม้จะไม่ได้ตอบรูปอะไรเลย:
`validateActivityCLOMapping` ตอบ `boolean` เปล่า ๆ ซึ่ง ADR-0036 บอกว่าไม่ต้อง
ตั้งชื่อให้ แต่ ADR-0046 ข้อ 1 พูดถึง query ไม่ใช่ชื่อ — `findMany` ที่ไม่มี
`select` อ่านสิบคอลัมน์ของทุกแถวมาเพื่อถามว่า "มีสักแถวไหม" ตอนนี้ `select`
คอลัมน์เดียว การไม่มีชื่อจึงไม่ได้แปลว่าไม่มีหนี้

หลักฐานว่าไม่มีใครเคยเลือกชุดเดิม อยู่ในคอลัมน์ที่หายไปตัวหนึ่ง: `activity_type`
เส้นนี้ส่งค่าดิบจากคอลัมน์ ซึ่ง `activities` เก็บเป็นตัวพิมพ์เล็ก ส่วน
`GET /activity` แปลงเป็นตัวพิมพ์ใหญ่ก่อนตอบ (ADR-0037 บอกว่า package สะกดตามที่
ค่าออกจาก API ไม่ใช่ตามที่คอลัมน์เก็บ) ฝั่ง web ประกาศคีย์นี้เป็น `activityType`
ซึ่งมีแค่ `"INDIVIDUAL" | "GROUP"` มาตลอด ผิดมาตลอด และไม่มีใครสังเกต เพราะไม่มี
ใครอ่าน

### 2. `id` ที่ไม่มีใครอ่าน กับ `key` prop ที่หายไป เป็นเรื่องเดียวกัน

`select` ที่แคบตามข้อ 1 อย่างเคร่งครัดจะไม่มี `id` เลย เพราะการ์ดทั้งสองใบไม่ได้
อ่านมัน

แต่ที่ไม่ได้อ่านเพราะทั้งสอง section วาดการ์ดด้วย `.map()` ที่ไม่มี `key` prop —
`eslint.config.js` ฝั่ง web มี `eslint-plugin-react-hooks` กับ
`eslint-plugin-react-refresh` แต่ไม่มี `eslint-plugin-react` ซึ่งเป็นเจ้าของกฎ
`react/jsx-key` จึงไม่มีอะไรทักตอน lint และ React ทักในคอนโซลเท่านั้น
เป็นข้อบกพร่องที่รอบนี้เดินชนตาม D9 ไม่ใช่ข้อที่ #68 สั่ง แก้ที่นี่แล้วสองบรรทัด
และ `id` อยู่ใน `select` เพราะเป็นสิ่งที่ `key` ต้องใช้

เขียนไว้เพราะถ้าไม่เขียน คนอ่าน `select` รอบหน้าจะเห็น `id` ที่ไม่มีใครอ่านและคิดว่า
เป็นเศษที่ลืมตัดออก

### 3. `select` ที่หายไปจาก query กับ response ของ create เป็นคนละคำถาม

ทั้งสอง POST ตอบแถวที่เพิ่งสร้างทั้งแถว — สิบคีย์และหกคีย์ — ส่วนฝั่ง web ประกาศไว้
ว่า `{ id: number }` และอ่านแค่ว่า body มาถึงหรือไม่ ก่อนจะ fetch ใหม่ทั้งรายการ

ที่แก้คือฝั่งที่ผิด: `ActivityCLOMapping` กับ `LearningActivityCLOMapping` เข้า
package โดยเขียนแถวจริงลงไป ส่วน API ไม่ขยับ

ต่างจากข้อ 1 ตรงที่ข้อ 1 เป็นการเติมสิ่งที่ขาด — `select` ที่ไม่เคยมี — ส่วนการหด
response ของ create ให้เหลือ `id` เป็นการออกแบบใหม่ให้เส้นที่ทำงานอยู่ ไม่มีผู้อ่าน
คนไหนร้องขอ และหน้าที่ของรอบ #68 คือเขียนสิ่งที่ API ตอบลงไป ไม่ใช่เลือกว่ามันควร
ตอบอะไร กติกาข้อ 1 ไม่ยืดไปถึงตรงนี้ เพราะที่นั่นการเปลี่ยนแปลงเกิดจากการเขียนรูป
ลง type แล้วพบว่า query ไม่เคยตัดสินใจ ที่นี่ query ตัดสินใจไปแล้วว่าจะตอบแถวที่สร้าง

ทั้งสองชื่อได้ที่ยืนตาม ADR-0036: มันเป็น object ที่ผู้อ่านต้องรู้คีย์ถึงจะหยิบค่าออก
ได้ ไม่ใช่ตัวเลขเปล่า

### 4. FK ที่มีจริง ทำให้ `findUnique` กลายเป็น `findUniqueOrThrow` ได้

ทั้งสอง query เดิมเป็น `findUnique` ที่ตอบ `T | null` ครึ่ง activity เอาไป spread
(`{...null}` คือ `{}` เงียบ ๆ) ครึ่ง learning activity คืน `null` ตรง ๆ ลง array
ทั้งสองอย่างเป็นรูปที่เขียนลง package ไม่ได้ถ้าไม่โกหก

`null` นั้นไปไม่ถึงจริง และไม่ได้เดาเอาจากชื่อ relation: migration แรกสร้าง
`fk_activity_clo_mapping_activity_id` และ `fk_learning_activity_clo_mapping_activity_id`
เป็น foreign key จริงทั้งคู่ พร้อม `ON DELETE CASCADE` แถว mapping จึงอยู่ต่อจาก
กิจกรรมที่มันชี้ไม่ได้ และเคส "fails for a learning activity that does not exist"
ใน `clo-mapping.test.ts` ก็ยืนยันอีกทางว่า FK บังคับใช้จริง

`findUniqueOrThrow` จึงเป็นคำที่ตรงกว่า: มันบอกว่าแถวอยู่ที่นั่นเสมอ และถ้าวันหนึ่ง
ไม่อยู่ เส้นนี้จะดังแทนที่จะตอบครึ่งเดียว

## สิ่งที่ไม่ได้ทำ

- **ไม่ได้ทำให้ `GET` ทั้งสองเส้นต้องล็อกอิน** route ของทั้งคู่มีแต่ `validate`
  ส่วน `POST` มี `requireRole("TEACHER")` คอมเมนต์ในเทสต์เคยอธิบายไว้ว่าเป็นเพราะ
  "หน้าผลการเรียนรู้ของนักศึกษาอ่านเส้นนี้" ซึ่งไม่จริง — ตาราง CLO บนหน้ารายวิชา
  ของนักศึกษาอ่าน `GET /course/clo` และผู้เรียกเดียวของสองเส้นนี้คือหน้าจอของ
  อาจารย์ รอบนี้แก้คอมเมนต์ให้ตรง แต่การจะเติม middleware หรือไม่เป็นคำถาม
  เดียวกับที่ #41 เคยตอบให้เส้นของ `/student` และไม่ใช่คำถามของรอบย้าย type
- **ไม่ได้ตั้งชื่อ response ของ `validateActivityCLOMapping`** มันตอบ `boolean`
  เปล่า ๆ ซึ่ง ADR-0036 บอกไว้แล้วว่าไม่ต้องมีชื่อ `ResponseWrapper<boolean>`
  พูดครบทุกอย่างที่ชื่อจะพูดได้ ส่วน `select` ที่มันขาดอยู่ ข้อ 1 เติมให้แล้ว
- **ไม่ได้รวม `generateHTML(... as JSONContent)` เป็น helper ตัวเดียว** ตอนนี้มี
  สามที่ — การ์ดสองใบของรอบนี้ กับ `announcement-card.tsx` ที่ทำแบบเดียวกันมาก่อน
  — แต่การเขียน helper ให้ทั้งสาม feature ใช้ร่วมกันเป็นงานของฝั่ง web ไม่ใช่ของ
  รอบย้าย type รอบนี้ทำแค่ให้คอมเมนต์ที่อธิบายการแคบ `unknown` มีอยู่จริงหนึ่งที่
  และอีกใบชี้มาที่มัน
- **ไม่มีรายการของ `key` prop ใน `BEHAVIOR-CHANGES.md` เป็นหัวข้อของตัวเอง** มัน
  อยู่ในช่อง "เหตุผล" ของข้อ 1 เพราะเป็นเหตุผลที่ `id` อยู่ใน `select` การไม่มี
  `key` ไม่เปลี่ยนสิ่งที่ผู้ใช้เห็น: ทั้งสองรายการถูกแทนที่ทั้งก้อนทุกครั้งที่
  fetch ไม่มีการสลับลำดับหรือแทรกกลางรายการที่ React จะ reconcile ผิด
- **ไม่ได้แตะ `activity_clo_mapping.detail`** เป็น `String?` ที่ไม่มีอะไรในระบบเขียน
  แต่มันอยู่ในแถวที่ create ตอบกลับ จึงถูกเขียนลง `ActivityCLOMapping` ตามที่เป็น
  พร้อมประโยคบอกว่าไม่มีใครเขียนมัน

## รูปที่ยังเขียนคาไว้ใน generic — สิ่งที่ #68 ปิดโดยไม่ได้ปิด

รอบนี้เจอ `ResponseWrapper<{ id: number }>` บน POST ทั้งสองเส้นของตัวเอง และแก้
ตามข้อ 3 แต่หลังจากนั้นนับทั้ง `apps/web/src` แล้วเจอโครงเดียวกันอีก **20 จุด**:

- `ResponseWrapper<{ id: number }>` — `POST`/`PUT`/`DELETE /activity`,
  `POST`/`PUT /learning-activity` และ `POST /course/clo`
- `ResponseWrapper<{ clo_id: number }>` — `PUT`/`DELETE /course/clo`
- `ResponseWrapper<{ is_bookmark: boolean }>` — เส้น bookmark ของทั้งสอง feature

ทุกจุดอยู่ในไฟล์ `*.service.ts` กับ `*-action.ts` ซึ่งอยู่**นอก** glob ที่
ADR-0028 ประกาศไว้ (`types/*.ts` และ `types.ts`) จึงไม่เคยอยู่ในจำนวนไฟล์ที่ #68
นับ และ #68 ปิดได้โดยไม่ต้องแตะมัน

อย่างน้อยชุด `/activity` ผิดแบบเดียวกับที่รอบนี้เพิ่งแก้: `createActivity` คืน
`tx.activities.create({ data })` และ `deleteActivity` คืน
`tx.activities.delete({ where })` — ทั้งคู่ไม่มี `select` จึงตอบสิบหกคอลัมน์
ให้ generic ที่ประกาศไว้ว่าคีย์เดียว

ไม่แก้ในรอบนี้ เพราะแต่ละจุดต้องเปิด service ของ feature ตัวเองเพื่อดูว่าตอบอะไร
จริง ซึ่งเป็นงานเท่ากับอีกหลายรอบ และเป็นคนละหน่วยกับ "หนึ่ง feature หนึ่งรอบ"
ที่ #68 ทำมาสิบเก้ารอบ บันทึกไว้ตรงนี้เพราะทุกบรรทัดในนั้นเป็นบรรทัดที่
[#67](https://github.com/khthana/Deep-Portfolio/issues/67) ต้องเขียนใหม่อยู่แล้ว
ตอนเปลี่ยน `ResponseWrapper` เป็น `ApiResponse` — คนที่ทำ #67 จะอ่าน `T` ทุกตัว
ผ่านตาอยู่ดี ส่วนจะให้ #67 รับงานนี้ไปด้วยหรือแยกเป็น ticket ใหม่ เป็นการตัดสินใจ
ที่ยังไม่ได้ทำ
