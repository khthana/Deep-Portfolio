# ADR-0001 — ใครเข้าถึง e-Portfolio ของใครได้

- **สถานะ**: ตัดสินแล้ว 10 สิงหาคม 2569
- **ที่มา**: [issue #31](https://github.com/khthana/Deep-Portfolio/issues/31)
- **เกี่ยวข้อง**: [#30](https://github.com/khthana/Deep-Portfolio/issues/30)
  (อาจารย์กับ section ที่ตัวเองสอน), D3 ของ
  [spec](../spec-refactor-redeploy.md#d3--การยืนยันตัวตน)

## บริบท

กลุ่ม `portfolio_*` ทั้งกลุ่ม — 10 router 56 endpoint — ไม่มี middleware ตรวจสิทธิ์
แม้แต่ตัวเดียว ทุก endpoint รับ `user_id` ของคนที่จะกระทำการแทนมาจาก query string
หรือ body ไม่ได้อ่านจาก session เลย ใครที่ยิง HTTP ได้โดยไม่ต้องล็อกอินจึงอ่าน
วันเกิด เบอร์โทร และอีเมลของนักศึกษาคนใดก็ได้ แก้หรือลบประวัติของคนอื่นได้ และ
ออก share link สาธารณะให้แฟ้มของคนอื่นได้ — และ `user_id` คือรหัสนักศึกษา 8 หลัก
ที่เดาได้

`requireRole` ที่มีอยู่แล้วปิดช่องนี้ไม่ได้ เพราะกฎที่ถูกไม่ใช่ "ต้องเป็นนักศึกษา"
แต่เป็น "ต้องเป็นเจ้าของแถว" ซึ่งเป็นคนละคำถามกับที่ middleware เดิมตอบได้

## สิ่งที่ต้องตัดสิน

แฟ้มสะสมผลงานหนึ่งแฟ้มมีผู้อ่านที่เป็นไปได้สามกลุ่ม

1. **เจ้าของ** — นักศึกษาที่แฟ้มนั้นเป็นของเขา
2. **ผู้ถือ share link** — ใครก็ได้ที่มี token ในมือ ซึ่งเป็นจุดประสงค์ของปุ่ม
   "แชร์" ทั้งปุ่ม
3. **อาจารย์** — ที่สอนนักศึกษาคนนั้น หรือที่ปรึกษา หรือทุกคนในภาควิชา

## การตัดสิน

**เจ้าของกับผู้ถือ share link เท่านั้น อาจารย์ยังไม่ได้**

กติกาหนึ่งเดียวที่ใช้ทั้ง 10 router คือ **ผู้กระทำคือเจ้าของ session เสมอ
ไม่ใช่คนที่คำขอบอกว่าเป็น** แตกเป็นสามแบบตามรูปของ endpoint

| รูปของ endpoint | กติกา | คำตอบเมื่อไม่ผ่าน |
| --- | --- | --- |
| คำขอที่**ระบุผู้ใช้** (`?user_id=`, `/:user_id`) | ต้องเป็นเจ้าของ session | `403` |
| คำขอที่**ระบุแถว** (`/:id`) | แถวนั้นต้องมี `user_id` ตรงกับ session | `403` |
| คำขอที่**เขียนแถวใหม่** (body) | ไม่รับ `user_id` จาก body อีกต่อไป ใช้ของ session | — |

ทุก endpoint อยู่หลัง `requireUser` คือไม่มี session แล้วได้ `401` ก่อนเสมอ
ยกเว้นข้อเดียว: **`GET /portfolio/public/:token` ยังเปิดสาธารณะตามเดิม** เพราะ
ตัว token คือหลักฐานการเข้าถึงในตัวมันเอง ถ้าบังคับให้ล็อกอินก่อน ฟีเจอร์แชร์ก็
ไม่เหลืออะไร

### ทำไม body ถึง "ไม่รับ" แทนที่จะ "ตอบ 403 เมื่อไม่ตรง"

ฟิลด์ที่หายไปจาก schema ปฏิเสธได้ 100% โดยไม่บอกอะไรผู้โจมตีกลับไปเลย ส่วนการ
เทียบแล้วตอบ 403 จะกลายเป็นเครื่องมือให้ลองว่ารหัสไหนมีอยู่จริง และยังทำให้รูปของ
คำขอโกหกต่อไปว่า "ระบุเจ้าของได้" ทั้งที่ระบุไม่ได้แล้ว — ส่วน `PUT` ของทั้งกลุ่ม
เป็นแบบนี้อยู่ก่อนแล้วตั้งแต่ #20 (zod ตัดคีย์ที่ไม่รู้จักทิ้ง) ข้อนี้แค่ทำให้
`POST` เหมือนกัน

ส่วน query ของคำขออ่านยังคง `user_id` ไว้แล้วเทียบ เพราะ **นั่นคือรอยต่อที่ #30
จะมาขยาย** ถ้าวันหนึ่งอาจารย์อ่านแฟ้มของนักศึกษาที่ตัวเองสอนได้ คำตอบของ
"ใครดูของใครได้" จะเลิกเป็น "ตัวเองเท่านั้น" — พารามิเตอร์ต้องยังอยู่เพื่อให้
เปลี่ยนกฎที่เดียวได้ ไม่ใช่ต้องคืนพารามิเตอร์กลับมาทั้งกลุ่ม

### ทำไมอาจารย์ยังไม่ได้

- **ยังไม่มีกฎให้บังคับ** "อาจารย์ที่สอนนักศึกษาคนนี้" ต้องนิยามผ่าน
  `course_sections_teacher` → `student_course` ซึ่งเป็นกฎเดียวกับที่ #30 ค้างอยู่
  การเดากฎนั้นล่วงหน้าที่นี่ แล้ว #30 ตัดสินเป็นอย่างอื่น จะได้ระบบที่มีสองกฎ
- **ยังไม่มีใครเรียก** ทั้ง `apps/web` มีหน้าแฟ้มสะสมผลงานอยู่ใต้
  `features/student/` อย่างเดียว ไม่มีหน้าไหนของอาจารย์เปิดแฟ้มของนักศึกษา และ
  TC-46 ถึง TC-75 ใน [tc-traceability](../tc-traceability.md) ไม่มีข้อไหนบรรยาย
  อาจารย์ดูแฟ้มของนักศึกษา — ทุกข้อเป็นนักศึกษาทำกับของตัวเอง บวก TC-75 ที่เป็น
  share link
- **เพิ่มทีหลังถูกกว่าถอนทีหลัง** ปิดไว้ก่อนแล้วเปิดเพิ่ม คือการเปลี่ยนกฎที่
  middleware ตัวเดียว ส่วนเปิดไว้ก่อนแล้วมาปิด คือการค้นว่ามีใครพึ่งพาช่องนั้นไป
  แล้วบ้าง

## ผลที่ตามมา

- middleware `requireSelf` กับ `requireOwnEntry` อยู่ที่
  `apps/api/src/middlewares/owner.middleware.ts` ใช้ซ้ำได้ทั้ง 56 endpoint
  ไม่มี router ไหนเขียนการตรวจ "ผู้กระทำคือเจ้าของ" ซ้ำเอง เหลือสองที่ที่
  middleware ตรวจแทนไม่ได้ เพราะสิ่งที่ต้องตรวจคือ **รายการ id ใน body** ไม่ใช่
  ตัวคำขอ — `selectedSkillIds` ของ `POST`/`PUT`/`PATCH /portfolio` และ
  `skillIds` ของ `POST /portfolio-skill/assign-work` ทั้งสองตรวจใน service
  ภายใน transaction เดียวกับการเขียน เพื่อไม่ให้เกิดช่องว่างระหว่างตรวจกับเขียน
- `user_id` หายจาก body ของ `POST` ทุกตัวในกลุ่ม — ผู้เรียกที่ยังส่งมาไม่พัง
  แต่ค่าจะถูกทิ้ง ดู [`BEHAVIOR-CHANGES.md`](../../BEHAVIOR-CHANGES.md)
- แถวที่ไม่มีอยู่จริงยัง**ไม่ใช่**เรื่องของ middleware ตัวนี้ — มันปล่อยผ่านไปให้
  controller ตอบ 404/500 เหมือนเดิม การตรวจสิทธิ์กับการมีอยู่ของแถวเป็นคนละคำถาม
  และการรวมสองอย่างเข้าด้วยกันจะลาก pin เรื่อง 500 ของ `PUT`/`DELETE` เข้ามาใน
  ticket นี้โดยไม่จำเป็น
- นักศึกษาที่ไม่มีบทบาทใน `user_roles` ยังใช้แฟ้มของตัวเองได้ เพราะกลุ่มนี้ใช้
  `requireUser` ไม่ใช่ `requireRole("STUDENT")` — แฟ้มเป็นของ **ผู้ใช้** ไม่ใช่
  ของบทบาท และอาจารย์ที่อยากมีแฟ้มของตัวเองก็มีได้ตามกติกาเดียวกัน
- **ตัวไฟล์ยังไม่อยู่หลังกติกานี้** ADR นี้คุมแต่ 10 router ของกลุ่ม
  `portfolio_*` ส่วน `GET /files?path=` กับ `/uploads/*` ใน
  `apps/api/src/routes/files.route.ts` ไม่มี middleware ตรวจสิทธิ์เลยแม้แต่
  `requireUser` ใครรู้ `file_path` ก็ยังโหลดใบประกาศหรือรูปโปรไฟล์ของคนอื่นได้
  ตรง ๆ ผลคือ metadata ของไฟล์ปิดแล้ว (ต้องเป็นเจ้าของแถวถึงจะเห็น `file_path`)
  แต่ตัวไฟล์ยังเปิดอยู่ ไม่ได้แก้ใน #31 เพราะ router ตัวนั้นเสิร์ฟไฟล์ของทั้ง
  ระบบ ไม่ใช่ของ portfolio อย่างเดียว การผูกเจ้าของกับ object key จึงเป็นการ
  ตัดสินคนละเรื่องกับ ADR นี้

## จะกลับมาทบทวนเมื่อไหร่

เมื่อ **#30 ตัดสินกฎ "อาจารย์คนไหนเห็น section ไหน"** เสร็จ ให้เอากฎนั้นมาเป็น
สาขาที่สองใน `requireSelf` / `requireOwnEntry` — จุดเดียว ไม่ต้องไล่แก้ router
หรือเมื่อมีผู้ใช้กลุ่มใหม่ที่ต้องอ่านแฟ้มของคนอื่นจริง ๆ (เช่น ที่ปรึกษา
ฝ่ายทะเบียน) ซึ่งจะเป็นคำถามเดียวกันในรูปแบบใหม่
