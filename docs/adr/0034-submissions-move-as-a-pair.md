# ADR-0034 — สอง feature ที่ใช้รูปเดียวกันจริง ๆ ย้ายรอบเดียวกัน

- **สถานะ**: ตัดสินแล้ว 19 สิงหาคม 2569
- **ที่มา**: [issue #68](https://github.com/khthana/Deep-Portfolio/issues/68)
  รอบ student-activity กับ student-learning-activity
- **เกี่ยวข้อง**: [ADR-0029](0029-api-types-per-feature.md) กติกาของแต่ละรอบ,
  [ADR-0030](0030-evaluation-row-union.md) response ที่ถือแถวหลายแบบเขียนเป็น
  union, [ADR-0033](0033-learning-activity-and-the-absent-key.md) รอบก่อนหน้า
  ใบนี้ไม่ได้ทบทวนข้อไหนของทั้งสามใบ

## บริบท

#68 บอกไว้ว่า "ทำทีละ feature หนึ่ง PR ต่อหนึ่ง feature" ตามที่ #61 ตัดสิน รอบนี้
ไม่ทำตามนั้น และนี่คือเหตุผล

`student-activity` กับ `student-learning-activity` ไม่ได้แค่ "คล้ายกัน" — มันใช้
**รูปเดียวกันตัวเดียวกัน** อยู่จริง ๆ สองที่:

- ฝั่ง API `student-learning-activity.model.ts` `import { SubmissionGroup } from
  "./student-activity.model"` มาใช้ตรง ๆ
- ฝั่ง web ทั้ง `features/teacher/activity/types/` และ
  `features/teacher/learning-activity/types/` อ่าน `UnacceptedMember` ตัวเดียวกัน
  จาก `src/types/activity-type.type.ts` และ `formatMarkedStudents` กับ
  `formatUnacceptedMembers` ก็เป็น helper ตัวเดียวที่ทั้งสองตารางเรียก

ถ้าย้ายทีละตัว รูปกลุ่มจะไปอยู่ใน package แล้ว feature ที่ยังไม่ย้ายจะต้องแก้
import ตาม ADR-0029 ข้อ 4 อยู่ดี — คือกลายเป็นรอบเดียวโดยปริยาย แต่ซ่อนไว้ในชื่อ
ที่บอกว่าทำทีละตัว รอบนี้จึงเขียนออกมาตรง ๆ ว่าเป็นรอบเดียวสองครึ่ง

**สิ่งที่ยังคงเป็นรอบละหนึ่ง** คือ *feature* ไม่ใช่ *ไฟล์*: package ได้ไฟล์แยกกัน
ห้าไฟล์ (`student.ts`, `group.ts`, `student-activity.ts`,
`student-learning-activity.ts` และของเดิมที่ขยาย) ตาม ADR-0029 ข้อ 2 เจ้าของรูป
เป็นตัวตัดสินว่าอยู่ไฟล์ไหน ไม่ใช่ว่าใครย้ายก่อน

## สิ่งที่ `as` ปิดไว้

| จุด                                          | type เดิมบอก                     | ของจริงที่ส่ง                                    |
| -------------------------------------------- | -------------------------------- | ------------------------------------------------ |
| `remark` (แถว roster ทั้งสองฝั่ง)             | ไม่ได้ประกาศฝั่ง API             | ส่ง (ฝั่ง web ประกาศไว้ ฝั่ง API ไม่)             |
| `score` (เส้น detail)                         | ไม่ได้ประกาศ                     | ส่ง — คู่กับ `student_score` ที่เป็นเลขเดียวกัน   |
| `status` (เส้น detail)                        | `StudentActivityStatus` มี `LATE` | คอลัมน์จริง มี `GRADING` ไม่มี `LATE`             |
| `submitted_at`, `graded_at` (เส้น detail)     | `Date` ไม่ยอม null               | `string \| null` ทั้งคู่                          |
| `student` กับ `group` (แถว roster)            | optional ทั้งคู่ บนแถวเดียว      | มีทีละอย่าง ตาม `submission_type`                |
| `id` (เส้น detail)                            | คลุมเครือ — มาจากทั้งสองครึ่ง     | เป็น `student_activity.id` เพราะ spread ทับทีหลัง |
| id ที่ไม่ตรงกับแถวไหน                          | บอกว่าตอบรูปเต็มเสมอ             | ตอบวัตถุที่มีคีย์เดียว (ดูข้อ 4)                  |

## การตัดสินใจ

**1. แถว roster เป็น union บน `submission_type` ตาม ADR-0030**

ของเดิมเป็นแถวเดียวที่มี `student?` กับ `group?` optional ทั้งคู่ ซึ่งเป็นรูปที่
กว้างกว่าความจริงสี่เท่า — มันยอมให้มีแถวที่มีทั้งสอง และแถวที่ไม่มีเลย ทั้งที่
service ไม่เคยสร้างทั้งสองแบบ

`submission_type` เป็น discriminant ที่มีอยู่แล้ว รอบนี้จึงเขียนเป็น union
สองแขน ผลที่ได้จับต้องได้ทันที: `formatMarkedStudents` เลิก `?? []` กับ
`? [x] : []` แล้วอ่านครึ่งที่มีอยู่จริงตรง ๆ และ**เคสสามเคสในไฟล์ test ของมัน
หายไป** เพราะทั้งสามอธิบายแถวที่ type ใหม่สร้างไม่ได้แล้ว

`submission_type` บอกรูปของ**แถว** ไม่ใช่ของกิจกรรม — นักศึกษาที่ไม่ได้อยู่กลุ่ม
ไหนเลยบนงานกลุ่ม กลับมาเป็นแถว `INDIVIDUAL` ซึ่งเป็นสิ่งเดียวที่ทำให้อาจารย์
มองเห็นเขา (#56, #64)

**2. รูปกลุ่มกับชื่อนักศึกษาได้ไฟล์ของตัวเอง**

`SubmissionGroup`, `UnacceptedGroupMember` และ `MemberStatus` อยู่ใน `group.ts`
ส่วน `StudentNameBrief` กับ `StudentFullNameTh` อยู่ใน `student.ts` ทั้งสองไฟล์มี
คอมเมนต์บอกว่า feature ของมันเองยังไม่ย้าย ตาม ADR-0029 ข้อ 2 — เหมือนที่
`StudentActivityStatusDB` เคยทำในรอบ gradebook

`StudentNameBrief` กับ `StudentFullNameTh` เป็นคนละตัวเพราะสายส่งคนละอย่าง: แถว
roster ส่ง `student_id` มาด้วย เส้น detail ไม่ส่ง

**3. `StudentActivityStatus` ที่มี `LATE` ไม่ได้ย้ายตามมา และนี่คือรอบที่ตอบ
คำถามนั้น**

คอมเมนต์ใน `student-activity.ts` เขียนค้างไว้ตั้งแต่รอบ gradebook ว่า "ตัวที่
คำนวณจะย้ายมาด้วยไหม เป็นคำถามของรอบที่ย้าย feature student-activity" คำตอบคือ
**ไม่** — `LATE` คือ `getDisplayStatus()` เอา deadline ไปเทียบกับนาฬิกา ไม่มีที่
ไหนเขียนมันลงคอลัมน์ และไม่มี endpoint ในรอบนี้ส่งมันเลย มันไปถึงหน้าจอทางเดียว
คือรายการงานของนักศึกษา ซึ่งเป็นของ feature `student` ที่ยังไม่ถึงคิว

ผลข้างเคียงที่ตามมาทันที: `ClassworkDetailFull.status` ฝั่ง web เคยเป็น
`ClassworkStatus` (มี `LATE` ไม่มี `GRADING`) ทั้งที่สองเส้นที่เติมค่านี้ส่ง
คอลัมน์จริงมาตลอด รอบนี้แก้เป็น `StudentActivityStatusDB` ตัวจริง ผู้อ่านทุกราย
เทียบกับ `"GRADED"` / `"NOT_SUBMITTED"` เป็นสตริงอยู่แล้ว จึงไม่มีใครพัง — และไม่
ใช่กรณีเดียวกับ #69 ตรงที่ไม่มีใครเอาค่านี้ไป lookup ในตารางคำแปล

`ClassworkDetailFull.submitted_at` ก็แคบลงในบรรทัดเดียวกันนี้ จาก `Date` ที่ไม่ยอม
`null` เป็น `string | null` ตามที่สองเส้นส่งจริง — และ fixture สอง fixture ใน
`course-slice.test.ts` ที่เคยใส่ `new Date(...)` ไว้หลัง `as unknown as` ก็แก้เป็น
string ตามไปด้วย เพราะมันคือรูปที่สายสร้างไม่ได้

**4. id ที่ไม่ตรงกับแถวไหน ตอบว่าไม่พบ — เปลี่ยนพฤติกรรม และตั้งใจเปลี่ยน**

ทั้งสองเส้น detail ไม่เคยตรวจว่าหาแถวเจอไหม อ่านไม่เจอแล้วเดินต่อไปหากิจกรรมด้วย
id `0` ซึ่งไม่เจอเหมือนกัน แล้ว spread ของว่างสองอันเข้าหากัน เหลือวัตถุที่มี
คีย์เดียวคือรายการไฟล์แนบที่ว่างเปล่า

รอบอื่น ๆ ของ #68 รักษาพฤติกรรมเดิมทุกไบต์ รอบนี้ไม่ เพราะรูปนั้นบังคับให้ต้อง
เลือกอย่างใดอย่างหนึ่ง: เขียน type เป็น union ของ "แถวเต็ม" กับ "มีแต่
`submitted_files`" ซึ่งทำให้ทุกหน้าจอที่อ่านต้อง narrow ก่อน — เพื่อรองรับรูปที่
ไม่มีใครออกแบบและไม่มีใครอ่าน — หรือทำให้มันตอบว่าไม่พบ เหมือนที่ `GET /activity`
กับ `GET /learning-activity` ตอบมาตลอดเมื่อไม่พบแถว

เลือกอย่างหลัง สิ่งที่เปลี่ยนอยู่ใน `BEHAVIOR-CHANGES.md`

**และมีผู้เรียกฝั่ง web ที่ต้องตามจริง ๆ หนึ่งราย** ซึ่งรอบนี้แก้ไปด้วยตาม
ADR-0029 ข้อ 4: `course-slice.ts` ส่ง `action.payload.data` เข้า
`mapActivityDetail` ใน `fulfilled` โดยไม่ตรวจอะไร และ mapper อ่าน `data.id`
ทันที ของเดิมมีวัตถุให้อ่านเสมอ — ว่างเปล่าแต่มีอยู่ — ของใหม่ไม่มี จึงเป็น
`TypeError` ไม่ใช่ค่าว่าง

คอมไพเลอร์มองไม่เห็นเพราะ `ResponseWrapper.data` ประกาศว่าไม่มีวันขาด ซึ่งเป็น
สิ่งที่ #67 ถืออยู่ รอบนี้จึงขยาย type ของ thunk ทั้งสี่ตัวเป็น `| undefined`
เพื่อให้คอมไพเลอร์บังคับ reducer ให้พูดถึงกรณีนี้ แล้ว reducer ตั้ง
`classworkDetail` เป็น `null` — ค่าเดียวกับตอนที่คำขอยังไม่กลับมา

นี่คือสิ่งที่ #68 บอกไว้เองว่าจะเจอ: type ที่เขียนตามสายจริงทำให้จุดที่เดาไว้ผิด
โผล่ออกมา ส่วนอีกสี่หน้าจอที่เรียกสองเส้นนี้เอา `data` ไปใส่ state ของตัวเอง
ต่อทันที ทั้งของเดิมและของใหม่จึงลงเอยที่ค่าที่ไม่มีอะไรให้อ่านเหมือนกัน

**สถานะยังเป็น `200` เหมือนเดิม** ไม่ใช่ `404` คำถามว่า endpoint ที่หาไม่เจอควร
ตอบอะไรเป็นคำถามทั้งระบบ ไม่ใช่ของสองเส้นนี้

**5. `byUnsubmittedLast` รับ ISO string แทน `Date`**

helper เรียงลำดับอ่าน `submitted_at` ซึ่งตอนนี้เป็น string เพราะ service เขียน
`toISOString()` เองแล้ว ทางเลือกที่ไม่เอาคือเรียงก่อนแล้วค่อยแปลงวันที่ ซึ่งแปลว่า
แถวมีสองรูประหว่างทาง — รูปที่เรียงได้กับรูปที่ส่งออก การให้ helper อ่านค่าเดียว
กับที่ผู้เรียกได้รับตรงกว่า

## ผลที่ตามมา

- เหลือสำเนาฝั่ง web 35 ไฟล์ 1,858 บรรทัด (จาก 38 ไฟล์ 2,035 หลังรอบ
  learning-activity) — สามไฟล์ที่หายไปคือ `src/types/activity-type.type.ts`,
  `src/types/student-activity-type.type.ts` และ
  `src/types/student-learning-activity-type.type.ts` ซึ่งว่างลงทั้งไฟล์ จึงลบทิ้ง
  ตามเหตุผลเดียวกับ ADR-0029 ข้อ 3
- API เพิ่มห้าเคส สี่เคสไล่ชื่อทุกคีย์ของสี่เส้น อีกหนึ่งเคสบันทึกว่าคะแนน `0`
  ออกสายเป็น `0` ไม่ใช่ `null` — นิพจน์ที่อ่านคอลัมน์เขียนว่า
  `a.score ? Number(a.score) : null` ซึ่ง**อ่านเหมือนบั๊ก falsy-zero แต่ไม่ใช่**
  เพราะ Prisma คืน `Decimal` มาเป็น object และ object เป็น truthy เสมอ เขียนเป็น
  เคสไว้เพราะคนอ่านคนต่อไปจะสงสัยเรื่องเดียวกัน
- ฝั่ง web หายไปสามเคส ทั้งสามอธิบายแถวที่ union สร้างไม่ได้แล้ว
- **`GET /student-activity/attachments` ไม่ได้ย้าย** มันเรียก `getAttachments`
  ก็จริง แต่แบนผลลัพธ์ลงเป็นรูปของตัวเองก่อนตอบ — รายการเดียวที่มี `url` กับ
  `file_path` อยู่บนวัตถุเดียวกัน ไม่ใช่ `AttachmentDetailResp` สิ่งที่ออกสายจึง
  เป็นคนละรูป และเป็นกรณีเดียวกับที่ ADR-0031 เจอใน `portfolio-*.model.ts`
  ส่วนเส้น grade กับ bookmark เป็น request body ซึ่ง ADR-0028 กันออกไปตั้งแต่ต้น
- ใน 35 ไฟล์ที่เหลือ สิบสี่ไฟล์เป็นของ portfolio ซึ่งมากกว่า feature อื่นทั้งหมด
  รวมกัน ที่เหลือกระจายอยู่ที่ course, calendar, home, group, material, mapping,
  lesson-plan, rubric, score-weight, gradebook, student และ user
- สี่ไฟล์ในนั้นไม่ได้รอรอบของ feature ไหนอีกแล้ว เพราะสิ่งที่เหลืออยู่ในมันไม่ใช่
  response: `global-type.ts` ถือ `ResponseWrapper` (เป็นของ #67),
  `attachment-type.type.ts` เหลือแต่ค่า runtime ตามที่ ADR-0031 อธิบายไว้ และ
  ไฟล์ type ของ activity กับ learning-activity ฝั่งอาจารย์เหลือแต่ค่า runtime
  (`activityType`, `SubmissionStatus` พร้อมตารางสีและคำแปล) กับ shape ของฟอร์ม
  และ request body ซึ่ง ADR-0028 กันออกไปตั้งแต่ต้น
- **`GradeStudentActivityResp` ย้ายไปด้วย** ทั้งที่เป็น response ของเส้น `POST`
  ไม่ใช่ `GET` — ขอบเขตของ ADR-0028 คือ "สิ่งที่ API ตอบ" ไม่ได้แยกตาม method
  และเคสที่ปักหมุดมันไว้มีอยู่แล้วใน `student-activity.test.ts` (`toEqual` ของ
  สองฟิลด์เป๊ะ ๆ) จึงไม่ต้องเขียนเคสใหม่
- **`POST /student-learning-activity/grade` ไม่ได้ย้าย** และไม่ใช่การลืม: มันคืน
  แถว Prisma ทั้งแถวจาก `update()` ฝั่ง web จึงเขียน `ResponseWrapper<any>` ไว้
  ไม่มี type ให้ย้าย มีแต่ type ให้**เขียนขึ้นใหม่** ซึ่งต้องเริ่มจากเคสที่ไล่ชื่อ
  ทุกคีย์ก่อนเหมือนสี่เส้นในรอบนี้ — เป็นงานของรอบที่ตั้งใจทำมัน ไม่ใช่ของท้ายรอบนี้
  (`any` ตัวนั้นอยู่ในกอง #63 ด้วย)
