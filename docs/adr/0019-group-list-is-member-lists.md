# ADR-0019 — `/student-activity-group/all` ตอบว่า "เคยทำงานกับใครบ้าง" ไม่ใช่ "อยู่กลุ่มไหนบ้าง"

- **สถานะ**: ตัดสินแล้ว 12 สิงหาคม 2569
- **ที่มา**: [issue #44](https://github.com/khthana/Deep-Portfolio/issues/44)
- **เกี่ยวข้อง**: [ADR-0003](0003-enrolment-access.md) ตัดสินว่า**ใครถามเส้นนี้ได้**
  (นักศึกษาที่ล็อกอินอยู่ ไม่ใช่ `student_id` จาก query) ไฟล์นี้ตัดสินคนละคำถาม คือ
  **คำตอบคือรายการของอะไร** ตารางใน ADR-0003 เขียนไว้ผ่าน ๆ ว่า `/all` ตอบ "กลุ่ม
  ทั้งหมดของนักศึกษาคนนั้นในกลุ่มเรียนนั้น" ซึ่งไม่ตรงกับโค้ดตั้งแต่วันที่เขียน — การ
  ยุบมาพร้อมโค้ดที่รับมอบตั้งแต่ commit แรกของ repo (`4022b32`, 8 ส.ค. 2569) ส่วน
  ADR-0003 เขียนขึ้นสองวันให้หลัง ตอนแก้ #26 (`3b52362`, 10 ส.ค. 2569) คำถามของวันนั้น
  คือใครถามได้ ไม่ใช่คำตอบเป็นรายการของอะไร จึงไม่มีใครเปิดโค้ดตรงนี้อ่าน
  [ADR-0017](0017-group-membership-means-accepted.md) วางกฎกว้างกว่านั้นไว้ว่า
  "`ACCEPT` คือคำตอบของ 'อยู่ในกลุ่มนี้' **ทุกที่ที่ตัดสินว่าใครได้อะไร**" ซึ่งเส้นนี้
  ไม่เข้า เพราะมันไม่ได้ตัดสินว่าใครได้อะไร ดู "จะกลับมาทบทวนเมื่อไหร่"

## บริบท

`getStudentActivityGroupInSec` ดึงกลุ่มทุกกลุ่มของนักศึกษาในกลุ่มเรียนหนึ่ง แล้วยุบ
กลุ่มที่มีรายชื่อสมาชิกชุดเดียวกันให้เหลือตัวเดียว ด้วยลายเซ็นที่เป็นรหัสนักศึกษา
เรียงแล้วต่อกัน

```ts
const groupSignature = members
  .map((m) => m.student_id)
  .sort()
  .join(",");
```

นักศึกษาคู่เดิมที่ทำงานกลุ่มด้วยกันสองกิจกรรมในกลุ่มเรียนเดียว จึงได้คำตอบที่มีกลุ่ม
เดียว และ response ก็ไม่มี `activity_id` ให้แยกแยะ #44 ตั้งต้นว่านี่คือข้อบกพร่อง และ
เกณฑ์ตรวจรับของมันสั่งไว้ว่า "ต้องเห็นทั้งสองกลุ่ม" กับ "ผู้เรียกต้องบอกได้ว่ากลุ่ม
ไหนของกิจกรรมไหน" — เกณฑ์นั้นเขียนก่อนอ่านผู้เรียก และผู้เรียกเป็นตัวเปลี่ยนคำตอบ

**ผู้เรียกมีที่เดียว และมันไม่ได้ถามหากลุ่ม** `create-groupwork-section.tsx` dispatch
`fetchStudentActivityGroupInSec` (หรือ `…LearningActivityGroupInSec` เมื่อชิ้นงานเป็น
learning activity) ทั้งคู่ลงที่ state ตัวเดียวกันคือ `studentGroupInSec` แล้ว
`create-groupwork-modal.tsx` เอาไปวางเป็นรายการ "กลุ่มที่เคยสร้าง" ในโมดัลสร้างกลุ่ม
แต่ละบรรทัดคือ `group-item.tsx` ซึ่งแสดง `members.map((m) => m.student_id).join(", ")`
และเมื่อคลิกก็ส่งต่อ `props.group.members` ตัวเดียว — เพื่อเติมรายชื่อลงฟอร์มของ
**กลุ่มใหม่** ที่กำลังจะสร้าง คำถามที่หน้าจอนี้ถามจึงเป็น "ชุดสมาชิกไหนที่ฉันเคยร่วม
งานด้วยในกลุ่มเรียนนี้ ขอหยิบมาใช้ซ้ำ" ไม่ใช่ "ฉันอยู่กลุ่มไหนบ้าง"

**สิ่งที่คำตอบมีแต่ไม่มีใครอ่าน** `group_id` ไม่ถูกอ่านเลยในเส้นทางนี้ ส่วน `role`
กับ `status` ของสมาชิกก็ถูกทิ้ง เพราะ `handleOnSelectedGroup` คำนวณบทบาทใหม่ทั้งชุด
(ผู้เรียกเป็น `LEADER` ที่เหลือเป็น `MEMBER`) แล้วเรียงใหม่เอง `group_id` ที่ระบบใช้
งานจริงตอนส่งงานมาจากคนละเส้น — `GET /student-activity-group` ที่ระบุ `activity_id`
ทีละกิจกรรม ผ่าน `submit-classwork-section.tsx` ที่เอาไปใส่ `FormData` เส้นนั้นไม่ต้อง
ยุบอะไร เพราะคำขอระบุกิจกรรมมาแล้วและมันคืนกลุ่มเดียว (`findFirst`)

**ถ้าเลิกยุบ หน้าจอจะแย่ลง ไม่ใช่ดีขึ้น** สองกิจกรรมที่มีสมาชิกชุดเดียวกันจะกลาย
เป็นสองบรรทัดที่มีตัวอักษรเหมือนกันทุกตัว คลิกอันไหนก็ได้ผลเท่ากันเป๊ะ (เพราะสิ่งที่
ส่งต่อคือรายชื่อ) และต่อให้เพิ่ม `activity_id` ลงไปตามเกณฑ์ของ #44 ผู้ใช้ก็ยังแยกไม่ออก
อยู่ดี — response ไม่มีชื่อกิจกรรม มีแต่ตัวเลข id การจะให้แยกออกจริงต้องส่งชื่อกิจกรรม
มาด้วยและออกแบบบรรทัดนั้นใหม่ ซึ่งเป็นการเพิ่มฟีเจอร์ให้หน้าจอ ไม่ใช่การซ่อมของเสีย

**ของที่เสียจริงคือลำดับ** `findMany` ไม่มี `orderBy` เลย ทั้งชั้นกลุ่มและชั้นสมาชิก
ตัวที่รอดจากการยุบจึงเป็น "แถวไหนก็ตามที่ Postgres คืนมาก่อน" และสตริงรหัสนักศึกษาที่
ผู้ใช้เห็นก็ไม่มีอะไรรับประกันว่าจะเรียงเหมือนเดิมทุกครั้ง ในทางปฏิบัติแถวออกมาตาม
ลำดับที่แทรกเข้าไป ซึ่งบังเอิญตรงกับคำตอบที่ถูกเมื่อหัวหน้ากลุ่มถูกใส่เป็นคนแรกและ
รหัสที่เหลือเรียงขึ้นอยู่แล้ว — กลุ่มที่ใส่หัวหน้าไว้ต้นรายการแต่รหัสสมาชิกสลับกัน
คืนลำดับที่แทรก ไม่ใช่ลำดับที่ตกลงกันไว้ (case `hands each list back leader first,
then by student id` ตกถ้าถอด `orderBy` ชั้นสมาชิกออก) และลำดับที่แทรกเองก็ไม่ใช่
สัญญาอะไร query planner เปลี่ยนใจเมื่อไหร่ก็หายไปได้

## สิ่งที่ต้องตัดสิน

1. เส้นนี้ตอบรายการของอะไร — กลุ่ม หรือชุดสมาชิก
2. ถ้าคำตอบคือชุดสมาชิก แล้ว `group_id` ที่ติดมากับแต่ละชุดคือกลุ่มไหน
3. เส้น learning activity ตอบเหมือนกันไหม

## การตัดสิน

> **การยุบอยู่ต่อ เพราะเส้นนี้ตอบ "ชุดสมาชิกที่เคยร่วมงานในกลุ่มเรียนนี้" ตามที่ผู้เรียก
> ถาม และตัวที่ตอบแทนแต่ละชุดคือกลุ่มที่เก่าที่สุด ไม่ใช่กลุ่มใดก็ได้**

### 1. เก็บการยุบไว้ แล้วเขียนกำกับว่าเส้นนี้ตอบอะไร

ที่ผ่านมาไม่มีอะไรในโค้ดบอกว่าการยุบมีไว้ทำไม — #44 จึงอ่านว่าเป็นข้อบกพร่อง และ
ก็สมควรอ่านแบบนั้น เพราะชื่อ `getStudentActivityGroupInSec` กับ path `/all` สัญญา
อีกอย่างหนึ่ง สิ่งที่ ticket นี้ทำจึงไม่ใช่เปลี่ยนพฤติกรรม แต่ทำให้เจตนามีที่อยู่:
comment เหนือ method ทั้งสองฝั่ง test ที่บอกว่าทำไมหนึ่งบรรทัดคือคำตอบที่ถูก และ ADR
ฉบับนี้

ไม่เปลี่ยนชื่อ endpoint เพราะการเปลี่ยน path เป็นการแก้สัญญากับหน้าเว็บเพื่อความสวยงาม
ของชื่ออย่างเดียว ผู้เรียกยังเป็นตัวเดิม คำตอบยังเป็นชุดเดิม

### 2. `group_id` คือกลุ่มที่เก่าที่สุดของชุดนั้น

`orderBy: { id: "asc" }` ที่ชั้นกลุ่ม ทำให้ตัวที่ผ่านการยุบเป็นตัวแรกเสมอ และ
`orderBy: [{ role: "asc" }, { student_id: "asc" }]` ที่ชั้นสมาชิก ทำให้สตริงที่ผู้ใช้
เห็นในรายการเรียงเหมือนกันทุกครั้ง คำตอบของ endpoint ไม่ควรขึ้นกับว่า Postgres คืน
แถวมาลำดับไหน

ที่เอา `role` ขึ้นก่อน `student_id` เพราะ enum `student_activity_group_member_role`
ประกาศ `LEADER` ไว้ก่อน `MEMBER` (Postgres เรียง enum ตามลำดับที่ประกาศ) หัวหน้ากลุ่ม
จึงอยู่ต้นรายการ เป็นรูปเดียวกับที่ `handleOnSelectedGroup` จัดหลังคลิก — หัวหน้าก่อน
แล้วที่เหลือเรียงตามรหัส (`a.role === "LEADER" ? -1 : …localeCompare`) ต่างกันตรงที่
ฝั่งเว็บนับ "หัวหน้า" จากผู้ใช้ที่ล็อกอินอยู่ ส่วนฝั่ง API นับจาก `role` ของแถว ซึ่ง
ตรงกันเมื่อคนที่เปิดหน้าจอเป็นหัวหน้าของชุดนั้นเอง การเรียงด้วย `student_id` ล้วนจะ
ทำให้บรรทัดก่อนคลิกกับรายชื่อหลังคลิก สลับตำแหน่งกันโดยไม่ได้ตั้งใจ

ไม่ตัด `group_id` ทิ้งจาก response ทั้งที่ผู้เรียกไม่ได้อ่าน เพราะมันใช้ type
`GetStudentActivityGroupResp` ร่วมกับ `GET /student-activity-group` ซึ่งที่นั่น
`group_id` คือของจำเป็น การตัดออกจึงต้องแตก type และแก้ฝั่งเว็บตาม โดยไม่มีใครได้อะไร
กลับมา ตอนนี้มันมีความหมายที่พูดออกมาได้แล้ว — "กลุ่มแรกที่ใช้ชุดสมาชิกนี้"

### 3. learning activity ตอบเหมือนกัน

`student-learning-activity-group.service.ts` เป็นโค้ดชุดเดียวกันบรรทัดต่อบรรทัด และ
ปลายทางก็เป็น state ตัวเดียวกันในหน้าจอเดียวกัน คำตอบที่ต่างกันจะแปลว่าโมดัลเดียวกัน
ทำงานคนละแบบขึ้นกับว่าชิ้นงานเป็นชนิดไหน ซึ่งไม่มีใครอธิบายให้ผู้ใช้ได้

## ผลที่ตามมา

- **รูปของ response ไม่เปลี่ยน แต่ลำดับเปลี่ยนได้** ฟิลด์เดิมทุกตัว จำนวนบรรทัดเท่าเดิม
  สิ่งที่ขยับได้คือลำดับรหัสในบรรทัดของ `group-item.tsx`: กลุ่มที่แถวสมาชิกถูกแทรกไว้
  ไม่ตรงกับ "หัวหน้าก่อน แล้วเรียงตามรหัส" จะเห็นสตริงเรียงใหม่ ไม่ต้องแก้อะไรฝั่งเว็บ
  เพราะมันแค่ `join(", ")` ตามที่ได้มา และคลิกแล้วก็เรียงเองอยู่ดี
- **`getStudentActivityGroup` ยังไม่เรียงสมาชิก** เส้นพี่น้องที่ถามทีละกิจกรรมไม่ได้
  ถูกแตะในตั๋วนี้ ทั้งที่ผู้เรียกของมันเอารายชื่อไปแสดงจริง — `show-groupwork-modal.tsx`
  map `members` ลง `selectedMembers` ตามลำดับที่ได้มา ลำดับตรงนั้นจึงยังเป็น "แถวไหน
  ก็ตามที่ Postgres คืนมาก่อน" และไม่รับประกันว่าตรงกับ `/all` ที่ปล่อยไว้เพราะ #44 ถาม
  ถึงเส้น `/all` เส้นเดียว และการแก้เส้นนั้นต้องมาพร้อม test ของมันเอง ถ้าจะแก้ ให้ยก
  `[{ role: "asc" }, { student_id: "asc" }]` ชุดเดียวกันนี้ไปใช้ ไม่ใช่คิดกฎใหม่
- **`activity_id` ไม่ถูกเพิ่ม** เกณฑ์ตรวจรับข้อนี้ของ #44 ถูกแก้ที่ตัว issue ไม่ใช่
  ทำตาม ตามกติกาใน `CLAUDE.md` ว่าเกณฑ์ที่เขียนก่อนอ่านโค้ดผิดได้
- **test ที่ปักพฤติกรรมเดิมไว้ถูกเขียนใหม่** จาก "collapses two groups with the same
  members into one" ที่บอกว่า "บันทึกไว้ ไม่ได้เห็นด้วย" เป็น "offers a member list
  once, however many activities used it" ที่ยืนยันว่าเหลือบรรทัดเดียว และบรรทัดนั้น
  ถือ `group_id` ของกลุ่มที่เก่ากว่า แล้วเพิ่ม "hands each list back leader first,
  then by student id" มาถือเรื่องลำดับสมาชิกโดยเฉพาะ — ทั้งสองไฟล์
- **entry ใน `BEHAVIOR-CHANGES.md` ยังอยู่ในรายการ "ยังไม่ได้แก้"** เพราะพฤติกรรมที่มัน
  ปักไว้ไม่ได้ถูกแก้ — สิ่งที่เติมเข้าไปคือประโยคว่ามันเป็นของที่ตั้งใจ พร้อมลิงก์มา
  ที่ ADR ฉบับนี้ ส่วนลำดับที่เปลี่ยนไปมี entry ของตัวเองในหมวด #44

## จะกลับมาทบทวนเมื่อไหร่

- **เมื่อมีหน้าจอที่ต้องการกลุ่มจริง ๆ ทั้งกลุ่มเรียน** เช่นหน้าอาจารย์ที่อยากเห็น
  ทุกกลุ่มของทุกกิจกรรม นั่นคือคำตอบคนละรูป (ทุกกลุ่ม พร้อมกิจกรรมของมัน) ควรเป็น
  endpoint ของตัวเองที่ตรวจสิทธิ์แบบอาจารย์ ไม่ใช่การผ่อนเส้นนี้ — เหตุผลเดียวกับที่
  ADR-0003 ให้ไว้ตอนตัดสินว่าหกเส้นนี้เป็นของนักศึกษาเท่านั้น
- **เมื่อมีคนถามว่ากลุ่มที่ตัวเองยังไม่ตอบรับ ควรอยู่ในรายการนี้ไหม** วันนี้ตัวกรอง
  คือ `some: { student_id }` เฉย ๆ ไม่ดู `status` คนที่ถูกชวนแล้วยังไม่กดรับ (หรือกด
  ปฏิเสธไปแล้ว) จึงเห็นชุดสมาชิกนั้นให้หยิบมาใช้ซ้ำได้ กฎของ ADR-0017 คือ `ACCEPT`
  ตัดสินความเป็นสมาชิก "ทุกที่ที่ตัดสินว่าใครได้อะไร" ซึ่งเส้นนี้ไม่เข้า เพราะการหยิบ
  รายชื่อเก่ามาเติมฟอร์มไม่ได้ให้คะแนน ไม่ได้ให้สิทธิ์ และไม่ได้ทำให้ใครอยู่ในกลุ่มใหม่
  จนกว่าเขาจะกดรับคำเชิญของกลุ่มนั้นอีกครั้ง แต่ถ้าจะถือว่ารายการนี้ควรกรอง `status`
  ด้วย นั่นคือการตัดสินของมันเอง ไม่ใช่ผลพลอยได้ของ ADR-0017
