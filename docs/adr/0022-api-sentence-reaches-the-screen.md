# ADR-0022 — ประโยคของ API ถูกวางไว้ที่ชั้น axios ไม่ใช่ที่ thunk ทีละตัว

- **สถานะ**: ตัดสินแล้ว 12 สิงหาคม 2569
- **ที่มา**: [issue #51](https://github.com/khthana/Deep-Portfolio/issues/51)
- **เกี่ยวข้อง**: [ADR-0015](0015-unmappable-activity.md) — หัวข้อ "จะกลับมาทบทวน
  เมื่อไหร่" ของไฟล์นั้นรอไฟล์นี้อยู่โดยตรง ("เมื่อมีใครตัดสินใจว่า thunk ควรส่ง
  ประโยคของ API ต่อไปให้หน้าจออย่างไร")

## บริบท

API เขียนประโยคภาษาไทยไว้ให้ผู้ใช้อ่าน `errorResponse()` ใน
`apps/api/src/utils/response.ts` ส่งทุกการปฏิเสธออกไปในซองเดียวกัน
`{ success: false, message }` และ `errorHandler` เป็นคนตัดสินว่าประโยคไหนปลอดภัย
พอที่จะออกไป ฝั่ง web มีสองเส้นทางที่จะรับมัน และมีแค่เส้นเดียวที่ทำงาน

**เส้นที่ทำงานอยู่แล้ว** — component ที่เรียก service ตรง ๆ แล้วอ่าน
`error.response?.data?.message` เอง มี 13 จุด: e-Portfolio ของนักศึกษา 12 จุด และ
`login-page.tsx` อีกหนึ่ง (issue #51 เขียนว่าทั้ง 13 จุดเป็น e-Portfolio ซึ่งนับ
เกินไปหนึ่ง — `login-page.tsx` ไม่ใช่ และมันเป็นจุดที่เขียนคอมเมนต์อธิบายไว้ชัดที่สุด
ว่าทำไมถึงต้องใช้ประโยคของ API)

**เส้นที่ไม่ทำงาน** — ทุกอย่างที่ผ่าน `createAsyncThunk` ซึ่งคือฝั่งอาจารย์ทั้งหมด
และหน้าที่ใช้ store ของนักศึกษา

- thunk 82 ตัวใน `*-action.ts` 14 ไฟล์ **ไม่มีตัวไหนเขียน payload creator ของตัวเอง
  เลย** — ทั้ง 82 ตัวเป็น `createAsyncThunk(type, serviceFn)` ตรง ๆ (คำว่า `async`
  ปรากฏ 0 ครั้งในไฟล์กลุ่มนั้น) และ `rejectWithValue` ไม่ปรากฏที่ไหนใน
  `apps/web/src` เลยสักครั้ง
- Redux Toolkit จึงย่อ error ที่ axios โยนออกมาเป็น `SerializedError` ซึ่งเก็บแค่
  `name`, `message`, `stack`, `code` — `response` หายไปทั้งก้อน พร้อมกับ body
- `message` ที่เหลืออยู่คือของ axios: `"Request failed with status code 400"`

ปลายทางของประโยคที่หายไปมีสองที่ และทั้งสองที่พังคนละแบบ

**`state.error` ในทุก slice ไม่มีใครอ่าน** — 79 จุดใน slice 14 ไฟล์เขียน
`state.error = action.error.message ?? "Something went wrong"` แต่ไม่มี component
ไหนอ่านฟิลด์นั้นกลับออกมาเลยสักที่ `useSelector` ทั้งหมดในโปรเจกต์รับทั้ง slice มา
แล้วอ่านแต่ flag กับข้อมูล ส่วน `message={error}` จุดเดียวที่มีอยู่
(`login-page.tsx`) เป็น `useState` ของหน้านั้นเอง ไม่ใช่ของ store ฟิลด์นี้จึงเป็น
ที่เก็บที่เขียนอย่างเดียว และประโยคภาษาอังกฤษที่อยู่ในนั้นไม่เคยถึงตาใคร

**`unwrap()` คือเส้นที่ถึงหน้าจอจริง** — 89 จุดใน 45 ไฟล์ `unwrap()` โยน
`SerializedError` ตัวนั้นออกมา และ component จับไว้ ที่ #51 เกิดขึ้นเพราะ #43 เพิ่ง
ให้ `POST /mapping/activity` มีประโยคสามประโยคที่บอกอาจารย์ตรง ๆ ว่าต้องไปทำอะไรก่อน
แต่ `mapping-section.tsx` แสดง `ไม่สามารถเพิ่มกิจกรรมได้ กรุณาลองใหม่อีกครั้ง` ตายตัว
ทั้งสามกรณี ซึ่งเป็นคำแนะนำที่ผิด — ลองใหม่กี่ครั้งก็ไม่สำเร็จ

## สิ่งที่ต้องตัดสิน

1. ประโยคของ API ถูกกู้คืนที่ชั้นไหน — thunk ทีละตัว ตัวห่อร่วม หรือ interceptor
2. `"Something went wrong"` ที่ 79 จุดจะเอาออกอย่างไร ในเมื่อไม่มีใครอ่านมันอยู่แล้ว
3. component ที่ทิ้ง error ทั้งก้อน (`} catch {` 46 จุดใน 23 ไฟล์) ต้องตามทั้งหมดไหม

## การตัดสิน

> **ประโยคถูกวางกลับลงบน `error.message` ที่ response interceptor ตัวเดียว ก่อนที่
> Redux จะได้เห็น error นั้น — ไม่มี thunk ไหนถูกแตะ และรูปของสิ่งที่ `unwrap()`
> โยนออกมาไม่เปลี่ยน**

```ts
error.message = messageToCarry(error);
```

เขียนทับเสมอ รวมถึงเขียนทับด้วยสตริงว่างเมื่อไม่มีประโยคให้วาง กติกาที่ได้จึงเป็น
ประโยคเดียว: **หลังคำขอล้มเหลว `error.message` คือประโยคของ API เอง หรือไม่ก็ว่าง
ไม่มีวันเป็นข้อความที่ axios เขียน** ครึ่งหลังคือครึ่งที่มีเขี้ยว — ดูข้อ 1.1

### 1. ทำไมเป็น interceptor ไม่ใช่ thunk

ทางเลือกทั้งสามที่ issue เสนอไว้ให้ผลปลายทางเหมือนกัน ต่างกันที่ราคาและที่ว่าอะไร
เปลี่ยนรูปไปบ้าง

`rejectWithValue` ทีละ thunk (ทางที่ 1) และตัวห่อร่วมอย่าง `apiThunk()`
(ทางที่ 2) ทั้งคู่ต้องแก้ทั้ง 82 จุด และทั้งคู่**เปลี่ยนสิ่งที่ `unwrap()` โยน**:
เมื่อ thunk ถูกปฏิเสธด้วยค่า `unwrap()` จะโยนค่านั้นออกมาแทน `action.error` ดังนั้น
`catch` ทั้ง 89 จุดจะได้รับของคนละชนิดกับที่เคยได้ ต้องไล่ดูทีละจุดว่าจุดไหนอ่าน
`.message` จากมันอยู่ นั่นคืองานที่ใหญ่กว่าปัญหาที่กำลังแก้ และไม่มี test ที่รอยต่อ
ไหนคอยรับ — thunk ไม่ได้อยู่ที่รอยต่อทั้งสองที่ T2 กำหนดไว้

interceptor (ทางที่ 3) เป็นจุดเดียวที่คำขอที่ล้มเหลว**ทุกคำขอ**วิ่งผ่าน ตอนที่
`response` ยังติดอยู่กับ error การเขียนทับ `message` ที่นั่นทำให้ `SerializedError`
ที่ Redux สร้างขึ้นมามีประโยคที่ถูกต้องอยู่แล้วตั้งแต่ต้น โดยที่ไม่มีอะไรใน
`createAsyncThunk`, ใน slice หรือใน `unwrap()` เปลี่ยนรูปเลย และ thunk ตัวที่ 83
ที่ใครจะเขียนต่อไปก็ได้มันไปด้วยโดยไม่ต้องรู้เรื่องนี้

**เงื่อนไขที่ issue ตั้งไว้ ("ต้องดูให้แน่ว่าไม่มีที่ไหนพึ่ง `message` เดิมของ
axios") ตรวจแล้ว** ก่อนแก้ ทั้ง `apps/web/src` มีสองจุดที่อ่าน `.message` ของ error
ที่จับได้ และทั้งสองจุดเอาไปแสดงบนหน้าจอตรง ๆ:

- `accept-invite-page.tsx` — `setErrorMessage(...)` แล้วแสดงเป็นบรรทัดของมันเอง
- `public-portfolio-page.tsx` — `error?.message || "ไม่พบหน้าที่คุณต้องการ ..."`
  ซึ่ง `?.` ทำให้ grep ที่ค้นด้วย `error\.message` มองไม่เห็น ทั้งที่มันอยู่ตรงนั้น

ทั้งคู่จึงเป็นจุดที่**ต้องการ**ประโยคของ API ที่สุด ไม่ใช่จุดที่พึ่งของเดิม ไม่มีที่
ไหนเปรียบเทียบ `message` กับสตริง ไม่มีที่ไหนแยกสาขาด้วยมัน และไม่มี test ไหนยืนอยู่
บนข้อความของ axios — คำว่า `"Request failed with status code"` ก่อนแก้ไม่ปรากฏใน
`apps/web/src` หรือ `apps/api/src` เลยสักครั้ง หลังแก้ปรากฏสี่ครั้ง และทั้งสี่เป็น
ครั้งที่ไฟล์นี้กับ test ของมันพูดถึงมันในฐานะข้อความที่ถูกลบทิ้ง ไม่ใช่ค่าที่ใครใช้

เขียนทับเฉพาะ `message` เท่านั้น `response`, `code`, `config` และ `request` คงเดิม
ทุกตัว — 13 จุดที่อ่าน body เองอยู่แล้วจึงเห็นของเดิมทุกอย่าง เงื่อนไข 401 ที่ตามมา
ในตัว interceptor เองอ่านค่าเดิมทั้งหมด และ `public-portfolio-page.tsx` ที่ดูว่า
`response?.status === 410` เพื่อแยก "ลิงก์หมดอายุ" ก็ยังเห็นสถานะเดิม

#### 1.1 ทำไมต้องลบข้อความของ axios ทิ้ง ไม่ใช่แค่เติมเมื่อมีประโยค

ฉบับแรกของการตัดสินนี้เขียนว่า `if (sentence) error.message = sentence` คือเติม
เฉพาะเมื่อมีประโยค แล้วปล่อยกรณีที่ไม่มีให้ประโยคสำรองของผู้เรียกรับไป **ซึ่งไม่
ทำงาน** และเป็นเกณฑ์ยอมรับข้อสองของ #51 พอดี: คำขอที่ไม่ถึงเซิร์ฟเวอร์ไม่ได้มาพร้อม
`message` ว่าง axios เขียน `"Network Error"` ลงไปให้แล้ว (`ERR_NETWORK`), timeout
เขียน `"timeout of 5000ms exceeded"` (`ECONNABORTED`), และ proxy ที่ตอบเป็นหน้า HTML
เขียน `"Request failed with status code 502"` ทั้งสามเป็นสตริงที่ไม่ว่าง ประโยคสำรอง
ที่ผู้เรียกส่งมาจึงไม่มีวันได้ทำงาน และอาจารย์จะเห็นคำว่า `Network Error` บนหน้าจอ

เมื่อ body หายไปกับ `SerializedError` แล้ว ปลายทางไม่มีทางแยกออกว่าประโยคที่ถืออยู่
มาจาก API หรือจาก axios การลบทิ้งคือสิ่งที่ทำให้ "ว่าง" แปลว่า "API ไม่ได้พูดอะไร"
ได้จริง ราคาที่จ่ายคือบรรทัดภาษาอังกฤษหายไปจาก `console.error` ด้วย ซึ่งแลกได้
เพราะ `code` บอกสิ่งเดียวกันในคำเดียว และ `response` กับ stack ยังอยู่ครบ

ทางเลือกอื่นที่ชั่งแล้วไม่เอา: ติดธงไว้บน `error.name` แล้วให้ปลายทางดูธง — ธงไม่รอด
`SerializedError` เฉพาะ `name` ที่รอด แต่การเขียนทับ `name` ทำให้ error ที่แอปโยนเอง
(`new Error("เกิดข้อผิดพลาดในการดำเนินการ")` ใน `accept-invite-page.tsx`) ถูกกลืนไป
ด้วย และการแยกด้วย `code` ของ axios ทีละค่า (`ERR_NETWORK`, `ECONNABORTED`, ...)
คือการไล่แจกแจงรายการที่ axios เป็นคนกำหนดและเพิ่มได้ตลอด

**วางไว้บนสุด ก่อนเงื่อนไข 401** เพราะเป็นตำแหน่งเดียวที่ครอบทุกทางออกของ handler
ตัวนี้ คำขอที่ถูกลองใหม่หลัง refresh แล้วล้มอีกจะวิ่งเข้า interceptor รอบสองและได้
ประโยคของรอบนั้น ส่วน error ของ `/auth/refresh` เองก็ผ่านบรรทัดนี้ไปแล้วเช่นกัน

### 2. ประโยคสำรองเป็นภาษาไทย ถึงจะยังไม่มีใครอ่าน

`state.error` เป็นฟิลด์ที่เขียนอย่างเดียว การแก้ 79 จุดจึงไม่เปลี่ยนอะไรที่ผู้ใช้
เห็นวันนี้ แต่ทำอยู่ดี ด้วยเหตุผลสองข้อ ข้อแรกคือ `"Something went wrong"` เป็น
ภาษาอังกฤษที่ไม่เคยตั้งใจให้ใครเห็น และวันที่มีใครต่อฟิลด์นี้เข้ากับหน้าจอ มันจะโผล่
ขึ้นมาเป็นภาษาที่สองบนหน้าที่เป็นภาษาไทยทั้งหน้า ข้อสองคือ `GENERIC_ERROR_MESSAGE`
ตัวเดียวกันนี้เป็นค่าตั้งต้นของ `messageToShow()` ด้วย ทั้งสองที่จึงพูดประโยคเดียวกัน
โดยไม่ต้องมีใครไปดูแลให้ตรงกัน

**ไม่ได้ลบฟิลด์ `error` ทิ้ง** ทั้งที่ไม่มีใครอ่าน — นั่นเป็นการตัดสินใจเรื่องรูปของ
state ที่กว้างกว่า #51 และ slice ทั้ง 14 ตัวมี test ยืนอยู่บนมันอยู่แล้ว
(`slice-cases.ts` ยืนยันทั้ง state ทุกเคส) การเอาออกจึงต้องเป็น ticket ของตัวเอง

### 3. ตาม component เฉพาะจุดที่มีประโยคให้แสดงจริง

`} catch {` 46 จุดใน 23 ไฟล์ทิ้ง error ทั้งก้อนแล้วแสดงประโยคตายตัวของหน้าตัวเอง
การไล่แก้ทั้งหมดในคราวเดียวคือการเปลี่ยนสิ่งที่ 23 หน้าจอพูด โดยไม่มี test ที่รอยต่อ
ไหนรับได้เลย — component test อยู่นอกขอบเขตตาม T2 — และประโยคสำรองแต่ละอันเป็นคำที่
เขียนไว้สำหรับหน้านั้นโดยเฉพาะ ไม่ใช่สิ่งที่ควรถูกกวาดทิ้งเป็นชุด

จุดที่แก้ในไฟล์นี้จึงมีสามไฟล์ และทั้งสามเป็นจุดที่**มีประโยคของ API ให้แสดงจริง
วันนี้**

- `mapping-section.tsx` สองจุด — คือเกณฑ์ยอมรับข้อแรกของ #51 และเป็นปลายทางของสาม
  ประโยคที่ ADR-0015 เขียนไว้
- `accept-invite-page.tsx` หนึ่งจุด — แสดง `error.message` อยู่แล้ว เท่ากับว่าก่อน
  แก้มันแสดง `"Request failed with status code 400"` ให้ผู้ใช้อ่าน และแสดงคำว่า
  `undefined` เมื่อ error ไม่มี message เลย
- `public-portfolio-page.tsx` หนึ่งจุด — อีกจุดที่แสดง `.message` อยู่แล้ว
  (`error?.message || "..."`) เปลี่ยนมาเรียก `messageToShow()` ทั้งที่ `||` ให้ผลถูก
  อยู่แล้วหลังจากที่ interceptor ลบข้อความของ axios ทิ้ง เพราะการเขียนไว้ตรง ๆ ทำให้
  หน้านี้ตั้งใจรับประโยคของ API ไม่ใช่รับมาโดยบังเอิญจากไฟล์ที่มันไม่รู้จัก และ
  `use-public-portfolio.ts` เลิกแต่ง `new Error("Unknown error")` ขึ้นมาเอง —
  ภาษาอังกฤษที่หน้านี้จะเอาไปแสดงแทนประโยคภาษาไทยของตัวเอง

ที่เหลือยังคงประโยคของตัวเองไว้ตามเดิม และตอนนี้มี `messageToShow(error, "...")`
รออยู่ให้เรียกเมื่อ endpoint ปลายทางของหน้านั้นมีประโยคที่ดีกว่าจะพูด

## ขอบเขต

- **ไม่มี thunk ตัวไหนถูกแก้** และ `rejectWithValue` ยังไม่ปรากฏใน `apps/web/src`
  เลย ซึ่งเป็นผลที่ตั้งใจ ไม่ใช่งานที่ค้าง
- **ไม่ได้แตะ 13 จุดที่อ่าน body เอง** — มันทำถูกอยู่แล้ว และ `messageToShow()` ให้
  ผลเหมือนกันกับที่มันเขียนไว้เอง การไล่เปลี่ยนให้เรียกฟังก์ชันเดียวกันเป็นการจัด
  ระเบียบ ไม่ใช่การแก้ข้อบกพร่อง
- **ไม่ได้เปลี่ยนอะไรฝั่ง API** ซองของ error กับกติกาว่าประโยคไหนออกไปได้เป็นของ
  `errorHandler` เหมือนเดิมทุกอย่าง
- **ไม่ได้ทำให้ `error.message` เป็นภาษาไทยเสมอ** — คำขอที่ไม่ถึงเซิร์ฟเวอร์ (เน็ต
  หลุด, CORS, timeout) ไม่มี body ให้อ่าน `message` จึงว่าง ตรงนั้นเป็นหน้าที่ของ
  ประโยคสำรองที่ผู้เรียกส่งเข้ามา ซึ่งตอนนี้ได้ทำงานจริงแล้ว
- **ไม่ได้แตะ error ที่แอปโยนเอง** — `new Error("...")` ที่เขียนไว้ในหน้าจอไม่ได้ผ่าน
  interceptor `message` ของมันจึงถึงผู้ใช้ตามเดิม และมันเป็นภาษาไทยอยู่แล้ว

## ผลที่ตามมา

- `messageToCarry()` และ `messageToShow()` เป็นฟังก์ชันบริสุทธิ์ใน `utils/` และมี
  test อยู่ข้างไฟล์ตามรอยต่อที่ T2 กำหนด (12 เคส) ตัว interceptor เองยังไม่มี test
  ยืนอยู่ — มันคือบรรทัดเดียวที่เรียกฟังก์ชันที่มี test แล้ว และ `axios.ts` ไม่ใช่
  ฟังก์ชันบริสุทธิ์ ส่วน test ที่เขียนคู่กันจำลองสองขั้นที่ error เดินผ่านจริง
  (interceptor แล้ว `SerializedError`) ไว้ในฟังก์ชันของตัวเอง เพื่อให้เคสที่ยืนยัน
  เกณฑ์ยอมรับข้อ 1 กับข้อ 2 ยืนอยู่บนรูปของ error ที่ axios สร้างจริง ไม่ใช่รูปที่
  แต่งขึ้นให้เคสผ่าน
- **`console.error` เห็นน้อยลงหนึ่งบรรทัด** — error ที่ log ออกไปจะไม่มีข้อความ
  `"Network Error"` หรือ `"Request failed with status code 500"` ติดมาอีก เหลือ
  `code`, `response` และ stack ซึ่งบอกเรื่องเดียวกันและระบุตำแหน่งได้ดีกว่า
- error ของ `/auth/refresh` ที่ล้มเหลวยังคงเป็น error ที่ผู้เรียกคำขอเดิมได้รับ
  (พฤติกรรมเดิม ไม่ได้เกิดจากไฟล์นี้) ต่างแค่ว่าตอนนี้มันพกประโยคของ API มาแทน
  `"Request failed with status code 401"` ซึ่งไม่มีผลกับใคร เพราะเส้นทางนั้นพาไป
  `/login` อยู่แล้ว
- ประโยคที่ผู้ใช้เห็นตอนนี้ผูกกับข้อความที่ API เขียนไว้ ถ้ามีใครแก้ประโยคฝั่ง API
  หน้าจอจะเปลี่ยนตามทันทีโดยไม่มีอะไรฝั่ง web ต้องแก้ — ซึ่งเป็นสิ่งที่ CLAUDE.md
  เขียนไว้ตั้งแต่แรกว่า "the frontend renders them directly" และเพิ่งจะจริงวันนี้

## จะกลับมาทบทวนเมื่อไหร่

เมื่อมีใครต้องการอ่าน `state.error` ของ slice จริง ๆ ตอนนั้นต้องตอบให้ได้ก่อนว่า
ฟิลด์ที่หนึ่ง slice ใช้ร่วมกันทุก thunk จะบอกได้อย่างไรว่าประโยคที่อยู่ในนั้นเป็น
ของคำขอไหน — ซึ่งเป็นเหตุผลที่ `unwrap()` เป็นเส้นทางที่ใช้จริงมาตลอด
