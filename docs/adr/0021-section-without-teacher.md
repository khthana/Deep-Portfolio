# ADR-0021 — section ที่ยังไม่มีอาจารย์ ยังเป็น section ที่มองเห็นได้

- **สถานะ**: ตัดสินแล้ว 12 สิงหาคม 2569
- **ที่มา**: [issue #48](https://github.com/khthana/Deep-Portfolio/issues/48)
- **เกี่ยวข้อง**: [ADR-0005](0005-announcement-date.md) เป็นเจ้าของประโยค
  "การซ่อนต้องมีคนสั่ง" และไฟล์นี้ใช้เหตุผลเดียวกันกับของที่ไม่เหมือนกัน —
  ADR-0005 ตัดสินให้**คอลัมน์ที่ว่างอยู่ในแถวเดียวกัน** (`announcement_date` ของ
  งานชิ้นนั้น) ส่วนที่นี่สิ่งที่หายไปคือ**แถวข้างเคียงทั้งแถว** ในตารางอื่น และผลของ
  การซ่อนไม่ได้ตกที่ของชิ้นเดียว แต่ตกที่ทุกอย่างที่แขวนอยู่กับ section นั้น
  ไม่มี ADR ฉบับไหนตัดสินว่า field ใน response ที่ตอบไม่ได้ควรเป็น `null` หรือ
  สตริงว่าง ไฟล์นี้เป็นเจ้าของการตัดสินนั้นเอง

## บริบท

`getCourseDetail()` ใน `course.service.ts` จบด้วยบรรทัดเดียวนี้ก่อนจะประกอบคำตอบ

```ts
if (!teacher || !subject || !teacherDetail) return null;
```

`teacher` มาจาก `course_sections_teacher.findFirst({ where: { section_id } })`
section ที่ยังไม่มีใครสอนจึงไม่มีแถวให้เจอ และทั้ง section หายไปทั้งอัน ทั้งที่
คำถามที่ผู้เรียกถามคือ "section นี้คือวิชาอะไร"

ผู้เรียกมีสองทาง และทั้งสองทางเจ็บ

| ผู้เรียก | สิ่งที่เกิดขึ้นเมื่อ section ไม่มีอาจารย์ |
| --- | --- |
| `GET /course?section_id=` | ตอบ `200` พร้อม `data: null` — ไม่ใช่ `404` เพราะ controller ส่งค่าที่ service คืนมาให้ `successResponse` ตรง ๆ |
| `getStudentCourseList()` | `null` ถูกกรองทิ้ง (`student.service.ts`) รายวิชานั้นหายไปจากรายการของนักศึกษาที่ลงทะเบียนไว้จริง |

และเพราะ `getStudentCalendarEvent()` สร้างรายการ `section_id` ของตัวเองจากผลของ
`getStudentCourseList()` งานทุกชิ้นใน section นั้นจึงหายไปจากปฏิทินด้วย — นักศึกษา
ไม่เห็นทั้งวิชาและกำหนดส่ง โดยไม่มีอะไรบอกว่าหายไปเพราะอะไร

สภาพนี้ไม่ใช่ข้อมูลเสีย `course_sections` กับ `course_sections_teacher` เป็น master
table ที่เข้าระบบผ่าน importer เท่านั้น — ไม่มี endpoint ไหนในทั้ง API ที่จัดอาจารย์
ให้ section ได้ section ที่เพิ่ง import เข้ามาและยังไม่ได้จัดอาจารย์จึงเป็นสถานะปกติ
ที่แก้ได้ทางเดียวคือ import รอบถัดไป

ในบรรทัดเดียวกันนั้นยังมีสองอย่างที่ตายแล้ว

- `getUserDetail(teacher?.user_id ?? "")` ถูกเรียก**ก่อน**การตรวจ `!teacher` เสมอ
  query ที่หา `users` ด้วย id `""` จึงวิ่งไปทุกครั้งที่ section ไม่มีอาจารย์ แล้วผล
  ถูกทิ้ง
- `!subject` เป็นไปไม่ได้ ทางเดินจาก `course_sections` ไปถึง `subjects` ผ่าน
  relation ที่ required ทั้งสองต่อ (`semester_courses` และ `subjects` ใน
  `schema.prisma` ไม่มี `?`) ถ้าเดินมาถึงบรรทัดนี้ได้ `subject` ก็มีอยู่แล้ว

## สิ่งที่ต้องตัดสิน

1. section ที่ไม่มีอาจารย์ ควรหายไปต่อ หรือแสดงโดยเว้นชื่ออาจารย์ไว้
2. ถ้าแสดง ช่องที่เว้นไว้เป็น `null` หรือสตริงว่าง
3. ฝั่ง web ตามมาในตั๋วเดียวกัน หรือแยกไปทีหลัง

## การตัดสิน

> **แสดง section ตามปกติ และให้ห้า field ของอาจารย์เป็น `null` พร้อมกันทั้งชุด
> ฝั่ง web ตามในตั๋วเดียวกัน**

### 1. แสดง ไม่ใช่ซ่อน

เหตุผลของ ADR-0005 ใช้ได้ทั้งดุ้น — **การซ่อนต้องมีคนสั่ง** การที่ยังไม่มีใครถูกจัด
ให้สอน section หนึ่ง ไม่ใช่คำสั่งให้ซ่อน section นั้นจากนักศึกษาที่ลงทะเบียนไว้ มัน
คือการที่ยังไม่มีใครสั่งอะไรเลย

และคนที่จ่ายราคาของการซ่อนไม่ใช่คนที่ทำให้เกิด นักศึกษาไม่มีทางรู้ว่าตารางไหนขาดแถว
ไหน ไม่มีทางแก้ และไม่ได้เห็นแม้แต่ร่องรอยว่ามีอะไรหายไป สิ่งที่เขาเห็นคือรายวิชา
ที่ลงทะเบียนแล้วไม่โผล่ และงานที่ถึงกำหนดส่งโดยไม่มีในปฏิทิน

ทางที่ 2 ของ issue (ซ่อนต่อ แต่ต้องมีที่ที่บอกว่ามี section ตกหล่น) แพงกว่าและได้
น้อยกว่า — ต้องมีที่ทางใหม่สำหรับ "รายการที่ถูกซ่อน" ทั้งที่ข้อมูลของ section เอง
ครบถ้วนอยู่แล้วทุก field ยกเว้นห้าช่องที่เป็นของอาจารย์

`section` ที่ไม่มีอาจารย์ยังตอบได้ครบทุกอย่างที่มันรู้ด้วยตัวเอง — รหัสวิชา ชื่อวิชา
หน่วยกิต กลุ่มเรียน ปีการศึกษา ภาคเรียน วันเวลาเรียน ห้องเรียน คำตอบที่ตรงคือตอบ
เท่าที่รู้ ไม่ใช่ไม่ตอบเลย

### 2. `null` ไม่ใช่สตริงว่าง

`CourseDetail` มี field ที่แปลว่า "ยังไม่มี" อยู่แล้วสี่ตัว — `day_of_week`,
`start_time`, `end_time`, `classroom` — ทั้งสี่ใช้ `null` และฝั่ง web อ่านมันด้วย
`?? "ยังไม่กำหนด"` อยู่แล้ว การให้ห้า field ของอาจารย์ใช้คำเดียวกันคือการเข้าแถว
กับสิ่งที่ type นี้พูดอยู่แล้ว ไม่ใช่การตั้งภาษาที่สอง

สตริงว่างแยกไม่ออกจากค่าที่มีอยู่จริงแต่ว่าง `""` ที่หน้าจอได้รับ ตอบไม่ได้ว่าเป็น
"ไม่มีอาจารย์" หรือ "มีอาจารย์แต่ชื่อว่าง" ส่วน `null` ตอบได้ข้อเดียว

**ทั้งห้าเป็น `null` พร้อมกันเสมอ** เพราะทั้งห้ามาจากแหล่งเดียว — แถวใน `users` ที่
`teacherDetail` ชี้ถึง ไม่มีทางที่บางช่องจะเป็น `null` ส่วนที่เหลือไม่ ข้อนี้เขียน
ไว้เป็น comment บน type ด้วย เพราะเป็นสิ่งที่ผู้อ่านฝั่ง web ต้องรู้ก่อนจะเขียน
`if` แยกทีละช่อง

**`teacher_phone` ยังเป็น `""` เมื่ออาจารย์มีตัวตนแต่ไม่ได้ให้เบอร์** —
`users.phone` เป็น nullable และของเดิมแปลงเป็น `""` ตรงนี้อยู่แล้ว ถ้าเปลี่ยนเป็น
`null` ด้วย `null` จะแบกสองความหมาย ("ไม่มีอาจารย์" กับ "อาจารย์ไม่ได้ให้เบอร์")
และข้อ "ทั้งห้าเป็น `null` พร้อมกัน" ข้างบนจะไม่จริงอีกต่อไป ค่าที่แปลว่า "ไม่มี
เบอร์" จึงถูกทิ้งไว้เป็น `""` ตามเดิม ไม่ใช่เพราะมันดี แต่เพราะการแก้มันเป็นคำถาม
คนละข้อกับที่ #48 ถาม

### 3. ฝั่ง web ตามในตั๋วเดียวกัน

การเปลี่ยน type จาก `string` เป็น `string | null` โดยไม่ตามไปแก้ผู้ใช้ จะได้
typecheck ที่พังทันที และถ้าปิดมันด้วย `?? ""` ก็เท่ากับเลือกทางที่ 2 ของข้อ 2 ที่
เพิ่งปฏิเสธไป ที่ที่ต้องตามมีเจ็ดแห่ง แบ่งเป็นสองแบบ

**ที่ที่แสดงค่าให้คนอ่าน (สี่แห่ง)** — `?? ` กับประโยคไทยที่หน้าจอนั้นใช้อยู่แล้ว
สำหรับค่าที่ยังไม่กำหนด

| ไฟล์ | ช่อง | ข้อความ |
| --- | --- | --- |
| `student/course/components/course-card.tsx` | `teacher_name_th` | `ยังไม่กำหนดอาจารย์ผู้สอน` |
| `student/course/components/course-info-section.tsx` | `teacher_name_th`, `teacher_email` | `ยังไม่กำหนด`, `-` |
| `teacher/course/components/course-info-section.tsx` | `teacher_name_th`, `teacher_email` | `ยังไม่กำหนด`, `-` |

การ์ดของนักศึกษาใช้ประโยคที่ยาวกว่า เพราะบรรทัดนั้นไม่มีหัวข้อกำกับ ต่างจากในหน้า
รายละเอียดที่มีคำว่า "อาจารย์ประจำวิชา" อยู่ข้างบนแล้ว ส่วน `teacher_phone` ทั้งสอง
หน้ามี `?? "-"` อยู่ก่อนแล้ว ไม่ต้องแก้

**ที่ที่ใช้ค่าเป็น `created_by` ของแถวใหม่ (สามแห่ง)** — `clo-table.tsx`,
`score-weight-table.tsx`, `lesson-plan-table.tsx` ทั้งสามมี `if
(!homeSlice.selectedCourse) return;` อยู่แล้วก่อนจะประกอบ body การแก้คือทำให้
เงื่อนไขเดิมแคบลงเป็น `if (!homeSlice.selectedCourse?.teacher_id) return;`

ทั้งสามหน้าเปิดจากรายวิชาของอาจารย์เอง ซึ่งเดินออกมาจาก `course_sections_teacher`
จึงมีอาจารย์เสมอ — เส้นทางนี้ไม่มีทางเจอ `null` จริง แต่ type เลิกรับประกันให้แล้ว
และการเขียน `""` ลงคอลัมน์ `created_by` แย่กว่าการไม่เขียน เหตุผลนี้เขียนไว้เต็มที่
`clo-table.tsx` อีกสองไฟล์ชี้มาที่นั่น

## ขอบเขต

- **ไม่ได้เพิ่ม foreign key บน `course_sections_teacher.user_id`** — คอลัมน์นี้ไม่มี
  FK ไปหา `users` มาตั้งแต่ baseline แถวที่ชี้ไปหา user ที่ไม่มีอยู่จึงเขียนได้ และ
  จะทำให้ `teacherDetail` เป็น `null` ทั้งที่ `teacher` มีอยู่ ผลที่ผู้เรียกเห็น
  เหมือนกับ section ที่ไม่มีอาจารย์ทุกประการ ซึ่งเป็นคำตอบที่ยอมรับได้สำหรับข้อมูล
  ที่ไม่ควรมีตั้งแต่แรก การเพิ่ม constraint เป็นงานของ schema ไม่ใช่ของ #48
- **ไม่ได้เพิ่ม endpoint ที่จัดอาจารย์ให้ section** — ยังเป็น importer เท่านั้น
  ตามที่ #1 ตั้งใจไว้ว่า master data เข้าทาง CLI
- **ไม่ได้แตะ `getAllCourses()`** — รายวิชาฝั่งอาจารย์เดินจาก
  `course_sections_teacher` เข้าไปหา section ไม่ได้เดินย้อนทาง section ที่ไม่มี
  อาจารย์จึงไม่เคยอยู่ในผลของมันอยู่แล้ว และไม่ควรอยู่ด้วย
- **ไม่ได้ตัด `if (!courseDetail) return null` ใน `getStudentCourseList()`** —
  `getCourseDetail()` ยังคืน `null` ได้เมื่อไม่มีแถว `course_sections` ตาม
  `section_id` ที่ขอ ตัวกรองยังทำหน้าที่เดิมของมัน แค่ไม่ทำงานเพราะเรื่องอาจารย์อีก

## ผลที่ตามมา

- `GET /course?section_id=` ที่ชี้ไปที่ section ซึ่งไม่มีอาจารย์ เปลี่ยนจาก
  `data: null` เป็นตัว section เต็ม ๆ — เป็นการเปลี่ยนรูปของ response ที่ผู้เรียก
  ทุกรายเห็น บันทึกไว้ใน `BEHAVIOR-CHANGES.md`
- `getUserDetail("")` ไม่ถูกเรียกอีก การเรียกถูกย้ายไปอยู่หลังการตรวจว่ามีอาจารย์
  หรือไม่ — query ที่หายไปเป็นผลพลอยได้ ไม่ใช่เป้าหมาย
- test สามเคสที่เคย pin พฤติกรรมเดิมไว้ (ใน `course.test.ts`, `student.test.ts`,
  `student-calendar.test.ts`) ถูกเขียนใหม่ให้ยืนบนพฤติกรรมใหม่ ไม่ได้ลบทิ้ง
- `enrolledCourse()` ใน `test/helpers/classroom.ts` ยังสร้างอาจารย์มาให้ด้วย แต่
  ความหมายเปลี่ยน — เดิมมันคือสิ่งที่ทำให้ section มองเห็นได้ ตอนนี้มันมีไว้ให้เคส
  ที่ต้องอ่านชื่ออาจารย์ออกจาก response เท่านั้น เขียนไว้ใน doc comment ของมันแล้ว
- ฐานข้อมูลที่ใช้พัฒนาอยู่ยังไม่มี section สักแถว (`course_sections` ว่าง) การ
  เปลี่ยนแปลงนี้จึงยังไม่กระทบข้อมูลจริงที่ import เข้าไปเมื่อ 9 สิงหาคม 2569

## จะกลับมาทบทวนเมื่อไหร่

เมื่อมี endpoint ที่จัดอาจารย์ให้ section ได้ — ตอนนั้น "ยังไม่มีอาจารย์" จะกลาย
เป็นสถานะที่มีคนแก้ได้จากในระบบ และคำถามว่าใครควรเห็นว่ามันค้างอยู่ (หน้าจอของ
เจ้าหน้าที่หลักสูตร?) จะเป็นคำถามที่ตอบได้จริง ต่างจากตอนนี้ที่คำตอบเดียวคือ import
รอบถัดไป
