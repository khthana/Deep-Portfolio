# ADR-0025 — คำเชิญออกใหม่ได้ ด้วยเส้นทางของตัวเอง

- **สถานะ**: ตัดสินแล้ว 13 สิงหาคม 2569
- **ที่มา**: [issue #57](https://github.com/khthana/Deep-Portfolio/issues/57)
- **เกี่ยวข้อง**: [ADR-0004](0004-group-leader.md) ตัดสินว่าสมาชิกภาพของกลุ่มเป็น
  ของหัวหน้ากลุ่ม ไฟล์นี้ใช้กติกานั้นกับการเชิญซ้ำ · [ADR-0017](0017-group-membership-means-accepted.md)
  ตัดสินว่า `members` แปลว่าคนที่ตอบรับแล้ว ซึ่งเป็นเหตุผลที่คนที่ยังไม่ตอบรับ
  "หายไป" จากทุกที่ที่นับสมาชิก · [ADR-0024](0024-unsubmitted-work-shares-the-roster.md)
  ข้อ 3 ชี้ไว้แล้วว่าแถวสมาชิกที่ปฏิเสธไปแล้วยังอยู่ และผูกข้อจำกัดนั้นไว้กับ #57

## บริบท

โทเค็นคำเชิญเกิดขึ้นได้แค่สองจังหวะ คือตอนสร้างกลุ่ม และตอน `PATCH` เพิ่มคนที่ยัง
ไม่เคยอยู่ในกลุ่มนี้เข้ามา ทั้งสองจังหวะให้เวลาเจ็ดวันเท่ากัน และ `acceptInvite`
กับ `validateInvite` ต่างก็ค้นด้วยเงื่อนไข `token_expiry: { gte: new Date() }`
โทเค็นที่เลยเจ็ดวันจึงไม่ถูกพบ และคนถือลิงก์ได้ `400` พร้อมประโยค
"โทเค็นคำเชิญไม่ถูกต้องหรือหมดอายุแล้ว"

หลังจากนั้นไม่มีปุ่มไหนออกโทเค็นใหม่ได้:

- **`PATCH` คัดโทเค็นเดิมกลับมา** ทางแก้ไขกลุ่มลบแถวสมาชิกทั้งชุดแล้วสร้างใหม่
  และสำหรับคนที่อยู่ในกลุ่มเดิมอยู่แล้ว มันเขียน `invite_token` กับ `token_expiry`
  ค่าเดิมกลับลงไป (`student-activity-group.service.ts` และฝั่งคู่แฝด) หัวหน้ากลุ่ม
  ที่กด "แก้ไข" แล้วกด "บันทึก" โดยไม่เปลี่ยนอะไรเลย จึงได้ลิงก์ที่ตายแล้วกลับมา
  ตายเหมือนเดิม
- **ทางอ้อมที่มีอยู่คือถอดชื่อออก บันทึก แล้วใส่กลับ บันทึกอีกครั้ง** ต้องเป็นสอง
  ครั้งจริง ๆ เพราะถ้าอยู่ในรายชื่อที่ส่งมาด้วยกัน เขาก็ยังนับเป็นคนเดิมและได้โทเค็น
  เดิม ทางนี้ได้ผล แต่ราคาคือหัวหน้ากลุ่มต้องรู้ว่ามันเป็นทางแก้ ต้องเขียนรายชื่อ
  ทั้งชุดใหม่สองรอบ และแถวสมาชิกเดิมถูกทำลายไปพร้อมกับสิ่งที่มันบันทึกไว้

ผลคือนักศึกษาที่ปล่อยให้ครบเจ็ดวันติดค้างอยู่ที่ `PENDING` เขาไม่ถูกนับเป็นสมาชิก
(ADR-0017) จึงไม่ได้คะแนนของกลุ่ม และหนทางกลับเข้ามามีอยู่ทางเดียวคือท่าที่ไม่มีใคร
เดาถูก

## สิ่งที่ต้องตัดสิน

1. ใครกดส่งคำเชิญซ้ำได้
2. ส่งซ้ำให้สมาชิกสถานะไหนได้บ้าง
3. มีเพดานการส่งซ้ำไหม
4. ทาง `PATCH` ที่คัดโทเค็นเดิมกลับมา ควรทำอย่างไร

**ข้อ 3 ของ #57 เองตกไป** ตัว issue ถามว่า "โทเค็นเดิมควรถูกยกเลิกไหม" ซึ่งไม่ใช่
คำถามที่ตอบได้สองทาง แถวสมาชิกมีคอลัมน์โทเค็นเดียว การเขียนโทเค็นใหม่**คือ**การ
ยกเลิกอันเก่า จะเก็บทั้งสองอันไว้พร้อมกันต้องมีตารางคำเชิญแยกออกมา ซึ่งเกินกว่าที่
ปัญหานี้เรียกร้อง — แก้ตัว issue แล้ว

## การตัดสิน

> **การเชิญซ้ำเป็นเส้นทางของตัวเอง ไม่ใช่ผลข้างเคียงของการแก้ไขกลุ่ม**
> `POST /student-activity-group/resend-invite` และคู่แฝดฝั่ง learning ทำอย่างเดียว
> คือเปลี่ยนโทเค็นบนแถวสมาชิกหนึ่งแถวแล้วส่งอีเมล

### 1. หัวหน้ากลุ่มอย่างเดียว

`requireGroupLeader` ตัวเดิมบนเส้นทางใหม่ ด้วยประโยคปฏิเสธเดิม
(`NOT_GROUP_LEADER` — "เฉพาะหัวหน้ากลุ่มเท่านั้นที่แก้ไขกลุ่มได้") การเปลี่ยนโทเค็น
บนแถวสมาชิกเป็นการเปลี่ยนกลุ่มในความหมายเดียวกับการยุบกลุ่ม ซึ่งเป็นเหตุผลที่
comment ของ middleware ตัวนั้นให้ไว้เองอยู่แล้วว่าทำไมประโยคเดียวจึงคลุมทั้งสองอย่าง

ทางที่ไม่เลือกคือให้เจ้าตัวกดขอลิงก์ใหม่เอง — คนที่คำเชิญหมดอายุมักไม่รู้ด้วยซ้ำว่า
เคยมีคำเชิญ และหน้าจอที่เขาจะกดยังไม่มี เพราะเขาไม่ใช่สมาชิกของกลุ่มไหนในสายตาระบบ

### 2. เฉพาะคนที่ยังไม่ตอบรับ

`PENDING` เท่านั้น `ACCEPT` ไม่มีอะไรให้เชิญ ส่วน `REJECTED` **ตอบไปแล้ว** — การไป
ถามซ้ำคนที่ปฏิเสธเป็นการตัดสินใจของคนที่ดูแลรายวิชา ไม่ใช่ของโค้ด เส้นทางนี้จึงไม่
ทำให้มันเกิดขึ้นเงียบ ๆ คำปฏิเสธเป็น `400` พร้อมประโยค
"ส่งคำเชิญซ้ำได้เฉพาะสมาชิกที่ยังไม่ตอบรับคำเชิญ"

หัวหน้ากลุ่มที่อยากได้คนที่ปฏิเสธกลับมาจริง ๆ ยังทำได้ด้วยทางอ้อมเดิม คือถอดชื่อ
ออกแล้วใส่กลับ ซึ่งออกโทเค็นใบใหม่ให้เอง — ตั้งใจให้มันยังต้องตั้งใจ

### 3. ไม่มีเพดาน

ไม่นับจำนวนครั้ง ไม่หน่วงเวลา การส่งซ้ำเปิดได้เฉพาะหัวหน้ากลุ่มของกลุ่มนั้น กับ
สมาชิกที่ยังไม่ตอบรับเท่านั้น ราคาที่แพงที่สุดของการกดรัว ๆ คืออีเมลซ้ำหลายฉบับถึง
เพื่อนร่วมกลุ่มของคนกดเอง ซึ่งไม่ใช่การโจมตีระบบ การนับครั้งต้องมีคอลัมน์หรือที่เก็บ
เพิ่ม และจะกลายเป็นกติกาที่ต้องอธิบายให้ผู้ใช้ฟังโดยไม่มีปัญหาจริงรองรับ

**นี่เป็นช่องที่รู้ตัว** ถ้าวันหนึ่งการส่งอีเมลมีค่าใช้จ่ายต่อฉบับ หรือมีการร้องเรียน
เรื่องอีเมลรบกวน เพดานควรอยู่ที่ระดับผู้ส่งอีเมล ไม่ใช่ที่ endpoint นี้ตัวเดียว

### 4. ปล่อย `PATCH` ไว้อย่างเดิม

การคัดโทเค็นเดิมกลับมาไม่ใช่จุดบกพร่องเมื่อมีเส้นทางส่งซ้ำแล้ว มันหมายความว่า
"แก้ไขรายชื่อ" ไม่ไปยุ่งกับคำเชิญที่ค้างอยู่ ซึ่งเป็นพฤติกรรมที่อธิบายง่ายกว่า

ทางที่ไม่เลือกคือให้ `PATCH` ออกโทเค็นใหม่ให้ทุกคนที่ยัง `PENDING` — ผลคือการแก้ชื่อ
คนเดียวจะยิงอีเมลถึงทุกคนที่ยังไม่ตอบ และหัวหน้ากลุ่มจะไม่มีทางแก้รายชื่อโดยไม่
รบกวนใครเลย

## สถานะที่ตอบกลับ

- **`404` เมื่อไม่มีแถวสมาชิกของนักศึกษาคนนั้นในกลุ่มนั้น** ("ไม่พบสมาชิกคนนี้ในกลุ่ม")
  ไม่ใช่ `400` แบบที่ [ADR-0020](0020-mapping-names-own-submission.md) ให้ไว้ กติกา
  ของ ADR-0020 คลุม id ที่เป็น**ค่าอยู่ข้างในแถวที่กำลังเขียน** แต่ที่นี่แถวสมาชิก
  **คือ**สิ่งที่ทั้ง endpoint กระทำต่อ ซึ่งเป็นกรณีของ
  [ADR-0009](0009-submission-ownership.md) ข้อ 3 และ [ADR-0012](0012-missing-row-status.md)
- **`400` เมื่อสมาชิกไม่ได้อยู่ที่ `PENDING`** ตามข้อ 2
- **`403` เมื่อคนขอไม่ใช่หัวหน้ากลุ่ม รวมทั้งเมื่อไม่มีกลุ่มนั้นอยู่จริง** เป็น
  พฤติกรรมเดิมของ `requireGroupLeader` ไม่ใช่สิ่งที่ไฟล์นี้เลือกใหม่

## ผลที่ตามมา

- **`mintInvite` เป็นที่เดียวที่รู้ว่าคำเชิญมีอายุเจ็ดวัน** เดิมสามบรรทัดนี้ถูกเขียน
  ซ้ำสี่ที่ (สร้างกลุ่มและแก้ไขกลุ่ม ฝั่งละสองที่) และ #57 จะเป็นที่ที่ห้า ตอนนี้ทั้ง
  ห้าเรียกฟังก์ชันเดียวใน `group.service.ts` ที่อยู่ข้าง `sendInviteEmail` ซึ่งเป็น
  ตัวที่บอกนักศึกษาว่า "ลิงก์นี้จะหมดอายุใน 7 วัน"
- **การส่งอีเมลล้มเหลวถูกบันทึกไว้ ไม่ถูกโยนต่อ** เหมือนสองทางที่ส่งคำเชิญครั้งแรก
  ตอนที่ส่งอีเมล แถวถูกเขียนไปแล้ว การโยน error จะบอกหัวหน้ากลุ่มว่าล้มเหลวทั้งที่
  โทเค็นถูกเปลี่ยนไปจริง และลิงก์เก่าตายไปแล้วอยู่ดี กดใหม่ได้เสมอ เสียแค่โทเค็นอีกอัน
- **หน้าจอ "กลุ่มของฉัน" มีลิงก์ "ส่งคำเชิญอีกครั้ง"** ขึ้นเฉพาะกับหัวหน้ากลุ่ม บน
  แถวที่ `PENDING` และเฉพาะตอนที่ไม่ได้อยู่ในโหมดแก้ไข — กติกาสองข้อแรกซ้ำกับที่ API
  บังคับ ข้อสามเป็นเรื่องของหน้าจอเอง เพราะโหมดแก้ไขมีปุ่มลบอยู่ที่เดิม
- **สำเร็จแล้วหน้าจอไม่เปลี่ยน** สถานะยังเป็น "รออนุมัติ" อยู่เหมือนเดิม เพราะมันเป็น
  อย่างนั้นจริง toast จึงเป็นคำตอบทั้งหมดที่ผู้กดได้รับ และตอนล้มเหลวหน้าจอเลือกแสดง
  ประโยคจาก API ก่อนประโยคของตัวเอง (ADR-0022) เพราะประโยคนั้นคือสิ่งเดียวที่แยก
  "เขาเพิ่งกดตอบรับไปเมื่อครู่" ออกจาก "เขาไม่ได้อยู่ในกลุ่มนี้"

## จะกลับมาทบทวนเมื่อไหร่

- **เมื่อคำเชิญต้องมีมากกว่าหนึ่งฉบับต่อคน** เช่น อยากให้ลิงก์เก่ายังใช้ได้ระหว่างที่
  ออกอันใหม่ หรืออยากเก็บประวัติว่าเชิญไปกี่ครั้ง ทั้งสองอย่างต้องมีตารางคำเชิญของ
  ตัวเอง ไม่ใช่คอลัมน์บนแถวสมาชิก และเมื่อถึงตอนนั้นข้อ 3 ข้างบนจะมีที่ให้นับ
- **เมื่อ #64 ได้คำตอบ** ถ้าคนที่ไม่มีกลุ่มควรให้คะแนนได้ ความหมายของ "ค้างอยู่ที่
  PENDING" จะเปลี่ยนไปด้วย เพราะเขาจะไม่ใช่คนที่หลุดจากระบบอีกต่อไป
