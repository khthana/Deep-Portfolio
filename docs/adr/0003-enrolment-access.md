# ADR-0003 — นักศึกษาคนไหนเข้าถึงกลุ่มเรียนไหนได้

- **สถานะ**: ตัดสินแล้ว 10 สิงหาคม 2569
- **ที่มา**: [issue #26](https://github.com/khthana/Deep-Portfolio/issues/26)
- **เกี่ยวข้อง**: [ADR-0002](0002-section-access.md) (คำถามเดียวกันจากฝั่งอาจารย์),
  [ADR-0001](0001-portfolio-access.md) (ผู้กระทำคือเจ้าของ session),
  [#20](https://github.com/khthana/Deep-Portfolio/issues/20) (ฟิลด์บังคับของ query),
  [#27](https://github.com/khthana/Deep-Portfolio/issues/27) (การเขียนกลุ่ม)

## บริบท

ADR-0002 ปิดครึ่งแรกของคำถาม "ใครอยู่ในกลุ่มเรียนนี้" ไว้แล้ว คือฝั่งอาจารย์ และ
เขียนไว้ตรง ๆ ว่าครึ่งหลัง — ฝั่งนักศึกษา — ยังไม่มีที่ไหนในระบบตรวจอยู่เลย ไฟล์นี้
คือครึ่งหลังนั้น

`GET` ของกลุ่มมีหกตัว สามตัวต่อหนึ่งชนิดงาน (`activity` กับ `learning_activity`)
รูปเหมือนกันทุกประการ

| endpoint | คำขอระบุอะไร | ตอบอะไร |
| --- | --- | --- |
| `GET /` | นักศึกษา + ชิ้นงาน | กลุ่มของนักศึกษาคนนั้นในชิ้นงานนั้น |
| `GET /all` | นักศึกษา + กลุ่มเรียน | กลุ่มทั้งหมดของนักศึกษาคนนั้นในกลุ่มเรียนนั้น |
| `GET /without-group` | กลุ่มเรียน + ชิ้นงาน | รายชื่อคนในกลุ่มเรียนที่ยังไม่มีกลุ่ม |

ทั้งหกตัวไม่มี middleware อะไรเลยนอกจาก `validate` ไม่ต้องล็อกอินก็เรียกได้ และ
`student_id` มาจาก query string ผลคือใครก็ได้ที่เดา `student_id` ถูก — ซึ่งเป็นรหัส
นักศึกษาแปดหลักที่เพื่อนร่วมชั้นรู้กันหมด — อ่านได้ว่าคนนั้นอยู่กลุ่มไหนกับใครบ้าง
ส่วน `/without-group` คายรายชื่อและชื่อ-นามสกุลจริงของทั้งกลุ่มเรียนโดยไม่ต้องระบุ
ตัวตนอะไรเลย

#20 ทำให้ `student_id` เป็นฟิลด์บังคับไปแล้ว (ก่อนหน้านั้นการไม่ส่งมาแปลว่า
`some: { student_id: undefined }` ซึ่ง Prisma อ่านเป็น "ไม่กรอง" ไม่ใช่ "ไม่ตรงกับ
อะไรเลย" `/all` จึงคายกลุ่มทั้งหมดของกลุ่มเรียนพร้อมรายชื่อสมาชิก) แต่ #20 หยุดไว้
ที่รูปของคำขอ ไม่ได้แตะว่าใครมีสิทธิ์ถาม

## สิ่งที่ต้องตัดสิน

1. `student_id` ของสาม `GET` มาจากไหน — query อย่างที่เป็นอยู่ หรือ session
2. `/without-group` ซึ่งไม่ได้ระบุนักศึกษาเลย ใช้อะไรตัดสินว่าใครถามได้

## การตัดสิน

### 1. มาจาก session

> การอ่านกลุ่มเป็นการอ่านของนักศึกษาที่ล็อกอินอยู่เท่านั้น `student_id` หายไปจาก
> query string ทั้งสองไฟล์ schema และ controller อ่านจาก session แทน

กติกาเดียวกับ ADR-0001 และกับ `created_by` ของ ADR-0002 — **ผู้กระทำคือเจ้าของ
session เสมอ ไม่ใช่คนที่คำขอบอกว่าเป็น** ฟิลด์ที่หายไปจาก schema จะส่งมาก็ไม่มีผล
คำขอที่ระบุ `student_id` ของเพื่อนจึงได้กลุ่มของตัวเองกลับไป ไม่ใช่ `403` เพราะไม่มี
อะไรให้ปฏิเสธแล้ว — มันไม่ใช่พารามิเตอร์อีกต่อไป

ทางเลือกอีกทางคือเก็บ `student_id` ไว้ใน query แล้วเพิ่ม middleware ตรวจว่าตรงกับ
session (แบบ `requireSelf` ของ ADR-0001) ไม่เลือกทางนั้นเพราะที่นี่พารามิเตอร์ไม่มี
ประโยชน์อะไรเลยนอกจากทำให้ผิดได้ — `requireSelf` มีอยู่เพราะ `user_id` อยู่ใน path
ของ REST resource ส่วนตรงนี้เป็นแค่ query ที่ frontend เติมค่าของตัวเองลงไปทุกครั้ง

ตรวจแล้วว่าผู้เรียกทั้งสามที่ใน `apps/web` ส่ง `student_id` ของคนที่ล็อกอินอยู่
เสมอ — `submit-classwork-section.tsx` และ `create-groupwork-section.tsx` ทั้งคู่อ่าน
จาก `classworkDetail.student_id` ของหน้าที่นักศึกษาเปิดอยู่ การตัดฟิลด์ทิ้งจึงไม่ได้
ทำให้หน้าไหนขออะไรไม่ได้

### 2. `/without-group` ใช้การลงทะเบียนเรียน

> นักศึกษาอ่านรายชื่อของกลุ่มเรียนที่ตัวเองลงทะเบียนเรียนเท่านั้น "ลงทะเบียน" คือมี
> แถวใน `student_course` ที่ `section_id` ตรงกับที่คำขอระบุ และ `student_id` ตรงกับ
> เจ้าของ session

ไม่ผ่านแล้วได้ `403` พร้อมข้อความเดียวกับ ADR-0002 —
`{ "success": false, "message": "คุณไม่มีสิทธิ์เข้าถึงข้อมูลของกลุ่มเรียนนี้" }`
เพราะจากมุมผู้เรียกมันคือคำตอบเดียวกัน คือ "กลุ่มเรียนนี้ไม่ใช่ของคุณ" และกลุ่มเรียน
ที่ไม่มีอยู่จริงก็ตอบ `403` เหมือนกัน ด้วยเหตุผลของ ADR-0002 ทุกข้อ — `section_id`
เป็นจำนวนเต็มเรียงกัน

เลือกความสัมพันธ์นี้ด้วยเหตุผลเดียวกับที่ ADR-0002 เลือก `course_sections_teacher`
คือเป็นความสัมพันธ์เดียวที่มีอยู่จริงในฐานข้อมูลแล้ว และเป็นแถวเดียวที่ค้นเจอด้วย
primary key `(section_id, student_id)` ที่มีอยู่ก่อนแล้ว

### ทำไม `/` กับ `/all` ไม่ต้องตรวจกลุ่มเรียนซ้ำ

เพราะ session แคบพอแล้ว ทั้งคู่กรองด้วยนักศึกษาที่ล็อกอินอยู่ ถ้าถามถึงกลุ่มเรียนหรือ
ชิ้นงานที่ตัวเองไม่ได้เกี่ยวข้อง คำตอบคือ `null` หรือ `[]` ซึ่งไม่ได้บอกอะไรที่ผู้ถาม
ยังไม่รู้ ส่วน `/without-group` ระบุกลุ่มเรียนแต่ **ไม่ระบุนักศึกษา** session จึงไม่ได้
แคบคำตอบเลย ต้องมี middleware มาแคบให้ นี่คือเส้นแบ่งว่าทำไม endpoint หนึ่งมี
`requireEnrolledSection` และอีกสองตัวไม่มี

### ทั้งหกตัวเป็นของนักศึกษาเท่านั้น

`requireRole("STUDENT")` เหมือนกับ `POST`/`PATCH` ของ router เดียวกันที่มีอยู่แล้ว
อาจารย์ได้ `403` พร้อม `"สิทธิ์การเข้าถึงเฉพาะนักศึกษาเท่านั้น"` ไม่มีหน้าไหนของ
อาจารย์ใน `apps/web` เรียก endpoint ทั้งหกตัวนี้ — ผู้เรียกทุกตัวอยู่ใต้
`features/student/` ถ้าวันหนึ่งอาจารย์ต้องเห็นกลุ่มของทั้งกลุ่มเรียน นั่นคือคำตอบคนละ
รูป (ทุกกลุ่ม ไม่ใช่กลุ่มของคนถาม) ควรเป็น endpoint ของตัวเองที่ใช้
`requireOwnSection` ไม่ใช่การผ่อนเงื่อนไขของหกตัวนี้

### middleware อยู่หลัง `validate`

เหมือน ADR-0001 และ ADR-0002 ทุกประการ ลำดับของ `/without-group` คือ `requireRole`
→ `validate` → `requireEnrolledSection` คำขอที่ไม่ระบุ `section_id` จึงเป็น `400`
ไม่ใช่ `403`

## ผลที่ตามมา

- `requireEnrolledSection` อยู่ใน `apps/api/src/middlewares/owner.middleware.ts`
  ข้าง `requireOwnSection` ทั้งคู่สร้างจาก `sectionRule` ตัวเดียวกัน ต่างกันแค่
  ตารางที่ใช้ตอบว่า "อยู่ในกลุ่มเรียนนี้ไหม" — `course_sections_teacher` สำหรับ
  อาจารย์ `student_course` สำหรับนักศึกษา บทบาทใหม่ที่ต้องเข้าถึงกลุ่มเรียนจึงเพิ่ม
  ได้ด้วยการเขียนฟังก์ชันค้นแถวอีกหนึ่งตัว
- ตอนนี้คำถาม "ใครอยู่ในกลุ่มเรียนนี้" มีคำตอบครบทั้งสองด้านแล้ว ตามที่ ADR-0002
  ค้างไว้
- สัญญากับ frontend เปลี่ยน — `student_id` หายไปจาก params สามตัวใน
  `apps/web/src/features/student/course/types/course-type.ts` ดู
  [`BEHAVIOR-CHANGES.md`](../../BEHAVIOR-CHANGES.md)
- **การเขียนกลุ่มยังไม่ได้ตรวจอะไรเลย** — `POST`/`PATCH` ของทั้งสอง router รับ
  `members` มาทั้งก้อนโดยไม่ตรวจว่าผู้เรียกอยู่ในนั้น ไม่ตรวจว่าเป็น `LEADER` และไม่
  ตรวจว่าสมาชิกที่ระบุลงทะเบียนกลุ่มเรียนเดียวกัน นักศึกษาจึงยังจับเพื่อนเข้ากลุ่มหรือ
  รื้อกลุ่มของคนอื่นได้ อยู่ที่ [#27](https://github.com/khthana/Deep-Portfolio/issues/27)
  ซึ่งใช้ `student_course` ตัวเดียวกันนี้ตอบได้
- endpoint อื่นของฝั่งนักศึกษาที่ระบุกลุ่มเรียนหรือชิ้นงานแล้วยังไม่ได้ตรวจการ
  ลงทะเบียน ยังมีอยู่ ไม่ได้ไล่ใน #26 เพราะเกณฑ์ยอมรับพูดถึงสาม `GET` ของกลุ่ม
  เท่านั้น แต่ `requireEnrolledSection` ใช้ได้ทันทีทุกตัวที่ `section_id` อยู่ใน query
  หรือ body

## จะกลับมาทบทวนเมื่อไหร่

เมื่อมีคนที่ต้องอ่านกลุ่มของกลุ่มเรียนที่ตัวเองไม่ได้เรียน — อาจารย์ที่ดูภาพรวมกลุ่ม
หรือผู้ช่วยสอน — ให้เพิ่มเป็น endpoint ของตัวเองที่ใช้ `requireOwnSection` ไม่ใช่
เพิ่มสาขาให้หกตัวนี้ เพราะคำตอบที่ต้องการเป็นคนละรูปกัน
