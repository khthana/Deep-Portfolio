# ADR-0016 — ไฟล์ที่อัปโหลดแล้ว ถูกเก็บคืนเมื่อ transaction ไม่ commit

- **สถานะ**: ตัดสินแล้ว 12 สิงหาคม 2569
- **ที่มา**: [issue #50](https://github.com/khthana/Deep-Portfolio/issues/50)
- **เกี่ยวข้อง**: [ADR-0008](0008-attachment-lifecycle.md) ตัดสินฝั่ง **ลบ** ไว้แล้ว
  — นับ reference ใน transaction แล้วลบ object หลัง commit ไฟล์นี้คือฝั่ง
  **สร้าง** ซึ่ง ADR-0008 ไม่ได้พูดถึงเลย

## บริบท

`AttachmentsService.createAttachments` รับ `tx` เป็นอาร์กิวเมนต์ตัวที่สามได้
(`const prismaClient = tx ?? prisma;`) ทั้งระบบเรียกมัน 24 จุด ในนั้น 11 จุดอยู่ใน
`$transaction` แต่มีแค่สี่จุด — ทางส่งงานทั้งสี่ของ `student.service.ts` — ที่ส่ง
`tx` เข้าไปจริง อีกเจ็ดจุดเขียนแถว `attachments` ด้วย client นอก transaction แถวจึง
commit ทันทีและไม่ย้อนกลับพร้อมกับสิ่งที่ล้อมมันอยู่ (อีก 13 จุดที่เหลือเป็นของ
e-Portfolio ซึ่งไม่มี transaction ล้อมอยู่เลย — ดูข้อ 2)

ผลที่ตามมามีสองชั้น และชั้นที่สองหนักกว่า

**แถวกำพร้าในฐานข้อมูล** `POST /course-material` ที่อ้างสัปดาห์ซึ่งไม่มีอยู่จริง
สร้างแถว `attachments` สำเร็จ แล้วโดน foreign key ของ `course_material` ปฏิเสธ
transaction ย้อนกลับเฉพาะแถว `course_material` ที่ไม่เคยถูกเขียนสำเร็จอยู่แล้ว
ส่วนแถว `attachments` ค้างอยู่โดยไม่มีตารางเชื่อมไหนชี้ถึง — อ่านไม่เจอผ่าน
endpoint ไหนเลย เพราะทุกทางอ่านเริ่มจากตารางเชื่อม (เหตุผลเดียวกับ ADR-0008)

**object ที่ค้างในถังโดยไม่มีใครรู้ key** ร้ายกว่า เพราะ MinIO ไม่ได้อยู่ใน
transaction ของ Postgres และย้อนกลับไม่ได้ ที่เดียวที่เคยจด key ของไฟล์ไว้คือ
`attachments.file_path` ของแถวที่กำลังจะหายไป พอแถวย้อนกลับ ไฟล์นั้นก็ค้างอยู่ใน
ถังโดยไม่มีอะไรในระบบชี้ถึงมันอีกเลย แม้แต่งานกวาดถังที่เทียบ key กับ
`attachments.file_path` — ซึ่ง ADR-0008 เขียนไว้ว่าอาจทำวันหน้า — ก็จะเก็บมันไป
เพราะมันดูเหมือนขยะจริง ๆ

## สิ่งที่ต้องตัดสิน

1. object ที่อัปโหลดไปแล้วก่อน transaction ล้ม จะจัดการอย่างไร
2. แก้เฉพาะเส้นที่ #50 ชี้ หรือทุกจุดที่มีอาการเดียวกัน
3. รูปของ API ที่จะเรียกใช้ — ใครเป็นคนจำว่าอัปโหลดอะไรไปแล้วบ้าง

## การตัดสิน

> **ห่อ transaction ที่มีการอัปโหลดไว้ใน `transactionWithUploads` ซึ่งส่ง `tx`
> ให้แถวย้อนกลับได้ และเรียก `removeFiles` เก็บ object คืนเมื่อ transaction
> ไม่ commit**

### 1. เก็บ object คืน ไม่ใช่ปล่อยค้าง

ทางเลือกที่ #50 เสนอไว้สองทาง คือปล่อยไฟล์กำพร้าค้างในถังแล้วแก้เฉพาะแถว หรือจับ
error แล้วเรียก `removeFiles` ตามเก็บ เลือกทางหลัง

`removeFiles` มีอยู่แล้วและถูกออกแบบมาให้พังเงียบได้พอดี — มัน log แล้วจบ ไม่
throw ต่อ ซึ่งเป็นสิ่งที่ต้องการตรงนี้ด้วย: คำขอกำลังจะตอบ error อยู่แล้ว การที่
ถังเก็บกวาดไม่สำเร็จไม่ควรไปเปลี่ยนว่าผู้เรียกได้ error ตัวไหน ตัว error เดิมต้อง
ถึงมือ `errorHandler` ให้ครบ

ตารางของ ADR-0008 ข้อ 2 กลับด้านได้พอดีสำหรับฝั่งสร้าง

| ลำดับ | เมื่อฝั่งที่สองพัง | คนอ่านเห็นอะไร |
| --- | --- | --- |
| เขียนแถวก่อน แล้วอัปโหลด | แถวชี้ไปยังไฟล์ที่ไม่มี | ดาวน์โหลดแล้วได้ `404` |
| อัปโหลดก่อน แล้วเขียนแถว | ไฟล์อยู่ในถัง ไม่มีแถวชี้ | ไม่เห็นอะไรเลย เปลืองเนื้อที่ |

ลำดับที่โค้ดใช้อยู่คืออย่างหลัง และถูกแล้ว — ทิศทางของความผิดพลาดตกไปทางที่คนอ่าน
ไม่เห็น เหมือนฝั่งลบ สิ่งที่ #50 เพิ่มเข้ามาคือ **ตามเก็บส่วนที่เปลืองเนื้อที่นั้น
ด้วย** ในเมื่อรู้อยู่แล้วว่าเพิ่งอัปโหลดอะไรไปในคำขอนี้

### 2. แก้ทั้งเจ็ดจุด ไม่ใช่แค่เส้นที่ตั้งเรื่อง

| ไฟล์ | เมธอด |
| --- | --- |
| `course-material.service.ts` | `createCourseMaterial` (สองรอบ — lecture และ record) |
| `activity.service.ts` | `createActivity`, `updateActivity` |
| `learning-activity.service.ts` | `createLearningActivity`, `updateLearningActivity` |
| `announcement.service.ts` | `createAnnouncement` |

ทั้งเจ็ดจุดมีอาการเดียวกันตัวอักษรต่อตัวอักษร และ `activity.service.ts` มี comment
เขียนกำกับไว้แล้วสองแห่งว่า "createAttachments ไม่ย้อนกลับพร้อม transaction นี้" —
เป็นเหตุผลที่มันย้ายการตรวจ rubric กับหมวดคะแนนขึ้นไปไว้หน้าสุด comment ทั้งสอง
ถูกเขียนใหม่แล้ว: การตรวจยังอยู่ที่เดิมเพราะการปฏิเสธที่ไม่เคยอัปโหลดอะไรเลยยังถูก
กว่าการอัปโหลดแล้วตามเก็บ แต่เหตุผลไม่ใช่ "ตามเก็บไม่ได้" อีกต่อไป

**สี่จุดใน `student.service.ts` อยู่นอกขอบเขตที่ #50 ตั้งไว้** ขอบเขตนั้นคือจุดที่
เรียก `createAttachments` ใน `$transaction` โดยไม่ส่ง `tx` และทั้งสี่จุดส่งอยู่แล้ว
— แถวของมันย้อนกลับถูกต้องมาตั้งแต่ต้น ที่ยังขาดคือครึ่งหลัง คือ object ยังไม่ถูก
เก็บคืน ยกไปเป็น [#52](https://github.com/khthana/Deep-Portfolio/issues/52) ไม่ใช่
เพราะแก้ไม่ได้ แต่เพราะทั้งสี่เป็นทางส่งงานซ้ำที่ ADR-0008 มีกติกาเรื่องลำดับการ
กวาดเฉพาะของมันอยู่ ([ดูหัวข้อ "ลำดับของการกวาดในทางที่ส่งงานซ้ำ"](0008-attachment-lifecycle.md))
กติกานั้นต้องมี test ของมันเองยืนยันว่าไม่ขยับ ซึ่งเป็นงานคนละก้อนกับที่ #50
ตั้งเรื่องไว้

**จุดที่อยู่นอก transaction ไม่นับ** 13 จุดที่เหลืออยู่ใน service ของ e-Portfolio
ทั้งเจ็ดตัว (`portfolio-{activity,award,certificate,internship,thesis,training}`
ตัวละสองจุด และ `portfolio-personal` อีกหนึ่ง) ทุกจุดเรียก `createAttachments`
ด้วย `prisma` เปล่า ๆ นอก `$transaction` — `$transaction` ที่มีอยู่ในไฟล์พวกนี้
เป็นบล็อกสั้น ๆ ของฝั่งลบตาม ADR-0008 ซึ่งปิดไปก่อนบรรทัดที่สร้างไฟล์แนบแล้ว
ตรงนั้นจึงไม่มี transaction ให้ขัดกัน มันเป็นปัญหาคนละข้อ — การเขียนหลายก้าวโดย
ไม่มี transaction เลย — ที่ #50 ไม่ได้ตั้งเรื่องไว้ และไม่ได้แก้

### 3. อาร์เรย์ที่เป็นของคำขอ ไม่ใช่ของ service

```ts
export async function transactionWithUploads<T>(
  work: (tx: Prisma.TransactionClient, uploads: string[]) => Promise<T>,
): Promise<T>
```

`createAttachments` รับ `uploads` เป็นอาร์กิวเมนต์ตัวที่สี่ แล้ว push key ของทุก
object ที่มันเพิ่งอัปโหลดลงไป **ก่อน** เขียนแถว จุดนั้นคือจุดเดียวที่ยังรู้ key
โดยไม่ต้องพึ่งแถวที่อาจจะย้อนกลับ

อาร์เรย์เป็นของ `transactionWithUploads` แต่ละครั้งที่ถูกเรียก ไม่ใช่ field ของ
`AttachmentsService` — service ถูกสร้างครั้งเดียวต่อ controller และใช้ร่วมกันทุก
คำขอ ถ้าเก็บสถานะไว้ในตัวมัน สองคำขอที่อัปโหลดพร้อมกันจะลบไฟล์ของกันและกัน

เป็น **ฟังก์ชันที่ export ออกมาต่างหาก** ไม่ใช่เมธอดของคลาส เพราะมันไม่ได้อ่าน
field ไหนของ `AttachmentsService` เลย มันอยู่ในไฟล์เดียวกับ `createAttachments`
เพราะสองตัวนี้ผูกกันด้วยสัญญาเดียว — ตัวหนึ่งเติมอาร์เรย์ อีกตัวหนึ่งอ่านมัน คนที่
มาแก้ตัวใดตัวหนึ่งต้องเห็นอีกตัว

**`tx` กับ `uploads` แยกกันได้ในลายเซ็น และนั่นคือช่องที่รู้ตัว** ทั้งคู่เป็น
อาร์กิวเมนต์ที่ไม่บังคับ คนเขียนโค้ดใหม่จึงส่ง `tx` โดยลืม `uploads` ได้ แล้วแถวจะ
ย้อนกลับส่วนไฟล์จะค้าง — คือครึ่งเดียวของการแก้ครั้งนี้ โดยไม่มี typecheck ไหนทัก
รวมทั้งคู่เป็นพารามิเตอร์ตัวเดียวจะปิดช่องนี้ได้ด้วย type แต่ทำไม่ได้ในรอบนี้ เพราะ
สี่จุดใน `student.service.ts` ที่ยกไป #52 ส่ง `tx` โดยไม่มี `uploads` อยู่จริง ๆ
และต้องส่งแบบนั้นต่อไปจนกว่า #52 จะเข้ามา ตอนที่ #52 ปิด ลายเซ็นควรถูกบีบให้รับ
ทั้งคู่พร้อมกัน แล้วช่องนี้จะปิดไปเอง

`return await` ใน `try` ไม่ใช่ความฟุ่มเฟือย ถ้าคืน promise ออกไปโดยไม่ `await`
`catch` จะไม่ทำงานเลย และการแก้ทั้งหมดนี้จะเงียบ ๆ ไม่มีผล

## ผลที่ตามมา

- **ผู้เรียกไม่เห็นความต่างในคำตอบ** status และ body เหมือนเดิมทุกจุด รวมทั้งเส้นที่
  ยังตอบ `500` อยู่ สิ่งที่เปลี่ยนคือสถานะของฐานข้อมูลและของถังหลังคำขอที่ล้มเหลว
  ดู [`BEHAVIOR-CHANGES.md`](../../BEHAVIOR-CHANGES.md)
- **การอัปโหลดเกิดขึ้นในขณะที่ transaction เปิดค้างอยู่** — เหมือนเดิมทุกประการ
  ลำดับไม่ได้ขยับ ที่เปลี่ยนคือแถวไปอยู่บน connection ของ `tx` ด้วย transaction
  ยาวเท่าเดิม
- **`P2003` ยังเป็น `500`** ไม่ได้แตะ ตรงกับที่ ADR-0012 ข้อ 3 ค้างไว้ และตรงกับ
  ขอบเขตของ #50 ซึ่งพูดถึงสถานะหลังคำขอที่ล้มเหลว ไม่ใช่รหัสที่มันตอบ
- **ถังพังตอนเก็บคืน = object ค้างเหมือนเดิม** `removeFiles` เป็น best-effort
  ตาม ADR-0008 การเก็บคืนนี้ปิดกรณีที่พบบ่อย ไม่ได้ให้การรับประกัน

## จะกลับมาทบทวนเมื่อไหร่

- เมื่อ [#52](https://github.com/khthana/Deep-Portfolio/issues/52) ถูกหยิบ — ทาง
  ส่งงานทั้งสี่ใน `student.service.ts` ได้ `transactionWithUploads` พร้อม test ที่
  ยืนบนลำดับของ ADR-0008 แล้วลายเซ็นของ `createAttachments` จะบีบ `tx` กับ
  `uploads` ให้มาด้วยกันได้
- เมื่อ e-Portfolio ได้ transaction ของตัวเอง ตอนนั้นเจ็ดจุดที่ยกเว้นไว้ข้างบนจะ
  เข้าเงื่อนไขเดียวกันทันที
