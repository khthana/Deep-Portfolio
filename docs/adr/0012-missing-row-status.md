# ADR-0012 — แถวที่ไม่มีอยู่ตอบ `404` ทั้งระบบ

- **สถานะ**: ตัดสินแล้ว 11 สิงหาคม 2569
- **ที่มา**: [issue #42](https://github.com/khthana/Deep-Portfolio/issues/42)
- **เกี่ยวข้อง**: [ADR-0009](0009-submission-ownership.md) ข้อ 1 วางเส้นแบ่งระหว่าง
  `400` กับ `403` ไว้ว่า "`403` เมื่อสิทธิ์ของผู้เรียกถูกปฏิเสธ `400` เมื่อค่าใน body
  ผิด" — ไฟล์นี้ต่อเส้นนั้นออกไปอีกช่อง คือ `404` เมื่อแถวที่ผู้เรียก**อ้างถึง**ไม่มีอยู่
  [ADR-0001](0001-portfolio-access.md) ไม่ได้ขวางเรื่องนี้: `requireOwnEntry` เขียนว่า
  `if (row && row.user_id !== session)` แถวที่ไม่มีอยู่จึงผ่านด่านไปถึง controller และ
  ได้ `404` ที่นั่น ไม่ใช่ `403` — ตรงตามที่ header ของ `owner.middleware.ts` ตั้งใจไว้
  ว่า "การพับสองเรื่องนี้เข้าด้วยกันจะเปลี่ยน `404` ทุกตัวในกลุ่มนี้ให้เป็น `403`"

## บริบท

Prisma ไม่คืน `null` เมื่อ `update` หรือ `delete` หาแถวเป้าหมายไม่เจอ — มัน **throw**
`PrismaClientKnownRequestError` รหัส `P2025` ส่วน `errorHandler` ไม่รู้จักรหัสนั้น
error ที่ไม่มีใครรู้จักจึงตกไปที่ `500` ผลคือคำขอที่ระบุ id ซึ่งไม่มีแถวรองรับ ได้คำตอบ
ว่า "เกิดข้อผิดพลาดภายในระบบ" ทั้งที่ไม่มีอะไรพังเลย

จุดนี้ถูก pin ไว้ตั้งแต่ #16/#17 พร้อมเหตุผลว่าการแก้ที่ `errorHandler` เปลี่ยนคำตอบของ
ทุก endpoint พร้อมกัน จึงควรเป็น ticket ของตัวเอง ตอนนั้นนับได้ 47 จุดใน 19 ไฟล์ test
ที่ยืนอยู่บน `expect(response.status).toBe(500)`

สิ่งที่ทำให้เรื่องนี้ไม่ใช่การ map รหัสเดียวจบ คือ `P2025` ไม่ได้แปลว่าอย่างเดียว
`connect: { score_ratio_id }` ใน `activity.service.ts` ก็โยน `P2025` ตัวเดียวกัน เมื่อ
ค่าที่มาจาก **body** ไม่ตรงกับแถวไหน ซึ่งตาม ADR-0009 เป็น `400` ไม่ใช่ `404`

## สิ่งที่ต้องตัดสิน

1. `404` มาจากที่เดียวหรือหลายที่ และผู้เรียกอ่านประโยคอะไร
2. `connect` ที่ค่ามาจาก body ตอบอะไร
3. รหัส Prisma ตัวอื่นที่ก็ทำให้เกิด `500` (`P2002`, `P2003`) อยู่ในขอบเขตนี้ไหม

## การตัดสิน

> **`errorHandler` แปลง `P2025` เป็น `404` เป็นพื้นทั้งระบบ เส้นที่มีประโยคของตัวเอง
> อยู่แล้วส่งประโยคนั้นเข้าไปที่จุดเรียก ส่วน `connect` ที่ค่ามาจาก body ถูกถามก่อนและ
> ตอบ `400`**

### 1. สองชั้น: พื้นของทั้งระบบ กับประโยคของแต่ละ resource

`errorHandler` ตอบ `404` `ไม่พบข้อมูลที่ต้องการ` ให้ `P2025` ทุกตัว เพื่อให้ endpoint ที่
ไม่มีใครนึกถึงก็ยังพูดถูก

ทับบนพื้นนั้น `orNotFound(work, NOT_FOUND)` ใน `utils/record-not-found.ts` วางอยู่ที่
จุดเรียกของ controller ที่ **มี `NOT_FOUND()` ของตัวเองอยู่แล้ว** — สิบ controller ใน
กลุ่ม e-Portfolio รวมสิบเอ็ดประโยค (`portfolio-skill` มีสองประโยค คือของทักษะกับของการ
เชื่อมโยง) ที่ `GET /:id` ตอบ `ไม่พบรางวัลที่ต้องการ`, `ไม่พบการอบรมที่ต้องการ` ฯลฯ
มาตั้งแต่ต้น ผลคือ `GET`, `PUT` และ `DELETE` ที่ชี้ไปแถวเดียวกันพูดเหมือนกัน

ทางเลือกที่ไม่เอาคือให้ `errorHandler` อ่าน `meta.cause` ของ `P2025` เพื่อเดาว่าเป็น
ตารางไหน — ข้อความนั้นเป็นภาษาอังกฤษ เป็นรายละเอียดภายในของ Prisma และไม่มีสัญญาว่า
จะคงรูปข้ามเวอร์ชัน `errorHandler` ส่งอะไรของ Prisma ออกไปไม่ได้อยู่แล้วตามข้อ 3 ของ #20

### 2. `connect` ที่ค่ามาจาก body ตอบ `400` — และถามก่อน ไม่ใช่ดักทีหลัง

`POST /activity` และ `PUT /activity` รับ `score_ratio_id` มาจาก body แล้ว `connect` ไป
ที่ `subject_score_ratio` ค่าที่ไม่ตรงกับแถวไหนจึงโยน `P2025` ตัวเดียวกับที่กิจกรรมที่
ไม่มีอยู่โยน — และในคำสั่ง `update` เดียวกันด้วย

ตาม ADR-0009: กิจกรรมคือแถวที่ผู้เรียก**อ้างถึง** ส่วนหมวดคะแนนคือ**ค่าที่ผู้เรียกส่ง
มา** อย่างหลังเป็น `400` `ไม่พบประเภทสัดส่วนคะแนนที่เลือก`

service จึงถามว่าหมวดคะแนนมีอยู่จริงไหม **ก่อน** เขียน แทนที่จะดัก `P2025` แล้วแยกแยะ
ทีหลัง เหตุผลคือกฎในข้อ 1 จะจริงได้ก็ต่อเมื่อไม่มีข้อยกเว้นให้ต้องจำ — วิธีนี้ลบ
ข้อยกเว้นทิ้งที่ต้นทาง แทนที่จะเพิ่มเงื่อนไขให้ `errorHandler` และการถามก่อนยังทำให้
คำขอที่ถูกปฏิเสธไม่เขียนอะไรเลย เพราะอยู่ใน transaction เดียวกันก่อนคำสั่งเขียนแรก

### 3. `P2002` และ `P2003` อยู่นอกขอบเขต

รหัสอื่นที่ทำให้เกิด `500` เหมือนกันยังเป็น `500` ต่อไป เพราะเป็นคนละข่าว

| | ความหมาย | คำตอบที่ควรจะเป็น |
| --- | --- | --- |
| `P2025` | แถวที่อ้างถึงไม่มี | `404` — ทำแล้วใน ticket นี้ |
| `P2002` | แถวนั้นมีอยู่แล้ว (unique) | น่าจะ `409` — ยังไม่ตัดสิน |
| `P2003` | ค่าใน body ชี้ไปที่ไม่มีอะไร (foreign key) | น่าจะ `400` — ยังไม่ตัดสิน |

สองแถวล่างต้องดูทีละจุดว่าคอลัมน์ไหนของ body เป็นต้นเหตุ ถึงจะเขียนประโยคที่ใช้ได้จริง
ให้ผู้ใช้ได้ การเหมารวมทั้งหมดเป็นสถานะเดียวคือการเปลี่ยน `500` ที่มีความหมายให้เป็น
`4xx` ที่ไม่มี test ทั้งสิบเอ็ดจุดที่ยังเป็น `500` มี comment บอกว่าเป็นรหัสอะไรหรือ
throw ตัวไหน และทำไมยังอยู่

## ขอบเขต

- **ไม่ได้แตะ `throw new Error(...)` ที่เขียนด้วยมือ** — `Group not found` และ
  `Invalid rubric data` ใน service ของการให้คะแนน กับ `Activity not found` ใน
  `activity-clo-mapping.service.ts` ยังเป็น `500` ทั้งหมด สองตัวหลังไม่ได้แปลว่า
  "ไม่มีแถว" อย่างเดียว — `Activity not found` ถูกโยนทั้งตอนที่กิจกรรมไม่มีอยู่ และตอนที่
  กิจกรรมมีอยู่แต่ไม่มีคะแนน การให้สถานะกับมันจึงต้องแยกสองกรณีออกจากกันก่อน
- **ไม่ได้เพิ่มการตรวจความเป็นเจ้าของที่ไหน** — เส้นที่มี `requireOwnEntry` อยู่แล้ว
  ตอบ `403` ให้แถวที่มีอยู่แต่ไม่ใช่ของผู้เรียกเหมือนเดิม ส่วนแถวที่ไม่มีอยู่ middleware
  ปล่อยผ่านมาตั้งแต่ต้น `404` ที่เพิ่มมาจึงมาแทน `500` เดิม ไม่ได้มาแทน `403` ตัวไหน
- **ไม่ได้เปลี่ยนสถานะของ `GET`** — เส้นที่คืน `null` หรือ `[]` เมื่อไม่เจอ ยังคืน
  เหมือนเดิม ticket นี้พูดถึงเฉพาะ error ที่หลุดมาจาก Prisma

## ผลที่ตามมา

- frontend ที่เคยเห็น `500` จากการลบของที่ถูกลบไปแล้ว (เช่น เปิดสองแท็บ) ตอนนี้เห็น
  `404` พร้อมประโยคไทยที่พิมพ์ออกหน้าจอได้เลย ไม่มีผู้เรียกไหนแยกสาขาตาม `500` อยู่ก่อน
  จึงไม่ต้องแก้อะไร
- `orNotFound` รับ **factory** ไม่ใช่ตัว error เพื่อไม่ให้สร้าง object บนเส้นทางที่ไม่มี
  อะไรผิด และให้ stack เป็นของจุดที่โยนจริง
- endpoint ใหม่ที่เขียนต่อจากนี้ได้ `404` ฟรีจากพื้น ถ้าอยากได้ประโยคของตัวเองค่อยห่อ
  ด้วย `orNotFound` เพิ่ม

## จะกลับมาทบทวนเมื่อไหร่

เมื่อ `P2002` หรือ `P2003` ถูกตัดสิน — ถ้าทั้งคู่ลงเอยที่ `errorHandler` เหมือนกัน
ควรทบทวนว่า `utils/record-not-found.ts` ควรกลายเป็นที่รวมของการแปลรหัส Prisma ทั้งชุด
แทนที่จะเป็นไฟล์ของรหัสเดียว
