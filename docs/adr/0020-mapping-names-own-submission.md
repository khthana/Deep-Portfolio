# ADR-0020 — ชิ้นงานที่ mapping อ้างถึง ต้องมีอยู่จริงและต้องเป็นของผู้เรียก

- **สถานะ**: ตัดสินแล้ว 12 สิงหาคม 2569
- **ที่มา**: [issue #47](https://github.com/khthana/Deep-Portfolio/issues/47)
- **เกี่ยวข้อง**: [ADR-0001](0001-portfolio-access.md) วางกติกาของกลุ่ม
  `portfolio` ไว้ว่า "ผู้กระทำคือเจ้าของ session เสมอ" และแตกเป็นสามรูปตามรูปของ
  endpoint — คำขอที่ระบุผู้ใช้ คำขอที่ระบุแถว และคำขอที่เขียนแถวใหม่ ซึ่งข้อสุดท้าย
  แปลว่า "ไม่รับ `user_id` จาก body" เท่านั้น ตารางนั้นไม่ได้ครอบคลุม id ที่อยู่ใน
  body แล้ว**ไม่ได้ระบุตัวผู้ใช้ แต่ระบุแถวที่มีเจ้าของ** — `assertOwnSkills` ซึ่ง
  เกิดจาก #31 ตั๋วเดียวกับ ADR-0001 เป็นคำตอบของกรณีนั้นสำหรับ `skill_id` ไฟล์นี้
  ตอบให้ id อีกตัวของ mapping ซึ่งไม่ได้ชี้ไปที่กลุ่ม `portfolio` เลย แต่ชี้ไปที่
  `student_activity`
  [ADR-0007](0007-group-membership.md) ข้อ 2 เป็นเจ้าของเส้นแบ่ง `400`/`403`
  (ค่าที่ผู้เรียกแก้เองได้ ไม่ใช่สิทธิ์ที่เขาไม่มี) และ
  [ADR-0012](0012-missing-row-status.md) ข้อ 2 เป็นเจ้าของกฎ "ถามก่อนเขียน"
  สำหรับ id ที่มาจาก body ส่วน [ADR-0009](0009-submission-ownership.md) ข้อ 3
  ตอบคำถามที่ **ใกล้เคียงแต่ไม่ใช่ข้อเดียวกัน** — ดูข้อ 2 ข้างล่างว่าทำไมคำตอบที่นี่
  จึงไม่ใช่ `404` ตามนั้น

## บริบท

`portfolio_skill_activity_mapping` คือแถวที่บอกว่า "ทักษะนี้ มีชิ้นงานนี้เป็น
หลักฐาน" มีคอลัมน์ id สองตัว

```prisma
skill_id            Int
student_activity_id Int
```

`skill_id` มี foreign key มาตั้งแต่ baseline (`fk_skill_activity`,
`ON DELETE CASCADE`) ส่วน `student_activity_id` ไม่มี ทั้งที่เป็น `NOT NULL`
เหมือนกันและถือค่าจากตารางเดียวเสมอ ผลคือสองอย่าง

**เขียน id ที่ไม่มีอยู่จริงลงไปได้** ไม่มีอะไรตรวจในโค้ด และไม่มีอะไรตรวจใน
ฐานข้อมูล แถวถูกเขียนสำเร็จ แล้ว `GET /portfolio-skill/works` ก็หา `feedback`
ไม่เจอแล้วคืน `null` — หน้าผลงานจึงมีทักษะที่อ้างหลักฐานซึ่งไม่มีตัวตน

**ลบชิ้นงานแล้ว mapping ยังอยู่** ไม่มี cascade มารับ แถวที่เหลือชี้ไปยัง id ที่
ว่างแล้ว และถ้า sequence เดินมาถึงเลขเดิมอีกครั้ง มันจะชี้ไปยังชิ้นงานของคนอื่น

เส้นที่เขียน mapping มีสามเส้น ไม่ใช่สองอย่างที่ #47 เขียนไว้ —
`POST /portfolio-skill` (พร้อมทักษะใหม่), `PUT /portfolio-skill/:id`
(แทนที่ของเดิมทั้งชุด) และ `POST /portfolio-skill/assign-work`

และมีเรื่องที่หนักกว่าการอ้างของที่ไม่มี: **การอ้างของที่มีอยู่แต่เป็นของคนอื่น**
`getPortfolioWorks` อ่าน mapping ทุกแถวที่ห้อยอยู่กับทักษะของผู้เรียก แล้ววิ่งไป
หยิบ `feedback` ของ `student_activity` ทุก id ที่ mapping เหล่านั้นชี้ไป โดยไม่ถาม
ว่าแถวนั้นเป็นของใคร นักศึกษาที่รู้ id ของเพื่อนจึงดึงคำวิจารณ์ที่อาจารย์เขียนถึง
เพื่อนมาไว้ในหน้าของตัวเองได้ foreign key อย่างเดียวไม่ปิดช่องนี้ เพราะ id นั้น
"มีอยู่จริง" ทุกประการ เป็นข้อบกพร่องประเภทเดียวกับที่ #38 ปิดไปแล้วสำหรับ
`POST /student/submit/activity`

ข้อเท็จจริงรอบ ๆ ที่ตรวจแล้ว

- **ฐานข้อมูลจริงไม่มีแถว mapping เลย** ตรวจเมื่อ 12 สิงหาคม 2569: `count(*)` เป็น
  `0` และแถวกำพร้าเป็น `0` migration จึงไม่มีข้อมูลเดิมให้สะดุด
- **คอลัมน์เป็น `NOT NULL` อยู่แล้ว** (baseline บรรทัด 514) ข้อ 3 ของ #47 ที่ถามว่า
  ควรทำให้ `NOT NULL` ด้วยไหม จึงตกไปเอง — ไม่มีอะไรให้ทำ
- **ทางกลุ่มไม่ได้ใช้แถวร่วมกัน** สมาชิกกลุ่มแต่ละคนมี `student_activity` แถวของ
  ตัวเองที่ถือ `student_id` ของตัวเอง (`student_activity_group_member` ผูกกับแถว
  นั้นแบบ `@unique`) กฎ "ต้องเป็นของผู้เรียก" จึงไม่ปิดทางงานกลุ่ม
- **หน้าเว็บส่ง id ของตัวเองเสมอ** ตัวเลือกใน `create-work-form.tsx` มาจาก
  `/student/activities/list` ซึ่งอ่านนักศึกษาจาก session (#41) ส่วน
  `work-edit-modal.tsx` ส่ง id ที่ได้จาก `/works` ของตัวเองกลับไป และไม่มีที่ไหน
  เรียก `POST /portfolio-skill` พร้อม `mappings` เลย — ทั้งสองที่เรียกด้วย
  `{ name }` เท่านั้น ส่วน `updatePortfolioSkill` ฝั่งเว็บไม่มีผู้เรียกสักราย

## สิ่งที่ต้องตัดสิน

1. `ON DELETE` ของ foreign key ใหม่
2. ตรวจความเป็นเจ้าของด้วยหรือไม่ และตอบด้วยรหัสอะไร
3. ให้ฐานข้อมูลตอบอย่างเดียว หรือให้ service ถามก่อนเขียน

## การตัดสิน

> **เพิ่ม foreign key แบบ `ON DELETE CASCADE` และให้ทั้งสามเส้นที่เขียน mapping
> ถามก่อนเขียน — id ที่ไม่มีอยู่จริงตอบ `400`, id ที่เป็นของคนอื่นตอบ `403`**

### 1. CASCADE

ลบชิ้นงาน แถว mapping หายตามไปด้วย

หลักฐานชี้ทางเดียวกันทั้งสามด้าน คอลัมน์อีกตัวของตารางเดียวกัน (`skill_id`) เป็น
CASCADE, ลูกทุกตัวของ `student_activity` ที่มีอยู่ก่อนหน้า — `_attachments`,
`_group_member`, `_rubric_score` — เป็น CASCADE ทั้งสามตัว และ 79 จาก 106 foreign
key ใน baseline เป็น CASCADE

เชิงความหมายก็ตรงกัน: mapping คือหลักฐานของทักษะ และสิ่งที่ทำให้มันเป็นหลักฐาน
คือชิ้นงานที่มันชี้ไป เมื่อชิ้นงานไม่อยู่แล้ว แถวที่เหลือไม่ได้พิสูจน์อะไรอีก

ราคาที่ต้องจ่ายมีจริงและควรพูดให้ชัด: `reflection`, `role_and_resp`,
`init_expect` เป็นข้อความที่นักศึกษาเขียนเอง และมันตายไปพร้อมกิจกรรมที่อาจารย์ลบ
โดยนักศึกษาไม่รู้ตัว ทางเลือกอื่นไม่ได้ดีกว่า — `RESTRICT` ทำให้อาจารย์ลบกิจกรรม
ของตัวเองไม่ได้เพราะนักศึกษาคนหนึ่งเอาไปใส่แฟ้มสะสมผลงาน และ `SET NULL` ต้องแก้
คอลัมน์ให้ nullable แล้วย้อนกลับไปสู่อาการเดิมคือ mapping ที่ไม่ชี้ไปไหน

### 2. `400` กับ `403` เป็นคนละคำตอบ

**ของคนอื่นตอบ `403`** ตามเส้นที่ ADR-0007 ข้อ 2 ลากไว้: `403` เมื่อสิ่งที่ถูก
ปฏิเสธคือ**สิทธิ์ของผู้เรียก** id ที่หาเจอแต่เป็นของคนอื่นเป็นอย่างนั้นเป๊ะ ๆ —
ค่าถูกต้องทุกประการ มีแถวจริง เพียงแต่ไม่ใช่ของเขา เท่ากับที่ `assertOwnSkills`
ในไฟล์เดียวกันตอบให้ `skill_id` และเท่ากับที่ ADR-0009 ตอบให้ทางส่งงาน

**ที่ไม่มีอยู่จริงตอบ `400` ไม่ใช่ `404`** ตรงนี้ต้องเลือก เพราะ repo นี้มี
บรรทัดฐานสองอันที่ไม่ตรงกัน และทั้งคู่ก็พูดถึง id ที่มาจาก body

- ADR-0012 ข้อ 2 — `score_ratio_id` ใน `POST /activity` ที่ไม่ตรงกับแถวไหน ตอบ
  `400` `ไม่พบประเภทสัดส่วนคะแนนที่เลือก` และถามก่อนเขียน
- ADR-0009 ข้อ 3 — `student_activity_id` ใน `POST /student/submit/activity` ที่ไม่
  ตรงกับแถวไหน ตอบ `404` `ไม่พบงานที่ต้องการส่ง`

สองอันนี้ไม่ได้ขัดกัน เพราะ id ทำหน้าที่คนละอย่าง ที่ทางส่งงาน ชิ้นงานคือ**แถวที่
คำขอกระทำต่อ** — ทั้ง endpoint มีไว้เพื่อเขียนลงแถวนั้นแถวเดียว ไม่มีมันก็ไม่มีอะไร
ให้ทำ ส่วนที่ `POST /activity` หมวดคะแนนเป็น**ค่าหนึ่งในแถวใหม่**ที่กำลังจะถูกเขียน

`student_activity_id` ของ mapping เป็นอย่างหลัง แถวที่ทั้งสามเส้นกำลังเขียนคือ
mapping ไม่ใช่ชิ้นงาน ชิ้นงานเป็นค่าที่อยู่ในแถวนั้น เหมือนที่ `skill_id` เป็น —
และคำขอเดียวอาจพก id มาหลายตัว (`POST` และ `PUT` รับ `mappings` เป็น array) ซึ่ง
`404` ตอบไม่ได้อยู่แล้วว่าหมายถึงตัวไหน จึงเป็น `400` ทั้งสามเส้น ด้วยประโยคที่
เลียนแบบเพื่อนบ้านที่ใกล้ที่สุด — `assertScoreRatioExists` ใน `activity.service.ts`

**และแยกสองกรณีออกจากกัน ไม่ยุบเป็นคำตอบเดียว** ADR-0007 ข้อ 2 ยุบ "ไม่มีอยู่จริง"
เข้ากับ "ไม่ผ่านกติกา" เป็น `400` อันเดียว โดยตั้งใจไม่บอกว่ารหัสนักศึกษานั้นมีอยู่
ไหม ตามเหตุผลของ ADR-0002 ที่นี่ไม่ทำอย่างนั้น ด้วยเหตุผลที่ ADR-0009 ข้อ 3 เขียน
ไว้แล้วสำหรับตารางเดียวกันนี้เอง: นักศึกษาทุกคนในชั้นมีแถว `student_activity` หนึ่ง
แถวต่อกิจกรรมหนึ่งชิ้นเสมอ การรู้ว่าเลขหนึ่งมีอยู่จึงไม่ได้บอกอะไรที่รายชื่อชั้นเรียน
ไม่ได้บอก และสิ่งที่ได้กลับมาคือข้อความที่ใช้ได้จริง — "เลือกงานผิด" กับ "งานนี้
ไม่ใช่ของคุณ" เป็นคนละเรื่องในสายตาคนที่เจอ

ลำดับคือ "มีอยู่ก่อน แล้วค่อยเป็นของใคร" คำขอที่ผสมทั้งสองแบบมาจึงได้ `400`
เพราะการบอกว่า id ที่ไม่มีตัวตน "เป็นของคนอื่น" นั้นไม่จริง สองประโยคคือ
`400` `ไม่พบชิ้นงานที่เลือก` และ `403` `มีชิ้นงานบางรายการที่ไม่ใช่ของผู้ใช้รายนี้`

### 3. ถามก่อนเขียน ไม่ใช่รอ Prisma พลาด

[ADR-0012](0012-missing-row-status.md) ข้อ 2 วางกฎนี้ไว้แล้วสำหรับ id ที่มาจาก
body: ตรวจก่อนเขียน แล้วตอบ `400` ด้วยประโยคที่บอกว่า id ตัวไหนผิด ที่นี่ทำตามนั้น
ตรง ๆ

ไม่เลือกทางที่แปลง `P2003` (foreign key violation) ที่ `errorHandler` เป็น `400`
ด้วยเหตุผลสามข้อ หนึ่ง — ADR-0012 ข้อ 3 เขียนไว้เองว่า `P2002`/`P2003` อยู่นอกขอบเขต
และยังไม่ตัดสิน การตัดสินใจแทนทั้งระบบจากในตั๋วนี้จะกระทบทุก endpoint ที่เขียน
ฐานข้อมูล สอง — ข้อความที่ได้จะเป็นข้อความกลางที่ไม่รู้ว่าคอลัมน์ไหนพัง สาม —
และสำคัญที่สุด: foreign key ไม่รู้เรื่องความเป็นเจ้าของเลย ทางนั้นปิดได้แค่ครึ่งเดียว
ของปัญหา

foreign key จึงไม่ใช่กลไกหลัก แต่เป็นเส้นสุดท้ายที่กันไม่ให้โค้ดกับฐานข้อมูล
เดินคนละทางในวันที่มีใครเพิ่มเส้นเขียนที่สี่แล้วลืมตรวจ

## ผลที่ตามมา

- **สามเส้นที่เขียน mapping ปฏิเสธ id ที่ไม่มีอยู่จริงด้วย `400` และ id ของคนอื่น
  ด้วย `403`** การตรวจอยู่ก่อนคำสั่งเขียนแรกของ transaction ทุกเส้น รวมถึงก่อนแถว
  `portfolio_skill` ที่ `POST /portfolio-skill` สร้าง คำขอที่ถูกปฏิเสธจึงไม่ทิ้ง
  อะไรไว้โดยไม่ต้องพึ่ง rollback ดู
  [`BEHAVIOR-CHANGES.md`](../../BEHAVIOR-CHANGES.md)
- **ลบกิจกรรม แถว mapping หายตามไปด้วย** `DELETE /activity` ลบ `student_activity`
  อยู่แล้ว ตอนนี้ cascade เดินต่ออีกขั้น ทักษะเองไม่ถูกแตะ
- **หน้าเว็บไม่ต้องแก้** ทุกเส้นทางบนหน้าจอส่ง id ของนักศึกษาคนที่ล็อกอินอยู่แล้ว
  การปฏิเสธใหม่ทั้งสองแบบจึงไม่มีทางเกิดจากการใช้งานปกติ — คนที่เจอคือผู้เรียก API
  ตรง ๆ (และถ้าเกิดขึ้นจริง ประโยคภาษาไทยยังไม่ถึงหน้าจอ เพราะ thunk ทิ้งไป — #51)
- **`updatePortfolioSkill` รับ `userId` เพิ่มมาหนึ่งตัว** middleware ตรวจไปแล้วว่า
  ผู้เรียกเป็นเจ้าของทักษะ แต่ service ต้องรู้ว่าใครถามเพื่อจะตอบเรื่องชิ้นงานได้
  controller ส่ง `sessionUserId(req)` ลงไปเหมือนที่ `createPortfolioSkill` ทำ
- **แถวเก่าไม่ถูกแตะ** migration ลบเฉพาะแถวที่อ้าง id ที่ไม่มีอยู่ ซึ่งในฐานข้อมูล
  นี้ไม่มีสักแถว แถวที่อ้างชิ้นงานของคนอื่นแต่มีอยู่จริง ไม่ถูกลบและไม่ถูกตรวจ
  ย้อนหลัง — กฎใหม่บังคับที่ทางเขียนเท่านั้น

## จะกลับมาทบทวนเมื่อไหร่

- เมื่อมีคนตัดสินใจเรื่อง `P2002`/`P2003` ทั้งระบบตาม ADR-0012 §3 — ข้อ 3 ข้างบน
  ไม่ได้ขัดกับการมีคำตอบกลาง มันแค่ไม่รอคำตอบนั้น
- เมื่อมีใครอยากให้ข้อความสะท้อนของนักศึกษารอดจากการลบกิจกรรม — นั่นคือคำขอให้
