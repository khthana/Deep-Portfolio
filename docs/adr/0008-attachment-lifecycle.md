# ADR-0008 — ไฟล์แนบตายพร้อมเจ้าของรายสุดท้าย

- **สถานะ**: ตัดสินแล้ว 10 สิงหาคม 2569
- **ที่มา**: [issue #34](https://github.com/khthana/Deep-Portfolio/issues/34)
- **เกี่ยวข้อง**: [ADR-0006](0006-file-access.md) คุมว่า *ใครโหลดไฟล์ได้* แล้วเขียน
  ค้างไว้ว่า "ไม่ได้แตะการลบไฟล์ ลบแถวแล้ว object ยังค้างอยู่ในถังเหมือนเดิม เป็นคนละ
  เรื่องและอยู่ที่ #34" — ไฟล์นี้คือส่วนที่ค้างอยู่นั้น

## บริบท

`attachments` เป็นตารางกลางตารางเดียวของทั้งระบบ ไฟล์และลิงก์ทุกชิ้น — เอกสาร
ประกอบการเรียน ไฟล์โจทย์ งานที่นักศึกษาส่ง ใบประกาศนียบัตร รูปโปรไฟล์ — เป็นแถวใน
ตารางนี้ทั้งหมด แล้วมี **12 ตารางเชื่อม** กับ **`portfolio_personal`** ที่ชี้เข้ามา
บอกว่าไฟล์ชิ้นนั้นเป็นของรายการไหน

การลบที่มีอยู่เดิมลบแค่ฝั่งเจ้าของ ลบใบประกาศนียบัตรหนึ่งใบ แถวใน
`portfolio_certificate_attachments` หายไปตาม cascade แต่แถวใน `attachments` กับ
object ใน MinIO ยังอยู่ครบ ไม่มี endpoint ไหนอ่านถึงมันได้อีก เพราะทุกทางอ่านเริ่มจาก
ตารางเชื่อม ผลคือไฟล์จริงของคนจริงค้างอยู่ในถังโดยไม่มีใครลบได้ผ่านหน้าจอ ขัดกับ
TC-24, TC-56 และ TC-62 ที่ระบุว่าลบแล้วต้องหายไปทั้งชุด

สองอย่างที่กำหนดรูปของทางออก

**FK ไม่ได้ช่วยอะไรเลยในทิศทางนี้** ความสัมพันธ์ทั้ง 12 ด้านประกาศไว้เป็น
`onDelete: Cascade` **บนฝั่ง `attachments`** แปลว่าถ้าลบแถวใน `attachments` ทิ้ง
แถวเชื่อมของ *ทุก* เจ้าของหายตามไปเงียบ ๆ ฐานข้อมูลไม่ได้กันไว้ให้ ใครก็ตามที่ลบแถว
ใน `attachments` ต้องรู้เองว่าไม่มีใครถืออยู่แล้วจริง ๆ (`portfolio_personal` เป็น
ข้อยกเว้น — เป็น optional และไม่ cascade)

**ตอนนี้ไม่มีไฟล์ชิ้นไหนถูกใช้ร่วมกันเลย** `AttachmentsService.createAttachments`
สร้างแถวใหม่ทุกครั้งที่อัปโหลด ต่อให้เป็นไฟล์เดิม แถวหนึ่งจึงมีเจ้าของหนึ่งราย
เสมอ **ในวันนี้** แต่ไม่มีอะไรในตารางที่บังคับไว้แบบนั้น

## สิ่งที่ต้องตัดสิน

1. ไฟล์แนบชิ้นเดียวถูกอ้างจากหลายรายการได้หรือไม่ — ลบตามเจ้าของได้เลย หรือต้องนับก่อน
2. object ใน MinIO ลบตอนไหนเทียบกับ transaction ของฐานข้อมูล
3. ขยะที่ค้างอยู่แล้วก่อนแก้ จัดการอย่างไร

## การตัดสิน

> **ลบแถวใน `attachments` เมื่อไม่มีตารางไหนชี้มาแล้วเท่านั้น แล้วจึงลบ object
> ใน MinIO หลัง transaction commit แบบ best-effort**

### 1. นับ reference ก่อนลบ

`AttachmentsService.deleteUnreferenced(attachmentIds, tx)` ถามฐานข้อมูลว่าใน id
ชุดที่ส่งมา เหลือชิ้นไหนที่ **ทั้ง 13 ความสัมพันธ์เป็น `none: {}`** แล้วลบเฉพาะชิ้น
นั้น คืน object key ของสิ่งที่ลบไปให้ผู้เรียกไปจัดการถังต่อ

ไม่เลือกทางที่ง่ายกว่า — ลบ `attachments` ตามเจ้าของไปเลย — เพราะ cascade ข้างบน
แปลว่าถ้าวันหนึ่งมีไฟล์ที่ถูกใช้ร่วมกัน (เช่นทำ "แนบไฟล์เดิมซ้ำ" หรือ dedupe ด้วย
checksum) การลบรายการหนึ่งจะไปดึงไฟล์ออกจากรายการของคนอื่นเงียบ ๆ โดยไม่มีอะไรร้อง
ราคาที่จ่ายคือ query เพิ่มหนึ่งครั้งต่อการลบหนึ่งครั้ง

**การเพิ่มตารางที่ชี้มาที่ `attachments` ต้องเพิ่มบรรทัดใน `where` ของเมธอดนี้ด้วย**
ตารางที่ลืมใส่จะทำให้ไฟล์ของมันถูกลบทั้งที่ยังมีคนถืออยู่ — comment เหนือเมธอด
เขียนเตือนไว้แล้ว

### 2. ลบ object หลัง commit แบบ best-effort

`MinIOService.removeFiles(paths)` ถูกเรียก **หลัง** `prisma.$transaction` คืนค่า
และถ้าถังตอบไม่สำเร็จ มันจะ log แล้วจบ ไม่ throw ต่อ ผู้เรียกได้ `200` เหมือนเดิม

ฐานข้อมูลคือแหล่งความจริง สองความผิดพลาดที่เป็นไปได้ไม่เท่ากัน

| ลำดับ | เมื่อฝั่งที่สองพัง | คนอ่านเห็นอะไร |
| --- | --- | --- |
| ลบ object ก่อน commit | แถวยังอยู่ ไฟล์หายแล้ว | ดาวน์โหลดแล้วได้ `404` |
| ลบ object หลัง commit | แถวหายแล้ว object ค้าง | ไม่เห็นอะไรเลย เปลืองเนื้อที่ |

อย่างหลังคือค่าใช้จ่าย อย่างแรกคือ bug ที่ผู้ใช้เจอ และ MinIO ก็ไม่ได้อยู่ใน
transaction ของ Postgres อยู่แล้ว จึงเลือกให้ทิศทางของความผิดพลาดตกไปทางที่คนอ่าน
ไม่เห็น

ลิงก์ (`attachment_type = "link"`) ไม่มี object อยู่ข้างหลัง `deleteUnreferenced`
จึงกรอง `file_path === null` ทิ้งก่อนคืนค่า

### 3. ปล่อยขยะเก่าไว้

ไม่มี migration กวาดของเดิม ระบบยังไม่เคยขึ้น production ข้อมูลที่มีอยู่มาจากการ
ทดสอบและจากตัว importer ซึ่งไม่แตะไฟล์แนบเลย ของที่ค้างอยู่จึงมีแต่ของ dev สคริปต์
กวาดถังเป็นโค้ดที่อันตรายกว่าปัญหาที่มันแก้ — ถ้าเงื่อนไขผิดไปข้อเดียวมันลบไฟล์ที่ยัง
มีคนถืออยู่ ทั้งที่ทางแก้ที่ปลอดภัยกว่าคือ `docker compose down -v` แล้วเริ่มใหม่

## ขอบเขต

กวาดทุกทางที่ทำให้ไฟล์แนบขาดเจ้าของรายสุดท้าย

| ทาง | ไฟล์ที่กวาด |
| --- | --- |
| `DELETE /course-material` | ไฟล์ของเอกสารชิ้นนั้น |
| `DELETE /portfolio-{certificate,training,internship,thesis,award,activity}/:id` | ไฟล์ของรายการนั้น |
| `PUT /portfolio-…` ผ่าน `ids_to_delete` | ไฟล์ที่คำขอสั่งเอาออก |
| `DELETE /activity`, `DELETE /learning-activity` | ไฟล์โจทย์ **และ** ไฟล์ที่นักศึกษาส่งของทุกคน |
| `PUT /activity`, `PUT /learning-activity` ผ่าน `remove_attachment_ids` | ไฟล์ที่คำขอสั่งเอาออก |
| `POST /student/submit/…` ทั้งสี่ทาง | ไฟล์ของรอบก่อนที่การส่งใหม่ไม่ได้เอ่ยถึงอีก |
| `DELETE /lesson-plan` | ไฟล์ของเอกสารทุกชิ้นในสัปดาห์นั้น |
| `PUT`/`upsert`/`DELETE /portfolio-personal` | รูปโปรไฟล์ใบก่อน |

สามทางท้ายตารางไม่ได้อยู่ในรายการของ #34 แต่อยู่ใต้คำว่า "ครอบคลุมอย่างน้อย" ของ
มัน ทั้งสามทำให้ไฟล์ขาดเจ้าของด้วยกลไกเดียวกัน — สัปดาห์ที่ถูกลบ cascade
`course_material` ทิ้ง และ `portfolio_personal.attachment_id` เป็นตัวชี้ตัวเดียวที่
เข้าถึงรูปโปรไฟล์ได้ การแก้ทีละครึ่งจะทิ้งรูที่หน้าตาเหมือนกันไว้ให้ค้นใหม่ทีหลัง

### ลำดับของการกวาดในทางที่ส่งงานซ้ำ

ในสี่ทางของ `POST /student/submit/…` การกวาดต้องอยู่ **หลัง** `createMany` ที่ผูก
`existing_files_ids` กลับเข้าไปใหม่ ไม่ใช่ต่อจาก `deleteMany` ที่ตัดของเดิมออก
ระหว่างสองจุดนั้นไฟล์ที่นักศึกษาตั้งใจเก็บไว้ยังไม่มีใครชี้ถึงชั่วคราว — กวาดตรงนั้น
คือลบงานที่เขาเลือกเก็บไว้เอง

### การกวาดดีได้แค่เท่าที่การลบแถวเชื่อมแม่นยำ

การนับ reference ตอบได้แค่ว่า "ตอนนี้ยังมีใครชี้อยู่ไหม" มันไม่รู้ว่าแถวเชื่อมที่
เพิ่งถูกลบไปเมื่อกี้ *ควร* ถูกลบหรือเปล่า `PUT /activity` กับ
`PUT /learning-activity` เคยลบแถวเชื่อมด้วย `attachment_id` เพียงอย่างเดียว การเอา
การกวาดมาต่อท้ายจึงเปลี่ยนบั๊กเดิมที่แค่ทำให้ไฟล์หลุดจากงานของคนอื่น ให้กลายเป็น
การลบไฟล์นั้นทิ้งถาวร แก้ไปพร้อมกันตาม D9 (ดู `BEHAVIOR-CHANGES.md` #34 ข้อ 5)

กติกาที่ตามมาสำหรับคนที่มาเพิ่ม endpoint ใหม่: **ลบแถวเชื่อมโดยผูกเงื่อนไขกับ
เจ้าของเสมอ** แล้วค่อยกวาด ไม่ใช่ลบด้วย id ของไฟล์ที่ผู้เรียกส่งมาลอย ๆ

## ผลที่ตามมา

- **ผู้เรียกไม่เห็นความต่างในคำตอบ** status และ body เหมือนเดิมทุกจุด สิ่งที่เปลี่ยน
  คือสถานะของฐานข้อมูลและของถังหลังจากนั้น ดู
  [`BEHAVIOR-CHANGES.md`](../../BEHAVIOR-CHANGES.md)
- **ลบแล้วลบเลย ไม่มีถังขยะ ไม่มี undo** ลบใบประกาศนียบัตรผิดใบแล้วต้องอัปโหลดใหม่
  ตรงกับสิ่งที่หน้าจอบอกผู้ใช้อยู่แล้ว
- **การลบทำงานหนักขึ้นหนึ่ง query** และการลบกิจกรรมหนึ่งรายการอ่านแถวเชื่อมของงานที่
  นักศึกษาส่งทั้งห้องก่อนลบ ยอมรับได้ในขนาดของกลุ่มเรียนหนึ่งกลุ่ม
- **object ที่ค้างเพราะถังพัง ไม่มีใครตามเก็บ** ทางแก้ตอนนี้คือดู log ถ้าวันหนึ่ง
  ต้องการให้แน่ ต้องมีคิวงานหรือคิวลบแยก ซึ่งใหญ่เกินกว่าที่ระบบนี้มี

## จะกลับมาทบทวนเมื่อไหร่

- เมื่อไฟล์เริ่มถูกใช้ร่วมกันจริง (dedupe ด้วย checksum หรือ "แนบไฟล์เดิมซ้ำ")
  ตอนนั้นการนับ reference จะเริ่มมีผลจริง และควรมี test ที่พิสูจน์ว่าลบรายการหนึ่ง
  แล้วอีกรายการยังเปิดไฟล์ได้ — มีอยู่แล้วหนึ่งเคสใน `portfolio-training.test.ts`
- เมื่อขึ้น production แล้วมี object ค้างจากถังล่ม ตอนนั้นค่อยคิดเรื่องงานกวาดถัง
  ที่เทียบ key ในถังกับ `attachments.file_path` ซึ่งตอนนี้ตัดสินว่ายังไม่คุ้ม
