# ADR-0018 — ธงที่ไม่ได้ส่งมาใน `POST` ให้ค่าตั้งต้นของคอลัมน์เป็นคนตอบ

- **สถานะ**: ตัดสินแล้ว 12 สิงหาคม 2569
- **ที่มา**: [issue #46](https://github.com/khthana/Deep-Portfolio/issues/46)
- **เกี่ยวข้อง**: ไม่มี ADR ฉบับไหนตัดสินเรื่องนี้ไว้ สเปกของ #1 มีแต่บรรทัดใน
  ตาราง Backend ว่า "ไม่มีการ validate request body เลย … → เพิ่ม validation ที่
  endpoint ซึ่งรับข้อมูลจากผู้ใช้" ซึ่งบอกว่าต้อง **ตรวจ** ไม่ได้บอกว่าค่าที่ตรวจ
  ผ่านแล้วแต่ไม่ได้ส่งมาแปลว่าอะไร
  [ADR-0005](0005-announcement-date.md) ตัดสินคำถามข้างเคียง — งานที่ไม่มีวัน
  ประกาศ นับว่าประกาศแล้ว คือเลือกการอ่านที่ใจกว้างให้ค่าที่หายไป — แต่มันตัดสิน
  ให้**ฝั่งอ่าน**ของคอลัมน์ที่ไม่มีค่าตั้งต้น ไม่ได้พูดถึงว่าฝั่ง**เขียน**ควรใส่
  อะไรลงไปเมื่อคำขอไม่ได้บอก ไฟล์นี้จึงเป็นเจ้าของการตัดสินนั้นเอง

## บริบท

`createPortfolioAward` เขียนแบบนี้

```ts
is_show: is_show === true,
```

คำขอที่ไม่ส่ง `is_show` มาจึงได้ `false` ลงคอลัมน์ ทั้งที่คอลัมน์ประกาศไว้ว่า
`Boolean? @default(true)` — ค่าตั้งต้นไม่มีโอกาสได้ทำงานเลย นักศึกษาที่ยิง API
ตรง ๆ โดยไม่ระบุธง จะได้รางวัลที่ไม่ปรากฏใน e-Portfolio ของตัวเอง โดยไม่มีอะไรบอก

สามข้อเท็จจริงที่ล้อมจุดนี้อยู่ ทั้งสามข้อชี้ไปทางเดียวกัน

**คอลัมน์ที่คุมการมองเห็นมี 25 ตัว และ 21 ตัวมีค่าตั้งต้นเป็น "แสดง"** — 12
คอลัมน์ `is_show*` ในเจ็ดส่วนของ e-Portfolio และอีก 9 คอลัมน์ `isShow*` ในตาราง
`portfolio` เอง ทุกตัวเป็น `Boolean? @default(true)` อีกสี่ตัวคือ `isShow*` ของ
`portfolio_skill_activity_mapping` ซึ่งเป็น `@default(false)` — ไม่ใช่ข้อยกเว้น
ของสิ่งที่ ADR นี้ตัดสิน เพราะกฎคือ "คอลัมน์เป็นคนตอบ" ไม่ใช่ "คำตอบคือแสดง"

**อีกหกส่วนที่มีธงแบบนี้ ปล่อยให้ค่าตั้งต้นทำงานอยู่แล้ว** `portfolio-activity`,
`portfolio-certificate`, `portfolio-education`, `portfolio-internship`,
`portfolio-thesis` และ `portfolio-training` ทุกตัวกระจาย `data` ลง `create` ตรง ๆ
ธงที่ไม่ได้ส่งมาจึงเป็น `undefined` และ Prisma ก็ไม่ใส่คอลัมน์นั้นลงใน `INSERT`
เลย (`portfolio-personal` ก็กระจายตรง ๆ เหมือนกัน แต่ตารางของมันไม่มีธงนี้)
นอกกลุ่มนี้ก็เหมือนกัน — `is_average_score` กับ
`is_self_assessment` ใน `activity.service.ts` ก็ส่ง `data.…` ต่อไปตรง ๆ แล้วรับ
`@default(false)` ของคอลัมน์ตัวเอง

**มีอีกที่หนึ่งที่ตอบแทนคอลัมน์ แต่บังเอิญตอบตรงกัน** `assignWorkToSkills` ใน
`portfolio-skill.service.ts` destructure ค่าตั้งต้นไว้ในลายเซ็นเอง
(`isShowRepo = false` และอีกสามตัว) ซึ่งตรงกับ `@default(false)` ของคอลัมน์พอดี
ไม่มีใครเห็นความต่าง มันจึงไม่ใช่ข้อบกพร่อง แต่ก็เป็นสำเนาที่สองของคำตอบเดียวกัน
แบบเดียวกับที่ award เป็น — ต่างกันแค่ award ตอบไม่ตรง ที่นั่นไม่ถูกแก้ในรอบนี้
เพราะไม่มีอะไรให้ผู้เรียกเห็น และการแก้ต้องมี test ของมันเอง (ดู "จะกลับมาทบทวน
เมื่อไหร่")

**ที่ที่ตอบคำถามเดียวกันไว้แล้ว ตอบว่า "ไม่รู้ = แสดง"** `portfolio.service.ts`
แปลง `isShow*` ทั้งเก้าตัวของตาราง `portfolio` ที่เป็น `null` ให้เป็น `true` ก่อน
ส่งออก และหน้าเว็บก็ทำอย่างเดียวกันกับธงย่อยของ internship และ thesis (`?? true`
ใน `use-portfolio.ts` และ `use-public-portfolio.ts`)

**แต่รายการรายแถวไม่มีการแปลนั้น** `use-portfolio.ts` เลือกรางวัลด้วย
`awardData.filter((a) => a.is_show)` ตรง ๆ (`use-public-portfolio.ts` เหมือนกัน)
ค่า `null` จึงหายไปจากหน้าจอเท่ากับ `false` ไม่มีใครแปลให้ทีหลัง — ซึ่งเป็นเหตุผล
ว่าทำไมค่าที่ถูกเขียนลงคอลัมน์ตอนสร้างแถวจึงเป็นคำตอบสุดท้ายจริง ๆ

**`optionalBool` ไม่ได้ผิด** `z.preprocess(toBoolean, z.boolean().optional())`
ปล่อย `undefined` ออกไปเป็น `undefined` ถูกต้อง ที่ #17 บันทึกไว้ว่า "รอ #20"
จึงไม่ตรงตั้งแต่ต้น — #20 เป็นเรื่องของ validation และมันทำถูกแล้ว ตัวที่แปลงคือ
service

**หน้าเว็บไม่เคยเจอ** `create-award-competition-form.tsx` ส่ง
`is_show: values.is_show ?? true` ทุกครั้ง และ service ฝั่งเว็บก็ใส่ลง `FormData`
เมื่อค่าไม่ใช่ `undefined` คนที่เจอคือผู้เรียก API ตรง ๆ เท่านั้น

มีทางเรียก `createPortfolioAward` อีกเส้นหนึ่งที่ spread `...values` โดยไม่มี
`?? true` คือสาขา create ใน `award-edit-modal.tsx` แต่วันนี้ยังไปไม่ถึง —
`award-competition-section.tsx` เปิด modal ด้วย `isOpen={!!editingItem}` เท่านั้น
จึงไม่มีทางเปิดมันโดยไม่มีแถวเดิม ถ้าวันหนึ่งมีคนเปิดทางนั้น หลังการแก้ครั้งนี้
คำตอบที่ได้ก็ยังถูก

## สิ่งที่ต้องตัดสิน

1. ธงที่ไม่ได้ส่งมาใน `POST` แปลว่าอะไร
2. แก้ด้วยการเขียนค่าตั้งต้นลงไป หรือด้วยการไม่เขียนอะไรเลย
3. `PUT` ต้องตอบเหมือน `POST` ไหม

## การตัดสิน

> **ธง optional ที่ไม่ได้ส่งมาใน `POST` ไม่ถูกแตะเลย ปล่อยให้ `@default` ของ
> คอลัมน์เป็นคนตอบ ส่วน `PUT` ยังแปลว่า "ไม่ส่งมา = ไม่แก้" เหมือนเดิม**

### 1. แสดง ไม่ใช่ซ่อน

#46 เสนอไว้สองทาง: ลบการแปลงทิ้ง หรือเก็บพฤติกรรมเดิมไว้แล้วเปลี่ยน
`@default(true)` ของคอลัมน์ให้เป็น `false` ตาม เลือกทางแรก

ทางหลังต้องมี migration ที่กลับค่าตั้งต้นของคอลัมน์เดียว ในบรรดา 21 คอลัมน์ของ
e-Portfolio ที่ทำงานเหมือนกันหมด แล้ว award จะต่างจากเพื่อนบ้านอย่างถาวรโดยไม่มี
เหตุผลเชิงโดเมนรองรับ — ไม่มีอะไรทำให้ "รางวัล" เป็นความลับมากกว่า "ใบรับรอง"
หรือ "การฝึกงาน"
และทิศทางของความผิดพลาดก็สำคัญ: ของที่ควรซ่อนแต่แสดงออกไป เจ้าของเห็นทันทีที่เปิด
e-Portfolio ของตัวเองแล้วกดซ่อนได้ ส่วนของที่ควรแสดงแต่ถูกซ่อน ไม่มีอะไรบอกใครเลย
ว่ามันหายไป

### 2. ไม่เขียนอะไรลงไป ไม่ใช่เขียน `true` ลงไป

ไม่ใช่ `is_show: is_show ?? true` — แบบนั้นแก้อาการได้ แต่ย้ายคำตอบ "ค่าตั้งต้นคือ
อะไร" มาไว้อีกที่หนึ่งซ้อนกับที่ที่มันอยู่แล้ว วันที่มีใครเปลี่ยนใจ เขาจะแก้
migration แล้วอีกหกส่วนจะตามทันที ส่วน award จะไม่ตาม เพราะคำตอบของมันถูก
hard-code ไว้ใน service ความจริงสองที่ที่แยกกันเดินได้ คือสิ่งเดียวกับที่ทำให้
เกิดข้อบกพร่องนี้แต่แรก

ด้วยเหตุผลเดียวกันจึงไม่ใส่ `.default(true)` ที่ `createPortfolioAwardSchema`
ด้วย — validation ตอบว่า "รูปแบบถูกไหม" ไม่ใช่ "ค่าเริ่มต้นของแถวใหม่คืออะไร"
การย้ายการแปลงจาก service ไป schema คือย้ายที่ผิดไปอีกที่หนึ่งเท่านั้น

### 3. `PUT` ตอบคนละคำถาม จึงตอบคนละอย่างได้

`POST` ถามว่า "แถวใหม่เริ่มต้นด้วยค่าอะไร" ส่วน `PUT` ถามว่า "ผู้ใช้ตั้งใจแก้อะไร
บ้าง" ธงที่ไม่ได้ส่งมาใน `PUT` จึงต้องแปลว่า "ไม่แตะ" — ถ้ามันแปลว่า "เอาค่าตั้งต้น"
คำขอที่แก้แค่ชื่อรางวัลจะเปิดการมองเห็นของแถวที่เจ้าของตั้งใจซ่อนไว้ทุกครั้ง

นี่คือเส้นเดียวกับที่ #20 ลากไว้ให้ `clearableDate` และ `clearableInteger` ซึ่งแยก
"ไม่ได้ส่งมา" ออกจาก "ส่งค่าว่างมา" ที่ชั้น schema แล้วปล่อย `updateData` ไปตรง ๆ
`updatePortfolioAward` ไม่ถูกแตะในรอบนี้เลย

## ผลที่ตามมา

- **`POST /portfolio-award` ที่ไม่ส่ง `is_show` ได้ `true` แทน `false`** ทั้งใน
  response และในฐานข้อมูล ดู [`BEHAVIOR-CHANGES.md`](../../BEHAVIOR-CHANGES.md)
- **หน้าเว็บไม่ต้องแก้** ส่งช่องนี้มาทุกครั้งอยู่แล้ว และค่าที่ส่งมาก็ยังถูกใช้
  ตรงตามที่ส่ง ทั้ง `true` และ `false`
- **แถวเก่าไม่ถูกแตะ** ไม่มี migration ย้อนหลัง เพราะแยกไม่ออกว่าแถวไหนเป็น
  `false` เพราะเจ้าของกดซ่อน และแถวไหนเพราะข้อบกพร่องนี้ การเดาแทนเจ้าของแล้ว
  เปิดของที่เขาตั้งใจซ่อน แย่กว่าปล่อยไว้
- **ส่วนที่เหลือของกลุ่มไม่ขยับ** ทั้งหกส่วนถูกอยู่แล้ว ไม่มีการแก้เผื่อ
- **`assignWorkToSkills` ก็ไม่ขยับ** ค่าตั้งต้นที่มันเขียนเองตรงกับคอลัมน์ ผู้เรียก
  จึงไม่เห็นความต่าง การแก้ที่นั่นเป็นการทำความสะอาด ไม่ใช่การซ่อมของเสีย

## จะกลับมาทบทวนเมื่อไหร่

- เมื่อมีใครแตะ `assignWorkToSkills` ด้วยเหตุผลอื่นอยู่แล้ว — ค่าตั้งต้นสี่ตัวใน
  การ destructure ควรถูกลบทิ้งตามข้อ 2 พร้อมเคสที่ยืนยันว่าคำขอที่ไม่ส่งธงมายังได้
  `false` เท่าเดิม
- เมื่อมีใครอยากให้ `PUT` ล้างธงกลับไปเป็นค่าตั้งต้นได้ — นั่นคือคำขอให้มี
  `clearableBool` เทียบเท่าของ #20 ไม่ใช่การกลับข้อ 3
