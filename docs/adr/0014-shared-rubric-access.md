# ADR-0014 — เกณฑ์สำเร็จรูปของหลักสูตรเป็นของอาจารย์ทุกคน ไม่แคบกว่านั้น

- **สถานะ**: ตัดสินแล้ว 11 สิงหาคม 2569
- **ที่มา**: [issue #49](https://github.com/khthana/Deep-Portfolio/issues/49)
- **เกี่ยวข้อง**: [ADR-0002](0002-section-access.md) (อาจารย์กับ section ที่ตัวเองสอน
  — กฎที่ **ไม่ได้** ใช้ที่นี่ และเหตุผลว่าทำไม),
  [ADR-0006](0006-file-access.md) (router อีกตัวที่ไม่มี middleware โดยตั้งใจ),
  [ADR-0012](0012-missing-row-status.md) (แถวที่ไม่มีอยู่ตอบอะไร)

## บริบท

`rubric.route.ts` เป็น router ตัวสุดท้ายในระบบที่ไม่มี middleware ตรวจสิทธิ์เลย
พบตอนไล่ตรวจรายการ pinned ใน `BEHAVIOR-CHANGES.md` เมื่อ 11 สิงหาคม 2569 — ไม่เคย
ถูกบันทึกไว้ที่ไหน เพราะ #13 ที่เขียน test ให้ endpoint คู่นี้มองว่ามันเป็น
"แคตตาล็อก" และ header ของไฟล์ test ก็เขียนไว้ตรง ๆ ว่า "Nothing here checks a
session"

| เส้น | สิ่งที่ผู้เรียกที่ไม่ได้ล็อกอินได้ไป |
| --- | --- |
| `GET /rubric/shared-rubric?program_id=` | เกณฑ์การประเมินทุกตัวของหลักสูตรนั้น |
| `GET /rubric/shared-rubric/detail?rubric_id=` | เกณฑ์ย่อย คำอธิบายทั้งสี่ระดับ และน้ำหนักคะแนน |

`program_id` เป็นรหัสหลักสูตรที่ประกาศอยู่ในเอกสารหลักสูตร ส่วน `rubric_id` เป็น
autoincrement เลขน้อย ๆ ทั้งคู่จึงเดาได้ ตัวคำขอเองเป็นสิ่งเดียวที่กั้นอยู่

router อื่นเกือบทุกตัวมี guard ตั้งแต่ 2 ถึง 18 จุดหลัง #30, #31, #36, #37, #38,
#40 และ #41 ที่ไม่มีเลยมีอีกสองตัวและทั้งคู่ตั้งใจ — `files.route.ts` เพราะลายเซ็น
ของ URL ทำหน้าที่แทน (ADR-0006) และ `group.routes.ts` เพราะสองเส้นตอบรับคำเชิญเปิด
จากลิงก์ในอีเมล invite token จึงเป็นสิทธิ์ทั้งหมด ที่ `rubric.route.ts` ไม่มีอะไร
ทำหน้าที่แทนเลย

## สิ่งที่ต้องตัดสิน

1. เกณฑ์สำเร็จรูปที่ "แชร์" ไว้ เป็นของใคร
2. ถ้าเป็นของอาจารย์ — อาจารย์คนไหนก็ได้ หรือเฉพาะอาจารย์ในหลักสูตรนั้น
3. `program_id` และ `rubric_id` ที่ไม่ตรงกับอะไรเลย ควรตอบอะไร

## การตัดสิน

### 1. `requireRole("TEACHER")` ทั้งสองเส้น

ผู้เรียกฝั่ง web ทั้งหมดอยู่ใต้ `features/teacher/activity/` — หน้าจอสร้างกิจกรรม
ที่อาจารย์เปิด modal เลือกเกณฑ์สำเร็จรูปแล้วคัดลอกเข้ามาในเกณฑ์ของกิจกรรมตัวเอง
มีสองที่ที่ dispatch จริง คือ `shared-rubric-title-table.tsx` กับ
`shared-rubric-detail-table.tsx` ซึ่งอยู่ใน `shared-rubric-modal.tsx` ทั้งคู่
ไม่มีหน้าจอของนักศึกษาไหนเรียกเลย

`requireUser` จึงกว้างเกินสิ่งที่มีอยู่จริง — เป็นการเขียนกฎให้ผู้เรียกที่ยังไม่มี
ตัวตน ถ้าวันหนึ่งนักศึกษาต้องอ่านเกณฑ์ที่ตัวเองจะถูกประเมิน เส้นทางนั้นเดินผ่าน
`GET /activity` ซึ่งคืนเกณฑ์ของกิจกรรมนั้นอยู่แล้ว ไม่ใช่แคตตาล็อกของทั้งหลักสูตร

### 2. อาจารย์คนไหนก็ได้ — ไม่ผูกกับหลักสูตร

เป็นจุดที่ต่างจาก ADR-0002 อย่างตั้งใจ กฎ "อาจารย์เอื้อมถึงเฉพาะของตัวเอง" ที่
`requireOwnSection` บังคับอยู่ 20 กว่าเส้นนั้นยืนอยู่บน `course_sections_teacher`
ซึ่งเป็นความสัมพันธ์ที่ระบบเขียนขึ้นจริงและมีข้อมูลอยู่จริง

กฎ "อาจารย์ในหลักสูตรนั้น" จะต้องยืนบน `users.program_id` แทน และคอลัมน์นั้น
**ไม่ใช่สิ่งที่ระบบบังคับให้กรอก** — ตัวนำเข้าขอแค่ `user_id` กับ `email`
(`docs/importer.md`) ไม่มี UI ไหนเขียนมัน และไม่มีโค้ดที่ไหนอ่านมัน กฎที่ยืนบน
คอลัมน์ว่างจะปฏิเสธอาจารย์ที่มีสิทธิ์จริงทุกคน ซึ่งแย่กว่าการเปิดกว้างเกินไป
หนึ่งขั้น

อีกอย่าง ในทางปฏิบัติ UI ไม่เคยถามหลักสูตรอื่นอยู่แล้ว —
`shared-rubric-title-table.tsx` ส่ง `homeSlice.selectedCourse?.program_id` ซึ่งมา
จากรายวิชาที่อาจารย์คนนั้นสอนอยู่ กฎที่แคบกว่านี้จึงไม่ได้ปิดอะไรที่ผู้เรียกจริง
ทำอยู่ ได้แต่เสี่ยงปฏิเสธคนที่ควรผ่าน

นอกจากนั้น คำว่า **shared** ในชื่อตารางเองก็ตอบข้อนี้ไว้แล้ว เกณฑ์พวกนี้เป็น
reference data ที่ไม่มี endpoint ไหนในระบบเขียนได้เลย — คนดูแลหลักสูตรใส่เข้ามา
ทางอื่น มันจึงเป็นแคตตาล็อก ไม่ใช่ข้อมูลของใครคนใดคนหนึ่ง สิ่งที่ #49 ปิดคือการ
ที่แคตตาล็อกนี้เปิดให้**คนนอกระบบ** ไม่ใช่การที่อาจารย์เห็นของหลักสูตรอื่น

### 3. id ที่ไม่ตรงกับอะไรเลย ยังตอบ `200` พร้อมรายการว่าง

ทั้งสองเส้นเป็น `findMany` ไม่ใช่การอ้างถึงแถวใดแถวหนึ่ง ADR-0012 จึงไม่บังคับ
`404` ที่นี่ — กฎนั้นพูดถึงแถวที่ผู้เรียก**ระบุ** แล้วไม่มี ส่วนรายการที่กรองแล้ว
ว่างเปล่าเป็นคำตอบที่ถูกต้องของคำถามที่ถาม

`program_id` ที่ไม่มีอยู่จริงกับหลักสูตรที่ยังไม่มีเกณฑ์ จึงตอบเหมือนกัน และนั่น
ก็เป็นสิ่งที่ควรเป็นด้วย: การแยกสองอย่างนี้ออกจากกันคือการบอกว่ารหัสหลักสูตรไหน
มีอยู่จริง

## ขอบเขต

- **ไม่ได้เพิ่มกฎว่าอาจารย์ต้องสังกัดหลักสูตรไหน** — จะเพิ่มได้ต้องมีคนเติม
  `users.program_id` ให้ครบก่อน หรือมีตารางความสัมพันธ์ของตัวเอง ทั้งสองอย่างเป็น
  งาน master data ไม่ใช่งาน middleware
- **ไม่ได้แตะ `rubrics.program_id` ที่เป็น nullable** — ตัวนำเข้าไม่ได้บังคับ
  คอลัมน์นี้เหมือนกัน (`docs/importer.md` ขอแค่ `rubric_code` กับชื่อ) เกณฑ์ที่
  นำเข้ามาโดยไม่ระบุหลักสูตรจึงไม่ปรากฏใน `program_id` ไหนเลย เป็นเรื่องของข้อมูล
  ไม่ใช่ของสิทธิ์ และอยู่นอก #49
- **ไม่ได้เปลี่ยนรูปของ response** — ฝั่ง web ไม่ต้องแก้อะไร `axiosInstance` ตั้ง
  `withCredentials: true` ไว้แล้วทั้งตัว และผู้เรียกทั้งสองที่ก็วิ่งผ่านมัน

## ผลที่ตามมา

- router ที่ไม่มี guard เหลืออยู่สองตัว และทั้งคู่มีเหตุผลเขียนไว้ในหัวไฟล์แล้ว:
  `files.route.ts` (ลายเซ็นของ URL ทำหน้าที่แทน ตาม ADR-0006) กับ
  `group.routes.ts` (สองเส้นตอบรับคำเชิญที่เปิดจากลิงก์ในอีเมล invite token
  เป็นสิทธิ์ทั้งหมด) ตัวหลังไม่เคยมีหมายเหตุในโค้ด — เกณฑ์ยอมรับของ #49 เองก็
  เขียนไว้ว่าเหลือแต่ `files.route.ts` ซึ่งไม่จริง จึงเติมหัวไฟล์ให้ในรอบเดียวกัน
- `rubric.test.ts` เลิกเป็นไฟล์เดียวที่ยิงทุกเคสโดยไม่ส่ง cookie — header ของไฟล์
  ที่เขียนว่า "Nothing here checks a session" ถูกแก้ให้ตรงกับสิ่งที่เป็น
- มีเคสหนึ่งที่ยืนบนข้อ 2 โดยตรง (`answers any teacher, not only one of that
  programme`) เพื่อให้การเปลี่ยนกฎให้แคบลงในอนาคตต้องแก้ test อย่างตั้งใจ
  ไม่ใช่หลุดผ่านไปได้

## จะกลับมาทบทวนเมื่อไหร่

เมื่อ `users.program_id` กลายเป็นข้อมูลที่ระบบเติมให้เองและเชื่อถือได้ หรือเมื่อมี
หน้าจอที่นักศึกษาต้องเปิดแคตตาล็อกเกณฑ์ทั้งหลักสูตร ตอนนั้นข้อ 1 และข้อ 2 ต้อง
ตอบใหม่พร้อมกัน
