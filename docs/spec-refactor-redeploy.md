## Problem Statement

โครงงาน DEEP Portfolio เป็นผลงานปริญญานิพนธ์ของนักศึกษาที่ส่งมอบมาในสภาพ **โฟลเดอร์ซอร์สโค้ดสองชุดที่ไม่มีประวัติ git และรันไม่ได้** ผู้ที่รับช่วงต่อเจอปัญหาดังนี้

**ปัญหาที่ 1 — ระบบยืนด้วยตัวเองไม่ได้**
Portfolio ถูกออกแบบให้เป็นระบบดาวเทียมของ DEEP Core ไม่ใช่ระบบเอกเทศ ผลคือ

- ไม่มีหน้า login เป็นของตัวเอง ทางเข้าเดียวคือ `GET /auth/login` ที่อ่าน cookie ชื่อ `token` ซึ่งออกโดย DEEP Core แล้ว verify ด้วย shared secret
- ไม่มีโค้ดสร้างหรือแก้ `users`, `student`, `user_roles` เลยแม้แต่บรรทัดเดียว
- 28 จาก 72 ตารางในฐานข้อมูลไม่มี write path ในระบบนี้ (อ่านอย่างเดียว 10 ตาราง ไม่ถูกแตะเลย 18 ตาราง)

แปลว่าต่อให้ deploy สำเร็จ ก็จะได้ฐานข้อมูลเปล่าที่ไม่มีใครล็อกอินเข้าได้

**ปัญหาที่ 2 — โครงสร้าง repository ไม่พร้อมส่งต่อ**
โค้ดแยกเป็นสองโฟลเดอร์อิสระ ไม่มี `.git` ทั้งคู่ ไม่มี `.env.example` ทั้งที่ระบบต้องการ environment variable 18 ตัว ไม่มีเอกสารวิธีรัน และ backend ไม่มี `build`/`start` script เลย — Dockerfile ที่ใช้ deploy จริงรัน `npm run dev` (`tsx watch`) ซึ่งเป็นโหมดพัฒนา

**ปัญหาที่ 3 — ไม่มีตาข่ายนิรภัย**
โค้ดรวม ~55,000 บรรทัด ไม่มี test แม้แต่ไฟล์เดียว (`npm test` ของ backend คือ `echo "Error: no test specified" && exit 1`) การแก้อะไรก็ตามจึงเสี่ยงพังโดยไม่รู้ตัว ทั้งที่มีของเสียชัดเจนรออยู่หลายจุด

**ปัญหาที่ 4 — เอกสารกับโค้ดไม่ตรงกัน**
เอกสารปริญญานิพนธ์ระบุ data dictionary ไว้ 35 ตาราง แต่ `schema.prisma` จริงมี 72 models — เอกสารครอบคลุมโครงสร้างจริงไม่ถึงครึ่ง ตารางที่หายไปจากเอกสารรวมถึงของสำคัญอย่าง `rubrics`, `roles`, `user_roles`, `subjects`, `student_course` และตาราง `*_attachments` เกือบทั้งหมด

## Solution

ทำให้ DEEP Portfolio กลายเป็น **ระบบเอกเทศที่รันได้ ทดสอบได้ และส่งต่อได้** ผ่านงานสี่ด้าน

**ด้านที่ 1 — ตัดขาดจาก DEEP Core**
เปลี่ยนการยืนยันตัวตนจาก DEEP Core SSO เป็น **Google OAuth ตรงที่ Portfolio** (DEEP Core เองก็ใช้ Google อยู่แล้ว จึงเป็น identity เดียวกัน โดยใช้ `users.email` ซึ่งเป็น unique key เป็นจุดเชื่อม) และให้ Portfolio มีฐานข้อมูลของตัวเองครบทั้ง 72 ตาราง พร้อมเครื่องมือนำเข้า master data

**ด้านที่ 2 — รวมและจัดโครง repository**
รวมเป็น monorepo เดียวด้วย npm workspaces โครงสร้าง `apps/api` + `apps/web` + `packages/` แก้ของเสียที่ชัดเจน และทำให้ `docker compose up` คำสั่งเดียวรันระบบครบทุก service บนเครื่อง local

**ด้านที่ 3 — สร้างตาข่ายนิรภัย**
เขียน integration test ครอบทุก endpoint บน PostgreSQL จริง โดยมี seam เดียวที่ขอบ HTTP และกำกับความครอบคลุมด้วย traceability table เทียบกับ 75 test case ที่มีอยู่ในเอกสารปริญญานิพนธ์

**ด้านที่ 4 — กู้เอกสารให้ใช้งานได้**
สกัด data dictionary และรายการ test case ออกจากไฟล์ `.docx` ขนาด 48 MB มาเป็น Markdown ที่ diff ได้ ค้นหาได้ และอยู่ใน git ได้

### ลำดับการทำงาน

งานแบ่งเป็น 5 เฟสตามลำดับที่ตกลงกัน โดยหลักการคือ **ไม่แก้ logic จนกว่าจะมี test คุ้ม**

| เฟส | ชื่อ | ผลลัพธ์ที่วัดได้ | สถานะ |
|---|---|---|---|
| 1 | รวม repo + จัดโครง | `git log` มี commit แรก, โครงสร้าง `apps/*` ครบ, `npm install` ที่ root สำเร็จ | เสร็จ (#2–#5) |
| 2 | ทำให้รันได้ | `docker compose up` แล้วเปิดเว็บได้, migration รันผ่าน, seed ลงข้อมูลได้ | เสร็จ (#6, #7) |
| 3 | เขียน test | ทุก endpoint มี test, traceability table ครบ TC-01..TC-75 | เสร็จ (#8–#19, #22) |
| 4 | แก้ของเสีย + auth ใหม่ | test เขียวทั้งหมด, `BEHAVIOR-CHANGES.md` บันทึกครบ | เสร็จ — auth (#10, #11) ของเสียแก้ไปพร้อม test ตาม D9 #20 กับ #21 ลง main แล้ว และตั๋วที่ตั้งไว้ระหว่างทางปิดครบ (#25–#54) |
| 5 | Deploy ขึ้น server จริง | (ไม่มีผลลัพธ์ที่ spec นี้รับผิดชอบ — ขอบเขตจบที่ `docker compose up` บนเครื่อง local ซึ่งเฟส 2 ส่งมอบไปแล้ว) | อยู่นอกขอบเขต ตามหัวข้อ Out of Scope — แยกไปที่ [#59](https://github.com/khthana/Deep-Portfolio/issues/59) ซึ่งส่งครึ่ง CI แล้ว ส่วนครึ่ง CD ต่อที่ [#65](https://github.com/khthana/Deep-Portfolio/issues/65) |

## User Stories

### กลุ่มที่ 1 — ผู้รับช่วงพัฒนาต่อ (Developer)

1. ในฐานะนักพัฒนาที่รับช่วงต่อ ฉันต้องการ clone repository เดียวแล้วได้โค้ดทั้ง frontend และ backend เพื่อที่ฉันจะไม่ต้องตามหาว่าโค้ดอีกครึ่งหนึ่งอยู่ที่ไหน
2. ในฐานะนักพัฒนา ฉันต้องการรัน `npm install` ครั้งเดียวที่ root แล้วได้ dependency ครบทั้งสอง app เพื่อที่ฉันจะไม่ต้องจำว่าต้อง install กี่ที่
3. ในฐานะนักพัฒนา ฉันต้องการเห็น `.env.example` ที่ระบุ environment variable ครบทั้ง 18 ตัวพร้อมคำอธิบาย เพื่อที่ฉันจะรู้ว่าต้องเตรียมค่าอะไรบ้างก่อนรัน
4. ในฐานะนักพัฒนา ฉันต้องการรัน `docker compose up` คำสั่งเดียวแล้วได้ระบบครบทุก service เพื่อที่ฉันจะเริ่มทำงานได้ภายในไม่กี่นาทีโดยไม่ต้องติดตั้ง PostgreSQL หรือ MinIO เอง
5. ในฐานะนักพัฒนา ฉันต้องการมี `README.md` ที่บอกวิธี setup ตั้งแต่ศูนย์ เพื่อที่ฉันจะไม่ต้องอ่านโค้ดเพื่อเดาวิธีรัน
6. ในฐานะนักพัฒนา ฉันต้องการให้ backend มี `build` และ `start` script จริง เพื่อที่ production จะไม่ต้องรันโหมด watch ของ development
7. ในฐานะนักพัฒนา ฉันต้องการให้ประวัติ git เริ่มต้นที่ commit ซึ่งเป็นโค้ดเดิมแบบไม่แก้ไข เพื่อที่ฉันจะ diff ได้ว่าอะไรถูกเปลี่ยนไปบ้างในการ refactor
8. ในฐานะนักพัฒนา ฉันต้องการให้ commit ของเฟสจัดโครงสร้างเป็นการย้ายไฟล์ล้วนๆ ไม่ปนการแก้ logic เพื่อที่ฉันจะ review ได้ง่าย
9. ในฐานะนักพัฒนา ฉันต้องการอ่าน data dictionary เป็น Markdown ที่ค้นหาได้ เพื่อที่ฉันจะไม่ต้องเปิดไฟล์ Word ขนาด 48 MB เพื่อดูว่าคอลัมน์หนึ่งหมายถึงอะไร
10. ในฐานะนักพัฒนา ฉันต้องการให้ repository ไม่มีไฟล์ binary ขนาดใหญ่ใน history เพื่อที่การ clone จะไม่ช้าไปตลอดกาล
11. ในฐานะนักพัฒนา ฉันต้องการให้ dead code ถูกลบออก เพื่อที่ฉันจะไม่เสียเวลาอ่านโค้ดที่ไม่มีใครเรียกใช้
12. ในฐานะนักพัฒนา ฉันต้องการให้ dependency ที่ไม่ได้ใช้ถูกถอดออกจาก `package.json` เพื่อที่ surface ของการอัปเดตความปลอดภัยจะเล็กลง
13. ในฐานะนักพัฒนา ฉันต้องการให้ชื่อโฟลเดอร์สะท้อนสิ่งที่อยู่ข้างในจริงๆ เพื่อที่ฉันจะไม่เข้าใจผิดว่า `models/` มี ORM model ทั้งที่มีแต่ type alias
14. ในฐานะนักพัฒนา ฉันต้องการให้โค้ด comment และชื่อ test เป็นภาษาอังกฤษ เพื่อที่เครื่องมือและผู้ร่วมงานในอนาคตจะทำงานกับมันได้โดยไม่ติดปัญหา encoding
15. ในฐานะนักพัฒนา ฉันต้องการอ่านเอกสารอธิบายสถาปัตยกรรมเป็นภาษาไทย เพื่อที่นักศึกษารุ่นถัดไปจะเข้าใจได้เร็ว

### กลุ่มที่ 2 — ผู้ดูแลระบบ / ผู้ deploy (Operator)

16. ในฐานะผู้ดูแลระบบ ฉันต้องการให้ค่าลับทั้งหมดมาจาก environment variable ไม่ใช่ hardcode ในไฟล์ เพื่อที่รหัสผ่าน MinIO จะไม่อยู่ใน `docker-compose.yml` ที่ commit ขึ้น git
17. ในฐานะผู้ดูแลระบบ ฉันต้องการให้ชื่อโดเมนทั้งหมดมาจาก configuration เพื่อที่ระบบจะ deploy ขึ้นโดเมนใหม่ได้โดยไม่ต้องแก้โค้ด
18. ในฐานะผู้ดูแลระบบ ฉันต้องการให้ volume path ของ MinIO มาจาก configuration เพื่อที่ระบบจะไม่ผูกกับ home directory ของนักศึกษาคนเดิม
19. ในฐานะผู้ดูแลระบบ ฉันต้องการให้ระบบปฏิเสธการทำงานถ้า secret สำคัญไม่ถูกตั้งค่า เพื่อที่ระบบจะไม่เผลอรันด้วย secret ค่า default ที่ใครก็เดาได้
20. ในฐานะผู้ดูแลระบบ ฉันต้องการให้ container ใช้ Node.js เวอร์ชันที่ยังได้รับการสนับสนุน เพื่อที่ระบบจะได้รับ security patch ต่อเนื่อง
21. ในฐานะผู้ดูแลระบบ ฉันต้องการรัน database migration ด้วยคำสั่งมาตรฐาน เพื่อที่การอัปเกรดโครงสร้างฐานข้อมูลจะทำซ้ำได้และย้อนกลับได้
22. ในฐานะผู้ดูแลระบบ ฉันต้องการนำเข้าข้อมูลตั้งต้นด้วยคำสั่งเดียว เพื่อที่ระบบใหม่จะมีข้อมูลอาจารย์ นักศึกษา และรายวิชาพร้อมใช้
23. ในฐานะผู้ดูแลระบบ ฉันต้องการให้การนำเข้าข้อมูลรันซ้ำได้โดยไม่ทำให้ข้อมูลซ้ำ เพื่อที่ฉันจะแก้ไฟล์ต้นทางแล้วนำเข้าใหม่ได้อย่างปลอดภัย
24. ในฐานะผู้ดูแลระบบ ฉันต้องการให้การนำเข้าข้อมูลตรวจสอบความถูกต้องก่อนเขียนลงฐานข้อมูล เพื่อที่ข้อมูลผิดรูปแบบจะถูกปฏิเสธพร้อมบอกว่าผิดที่แถวไหน
25. ในฐานะผู้ดูแลระบบ ฉันต้องการเห็น log ที่บอกได้ว่าเกิดอะไรขึ้นเมื่อระบบมีปัญหา เพื่อที่ฉันจะแก้ไขได้โดยไม่ต้องเดา
26. ในฐานะผู้ดูแลระบบ ฉันไม่ต้องการให้ stack trace ของ error หลุดไปถึงผู้ใช้ใน production เพื่อที่ข้อมูลภายในระบบจะไม่รั่ว

### กลุ่มที่ 3 — การยืนยันตัวตน (Authentication)

27. ในฐานะอาจารย์ ฉันต้องการล็อกอินเข้า Portfolio ด้วยบัญชี Google ของสถาบันโดยตรง เพื่อที่ฉันจะไม่ต้องผ่านระบบ DEEP Core ก่อน
28. ในฐานะนักศึกษา ฉันต้องการล็อกอินด้วยบัญชี Google เดียวกับที่ใช้กับระบบอื่นของสถาบัน เพื่อที่ฉันจะไม่ต้องจำรหัสผ่านชุดใหม่
29. ในฐานะผู้ใช้ ฉันต้องการให้ระบบจำการล็อกอินไว้ระยะหนึ่ง เพื่อที่ฉันจะไม่ต้องล็อกอินใหม่ทุกครั้งที่เปิดหน้าเว็บ
30. ในฐานะผู้ใช้ ฉันต้องการให้ session ต่ออายุอัตโนมัติในเบื้องหลัง เพื่อที่ฉันจะไม่ถูกเตะออกกลางคันขณะกรอกฟอร์มยาวๆ
31. ในฐานะผู้ใช้ ฉันต้องการให้การกดออกจากระบบลบ session ได้จริง เพื่อที่คนที่ใช้เครื่องต่อจากฉันจะเข้าบัญชีฉันไม่ได้

## Implementation Decisions

### D1 — โครงสร้าง Monorepo

ใช้ **npm workspaces** ไม่เพิ่มเครื่องมืออื่น (ไม่ใช้ pnpm, ไม่ใช้ Turborepo) เหตุผลคือโปรเจกต์มีแค่ 2 app และผู้รับช่วงต่อเป็นนักศึกษา — เครื่องมือที่น้อยกว่าคือต้นทุนการเรียนรู้ที่ต่ำกว่า

โครงสร้างเป้าหมาย

```
apps/
  api/          <- เดิมคือ backend-main
  web/          <- เดิมคือ frontend-main
packages/       <- เว้นไว้สำหรับ shared types ในอนาคต (ยังไม่สร้างเนื้อหาในเฟสนี้)
docs/
```

`package.json` ที่ root เป็น private workspace root ถือ script ระดับบนสุด (`dev`, `build`, `test`, `lint`) ที่ delegate ลงไปแต่ละ workspace ด้วย `npm -w`

**ไม่** ย้าย type ที่ frontend เขียนเองไปไว้ใน `packages/` ในเฟสนี้ — frontend มี type ที่มิเรอร์ response ของ backend อยู่ราว 2,188 บรรทัดใน 38 ไฟล์ ซึ่งเป็นความซ้ำซ้อนจริง แต่การย้ายเป็นงานระดับที่เกินขอบเขตที่ตกลงกัน จึงบันทึกไว้เป็นงานอนาคตเท่านั้น

**สถานะ: เสร็จแล้ว** โครงสร้างและคำสั่งที่ root อธิบายไว้ใน [`README.md`](../README.md) มีสองเรื่องที่ตัดสินใจเพิ่มระหว่างทำ

- เพิ่ม `concurrently` เป็น devDependency ที่ root ตัวเดียว เพื่อให้ `npm run dev` รันสอง app พร้อมกันได้ — การใช้ `&` ต่อท้ายคำสั่งไม่ทำงานบน Windows ซึ่งเป็นเครื่องที่ใช้พัฒนาอยู่
- lockfile ของสอง app ถูกยุบเป็นไฟล์เดียวที่ root โดย**คงเวอร์ชันเดิมทุกตัว** ไม่ปล่อยให้ npm resolve ใหม่ การ resolve ใหม่ทำให้ direct dependency 41 ตัวลอยขึ้นเวอร์ชันและเกิด type error ใหม่ 23 จุด (`@types/express` 5.0.3 → 5.0.6 เปลี่ยน type ของ `req.params` เป็น `string | string[]` เป็นต้น) ซึ่งขัดกับลำดับใน spec ที่ให้ย้ายโครงก่อน แล้วค่อยแก้ของเสียตอนที่มี test คุมแล้ว การอัปเกรด dependency จึงเป็นงานแยกที่ต้องตั้งใจทำทีหลัง

### D2 — ฐานข้อมูลและ Migration

**`schema.prisma` เป็น source of truth** เอกสารปริญญานิพนธ์ใช้เป็นแหล่ง cross-check เท่านั้น เพราะเอกสารครอบคลุมแค่ 35 จาก 72 ตาราง

Portfolio เป็นเจ้าของฐานข้อมูล **ทั้ง 72 ตาราง** แบบ standalone ตัดขาดจาก DEEP Core โดยสมบูรณ์ ดังนั้น Prisma เป็นเจ้าของ schema ทั้งหมด และใช้ Prisma Migrate ได้ตรงไปตรงมา

ปัจจุบัน `prisma/` มีแต่ `schema.prisma` ไม่มีโฟลเดอร์ `migrations/` และรูปแบบชื่อ relation (เช่น `user_roles_user_roles_user_idTousers`) บ่งชี้ว่า schema มาจากการ introspect ฐานข้อมูลที่สร้างด้วย SQL มือ — จึงต้องสร้าง **initial migration** จาก schema ปัจจุบันเป็น baseline

**ไม่เปลี่ยนชื่อตาราง คอลัมน์ หรือ relation ในเฟสนี้** แม้ชื่อ relation ที่ Prisma generate มาจะอ่านยาก เพราะการเปลี่ยนกระทบทั้ง 208 จุดที่เรียก Prisma และไม่มี test คุ้มในตอนที่ต้องทำ

บันทึกความผิดปกติที่พบไว้ในเอกสาร แต่ไม่แก้ในเฟสนี้ ได้แก่ คอลัมน์ `student.test` ที่เป็นเศษเหลือจากการพัฒนา และการที่ `rubrics`/`rubric_details` ไม่มี write path ขณะที่ `rubric_levels`/`rubric_activity_mapping` มี

**สถานะ: เสร็จแล้ว** (issue #5) — `prisma/migrations/20260808000000_baseline/` สร้างครบ 72 ตาราง พิสูจน์แล้วว่าตั้งจากฐานข้อมูลเปล่าได้ และ `prisma migrate diff` เทียบกับ `schema.prisma` ไม่มีความต่าง

สิ่งที่ค้นพบระหว่างทำ คือ **`schema.prisma` ไม่ได้เป็น source of truth ที่สมบูรณ์จริง** — SQL ที่ Prisma generate ออกมาตรง ๆ รันไม่ผ่าน ต้องแก้มือ 3 จุด ทั้งสามจุดมีคอมเมนต์กำกับไว้ในไฟล์ migration แล้ว

| จุด | ปัญหา | ทำอะไร |
|---|---|---|
| `student.full_name_th`, `student.admission_year` | ของเดิมเป็น generated column แต่ Prisma introspect ออกมาเป็น `@default(dbgenerated(...))` ธรรมดา พอ generate SQL กลับจึงได้ `DEFAULT` ที่อ้างถึงคอลัมน์อื่น ซึ่ง PostgreSQL ปฏิเสธ (`cannot use column reference in DEFAULT expression`) | เขียนกลับเป็น `GENERATED ALWAYS AS (...) STORED` ตรวจแล้วว่าไม่มีโค้ดตรงไหนเขียนค่าลงสองคอลัมน์นี้ มีแต่ `select` |
| `learning_activity_enum`, `cognitive_level_enum` | สองคอลัมน์ใน `subject_clo_measurable_behavior` เป็น `Unsupported(...)` Prisma จึงอ้างชื่อ type แต่ไม่สร้างให้ migration ล้มทันทีที่ถึงตารางนี้ | ประกาศเองเป็น **enum ว่าง** เพราะค่าจริงกู้ไม่ได้ — ฐานข้อมูลเดิมไม่มีแล้ว ไม่มีโค้ดแตะตารางนี้เลย และเอกสารก็ไม่ได้บันทึกไว้ เลือกให้ INSERT ล้มเสียงดัง ดีกว่าเดาค่าขึ้นมาเอง เติมทีหลังด้วย `ALTER TYPE ... ADD VALUE` ได้ — แต่เท่านั้นยังไม่พอให้ตารางนี้เขียนได้ ต้องแก้ `schema.prisma` ให้ประกาศทั้งคู่เป็น `enum` จริงด้วย ดู [#58](https://github.com/khthana/Deep-Portfolio/issues/58) |
| check constraint 4 ตาราง | Prisma ไม่รองรับ check constraint จึง introspect ไม่เห็นตั้งแต่แรก (มีคอมเมนต์เตือนอยู่ใน `schema.prisma` เอง) ฐานข้อมูลที่ migrate แล้วจึงมี check constraint **0 ตัว** | ไม่เพิ่มกลับในเฟสนี้ เพราะไม่รู้เงื่อนไขเดิม บันทึกไว้ให้เห็นแทน |

ข้อสรุปที่ตามมาสำหรับงานถัดไป: การ round-trip `schema.prisma` → SQL → ฐานข้อมูล ไม่ได้ปลอดภัยโดยอัตโนมัติ ทุกครั้งที่เพิ่ม migration ต้องรันจริงบนฐานข้อมูลเปล่า ไม่ใช่แค่ดูว่า generate ผ่าน

### D3 — การยืนยันตัวตน

เปลี่ยนจาก DEEP Core SSO เป็น **Google OAuth ที่ Portfolio โดยตรง**

พฤติกรรมที่ต้องได้

- ผู้ใช้กดปุ่มเข้าสู่ระบบ ระบบพาไปยืนยันตัวตนกับ Google แล้วกลับมาพร้อม identity ที่ยืนยันแล้ว
- ระบบใช้ **อีเมล** เป็นกุญแจเชื่อมกับ `users.email` (เป็น unique constraint อยู่แล้ว)
- **ถ้าไม่พบอีเมลนั้นในตาราง `users` ให้ปฏิเสธการเข้าระบบ** — ไม่สร้าง user ใหม่อัตโนมัติ เพราะ `users.user_id` เป็น `VarChar(8)` ที่มีความหมายเชิงธุรกิจ (เข้ากับรหัสนักศึกษา 8 หลัก) และกติกาการกำหนดค่านี้สำหรับอาจารย์ยังไม่ทราบ ผู้ใช้ต้องถูกนำเข้าระบบผ่าน importer ก่อน
- ระบบออก session ของตัวเองเป็น httpOnly cookie คู่ access/refresh เหมือนเดิม
- บทบาทยังคงอ่านจาก `user_roles` เหมือนเดิม ไม่เปลี่ยนโครงสร้างสิทธิ์

การ verify Google ID token ถูกวางไว้หลัง **interface เดียว** เพื่อให้ test เปลี่ยนเป็น fake identity provider ได้ — นี่เป็นขอบเขตเดียวในระบบที่ถูก mock ใน test

รวม `verifyTeacher` และ `verifyStudent` ที่คัดลอกกันมาเป็น middleware ตัวเดียวที่รับบทบาทเป็นพารามิเตอร์ และให้ `verifyAnyRole` ตรวจสอบว่าผู้ใช้มีตัวตนจริงในระบบ ไม่ใช่แค่ decode token ผ่าน

ตัดโค้ดที่เกี่ยวกับ DEEP Core SSO ออกทั้งหมด รวมถึง `DEEP_CORE_SECRET`

**สถานะ: เสร็จแล้ว** (issue #10 ส่วน middleware, issue #11 ส่วน Google OAuth)

`verifyTeacher` / `verifyStudent` ที่เป็นโค้ดชุดเดียวกันคัดลอกกันมา กลายเป็น `requireRole(...roles)` ตัวเดียว และ `verifyAnyRole` กลายเป็น `requireUser` ที่ตรวจว่าผู้ใช้มีอยู่จริงก่อนปล่อยผ่าน — 15 route file ที่เคย import ของเดิมเรียก `requireRole("TEACHER")` / `requireRole("STUDENT")` ตรงจุดที่ใช้แทน

| ตัดสินใจ | เหตุผล |
| --- | --- |
| ทำ #10 ก่อนเขียน test ส่วนใหญ่ | ถ้าเขียน test ครอบทุก endpoint ก่อนแล้วค่อยรวม middleware จะต้องไล่แก้ expectation ของ `401`/`403` ทุก route ที่ตรวจสิทธิ์ |
| `requireRole` รับได้หลายบทบาท | route ที่ยอมรับหลายบทบาทยังไม่มี แต่การรับ `...roles` ไม่ได้แพงกว่ารับตัวเดียว และเป็นเหตุผลทั้งหมดที่ต้องรวม middleware ตั้งแต่แรก |
| ข้อความ `403` ยังแยกตามบทบาท | ข้อความไปถึงผู้ใช้ตรงๆ "เฉพาะอาจารย์เท่านั้น" บอกอะไรได้มากกว่า "ไม่มีสิทธิ์" การรวม middleware เป็นเรื่องภายใน ผู้เรียกไม่ควรรู้สึกอะไร — มี test คุมข้อความทั้งสองไว้ |
| `requireUser` ตอบ `401` ไม่ใช่ `403` เมื่อไม่พบผู้ใช้ | token ที่ชี้ไปยังบัญชีที่ไม่มีอยู่ ไม่ใช่ session ที่ใช้ได้ ไม่ใช่ session ที่ใช้ได้แต่สิทธิ์ไม่พอ (บันทึกใน `BEHAVIOR-CHANGES.md` ข้อ 1) |
| `sessionUserId(req)` แทน `(req as AuthRequest).user?.user_id` | พอ `AuthRequest.user` เลิกเป็น `any` ทุก controller ก็ได้ `string \| undefined` มาแทน ซึ่ง "undefined" ไม่ใช่ primary key — helper ตัวนี้โยน error ทันทีถ้าไม่มี session เพราะกรณีนั้นแปลว่า route ถูก mount โดยลืม middleware ไม่ใช่ request ที่ auth ไม่ผ่าน (request แบบนั้นไปไม่ถึง controller) |

**ส่วน Google OAuth (#11)** — `POST /auth/google` รับ Google ID token จากเบราว์เซอร์ ตรวจแล้วออก session ชุดเดิม flow นี้ **ไม่มี client secret อยู่เลย** เพราะเบราว์เซอร์ขอ ID token จาก Google โดยตรง (Google Identity Services) แล้ว server มีหน้าที่ verify อย่างเดียว — `GOOGLE_CLIENT_ID` ที่ต้องตั้งจึงเป็นค่าสาธารณะ ไม่ใช่ค่าลับ แต่ยังบังคับ เพราะการตรวจ `audience` คือสิ่งที่กัน token ที่ Google ออกให้เว็บอื่นไม่ให้เอามาใช้ที่นี่

| --- | --- |

| `IdentityProvider` เป็น interface ที่มีเมธอดเดียว | รอยต่อที่ mock ได้ต้องแคบที่สุด สิ่งที่ fake ตัดสินคือ "Google รู้จัก token นี้ไหม และเป็นอีเมลอะไร" เท่านั้น ส่วน "อีเมลนี้เข้าระบบได้ไหม" ตัดสินโดย controller กับตาราง `users` จริง ไม่มีการ mock |

| ค้น `users.email` แบบไม่สนตัวพิมพ์ | Google คืนอีเมลตัวพิมพ์เล็กเสมอ ส่วนแถวใน `users` เก็บตามที่ import มา บัญชีที่มีอยู่จริงต้องไม่เข้าไม่ได้เพราะความต่างที่มองไม่เห็น |

test อยู่ที่ `apps/api/test/auth.test.ts` (ไม่มี session → `401`, บทบาทผิด → `403`, บทบาทถูก → ผ่าน, token เซ็นด้วย secret ผิด → `401`, token หมดอายุ → `401`, บทบาทที่ `is_active = false` → `403`, และ login/logout/refresh ที่เทียบ attribute ของ cookie ฝั่ง set กับฝั่ง clear ตรงๆ) กับ `apps/api/test/env.test.ts` (import `src/config/env.ts` ใหม่โดยลบค่าลับออก แล้วยืนยันว่ามัน throw — คือ test ที่จะล้มถ้ามีใครใส่ fallback กลับเข้ามาเพื่อให้รัน local ง่ายขึ้น)

`app.test.ts` เหลือเคส auth ไว้เคสเดียวคือ "request วิ่งผ่าน middleware ตัวจริง" ส่วนที่เหลือย้ายไป `auth.test.ts` ทั้งหมด — ไฟล์นั้นเป็นเรื่องของรอยต่อ ไม่ใช่ของฟีเจอร์

### D4 — การแยก App ออกจาก Server

ปัจจุบัน `app.ts` เรียก `app.listen()` และ `setupAssignTasksCron()` ตอน import module ทำให้การ import เพื่อทดสอบจะเปิด port และเริ่ม cron job ทันที

**แยกเป็นสองส่วน**

- ส่วนประกอบ app — export Express application ที่ติดตั้ง middleware และ route ครบแล้วแต่ยังไม่ listen
- ส่วน entry point — เรียกส่วนแรก แล้ว listen และเริ่ม cron

นี่คือการเปลี่ยนโครงสร้างชิ้นเดียวที่จำเป็นต่อความสามารถในการทดสอบ และเป็นเงื่อนไขของ seam หลัก

ย้าย route จัดการไฟล์ที่เขียน inline อยู่ใน `app.ts` (`/uploads/:filename` และ `/files`) ไปอยู่ใน router ให้เหมือนส่วนอื่น และลบ route ทดสอบที่คืนข้อความขยะออก

**สถานะ: เสร็จแล้ว** (issue #6) — `src/app.ts` export Express app ที่ยังไม่ listen, `src/server.ts` เป็น entry point ที่ listen และเริ่ม cron, route ไฟล์ย้ายไป `src/routes/files.route.ts` แล้ว mount เป็นตัวแรกใน `routes/index.ts` เพื่อรักษาลำดับเดิม

พิสูจน์ด้วยสคริปต์ชั่วคราวว่า import `src/app` แล้ว **ไม่เปิด socket, ไม่โหลดโมดูล `node-cron` เลย, ไม่มี cron task ถูก schedule** และ app ยังตอบ request ได้ครบเมื่อสั่ง listen เอง สคริปต์นี้ไม่ได้ commit ไว้ เพราะยังไม่มี test harness — **T2/#8 ควรแปลงเป็น test จริง** เพื่อกันไม่ให้ side effect เล็ดลอดกลับเข้า `app.ts` อีก

> **ปิดข้อค้างนี้แล้ว (issue #8)** — `apps/api/test/app.test.ts` มีเคส `expect(cron.getTasks().size).toBe(0)` หลัง import app จริง เท่ากับสคริปต์ชั่วคราวถูกแปลงเป็น test ที่รันทุกครั้งแล้ว

### D5 — การจัดการ Configuration

รวมการอ่าน environment variable ไว้ที่ **โมดูลเดียว** ที่ตรวจสอบความถูกต้องตอนระบบเริ่มทำงาน และล้มทันทีพร้อมข้อความชัดเจนถ้าค่าจำเป็นขาดหาย

**ห้ามมี fallback สำหรับค่าลับ** — ปัจจุบัน `JWT_SECRET` มี fallback เป็น `"your_secret_key"` ซึ่งหมายความว่าถ้า environment ตั้งค่าไม่ครบ ระบบจะยอมรับ token ที่ใครก็ปลอมได้ โดยไม่มีสัญญาณเตือน

ค่าที่ต้องย้ายจาก hardcode ไป configuration

- โดเมนของ cookie ทั้งหมด (ปัจจุบัน hardcode `.deep-core.net` และ `portfolio-api.deep-core.net`)
- รหัสผ่าน MinIO (ปัจจุบันอยู่ใน `docker-compose.yml`)
- volume path ของ MinIO (ปัจจุบันชี้ home directory ของนักศึกษาคนเดิม)

จัดทำ `.env.example` ที่ครอบคลุม environment variable ทุกตัวพร้อมคำอธิบายและค่าตัวอย่าง

**สถานะ: เสร็จ** (#6, #7, #10, #11 — รายละเอียดว่าใบไหนปิดข้อไหนอยู่ย่อหน้าถัดไป)

เสร็จแล้ว — `src/config/env.ts` เป็นโมดูลเดียวที่อ่าน `process.env` ตรวจทุกค่าตอน import (คือตอน startup ก่อน listen) และรวบรวมตัวที่ขาดทั้งหมดมาแจ้งในข้อความเดียว ไม่ใช่แจ้งทีละตัว ค่าลับไม่มี fallback สักตัว ผลข้างเคียงที่ตั้งใจให้เกิดคือ `JWT_REFRESH_SECRET` กับ `DEEP_CORE_SECRET` ซึ่งเดิมเขียน `process.env.X!` ลอย ๆ (ไม่ตรวจอะไรเลย) และ `MINIO_INTERNAL_HOST` / `MINIO_PUBLIC_HOST` ซึ่งเดิมตรวจตอนถูกเรียกใช้ ตอนนี้ล้มตั้งแต่ startup ทั้งหมด

`EMAIL_USER` / `EMAIL_PASS` **จงใจไม่บังคับ** เพราะการส่งอีเมลเชิญอยู่ใน try/catch อยู่แล้ว บัญชีเมลว่างต้องไม่ทำให้ server สตาร์ตไม่ขึ้น

เสร็จเพิ่มใน **#7** — สองข้อล่างของรายการนี้ปิดแล้ว รหัสผ่าน MinIO มาจาก `.env` ที่ root ผ่าน `${MINIO_ROOT_USER:?...}` / `${MINIO_ROOT_PASSWORD:?...}` และ volume ทุกตัวเป็น named volume (`db-data`, `minio-data`, `api-uploads`) ไม่มี path ที่ผูกกับเครื่องใครเหลืออยู่ — `api-uploads` ถูกลบทิ้งใน [#36](https://github.com/khthana/Deep-Portfolio/issues/36) พร้อมกับ route ที่เสิร์ฟมัน ไฟล์ทุกตัวอยู่ใน MinIO อย่างเดียว

*(หมายเหตุความถูกต้อง: รหัสผ่านที่เขียนตรง ๆ กับ volume path ที่ชี้ home directory ของนักศึกษาคนเดิม ถูกถอดออกไปตั้งแต่รอบล้าง secret ก่อน push ครั้งแรก จึงไม่ปรากฏใน git history — ที่ #7 เพิ่มขึ้นมาคือย้ายไปอ่านจาก `.env` ที่ root พร้อม guard `:?` และทำ named volume ให้ครบทั้งสามตัว)*

เสร็จเพิ่มใน **#10** — โดเมนของ cookie ปิดแล้ว เดิมตั้งใจยกยอดไปทำพร้อม **#11 (Google OAuth)** เพราะ #11 เขียน flow ของ cookie ใหม่ทั้งก้อนอยู่แล้ว แต่ #10 มีเงื่อนไขว่า logout ต้องเคลียร์ cookie ด้วยโดเมนเดียวกับตอน set ซึ่งทำไม่ได้ถ้าสองฝั่งยังเขียนโดเมนแยกกันคนละที่ ทางที่เล็กที่สุดคือทำให้อ่านจากที่เดียว และ "ที่เดียว" นั้นก็คือ configuration พอดี — `src/config/cookies.ts` ประกอบ attribute ทั้งชุดจาก `COOKIE_DOMAIN` ค่าเริ่มต้นคือเว้นว่าง แปลว่าไม่ใส่ `Domain` เลย (host-only cookie) ซึ่งเป็นค่าที่ถูกสำหรับเครื่อง dev อยู่แล้ว

`res.clearCookie("token", { domain: ".deep-core.net" })` ใน logout ที่เคยเหลือค้างอยู่ (ตั้งใจปล่อยไว้ตอน #10 — เป็น cookie ของโดเมน DEEP Core ที่ API นี้ลบไม่ได้อยู่แล้ว) ถูกลบไปพร้อมทาง SSO ใน **#11** ตามที่บอกไว้ ตอนนี้ไม่มีโดเมนที่ hardcode เหลือในโค้ดฝั่ง backend แล้ว

### D6 — Docker และการรัน

`docker compose up` คำสั่งเดียวที่ root ต้องได้ระบบครบ ประกอบด้วย PostgreSQL, MinIO, API และ web

Dockerfile ของ API เปลี่ยนเป็น **multi-stage build** ที่ compile TypeScript แล้วรันผลลัพธ์ที่ compile แล้ว — ไม่ใช่รัน `tsx watch` แบบปัจจุบัน

อัปเกรด base image จาก `node:18-alpine` เป็น **Node.js 22 LTS** (Node 18 หมดระยะสนับสนุนแล้ว)

Dockerfile ต้องรองรับโครงสร้าง npm workspaces (build context ที่ root เพื่อให้เห็น lockfile ร่วม)

คงการใช้ **MinIO** ไว้ ไม่เปลี่ยนไปใช้ S3 หรือบริการ managed อื่น

**สถานะ: เสร็จแล้ว** (issue #7)

`docker-compose.yml` ตัวเดียวที่ root แทนของเดิมที่แยกอยู่สอง app (ลบทิ้งทั้งคู่แล้ว) มี 6 service — `db`, `minio`, `minio-init`, `migrate`, `api`, `web` โดยสองตัวกลางเป็น one-shot ที่ทำงานเสร็จแล้วจบ ส่วน `api` รอทั้งคู่ด้วย `condition: service_completed_successfully` ทำให้ `docker compose up` ครั้งเดียวได้ฐานข้อมูลที่ migrate ครบและ bucket ที่สร้างไว้แล้วโดยไม่ต้องสั่งอะไรเพิ่ม

Dockerfile ทั้งสองตัวเป็น multi-stage บน `node:22-alpine` และใช้ build context ที่ root — จำเป็น เพราะ `package-lock.json` อยู่ที่ root ถ้า context เป็น `apps/api` จะเห็น `package.json` ที่ไม่มี lockfile อยู่ข้าง ๆ แล้ว `npm ci` จะไม่ยอมรัน แต่ละตัวติดตั้งเฉพาะ workspace ของตัวเองด้วย `npm ci --workspace ... --include-workspace-root` จึงไม่ลาก dependency ของอีกฝั่งเข้ามา ภาพของเว็บเป็น nginx ที่มีแต่ไฟล์ static (98 MB) ส่วนภาพของ API รัน `node dist/server.js` ในฐานะ user `node` ไม่ใช่ root

| ภาพ API ใหญ่ 685 MB เพราะยังมี dev dependency ติดมา | ยอมรับ ไม่ prune | Prisma CLI เป็น dev dependency และเป็นตัวที่ generate `@prisma/client` ตอน install **และ** เป็นตัวที่รัน `migrate deploy` — service `migrate` คือภาพเดียวกันนี้เปลี่ยนแค่ command ตัด dev dependency ออกแล้วพังทั้งสองทาง การแยกให้เล็กลงเป็นงานของ ticket deploy ไม่ใช่ของ local stack |
| `NODE_ENV` ใน compose ตั้งเป็น `development` | ตั้งใจ | production ตั้ง cookie เป็น `secure: true` ซึ่งเบราว์เซอร์จะไม่ส่งกลับผ่าน http ธรรมดา ทำให้ถือ session บน `http://localhost` ไม่ได้เลย stack นี้จึงเป็นของ local ล้วน ๆ *(ตอนเขียน #7 เหตุผลยังรวมโดเมน `*.deep-core.net` ที่ hardcode ไว้ด้วย ซึ่งย้ายไป configuration แล้วใน #10 และหายไปทั้งหมดใน #11)* |

**เรื่อง `.env` สองไฟล์** — `.env` ที่ root เป็นของ compose เท่านั้น ส่วน `apps/api/.env` เป็นของตอนรัน API บนเครื่องตรง ๆ ไม่ใช่ของซ้ำกันและรวมกันไม่ได้ เพราะค่าเดียวกันต้องต่างกัน: ฐานข้อมูลอยู่ที่ `db:5432` เมื่อมองจากใน compose network แต่อยู่ที่ `localhost:5432` เมื่อมองจาก host ไฟล์ที่ root เก็บเฉพาะค่าลับ ส่วนชื่อ host กับ port ที่ compose กำหนดเองเขียนเป็น literal ใน `docker-compose.yml` — ค่าที่จำเป็นใช้ `${VAR:?...}` ทั้งหมด ถ้าลืมเติม compose จะหยุดพร้อมบอกว่าขาดตัวไหน ไม่ใช่สตาร์ตขึ้นมาด้วยรหัสผ่านว่าง

port ฝั่ง host ทุกตัวเป็นตัวแปร (`WEB_PORT`, `API_PORT`, `DB_PORT`, `MINIO_API_PORT`, `MINIO_CONSOLE_PORT`) และ URL ที่ขึ้นกับ port ถูก derive จากตัวแปรเดียวกัน — เปลี่ยน `WEB_PORT` แล้ว `CLIENT_URL` (คือ origin ที่ API ยอมให้ผ่าน CORS) ขยับตามเอง ที่ต้องทำแบบนี้เพราะเครื่อง dev มักมีของอื่นจับ 3000 หรือ 5432 อยู่แล้ว ซึ่งเกิดขึ้นจริงตอนทดสอบ

**เกิดขึ้นจริงอีกครั้งตอนนำเข้าข้อมูลใน #23** และอาการหลอกกว่าที่คิด — เครื่องที่ใช้มี PostgreSQL ที่ติดตั้งบน Windows ตรง ๆ (ไม่ใช่ Docker) ฟังอยู่ที่ `0.0.0.0:5432` และชนะ port proxy ของ Docker การต่อไปที่ `localhost:5432` จึงไปถึง server คนละตัว แล้ว `prisma migrate deploy` ตอบ `P1000 Authentication failed against database server` ซึ่งอ่านเหมือนรหัสผ่านผิด ทั้งที่รหัสผ่านถูก วิธียืนยันคือนับจำนวน process ที่ถือ port นั้น (`netstat -ano -p tcp | grep :5432` เห็นสอง PID) ไม่ใช่ไล่แก้รหัสผ่าน ทางแก้คือตั้ง `DB_PORT` เป็นเลขอื่นใน `.env` ที่ root แล้วชี้ `DATABASE_URL` ใน `apps/api/.env` ตามไปด้วย — มีบันทึกไว้ใน [README](../README.md) ส่วนแก้ปัญหา

**ผลตรวจสอบจริง** (ไม่ใช่แค่ `config` ผ่าน) — `docker compose up` จากศูนย์ขึ้นครบทั้ง 6 service, migration ลงครบได้ 73 ตาราง (72 + `_prisma_migrations`) กับ enum 17 ตัว, bucket ถูกสร้าง, API ต่อ MinIO ด้วย credential จริงแล้ว `bucketExists` เป็น true, เว็บเสิร์ฟ SPA fallback ได้ (`/login` → 200), CORS ตอบ origin ที่ derive มาถูกต้อง, volume `uploads` เขียนได้จาก user `node` (volume นี้ไม่มีแล้วตั้งแต่ #36), `down` แล้ว `up` ใหม่ข้อมูลอยู่ครบและ migration ขึ้น "No pending migrations", `down -v` แล้ว `up` ใหม่ migrate ใหม่จากศูนย์ได้

**ที่ยังทำไม่ได้ในนี้** — ยัง login ไม่ได้ ทางเข้าเดียวที่โค้ดมีคือ SSO cookie ที่ระบบ DEEP Core เป็นคนออก ซึ่ง local ไม่มี stack นี้จึงพิสูจน์ได้ว่าทุก service ขึ้นครบและคุยกันได้ แต่ยังไม่ใช่การใช้งานจริงตั้งแต่หน้า login — ต้องรอ **#11**

### D7 — เครื่องมือนำเข้าข้อมูล

### D9 — นโยบายเมื่อพบพฤติกรรมที่ผิด

**แก้ทันทีที่เจอ และเขียน test ให้สะท้อนพฤติกรรมที่ถูกต้อง** ไม่ล็อกพฤติกรรมที่ผิดไว้

ความเสี่ยงที่ตามมาคือ frontend อาจเขียนโดยพึ่งพาพฤติกรรมเดิม จึงต้องมีมาตรการควบคุม

- ทุกการเปลี่ยนพฤติกรรมบันทึกใน `BEHAVIOR-CHANGES.md` ระบุ endpoint พฤติกรรมเดิม พฤติกรรมใหม่ และเหตุผล
- ทุกครั้งที่บันทึก ต้องไล่ตรวจโค้ด frontend ที่เรียก endpoint นั้นและแก้ให้สอดคล้องในการเปลี่ยนแปลงเดียวกัน

`BEHAVIOR-CHANGES.md` ที่ root เริ่มใช้จริงตั้งแต่ **#10** ซึ่งเป็นตั๋วแรกที่เปลี่ยนพฤติกรรมที่ผู้เรียกเห็น แต่ละรายการมีช่อง "frontend ที่ต้องตามแก้" เสมอ — และคำว่า "ไม่ต้องแก้" ก็ต้องมีเหตุผลกำกับ ไม่ใช่ปล่อยว่าง

### D10 — โครงสร้างชั้นของ Backend

**คงโครงสร้างเดิม** — `controllers` / `services` / `routes` / `middlewares` / `jobs` / `utils` ยังใช้ได้และเป็นรูปแบบที่คุ้นเคย ไม่ตัด layer ใหม่ ไม่ทำ dependency injection ไม่แยก repository layer

ข้อยกเว้นเดียวคือโฟลเดอร์ `models/` ซึ่งชื่อทำให้เข้าใจผิด — ข้างในมีแต่ type alias ไม่ใช่ ORM model (Prisma generate type ให้อยู่แล้ว) จึงเปลี่ยนชื่อให้ตรงกับสิ่งที่อยู่ข้างในจริง

ไม่แตะ `student.service.ts` (930 บรรทัด) และ `student-activity.service.ts` (700 บรรทัด) ในเชิงโครงสร้าง

*#20 เพิ่มโฟลเดอร์เดียวนอกโครงนี้คือ `apps/api/src/validation/` ซึ่งเก็บ schema ของแต่ละกลุ่ม endpoint กับ middleware ที่เรียกใช้ — ไม่ใช่ layer ใหม่ในทางไหล่ของ request เพราะไม่มีใครเรียกต่อจากมัน แต่เป็นที่เก็บ schema ที่ทั้ง route (ตอนตรวจ) และ controller (ตอนอ่านค่าที่ตรวจแล้ว) อ้างถึงร่วมกัน วางแยกเพราะถ้าอยู่ใน `models/` จะปนกับ type alias ที่ D10 เพิ่งแยกออกมาให้ชัด*

### D11 — โครงสร้าง Frontend

**คงโครงเดิมทั้งหมด** โครงสร้าง feature-based ที่แยกตามบทบาท (`features/student/*`, `features/teacher/*`, `features/shared/*`) โดยแต่ละ feature มี `components` / `pages` / `services` / `stores` / `types` ของตัวเอง เป็นสถาปัตยกรรมที่ดีกว่าฝั่ง backend อยู่แล้ว

แตะเฉพาะ: ย้ายเข้า `apps/web`, เขียนหน้า login ใหม่, แก้ axios interceptor, ลบ `console.log`, เพิ่ม typed environment, และปรับจุดที่ backend เปลี่ยนพฤติกรรมตามที่บันทึกใน `BEHAVIOR-CHANGES.md`

*#19 เพิ่มโฟลเดอร์เดียวนอกโครงนี้คือ `apps/web/src/test/` ซึ่งเก็บของที่ใช้ร่วมกันระหว่าง test ของหลาย feature — ตัว test เองยังวางข้างไฟล์ที่มันทดสอบตามโครงเดิม ส่วนงานสุขอนามัยที่เหลือฝั่งเว็บอยู่ที่ [issue #21](https://github.com/khthana/Deep-Portfolio/issues/21)*

### D13 — Version Control

`git init` ที่ root พร้อม `.gitignore` รวมที่ครอบคลุมทั้งสอง app (ปัจจุบันไม่มี git repository ทั้งสองฝั่ง)

Commit แรกเป็นโค้ดเดิมแบบไม่แก้ไข เพื่อให้ diff การ refactor ทั้งหมดได้ Commit ของเฟสจัดโครงสร้างต้องเป็นการย้ายไฟล์ล้วนๆ แยกจาก commit ที่แก้ logic

**สถานะ: เสร็จแล้ว** — remote คือ [`khthana/Deep-Portfolio`](https://github.com/khthana/Deep-Portfolio) ซึ่งเป็น **repo สาธารณะ** ค่าลับทุกตัวถูกถอดออกก่อน commit แรก `.env.example` ทุกไฟล์เว้นค่าว่างไว้ และค่าที่ใช้ใน test เป็นค่าสมมติที่อ่านออกว่าเป็นค่าสมมติ — กติกานี้ยังบังคับอยู่กับทุก commit ต่อจากนี้

**ขยายความหลัง #23** — สิ่งที่ห้ามเข้า repo ไม่ได้มีแค่ค่าลับ แต่รวม **ข้อมูลส่วนบุคคลจริง** ด้วย ไฟล์ CSV ที่ป้อนให้ importer อยู่ในโฟลเดอร์ `data/` ที่ root ซึ่งใส่ไว้ใน `.gitignore` แล้ว เพราะข้างในมีชื่อ อีเมล และเบอร์โทรของอาจารย์จริง กติกาคือ **ห้าม commit `data/` และห้ามคัดชื่อ อีเมล หรือเบอร์โทรจากในนั้นออกมาใส่ commit message, issue, test fixture หรือเอกสารใด ๆ** ไฟล์เหล่านั้นอยู่บนเครื่องที่รัน import เท่านั้น

## Testing Decisions

### T1 — หลักการ: ทดสอบพฤติกรรมภายนอก ไม่ทดสอบรายละเอียดภายใน

Test ที่ดีในโปรเจกต์นี้ต้อง

- **assert กับสิ่งที่ผู้เรียกเห็น** — HTTP status, โครงสร้างและค่าใน response body, และสถานะข้อมูลในฐานข้อมูลหลังการเรียก
- **ไม่ assert ว่าโค้ดภายในถูกเรียกอย่างไร** — ไม่ตรวจว่า service ตัวไหนถูกเรียก ไม่ตรวจว่า Prisma ถูกเรียกด้วย argument อะไร เพราะสิ่งเหล่านั้นคือรายละเอียดการ implement ที่การ refactor ควรเปลี่ยนได้โดย test ไม่พัง
- **รอดจากการ refactor ที่ไม่เปลี่ยนพฤติกรรม** — ถ้าย้ายโค้ดจาก controller ไป service แล้ว test แดง แปลว่า test นั้นผูกกับรายละเอียดภายในมากเกินไป

เหตุผลที่ยึดหลักนี้เข้มงวดเป็นพิเศษ: จากการสำรวจพบว่า service ในระบบนี้มีการเรียก Prisma 208 จุดและใช้ `$transaction` 24 จุด ขณะที่ `utils/` ทั้งหมดรวมกันมีแค่ 100 บรรทัด — แปลว่า **ตรรกะของระบบอยู่ในตัว query เอง ไม่ใช่ในฟังก์ชันบริสุทธิ์** การ mock Prisma จึงจะได้ test ที่ยืนยันแค่ว่า mock ถูกเรียก ไม่ได้พิสูจน์ว่า query ถูกต้อง

### T2 — Seam

**Seam หลัก (หนึ่งเดียว): ขอบ HTTP ของ Express application**

Test import Express app ที่ประกอบเสร็จแล้ว (ยังไม่ listen — ดู D4) ยิง request ด้วย supertest แล้ว assert กับ response และสถานะฐานข้อมูล

Seam เดียวนี้ครอบคลุมทุกอย่างที่อยู่ใต้มัน — 142 endpoints, 30 route modules, 35 controllers, 42 services, middleware ทั้งหมด และความถูกต้องของ Prisma query — โดยไม่ต้องมี seam ภายในเลย นี่คือ seam ที่สูงที่สุดเท่าที่เป็นไปได้ และเป็นเหตุผลที่เลือกมัน

**Seam รอง: ฟังก์ชันบริสุทธิ์ฝั่ง frontend**

import ฟังก์ชันมาเรียกตรงๆ ไม่มี DOM ไม่มี mock ครอบคลุม `utils/` 8 ไฟล์ 210 บรรทัด (การจัดรูปแบบวันที่ไทย, การประกอบ form data, การแปลงเวลา, การจัดการปีการศึกษา) และ reducer ของ redux slice 14 ตัว

**ขอบเขตเดียวในระบบที่ถูก mock: การ verify Google ID token**

เพราะเป็นบริการภายนอกจริงที่เรียกใน test ไม่ได้ จึงวางไว้หลัง interface เดียว (ดู D3) แล้ว test สลับเป็น fake ที่คืน identity ตามต้องการ

สิ่งที่ **ไม่** mock — PostgreSQL ใช้ตัวจริง, MinIO ใช้ตัวจริงใน container, และ session cookie ใน test สร้างผ่าน helper ที่เซ็น token ด้วย secret ของ test แล้ววิ่งผ่าน middleware ตรวจสิทธิ์ตัวจริง ไม่ bypass

**สถานะ: เปิดครบทั้งสอง seam แล้ว**

| seam | ปิดใน | ที่ได้ |
| --- | --- | --- |
| ขอบ HTTP ของ Express | #12 (ตั้งค่ารายวิชา), #13 (ออกแบบการประเมิน), #14 (ส่งงาน/งานกลุ่ม), #15 (ให้คะแนน), #16–#17 (e-Portfolio), #18 (identity) | 690 เคส 38 ไฟล์ ใน `apps/api/test/` |
| ฟังก์ชันบริสุทธิ์ฝั่ง frontend | #19 | 390 เคส 22 ไฟล์ วางข้างไฟล์ที่ทดสอบ — `utils/` 8 ไฟล์ และ reducer ของ slice ทั้ง 14 ตัว |

ข้อสังเกตจาก seam รอง: slice ทั้ง 14 ตัวมีรูปแบบเดียวกันจนเคสของ 79 thunk ซ้ำกันเกือบทั้งหมด จึงยุบส่วนที่ซ้ำเป็นตารางที่ `apps/web/src/test/slice-cases.ts` ซึ่ง assert state ทั้งก้อนทุกครั้ง (handler ที่เผลอเขียนช่องอื่นจะตกที่นั่น) แล้วให้ไฟล์ของแต่ละ slice เขียนมือเฉพาะสิ่งที่เป็นของตัวเอง — action ถูกประกอบจาก `typePrefix` ของ thunk เอง thunk ที่ถูกเปลี่ยนชื่อจึงยังวิ่งถึง reducer และ thunk ที่ถูกลบจะ compile ไม่ผ่าน

### T3 — เครื่องมือและโครงสร้างพื้นฐาน

**Vitest** เป็น test runner เดียวทั้ง workspace — frontend เป็น Vite อยู่แล้ว การใช้ runner เดียวหมายถึงไม่ต้องตั้ง `ts-jest` และมี config รูปแบบเดียวให้เรียนรู้

**supertest** สำหรับยิง request เข้า Express app

**PostgreSQL** มาจาก compose file แยกสำหรับ test โดยใช้กลไก **template database** — migrate และ seed ลงฐานข้อมูลต้นแบบครั้งเดียว จากนั้นแต่ละ test file สร้างฐานข้อมูลของตัวเองด้วย `CREATE DATABASE ... TEMPLATE ...` ซึ่ง PostgreSQL คัดลอกได้เร็วมาก

เหตุผลที่เลือกวิธีนี้แทน truncate ระหว่างเคส: test แต่ละไฟล์แยกฐานข้อมูลกันสมบูรณ์จึง **รันขนานกันได้** ซึ่งสำคัญเมื่อชุด test มีขนาดราว 300 เคส และเหตุผลที่เลือกแทน testcontainers: startup เร็วกว่า และหลีกเลี่ยงปัญหาจุกจิกของ Docker Desktop บน Windows

เหตุผลที่ไม่ห่อทุกเคสใน transaction แล้ว rollback: โค้ดใช้ `$transaction` เองอยู่ 24 จุด การซ้อน transaction จะทำให้ทดสอบพฤติกรรม transaction จริงไม่ได้

**สถานะ: เสร็จแล้ว** (issue #8) — `npm test` ที่ root สั่งเดียวจบ ยกคอนเทนเนอร์เอง migrate เอง แล้วรัน test ทั้งสอง workspace

โครงที่ได้

| ไฟล์ | หน้าที่ |
| --- | --- |
| `docker-compose.test.yml` | Postgres + MinIO สำหรับ test โดยเฉพาะ คนละ project name และคนละ port กับ stack ของ dev |
| `apps/api/test/global-setup.ts` | รันครั้งเดียวต่อการเรียก `vitest` — `docker compose up --wait` แล้ว `prisma migrate deploy` ลงฐานข้อมูลต้นแบบ |
| `apps/api/test/setup.ts` | รันครั้งเดียว**ต่อ test file** — สร้างฐานข้อมูลจาก template และ bucket ของไฟล์นั้น แล้วลบทิ้งใน `afterAll` |

การตัดสินใจที่เกิดขึ้นระหว่างทำ

| เรื่อง | ที่ตัดสิน | เหตุผล |
| --- | --- | --- |
| จุดที่ตั้งค่า `DATABASE_URL` | ใน `setupFiles` ไม่ใช่ `globalSetup` | Vitest รัน setup file และรอ top-level `await` ของมัน **ก่อน** import ของ test file — จังหวะนี้คือจังหวะเดียวที่ยังตั้งค่าได้ก่อน `new PrismaClient()` ทั้งสามจุดในโค้ดจะถูกสร้าง แปลว่าโค้ดจริงไม่ต้องรู้เลยว่ากำลังถูกทดสอบ |

| การลบฐานข้อมูล | `DROP DATABASE ... WITH (FORCE)` | connection pool ของ Prisma ไม่ได้ปิดทันทีเสมอ ถ้าไม่ force จะเหลือฐานข้อมูลค้างสะสม |

พิสูจน์แล้วว่าแยกกันจริง ไม่ใช่แค่ test เขียว: ลองแก้ให้ทุกไฟล์ใช้ชื่อฐานข้อมูลเดียวกันชั่วคราว แล้ว `isolation.a` / `isolation.b` ล้มทันทีด้วย `database "..." already exists` — แปลว่าสองไฟล์รันขนานกันจริงและได้ฐานข้อมูลคนละตัวจริง

**ยังไม่ทำในตั๋วนี้** — baseline seed และ factory helper ตาม T4 (*ทำแล้วใน #9*), ตารางเทียบ TC-01..TC-75 ตาม T5, และ CI

### T4 — การเตรียมข้อมูล

**Baseline seed + factory helper**

- **Baseline seed** ลงข้อมูลอ้างอิงที่ไม่เปลี่ยนแปลงระหว่างเคส — คณะ ภาควิชา หลักสูตร รายวิชา บทบาท ภาคการศึกษา — ลงในฐานข้อมูลต้นแบบครั้งเดียว
- **Factory helper** ให้แต่ละเคสสร้างข้อมูลเฉพาะของตัวเอง เช่น สร้างรายวิชา สร้างกิจกรรม สร้างนักศึกษา สร้างการส่งงาน โดยรับเฉพาะค่าที่เคสนั้นสนใจ ส่วนที่เหลือใช้ค่า default ที่สมเหตุสมผล

เหตุผล: schema มี 115 relation การให้ทุกเคสสร้างข้อมูลเองตั้งแต่ศูนย์จะทำให้โค้ด test ยาวกว่าโค้ดจริง ขณะที่การ seed ชุดใหญ่ชุดเดียวให้ทุกเคสใช้ร่วมกันจะทำให้ test ผูกกันแน่นจนแก้ seed ทีเดียวพัง test หลายสิบเคส

ข้อมูลใน test เป็น **ข้อมูลสังเคราะห์ทั้งหมด** ไม่ผูกกับข้อมูลจริงของสถาบัน ทำให้ test รันได้บนเครื่องใครก็ได้ ไม่มีข้อมูลส่วนบุคคลใน repository และไม่ต้องรอ importer เสร็จ

> **importer เสร็จแล้ว (#23) และฐานข้อมูล dev มีข้อมูลจริงอยู่แล้วตั้งแต่ 9 ส.ค. 2569 แต่กติกาข้อนี้ไม่ได้อ่อนลง** — test ของ importer เองก็เขียนไฟล์ CSV สังเคราะห์ขึ้นมาในโฟลเดอร์ชั่วคราวต่อเคส ไม่เคยอ่านจาก `data/` และไม่มีเคสไหนสมมติว่าฐานข้อมูลมีข้อมูลของสถาบันอยู่ ข้อมูลจริงอยู่แค่ในฐานข้อมูลบนเครื่องกับโฟลเดอร์ `data/` ที่ gitignore ไว้ (ดู D13)

หลักการเขียน fixture: **เคสอ่านแล้วต้องรู้ทันทีว่าสนใจอะไร** — สิ่งที่เกี่ยวข้องกับเคสต้องปรากฏในตัวเคส ไม่ซ่อนอยู่ใน helper

### T5 — ขอบเขตและนิยามความครอบคลุม

**นิยามที่ตกลงกัน: ทุก endpoint ต้องมีอย่างน้อยหนึ่งเคสที่สำเร็จและหนึ่งเคสที่ล้มเหลว**

- 142 endpoints ใน 30 route modules → ประมาณ 300+ เคส
- endpoint ที่มี middleware ตรวจสิทธิ์ ต้องมีเคสยืนยันการปฏิเสธผู้ไม่มีสิทธิ์ (401 สำหรับไม่มี session, 403 สำหรับบทบาทไม่ถูกต้อง)

เลือกนิยามนี้แทนการตั้งเป้า line coverage เป็นเปอร์เซ็นต์ เพราะเปอร์เซ็นต์หลอกได้ — เขียน test ที่วิ่งผ่านโค้ดเยอะแต่ไม่ assert อะไรสำคัญก็ได้ตัวเลขสวย ขณะที่การนับ endpoint วัดตรงไปตรงมาและไม่มีช่องว่าง

**Traceability กับเอกสาร**

จัดทำตารางเทียบ TC-01 ถึง TC-75 จากบทที่ 4 ของปริญญานิพนธ์กับ automated test ที่เขียนจริง โดยระบุสถานะแต่ละข้อว่าครอบคลุมแล้ว ครอบคลุมบางส่วน หรือครอบคลุมไม่ได้

ข้อจำกัดที่ต้องยอมรับล่วงหน้า: **75 test case ในเอกสารเป็น manual UI test** (ระดับ "กดปุ่มแล้วเห็นอะไรบนหน้าจอ") จึงแปลงเป็น API integration test ตรงๆ ไม่ได้ทั้งหมด — ข้อที่เป็นการตรวจสอบการแสดงผลล้วนจะถูกทำเครื่องหมายว่าอยู่นอกขอบเขตของ automated test พร้อมเหตุผล ตารางนี้จึงเป็นทั้งเครื่องมือวัดและเอกสารยอมรับข้อจำกัด

**กลุ่มที่ตัดได้ถ้าต้องลดขนาดงาน**

ถ้าถึงจุดที่ต้องลดขอบเขต จุดที่ปลอดภัยที่สุดคือลดเคส error path ของกลุ่ม `portfolio_*` ซึ่งมี 14 controller ที่เป็น CRUD หน้าตาเหมือนกันเกือบทั้งหมด — เก็บ happy path ครบ และเลือกทำ error path ให้ครบเฉพาะตัวแทนหนึ่งตัวของกลุ่ม

**สถานะ: นิยาม "หนึ่งสำเร็จหนึ่งล้มเหลวต่อ endpoint" ทำครบแล้ว** ตลอด #12–#18 ไม่ต้องใช้ทางลดขอบเขตข้างบนเลย ข้อยกเว้นที่บันทึกไว้ในไฟล์ test เองคือ endpoint ที่ไม่รับ input อะไรเลยจึงไม่มีคำขอให้ปฏิเสธ (เช่น `GET /portfolio/templates`)

**ตารางเทียบ TC-01..TC-75 ทำแล้วใน [#22](https://github.com/khthana/Deep-Portfolio/issues/22)** → [`tc-traceability.md`](./tc-traceability.md) — ครอบคลุมแล้ว 62 ข้อ ครอบคลุมบางส่วน 11 ข้อ ครอบคลุมไม่ได้ 2 ข้อ (TC-01, TC-02 คือการเข้าสู่ระบบด้วยรหัสผ่านซึ่ง D3 เอาออกไปแล้ว) ช่องว่างที่ไล่แล้วพบว่าควรครอบได้แต่ยังไม่ครอบ แยกเป็น [#34](https://github.com/khthana/Deep-Portfolio/issues/34) และ [#35](https://github.com/khthana/Deep-Portfolio/issues/35) ไม่กลบไว้ในตาราง

### T6 — สิ่งที่ต้องระวังใน Test

**Cron job** — `setupAssignTasksCron()` ต้องไม่ทำงานระหว่าง test (แก้ได้โดยการแยก app ออกจาก server ตาม D4) — *ปิดแล้วใน #8 ด้วยเคสที่ assert `cron.getTasks().size === 0` หลัง import app*

**การอัปโหลดไฟล์** — endpoint ที่ใช้ multer และ MinIO ต้องทดสอบกับ MinIO จริงใน container และแยก bucket ของ test ออกจาก bucket อื่น — *ปิดแล้วใน #8: MinIO ตัวจริงใน container และ **bucket ต่อ test file** ไม่ใช่ bucket เดียวร่วมกัน*

**เขตเวลา** — schema ใช้ `AT TIME ZONE 'Asia/Bangkok'` เป็นค่า default ของหลายคอลัมน์ และมีคอลัมน์คำนวณอัตโนมัติ (เช่น `student.admission_year` ที่คำนวณจากรหัสนักศึกษา, `student.full_name_th` ที่ต่อจากชื่อและนามสกุล) — test ต้องไม่ตั้งสมมติฐานว่าเครื่องที่รันอยู่เขตเวลาใด — *ปิดแล้วใน #8: บังคับ UTC ทั้งฝั่ง container (`TZ`/`PGTZ`) และฝั่ง Node ทั้งสอง workspace พร้อมเคสที่ assert `getTimezoneOffset() === 0` เพื่อไม่ให้การบังคับนั้นหลุดไปเงียบๆ* — *#19 เพิ่มอีกชั้นฝั่งเว็บ: เคสเรื่องวันที่สร้าง `Date` จากส่วนประกอบเวลาท้องถิ่นหรือถาม `now` จากนาฬิกาจริง จึงผ่านเหมือนกันหมดแม้ถอด `TZ=UTC` ออก (ยืนยันด้วยการรันจริงใต้ `Asia/Bangkok`, `America/New_York`, `Pacific/Kiritimati`) การบังคับ UTC ที่เหลือไว้มีไว้ให้ผลอ่านตรงกันทุกเครื่อง ไม่ใช่ให้ test พึ่ง*

**คะแนนทศนิยม** — คอลัมน์คะแนนเป็น `Decimal` การเปรียบเทียบต้องไม่ใช้การเทียบ float ตรงๆ และ `gradebook.service` มีการปัดเศษที่ต้องยืนยันว่าถูกต้อง — *#15 กับ #16 แปลง `score` และ `gpa` ให้ออกเป็นตัวเลขตามที่ type ฝั่ง frontend ประกาศไว้ ส่วนคอลัมน์ `Decimal` ที่เหลือยังไม่ได้ไล่ตรวจ แยกเป็น [issue #33](https://github.com/khthana/Deep-Portfolio/issues/33)*

### T7 — Prior Art

**ไม่มี** — โปรเจกต์นี้ไม่มี test อยู่เลยแม้แต่ไฟล์เดียว ทั้ง backend และ frontend ไม่มีการติดตั้ง test framework ใดๆ

ดังนั้น test ชุดแรกที่เขียนจะกลายเป็นแบบอย่างสำหรับที่เหลือ จึงควรเลือกเขียน **กลุ่ม auth และ course ก่อน** เพราะเป็นกลุ่มที่ผู้อื่นจะลอกรูปแบบไปใช้มากที่สุด และตั้งใจทำ helper กับ factory ของสองกลุ่มนี้ให้ดีก่อนขยายไปกลุ่มอื่น

## Out of Scope

**การรื้อโครงสร้างชั้นของ backend** — ไม่ตัด repository layer ใหม่ ไม่ทำ dependency injection ไม่สร้างลำดับชั้นของ error class ไม่แยกไฟล์ service ที่ยาว ตกลงกันไว้ว่าการ refactor อยู่ที่ระดับ "จัดโครงและแก้ของเสียที่ชัดเจน" เท่านั้น

**การย้าย type ที่ frontend เขียนเองไปเป็น shared package** — frontend มี type ที่มิเรอร์ response ของ backend อยู่ราว 2,188 บรรทัดใน 38 ไฟล์ เป็นความซ้ำซ้อนจริงและเป็นงานที่ควรทำในอนาคต แต่เกินขอบเขตที่ตกลง เตรียมโฟลเดอร์ `packages/` ไว้รองรับแล้วแต่ยังไม่ย้าย — แยกเป็น [#61](https://github.com/khthana/Deep-Portfolio/issues/61)

**Component test และ E2E test ของ frontend** — ทดสอบเฉพาะฟังก์ชันบริสุทธิ์ ไม่ติดตั้ง React Testing Library และไม่ทำ Playwright ในเฟสนี้ — แยกเป็น [#62](https://github.com/khthana/Deep-Portfolio/issues/62)

**การไล่แก้ `any` ฝั่ง frontend 115 จุด และการซอยไฟล์ 500–600 บรรทัด** — เสี่ยงเกินประโยชน์เมื่อไม่มี test คุ้ม — แยกเป็น [#63](https://github.com/khthana/Deep-Portfolio/issues/63) พร้อมตัวเลขที่นับใหม่

**การเปลี่ยนชื่อตาราง คอลัมน์ หรือ relation ในฐานข้อมูล** — รวมถึงชื่อ relation ที่ Prisma generate มาแบบอ่านยาก และคอลัมน์ `student.test` ที่เป็นเศษเหลือ บันทึกไว้เป็นข้อสังเกตแต่ไม่แก้

**การเพิ่ม admin CRUD สำหรับ master data** — 28 ตารางที่ไม่มี write path จะจัดการผ่าน importer ไม่ใช่ผ่าน UI

**การสร้าง user อัตโนมัติเมื่อล็อกอินครั้งแรก** — เพราะกติกาการกำหนด `users.user_id` สำหรับอาจารย์ยังไม่ทราบ

**การ deploy ขึ้น server จริงและการตั้ง CI/CD** — ขอบเขตของเฟสนี้จบที่ระบบรันครบบนเครื่อง local ด้วยคำสั่งเดียว เรื่อง server ปลายทาง, pipeline, และ Jenkins ที่เอกสารเดิมอ้างถึง จะคุยกันหลังจากนั้น — แยกเป็น [#59](https://github.com/khthana/Deep-Portfolio/issues/59)

**การเปลี่ยน MinIO เป็น S3 หรือบริการ managed** — คงสถาปัตยกรรมการเก็บไฟล์เดิม

**การเชื่อมต่อกลับไปยัง DEEP Core** — ไม่มีการเรียก API ข้ามระบบ ไม่มีการ sync ข้อมูล ตัดขาดโดยสมบูรณ์

## Further Notes

### ข้อสังเกตสำคัญเกี่ยวกับลักษณะที่แท้จริงของงาน

โจทย์ตั้งต้นคือ "re-deploy + refactor" แต่จากการสำรวจโค้ด งานจริงคือ **การทำให้ระบบที่ไม่เคยยืนได้ด้วยตัวเอง ยืนได้ด้วยตัวเอง** — เพราะ Portfolio ถูกออกแบบมาเป็นดาวเทียมของ DEEP Core ไม่ใช่ระบบเอกเทศ การตัดขาดจึงเป็นงานหลัก ไม่ใช่งานแถม ควรตั้งความคาดหวังตามนี้ตั้งแต่ต้น

### สัดส่วนความพยายามที่ประเมินไว้

- **การเขียน test ประมาณ 60%** — เป็นส่วนที่ใหญ่ที่สุดของโครงการ ใหญ่กว่าตัว refactor มาก

- **การเปลี่ยนระบบ auth ประมาณ 15%**

เหตุผลที่ test กินสัดส่วนสูง: 142 endpoints คูณอย่างน้อย 2 เคส บน foreign key graph ที่มี 115 relation แปลว่างานเขียน factory และการเตรียมข้อมูลจะมีปริมาณพอๆ กับงานเขียน assertion เอง
